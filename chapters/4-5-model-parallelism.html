Part 4 · Model optimization · Chapter 4.5

Model parallelism

Large models do not fit on one GPU, and even when they fit, one GPU may be too slow or leave too little room for the KV cache. Parallelism spreads one model over several GPUs. There are four basic ways to split it (by replica, by tensor, by layer, by expert) plus a few special ones, and each trades memory, speed and communication differently. This chapter builds each split from a single matrix multiply, shows what it costs to communicate, and ends with a method for choosing a layout.

1. Why split a model at all

Three reasons, in order of how often they decide the layout:

  1. It does not fit. Llama 3.1 70B in BF16 is 141 GB of weights; an H100 has 80 GB. DeepSeek-V3 (671B parameters) in FP8 is about 700 GB; a node of eight H100s has 640 GB.
  2. It fits, but leaves no room for the KV cache. Weights that fill 90% of memory leave space for only a handful of sequences (chapter 2.4). More GPUs means more total memory for KV, so bigger batches and longer contexts.
  3. It fits, but is too slow. Decode is bound by reading the weights (chapter 2.5). If 4 GPUs each read a quarter of the weights in parallel, each step can be up to 4 times faster, minus the cost of communicating.

A first estimate of the GPUs needed: weight bytes plus the KV cache you want, divided by usable memory per GPU, rounded up to a size the hardware offers (1, 2, 4 or 8 GPUs in a node).

GPUs ≥ (parameters × bytes per parameter + KV budget) ÷ (memory per GPU × usable fraction)

2. Data parallelism: copies, not splits

The simplest option is not to split the model at all: run several complete copies (replicas) and send each request to one of them. No communication between replicas during inference, and throughput scales linearly with copies. It does not help a model that does not fit, and it does not make any single request faster. In engines this is --data-parallel-size, or just more replicas behind a router (chapter 6.4). Every other method below exists because data parallelism alone is not enough.

3. Tensor parallelism: split every layer

Tensor parallelism (TP) splits each weight matrix across n GPUs. All GPUs work on every token at every layer, each with 1/n of the weights. Two splits of a matrix multiply Y = X W make this work:

  • Column split. Split W by columns: GPU i holds Wᵢ and computes X Wᵢ, a slice of the output columns. No communication: every GPU already has the full input X.
  • Row split. Split W by rows and X by columns: GPU i computes Xᵢ Wᵢ, a partial sum of the full output. The partial sums must be added across GPUs: an all-reduce.

The standard transformer recipe (from Megatron-LM) pairs them so each block needs only one all-reduce:

  • MLP: the first (up) projection is column-split, so each GPU applies the activation function to its own slice with no communication. The second (down) projection is row-split, and one all-reduce sums the result.
  • Attention: heads are split across GPUs (column split of the Q, K and V projections). Each GPU runs attention for its own heads, with its own share of the KV cache. The output projection is row-split, followed by one all-reduce.

So TP needs two all-reduces per layer, each of size [tokens in the step × model width], at every forward pass. Part C of the lab builds this split in a few lines and checks it matches the unsplit result.

Definitions

Collective: a communication pattern among a group of GPUs. All-reduce: every GPU contributes a tensor and every GPU ends with the sum. All-gather: every GPU ends with all pieces. All-to-all: every GPU sends a different piece to every other GPU.

Ring all-reduce: a common algorithm in which each GPU sends and receives about 2 × (n − 1) ÷ n times the tensor size. NCCL (NVIDIA) and RCCL (AMD) are the libraries that implement collectives.

In decode each all-reduce is small (for Llama 3.1 70B at batch 64: 64 × 8,192 × 2 bytes = 1 MB) but there are 160 of them per step (2 per layer × 80 layers). Each one also has a fixed latency of several microseconds. Over NVLink the total is a modest share of the step; over PCIe or the network it can dominate. That is why TP is used inside a node, and why GPUs without NVLink scale poorly beyond TP 2.

The compute bound is checked too. An idealized model: real systems overlap some communication with work.

Two things to see. On NVLink, going from TP 4 to TP 8 still cuts the step time noticeably, so per-user speed rises; on PCIe the communication eats most of the gain. And TP 1 and TP 2 are often impossible: the weights alone, or weights plus KV, do not fit.

Limits of TP

  • The split must divide the number of attention heads (and KV heads). A model with 8 KV heads can use TP up to 8; beyond that, KV heads are replicated, not split.
  • MLA models (DeepSeek) have a single compressed latent per token, which cannot be split by head. Under TP, every GPU must hold the full latent cache: the KV cache is duplicated on every rank. The fix is data-parallel attention (section 6).
  • Efficiency per GPU falls as n grows: each GPU does less work per all-reduce.

4. Pipeline parallelism: split by layers

Pipeline parallelism (PP) gives each GPU (or group of GPUs) a contiguous range of layers, a stage. Activations pass from one stage to the next: one [tokens × width] tensor per stage boundary per step, sent point to point. That is far less communication than TP, so PP works across nodes and over slower links.

The cost is idle time. One request's token must go through the stages in order, so with P stages and one batch in flight, each GPU works 1/P of the time. These idle periods are pipeline bubbles. With M batches (micro-batches) in flight, the idle fraction is about (P − 1) ÷ (M + P − 1).

Worked example

4 stages. One batch in flight: (4 − 1) ÷ (1 + 4 − 1) = 75% idle. Eight batches in flight: 3 ÷ 11 = 27%. Thirty-two: 3 ÷ 35 = 9%. Engines keep several batches in the pipeline at once so all stages stay busy; this raises throughput but does nothing for one token's latency.

PP is the usual way to cross nodes for a dense model (TP inside each node, PP between them), and to use GPU counts that do not divide the head count (for example 3 or 6 GPUs).

# 2 nodes of 8 GPUs: TP 8 inside each node, 2 pipeline stages across nodes
vllm serve meta-llama/Llama-3.1-405B-Instruct --tensor-parallel-size 8 --pipeline-parallel-size 2

5. Expert parallelism: split the experts

An MoE layer (chapter 2.6) has many experts, and each token uses only a few. Expert parallelism (EP) places whole experts on different GPUs: with 256 routed experts on 8 GPUs, each GPU holds 32. The router is small and replicated on every GPU.

  1. Each GPU runs the router for its tokens and learns which experts they need.
  2. Dispatch: an all-to-all sends each token's hidden state to the GPUs holding its chosen experts.
  3. Each GPU runs its experts on the tokens it received, as ordinary dense matmuls.
  4. Combine: another all-to-all sends results back, and each token sums its experts' outputs, weighted by the router.

EP keeps each expert's weights whole, so every expert matmul is large and efficient, and it spreads the memory of hundreds of experts. The challenges: two all-to-alls per MoE layer, and load imbalance. If many tokens pick experts on the same GPU, that GPU becomes the straggler that everyone waits for. Production systems replicate popular experts on several GPUs (DeepSeek calls these redundant experts) and use specialized all-to-all kernels (for example DeepEP).

The tools DeepSeek published for EP

  • DeepEP provides the dispatch and combine all-to-alls over NVLink inside a node and RDMA between nodes, with FP8 dispatch. Version 1 had two kinds of kernels: high-throughput kernels for prefill (large batches, where bandwidth matters) and low-latency kernels for decode (small batches, where each step's fixed latency matters). Version 2 (2026) merged both behind one EPBuffer interface, compiles its kernels at runtime and adds NVLink exchange of redundant experts' weights.
  • EPLB decides which experts to replicate and where. Its hierarchical policy first packs groups of experts onto nodes (so a token's traffic stays mostly inside a node, matching DeepSeek-V3's node-limited routing) and then replicates within nodes; DeepSeek uses it for prefill. Its global policy replicates and places experts across all GPUs regardless of groups, for decode with a large EP size. In DeepSeek's V4.1 service, prefill keeps 4 redundant experts per GPU and re-places them every 1,000 steps, and decode keeps 1 per GPU and re-places every 10,000 steps, reaching a slowest-to-average load ratio of about 1.07 and 1.09 (chapter 4.8).

Overlap is the other half. Comet (ByteDance, arXiv 2502.19811) reports that MoE communication can take 47% of execution time and overlaps it with the expert matmuls at a finer grain than splitting the batch in two: it analyzes data dependencies so each part of the expert computation starts as soon as its tokens arrive, giving 1.96 times faster MoE layers and 1.71 times end to end on average, and runs in ByteDance's ten-thousand-GPU clusters. DeepSeek-V4 goes further with waves of experts inside one fused "mega-kernel" (MegaMoE in DeepGEMM): while one wave computes, the next wave's tokens arrive and the finished wave's results go out. It reports 1.50 to 1.73 times speedup over strong unfused baselines for general inference and up to 1.96 times for small, latency-sensitive batches. Its report also gives the rule for when communication can be hidden completely: peak compute ÷ interconnect bandwidth must not exceed computation ÷ communication per token. For V4-Pro that is 2 × hidden size = 6,144 FLOPs per byte, so each GB/s of interconnect hides the communication for 6.1 TFLOP/s of compute; beyond that, more bandwidth brings little.

Watch out

In vLLM, EP is not a separate size: it is a flag (--enable-expert-parallel) that changes how the MoE layers are split when TP or DP is greater than 1. Without it, every GPU holds a slice of every expert (TP-style sharding).

6. Combining them, and data-parallel attention

Real deployments mix methods, and often split different parts of the model differently. The most important mix for large MoE models is DP attention + EP experts:

  • Attention layers are replicated: each GPU runs full attention for its own subset of requests, holding only those requests' KV cache. No head splitting, so no KV duplication even for MLA.
  • MoE layers use EP across all GPUs: tokens from every GPU's requests are dispatched to the experts they need.

AMD's vLLM benchmarks of DeepSeek-R1, Qwen3-235B and Llama 4 Maverick on MI300X found the crossover practitioners expect: TP + EP gives lower latency at low concurrency; DP + EP scales better for high-throughput batch serving.

# one 8-GPU node: TP 8 for attention, experts split by EP (lower latency)
vllm serve deepseek-ai/DeepSeek-V3 --tensor-parallel-size 8 --enable-expert-parallel
# one 8-GPU node: DP 8 attention, EP experts (higher throughput)
vllm serve deepseek-ai/DeepSeek-V3 --data-parallel-size 8 --enable-expert-parallel

Splitting attention from experts: AFD and disaggregated expert parallelism

DP attention + EP keeps attention and experts on the same GPUs. They want different things: attention is memory-bound and grows with the KV cache, experts want large batches. Three systems separate them onto different GPU pools, a second axis of disaggregation next to prefill and decode (chapter 4.6):

  • MegaScale-Infer (ByteDance, arXiv 2504.02263) puts attention and expert modules on separate GPUs, each with its own parallelism and even different hardware, and uses ping-pong pipelining: the batch is split into micro-batches that shuttle between the attention pool and the expert pool so both stay busy. A custom many-to-many library avoids GPU-to-CPU copies and synchronization. It reports up to 1.90 times higher per-GPU throughput.
  • Step-3 (StepFun, arXiv 2507.19427), a 321B vision-language model with 38B active parameters, co-designs the model with attention-FFN disaggregation (AFD) and a new attention (Multi-Matrix Factorization Attention) whose arithmetic intensity suits the attention pool. The report argues that decode cost depends on how well each part matches its hardware, not on active parameters alone, and reports 4,039 tokens per second per GPU on Hopper under a 50 ms TPOT target (4K context, FP8, no MTP) against 2,324 for DeepSeek-V3 in the same setup.
  • Huawei's xDeepServe on CloudMatrix384 (below) supports MoE-attention disaggregation as well as prefill-decode disaggregation.

A supernode built for EP: Huawei CloudMatrix384

CloudMatrix384 (arXiv 2506.12708) connects 384 Ascend 910 NPUs and 192 Kunpeng CPUs with a high-bandwidth Unified Bus, so every NPU can reach every other directly, and resources such as memory can be pooled dynamically. Its serving system, CloudMatrix-Infer, scales prefill, decode and caching independently, runs DeepSeek-R1 with expert parallelism across 320 NPUs (EP320), and uses INT8 quantization. The paper reports 6,688 prefill tokens per second per NPU and 1,943 decode tokens per second per NPU at under 50 ms TPOT, and 538 decode tokens per second per NPU under a 15 ms limit. A second paper (arXiv 2508.02520) describes xDeepServe, the production system behind Huawei Cloud's model service on the same supernode, serving DeepSeek, Kimi, GLM, Qwen and MiniMax models, reaching 2,400 tokens per second per Ascend 910C at about 50 ms TPOT in a peak decode configuration. This is the hardware lineage behind DeepInfer's Ascend 950 support (chapter 4.8).

Context parallelism

For very long prompts, context parallelism (CP) splits the sequence itself across GPUs. Each GPU computes attention for its chunk of queries while keys and values are passed around a ring of GPUs (ring attention), and partial results are merged with the log-sum-exp trick from chapter 4.2. It cuts prefill time and per-GPU activation memory for million-token prompts, and is common in video generation. Chapter 4.7 returns to it.

Decode over multi-million-token histories has the opposite problem: TP cannot split attention further than the number of KV heads without duplicating KV, and every step reads the whole cache. Helix parallelism (NVIDIA, arXiv 2507.07120) shards the KV cache across GPUs along the sequence during attention, then reuses the same GPUs for TP (or TP × EP) in the feed-forward layers, with a small exchange in between and batch-wise overlap to hide it. It reports up to 1.5 times lower token-to-token latency at fixed batch and up to 32 times larger batches under the same latency for DeepSeek-R1 on Blackwell.

7. Choosing a layout

  1. Fit. Find the smallest GPU count where weights plus a useful KV budget fit (section 1). Consider quantization first (chapter 4.1): FP8 often halves the GPU count.
  2. Inside a node, dense model: TP up to the node size. Larger TP lowers per-user latency; smaller TP with more replicas (DP) usually gives more throughput per GPU.
  3. Inside a node, MoE model: TP + EP for latency; DP attention + EP for throughput.
  4. Across nodes: TP inside, PP across (dense); or wide EP across nodes (MoE). Only cross nodes when the model or KV does not fit one node: otherwise extra nodes are better used as more replicas or for disaggregation (chapter 4.6).
  5. Measure. Benchmark two or three candidate layouts on your traffic (chapter 6.1). Interconnect, kernel support and batch size change the answer.

8. Expert layer

Hiding communication

Communication time only matters if the GPU waits for it. Engines overlap collectives with independent work: for example splitting a batch into two halves so one half's all-to-all runs while the other half computes (DeepSeek describes this "dual micro-batch" overlap for its serving). Custom all-reduce kernels for small decode tensors, and fusing the all-reduce with the following RMSNorm, cut the fixed latency per collective.

Rack-scale NVLink

NVL72 systems (GB200, GB300) connect 72 GPUs in one NVLink domain. Within that domain, collectives run at NVLink speed, so wide EP (and larger TP) no longer pays the inter-node penalty. This changes the layout trade-offs for the largest MoE models, which is why serving stacks for these systems emphasize wide expert parallelism.

Sequence parallelism and vocabulary parallelism

In training stacks such as Megatron-Core, the all-reduce after a row split is often replaced by a reduce-scatter (each GPU keeps a slice of the sequence for the element-wise ops) and an all-gather before the next column split. The embedding table and output head can be split by vocabulary. The same ideas appear in inference engines in simplified forms; the principle is always "decompose the tensor op, and pick the cheapest collective that restores what the next op needs".

9. Common mistakes

  • Picking the smallest GPU count that fits the weights and leaving no room for the KV cache.
  • Running TP across nodes, or TP above 2 on GPUs connected only by PCIe.
  • Expecting pipeline parallelism to cut single-request latency.
  • Using TP for an MLA model at large scale and wondering why the KV cache is duplicated on every GPU.
  • Spreading a model over 16 GPUs when it fits on 8, instead of running two replicas.
  • Ignoring expert load imbalance when reading MoE benchmark numbers.
  • Choosing a TP size that does not divide the number of attention heads.

Part B: plan three deployments

  1. Llama 3.1 70B in BF16 on H100 80 GB. How many GPUs to fit the weights, and how many to also hold 64 sequences of 8K tokens (KV 320 KiB per token) with a 0.9 usable fraction?
  2. The same model in FP8 (weights and KV).
  3. DeepSeek-V3 (671B, FP8, about 700 GB of weights) on H100 vs H200 (141 GB) nodes of 8.
Answers
  1. Weights 141 GB → 2 GPUs (144 GB usable) barely fit the weights with almost nothing left. KV: 64 × 8,192 × 327,680 bytes = 172 GB. Total 313 GB ÷ 72 GB usable = 4.3, so TP 8 (TP must be a power of 2 that divides 64 heads and 8 KV heads; 4 is not enough).
  2. Weights 70.6 GB, KV 86 GB: 157 GB ÷ 72 = 2.2, so TP 4 with room to spare, or TP 2 with fewer sequences.
  3. 8 × H100 = 640 GB total, less than the weights: does not fit in one node (needs 2 nodes or a smaller format). 8 × H200 = 1,128 GB: fits with about 300 GB usable for KV after a 0.9 fraction. This is why DeepSeek-V3 is commonly served on one H200 or B200 node.

Part C: tensor parallelism by hand (CPU, seconds)

import torch
torch.manual_seed(0)
B, D, F, n = 4, 512, 2048, 4                  # tokens, width, MLP width, "GPUs"
x = torch.randn(B, D)
W1, W2 = torch.randn(D, F) / D**0.5, torch.randn(F, D) / F**0.5
ref = torch.relu(x @ W1) @ W2                  # full MLP on one device

# TODO: split W1 by columns and W2 by rows into n pieces (torch.chunk),
#       compute each "GPU's" partial output relu(x @ W1_g) @ W2_g,
#       then sum the partials (that sum is the all-reduce).
out = ...
print("max error vs full:", (out - ref).abs().max().item())
Solution 
W1s, W2s = W1.chunk(n, dim=1), W2.chunk(n, dim=0)
partials = [torch.relu(x @ W1s[g]) @ W2s[g] for g in range(n)]
out = sum(partials)

Measured maximum error: about 1 × 10⁻⁶ (float32 rounding). Each "GPU" holds a quarter of the weights; the only communication is one sum of a [tokens × width] tensor. Now try splitting W1 by rows instead: the activation function would see partial sums, so you would need a second all-reduce before it. That is why the up projection is column-split.

Part D: pipeline bubbles

def bubble(P, M):           # P stages, M micro-batches, 1 time unit per stage per micro-batch
    return (P - 1) / (M + P - 1)
for P in [2, 4, 8]:
    print(P, [f"{bubble(P, M):.0%}" for M in (1, 8, 32)])
What we measured

P = 2: 50%, 11%, 3%. P = 4: 75%, 27%, 9%. P = 8: 88%, 47%, 18%. Deep pipelines need many batches in flight to stay busy, which is why PP is used for as few stages as possible.

11. In the real world

Layouts in production
  • Dense 70B-class models are commonly served at TP 2 to 8 inside one node, with many replicas.
  • Large MoE models (DeepSeek, Kimi, Qwen3-235B) use EP, often with DP attention, on one 8-GPU H200 or B200 node, or wide EP across nodes or NVL72 racks for the largest deployments.
  • 405B-class dense models in BF16 need two nodes (TP 8 × PP 2) or FP8 on one node.
  • Kubernetes stacks (llm-d, Dynamo, KServe) treat a multi-GPU or multi-node replica as one unit that is scheduled, scaled and restarted together.

13. Summary

  • Split a model when it does not fit, when it leaves no room for KV, or when one GPU is too slow.
  • DP copies the model (no communication); TP splits every matrix (two all-reduces per layer, NVLink only); PP splits layers (cheap communication, bubbles); EP spreads experts (all-to-all, load balance); CP splits long sequences.
  • Column then row split gives TP one all-reduce per block; heads split naturally in attention.
  • Large MoE models use EP, often with DP attention to avoid KV duplication.
  • Choose the smallest layout that fits with KV headroom, stay inside a node when possible, and measure two or three candidates on real traffic.

Notes on sources

  • The Kiely book's table describes pipeline stages as handling "the forward and backward pass". Inference has no backward pass; the description is carried over from training.
  • DeepEP's README no longer shows the separate normal and low-latency mode tables from 2025: version 2 unified them in EPBuffer. The description above of two kernel families refers to version 1, which earlier DeepEP documentation and many engine docs describe.
  • The Kiely book says EP needs less communication than TP. That depends on the model and batch: EP avoids per-layer all-reduces in the MoE layers but adds two all-to-alls, whose cost grows with tokens and suffers from load imbalance. Measure both for your model.
