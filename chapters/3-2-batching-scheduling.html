Batching and scheduling

Chapter 2.5 showed that a decode step costs almost the same for 1 sequence as for 64. Turning that fact into real throughput is the job of the scheduler: the part of an engine that decides, every few milliseconds, which requests run and how many tokens each one processes. This chapter builds the scheduler up from the simplest batch to continuous batching with chunked prefill, and shows how its settings trade time to first token against smooth streaming.

Answers
  1. Static batching fixes a group of requests and runs it until the longest one finishes. Continuous batching re-forms the batch at every step: finished requests leave and new ones join immediately.
  2. A long pause in their token streams while the whole prefill runs in one step (hundreds of milliseconds or more).
  3. Inter-token latency gets smoother and lower, because each step carries less prefill work. TTFT for long prompts gets longer, because their prefill is split over more steps.

1. Why batching is the main lever

From chapter 2.5: a decode step reads all the weights once, whatever the batch size. At batch 1 the GPU's math units are idle more than 99% of the time. At batch 64, total throughput is about 30 times higher while each user slows only about 2 times. So a server that runs requests one at a time wastes almost all of its GPU.

The question is how to batch. Requests arrive at random times, have prompts of different lengths, and want outputs of different lengths. A good batching method keeps the GPU full without making anyone wait too long.

2. Static batching

The simplest method, borrowed from classic machine learning serving:

  1. Collect requests until the batch is full (or a timer expires).
  2. Pad all prompts to the longest prompt in the batch.
  3. Generate until every request in the batch is finished.
  4. Return the results, and start the next batch.

This fails for LLMs because output lengths vary enormously. One request wants 20 tokens, another 2,000. The short one finishes early but its slot stays empty until the long one is done, and new arrivals wait outside. Dynamic batching (form a batch from whatever arrived within a short window) helps with arrivals but has the same problem: the batch is fixed for its whole life.

3. Continuous batching

The fix is to schedule at the level of a step (one forward pass), not a request. This is called continuous batching, also known as iteration-level scheduling. It was introduced by the Orca system (OSDI 2022) and is used by every modern engine.

Orca had to solve a second problem to make this work: requests in one step are at different positions and lengths, so their attention inputs have different shapes. Its answer, selective batching, batches the operations that do not care about sequence boundaries (the linear layers, which see a flat list of tokens) and runs attention separately per request. Every engine since keeps this split: one flat token batch for matmuls, and per-sequence metadata that tells the attention kernel where each request starts and ends (chapter 3.4, section 5).

  1. At each step, the scheduler looks at every request.
  2. Requests that finished in the last step leave the batch and free their KV memory.
  3. Waiting requests join the batch if there is room (in sequences, tokens and KV memory).
  4. The model runs one forward pass for everyone: new requests do their prefill, running ones decode one token.

No slot is idle for long, and a new request starts within one step of a slot opening. Published benchmarks from 2023 measured up to 23 times higher throughput than static batching for the same model, by combining continuous batching with better KV memory management (chapter 3.3).

4. The prefill problem

Continuous batching mixes two very different kinds of work in one step:

  • Decode for running requests: 1 token each, memory-bound, cheap.
  • Prefill for new requests: the whole prompt, compute-bound, possibly thousands of tokens.

The step takes as long as its total work. If a new 30,000-token prompt is prefilled in one step, that step may take a second or more, and every streaming user sees a pause of that length. The time between two output tokens is the inter-token latency (ITL, chapter 2.4). Long prefills cause ITL spikes.

Two simple policies both fail:

  • Prefill first: run new prompts as soon as they arrive. Good TTFT, bad ITL spikes.
  • Decode first: finish decodes before starting new prompts. Smooth ITL, but new requests wait and TTFT suffers.

5. Chunked prefill and the token budget

Chunked prefill removes the dilemma. Each step has a fixed token budget: the maximum number of tokens it may process (in vLLM, max-num-batched-tokens). The scheduler fills the budget in this order:

  1. One token for every running decode request.
  2. The remaining budget goes to prefill, taking a chunk of a waiting prompt (the rest continues in later steps).

Each step now has a bounded size, so ITL stays smooth. And because the prefill chunks ride along with decodes, the GPU does useful compute-bound work in steps that would otherwise be memory-bound. The Sarathi-Serve paper calls these "stall-free" schedules. vLLM enables chunked prefill by default in its current engine and gives decodes priority.

The trade-off in one sentence

A smaller budget gives smoother ITL but a longer TTFT for long prompts (their prefill is spread over more steps). A larger budget gives faster TTFT and higher throughput, but bigger ITL spikes. vLLM's documentation suggests about 2,048 for the best ITL and above 8,192 for the best throughput, especially for small models on large GPUs.

7. Queues, fairness and bounded waiting

Every server has a maximum throughput. If requests arrive faster than that, the queue grows without limit, and waiting time grows with it. This is basic queueing, and it bites production systems: teams have reported requests waiting tens of minutes in an engine's queue under sustained overload.

Interactive: load vs queueing
Requests arrive at random at the chosen rate. The server finishes at most its capacity per second. As load approaches capacity, waiting time rises sharply; above it, the queue grows forever.

Engines and the systems around them use four tools:

  • Admission control. Reject or redirect requests when the queue is too long, rather than accepting work you cannot finish in time (chapter 6.4).
  • Timeouts and cancellation. When a client disconnects or times out, the engine aborts the request: it leaves the batch and its KV blocks return to the free pool at once. Without this, abandoned requests keep consuming GPU time.
  • Priorities. With a priority policy, interactive requests go before batch jobs. Low-priority work must still make progress, or it starves.
  • Fair sharing. With many clients, first come, first served lets one heavy client fill the queue. The Virtual Token Counter (VTC) scheduler tracks tokens served per client (weighting input and output tokens) and always serves the client with the lowest count, which bounds how far any backlogged client can fall behind.

Across many engine instances, a router places requests (chapter 6.4). Systems such as Llumnix go further and migrate running requests, with their KV cache, between instances to rebalance load, free memory, or speed up high-priority requests. Its authors report an order-of-magnitude improvement in tail latency.

8. Throughput, latency and goodput

Batching always trades per-user speed for total throughput. The right operating point depends on a service-level objective (SLO), for example "TTFT p95 under 1 s and ITL p95 under 50 ms". Goodput is the throughput of requests that meet the SLO. A server that pushes raw throughput by running huge batches may have lower goodput than one that runs smaller batches and keeps latency in bounds. Chapter 6.1 shows how to measure it.

A useful identity, Little's law, links the three numbers for any stable system:

requests in the system = arrival rate × average time in the system

At 10 requests per second and 6 seconds per request, about 60 requests are in flight on average. That number must fit in max-num-seqs and in KV memory, or they wait in the queue.

9. Expert layer

Mixed batches and attention kernels

A continuous batch holds sequences at different stages and lengths: some prefilling a chunk, others decoding with long histories. Engines flatten all tokens into one array and pass metadata (start offset and context length of each sequence) to attention kernels that handle variable lengths. They often run prefill tokens and decode tokens through different attention kernels within the same step.

Asynchronous scheduling

Scheduling and input preparation take CPU time. If the GPU waits for the scheduler at every step, small models lose much of their speed. Engines overlap the scheduling of step n + 1 with the GPU execution of step n. This is one reason engine cores run in a separate process from the API server.

Preemption policies

When KV memory runs out mid-generation, the scheduler must evict a running request. It can drop its KV blocks and recompute them later (recompute), or copy them to CPU memory and back (swap). Recompute is usually cheaper on modern GPUs for short sequences. Repeated preemption is a sign that max-num-seqs is too high for the memory (chapter 3.3).

Prefill and decode on different GPUs

Chunked prefill shares one GPU between two kinds of work. The other answer is to separate them: run prefill on some GPUs and decode on others, and move the KV cache between them. This disaggregation (chapter 4.6) removes the interference entirely, at the cost of KV transfer and more complex scheduling.

10. Common mistakes

  • Benchmarking with every request arriving at once and identical lengths. Real traffic has random arrivals and mixed lengths; scheduler behaviour changes completely.
  • Raising max-num-seqs without checking KV memory, then suffering constant preemption.
  • Setting max-num-batched-tokens for throughput on a chat service and getting ITL spikes.
  • Running near 100% load and wondering why latency explodes. Plan for headroom (often 60% to 80% of measured capacity).
  • Not aborting requests when clients disconnect.

Part A: a continuous-batching simulator

The AI may write the simulator. Your job: set the workload and predict the results before each run. This complete version uses the step-time model of chapter 2.5.

import random, statistics as st

def step_time(n_decode, n_prefill_tokens, ctx_tokens):
    # Llama-3.1-8B-like model on one H100 (chapter 2.5): the larger of memory time and compute time
    mem = (16.06e9 + ctx_tokens * 131072) / (3.35e12 * 0.7)
    comp = 2 * 8.03e9 * (n_decode + n_prefill_tokens) / (989e12 * 0.6)
    return max(mem, comp) + 0.002                      # plus 2 ms fixed overhead per step

def simulate(reqs, mode="continuous", max_seqs=32, budget=None):
    """reqs: list of (arrival_s, prompt_len, output_len). Returns throughput and latency stats."""
    queue = sorted(reqs); running, done, t = [], [], 0.0
    while queue or running:
        can_admit = (mode == "continuous") or not running     # static: only when the batch is empty
        while can_admit and queue and queue[0][0] <= t and len(running) < max_seqs:
            a, p, o = queue.pop(0)
            running.append(dict(a=a, p=p, o=o, pre=p, gen=0, first=None, gaps=[], last=None))
        if not running:                                      # idle: jump to the next arrival
            t = queue[0][0]; continue
        decoding = [r for r in running if r["pre"] == 0 and r["gen"] < r["o"]]
        left = budget - len(decoding) if budget else float("inf")
        prefill_tokens, finishing_prefill = 0, []
        for r in running:                                    # chunked prefill uses the leftover budget
            if r["pre"] > 0 and left > 0:
                take = min(r["pre"], left)
                r["pre"] -= take; prefill_tokens += take; left -= take
                if r["pre"] == 0: finishing_prefill.append(r)
        ctx = sum(r["p"] - r["pre"] + r["gen"] for r in running)
        t += step_time(len(decoding), prefill_tokens, ctx)
        for r in decoding + finishing_prefill:               # each emits one token this step
            r["gen"] += 1
            if r["first"] is None: r["first"] = t
            else: r["gaps"].append(t - r["last"])
            r["last"] = t
        for r in running:
            if r["gen"] >= r["o"] and "end" not in r:
                r["end"] = t; done.append(r)
        if mode == "continuous":
            running = [r for r in running if "end" not in r]
        elif all("end" in r for r in running):               # static: release only when all finish
            running = []
    q = lambda xs, f: sorted(xs)[min(len(xs) - 1, int(f * len(xs)))]
    ttft = [r["first"] - r["a"] for r in done]
    long_ttft = [r["first"] - r["a"] for r in done if r["p"] > 4000] or [0]
    gaps = [g for r in done for g in r["gaps"]]
    return dict(tok_per_s=round(sum(r["o"] for r in done) / t), ttft_p50=round(q(ttft, .5), 3),
                ttft_p99=round(q(ttft, .99), 3), long_prompt_ttft_p50=round(q(long_ttft, .5), 3), itl_p99_ms=round(1000 * q(gaps, .99), 1) if gaps else None, itl_max_ms=round(1000 * max(gaps), 1) if gaps else None)

random.seed(0)
t = 0.0; reqs = []
for i in range(400):                          # Poisson arrivals at 8 requests per second
    t += random.expovariate(8.0)
    reqs.append((t, random.randint(100, 1500), random.choice([20, 50, 200, 800])))
for mode in ["static", "continuous"]:
    print(mode, simulate(reqs, mode))

Predict first: by roughly what factor will continuous batching beat static batching in output tokens per second for this workload? Which latency number will change the most?

What you should see

About 850 vs 1,850 tokens per second (about 2.2 times). The biggest change is TTFT: static batching makes new requests wait for whole batches to finish, so the queue builds and median TTFT reaches tens of seconds, while continuous batching keeps it around tens of milliseconds. Then change the arrival rate (the 8.0) and the output-length choices: the gap shrinks when outputs are all the same length, and grows when they vary widely.

12. In the real world

How production systems schedule
  • All major engines (vLLM, SGLang, TensorRT-LLM) use continuous batching with chunked prefill by default or as a standard option.
  • Chat products tune for ITL and TTFT SLOs with modest token budgets; offline batch jobs (evaluation, data generation) use large budgets and high concurrency for throughput.
  • Multi-tenant platforms add priority classes, per-tenant rate limits and fair queueing in front of or inside the engine.
  • Capacity planning uses measured goodput at the SLO, not peak throughput.

14. Summary

  • Batching is cheap for memory-bound decode, so the scheduler's job is to keep batches full without long waits.
  • Static and dynamic batching fix a batch for its life; continuous batching re-forms it every step.
  • Mixing long prefills with decodes causes ITL spikes; chunked prefill caps each step with a token budget, decodes first.
  • Small budget: smooth ITL, slower long-prompt TTFT. Large budget: fast TTFT and throughput, bigger spikes.
  • Key vLLM knobs: max-num-seqs, max-num-batched-tokens, gpu-memory-utilization, max-model-len, scheduling-policy.
  • Above capacity, queues grow without limit: use admission control, timeouts, aborts, priorities and fair scheduling.
