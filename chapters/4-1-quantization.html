Quantization

Quantization stores a model's numbers in fewer bits. Fewer bits means less memory, fewer bytes to read each decode step, and faster math in prefill. It is usually the first optimization to try and the one with the most ways to go wrong. Chapter 1.3 covered the number formats themselves. This chapter covers how a real model is quantized: the scale and zero point, outliers, the three classic algorithms (GPTQ, AWQ, SmoothQuant), FP8 and FP4 serving, KV cache quantization, and how to prove that quality did not drop.

  2. Weights are fixed and known before serving, so their scales can be chosen carefully once. Activations change with every input and contain rare, very large outlier channels.
  3. Not necessarily. Run the original model several times to measure its own run-to-run noise. A loss counts only if it is clearly larger than that noise.

1. What quantization buys, phase by phase

Chapter 2.5 split inference into two regimes. Quantization helps each in a different way:

  • Decode is memory-bound. Each step reads every weight once. Weights in 8 bits instead of 16 means half the bytes per step, so the step can be up to about twice as fast. This works even if the math stays in 16-bit.
  • Prefill is compute-bound. It only gets faster if the matmul itself runs in lower precision. An H100 does about 989 TFLOP/s in BF16 and about 1,979 TFLOP/s in FP8 (dense). For that, both inputs of the matmul, the weights and the activations, must be in FP8.

Quantization also frees memory. Smaller weights leave more room for the KV cache, so more requests fit in a batch (chapter 2.4), which raises throughput even when each step is no faster.

In practice the gain is less than the bit ratio. Scales must be loaded and applied, and some layers stay in 16-bit. Going down one precision level (for example BF16 to FP8) typically gives about 30% to 50% better performance for LLMs, not 100%. vLLM's documentation reports up to 1.6 times higher throughput for FP8 with a 2 times memory reduction.

The naming scheme

Definitions

WxAy: weights stored in x bits, activations (the inputs to each matmul) in y bits. W4A16 is weight-only quantization; W8A8 quantizes both.

Weight-only quantization: weights are stored in low precision and converted back (dequantized) to 16-bit inside the matmul kernel. The math runs in 16-bit.

Weight-and-activation quantization: both matmul inputs are in low precision, so the tensor cores run the low-precision instruction.

KV cache quantization: the stored keys and values use fewer bits (often FP8), independent of the weights.

PTQ (post-training quantization): quantize a finished model, using at most a small calibration set. QAT (quantization-aware training): train with the low precision simulated, so the weights adapt to it.

2. The core operation: scale and zero point

Every quantizer maps a range of real numbers onto a small set of integer codes, stores the codes, and keeps a scale (and sometimes a zero point) to map them back. There are two ways to do the mapping.

Symmetric (absmax) quantization

Map the largest absolute value to the largest code, and keep 0 at 0. For signed 4-bit integers the codes are −8 to 7, so use 7 as the top:

scale = max(|w|) ÷ 7    code = round(w ÷ scale)    restored = code × scale
Worked example

Row w = [0.2, −1.6, 2.9]. scale = 2.9 ÷ 7 ≈ 0.414. Codes: round(0.48) = 0, round(−3.86) = −4, round(7.0) = 7. Restored: [0, −1.66, 2.90]. The 0.2 is lost entirely: it is smaller than half a step (0.207). Small weights next to a big one suffer most.

Asymmetric (zero-point) quantization

Map the minimum to the lowest code and the maximum to the highest. This uses every code even when the values are not centered on 0, but needs a second number, the zero point z: the code that stands for real 0.

scale = (max − min) ÷ (2^bits − 1)    z = round(−min ÷ scale)    code = round(w ÷ scale) + z    restored = (code − z) × scale

Symmetric is simpler and faster in kernels (no subtraction). Asymmetric is more accurate for skewed ranges, such as activations after a ReLU-like function. Many INT4 weight formats (GPTQ, AWQ) store a zero point per group.

3. Outliers, calibration, and static vs dynamic scales

Weights are easy, activations are hard

Weights are roughly bell-shaped and fixed. Their scales can be computed once, offline, with no data at all. Round-to-nearest (RTN) per channel works well at 8 bits.

Activations are different. In LLMs a few hidden channels carry values far larger than the rest, and they appear in the same channels for almost every token. The lab measures this on Qwen2.5-0.5B: in the layers checked, the largest input channel is 11 to 63 times the median channel, and larger models show stronger outliers. A per-tensor INT8 scale sized for that channel leaves a step size too coarse for all the others.

Calibration

Choosing the range to map is called calibration. For activations, you run a few hundred representative prompts through the model and record the ranges. Choices include the absolute max, a percentile (which clips the rare extremes), or the range that minimizes error. Use calibration data that looks like your real traffic: chat, code or your domain.

Static and dynamic activation scales

  • Static: the activation scale is fixed after calibration. Fastest, but wrong when traffic differs from the calibration set.
  • Dynamic: the kernel computes the scale at run time from the actual values, usually one scale per token (per row). It costs a small reduction per matmul and needs no calibration. The common FP8 recipe for vLLM is exactly this: static per-channel weight scales plus dynamic per-token activation scales (llm-compressor's FP8_DYNAMIC scheme).

4. Three classic algorithms

Round-to-nearest treats each weight on its own. At 4 bits and below that loses too much. Three methods fix this in different ways. The aim here is the idea, not the full math.

GPTQ: fix each rounding error with the weights not yet rounded

GPTQ quantizes one layer at a time, one column of weights at a time. After rounding a column, it measures the error that rounding caused on the layer's output (using calibration inputs), and nudges the columns not yet quantized to cancel that error. Weights in a layer work together, so a small change to the remaining weights can absorb most of the error. The size of each nudge comes from second-order information about the layer's inputs (the inverse of the Hessian matrix, H = 2XXᵀ, where X is the calibration input).

Intuition in two weights

A neuron computes y = w₁x₁ + w₂x₂, and x₁ and x₂ are usually similar. Round w₁ = 0.65 to 1.0: the output rises by about 0.35 × x₁. Since x₂ is close to x₁, lowering w₂ by about 0.35 before it is rounded cancels most of that. GPTQ does this for thousands of weights at once, weighting each correction by how the inputs correlate.

Results reported in the GPTQ paper: a 175B model quantized in about four GPU hours to 3 or 4 bits, with little accuracy loss and end-to-end speedups of about 3.25 times on an A100 and 4.5 times on an A6000 over FP16 (because the 4-bit model fits on fewer GPUs and reads fewer bytes).

AWQ: protect the weights that see large activations

AWQ observes that not all weights matter equally: protecting about 1% of salient weight channels greatly reduces error, and saliency is best judged by the size of the activations that multiply them, not by the weights themselves. Instead of keeping those channels in 16-bit (awkward for kernels), AWQ multiplies each important input channel's weights by a factor s > 1 before quantizing, and divides the matching activation by s. The product w × x is unchanged, but the important weight now uses more of the code range, so its relative rounding error shrinks.

Worked example

A weight 0.65 on a grid with step 1: it rounds to 1.0, error 0.35. With s = 2: 0.65 × 2 = 1.3 rounds to 1.0, which stands for 1.0 ÷ 2 = 0.5 in the original units. Error 0.15. The division by s is folded into the previous layer (for example the RMSNorm weights), so it costs nothing at run time.

AWQ needs only activation statistics, no backpropagation and no weight updates, so it overfits the calibration set less. It is the most common 4-bit format for weight-only serving on GPUs, alongside GPTQ.

SmoothQuant: move the difficulty from activations to weights

SmoothQuant targets W8A8. Activations have outlier channels; weights do not. So divide each activation channel j by a factor sⱼ and multiply the matching weight row by sⱼ. Again the product is unchanged:

Y = X W = (X ÷ s) (s W)    sⱼ = max|Xⱼ|^α ÷ max|Wⱼ|^(1−α)

With α = 0.5 the outliers are shared evenly: activations get smaller peaks, weights get slightly larger ones, and both quantize well to INT8. The paper reports up to 1.56 times speedup and 2 times memory reduction with negligible accuracy loss. The same "rescale before quantizing" idea reappears in newer methods that rotate the hidden space (for example with Hadamard matrices) to spread outliers across all channels; vLLM supports such rotated NVFP4 checkpoints.

5. FP8 and FP4 in serving

Chapter 1.3 explained why floating-point formats handle outliers better than integers: the exponent gives a wide range. For serving this means:

  • FP8 E4M3 (4 exponent bits, 3 mantissa bits) reaches ±448 and is used for weights and activations. E5M2 reaches ±57,344 with less precision. FP8 matmuls need compute capability 8.9 or newer (Ada, Hopper, Blackwell). On Turing and Ampere, vLLM still runs FP8 checkpoints, as weight-only W8A16 through its Marlin kernels.
  • MXFP8 and MXFP4 add one power-of-two scale per 32 values; NVFP4 one FP8 scale per 16 values plus a tensor scale. Blackwell tensor cores apply these scales in hardware.
  • INT4 weight-only (GPTQ, AWQ) runs on almost any GPU, because the math stays in 16-bit.

Practitioners' rule of thumb, which both the Kiely book and the vLLM docs support: FP8 (with per-channel or block scales) is the sweet spot for quality-sensitive serving on Hopper and Blackwell; 4-bit is for fitting large models on fewer or smaller GPUs, and needs careful evaluation.

Where the speed comes from

Interactive: one decode step of Llama 3.1 8B on an H100
An idealized roofline (chapter 2.5): step time = the larger of math time and memory time. W4A16 reads the fewest bytes but does its math in BF16; FP8 halves the bytes and doubles the math rate. Real kernels reach less than these peaks, and 4-bit kernels also spend time unpacking.

Move the batch from 1 to 1,024. At batch 1, W4A16 wins: weights dominate the bytes. As batch and context grow, the KV cache dominates the bytes (weight-only quantization does not touch it) and eventually the math dominates the time (W4A16 still runs in BF16). That is why large-scale serving prefers W8A8 FP8 plus an FP8 KV cache, while single-user local inference prefers 4-bit weights.

6. What to quantize, and what to leave alone

Parts of the model differ in how much error they tolerate. From least to most sensitive:

  1. Linear-layer weights. The bulk of the bytes and the safest to quantize.
  2. Activations (matmul inputs). Need good scales because of outliers.
  3. KV cache. Errors in a cached key or value affect every later token that attends to it.
  4. Attention math itself (scores and softmax). Almost always kept in higher precision.

Even within the linear layers, recipes commonly skip the output head (lm_head), and some skip the first and last blocks. MoE routers are usually kept in high precision. For MoE models, quantizing the experts gives most of the memory gain because they hold most of the parameters (chapter 2.6).

KV cache quantization

Chapter 2.4 showed that at long contexts and large batches the KV cache, not the weights, fills memory and dominates decode bytes. An FP8 KV cache halves both: twice as many tokens fit, and each decode step reads half the KV bytes. In vLLM:

vllm serve Qwen/Qwen2.5-7B-Instruct --kv-cache-dtype fp8
  • Without calibration, vLLM uses a scale of 1.0 for keys and values. That works when the values already fit FP8's range, but calibrated scales (computed with llm-compressor and stored in the checkpoint) are the recommended path.
  • Scales can be per tensor or per attention head (per-head needs calibration and specific attention backends).
  • Some layer types are more sensitive. vLLM can leave chosen layers unquantized, for example sliding-window layers: --kv-cache-dtype-skip-layers sliding_window.
  • With some backends (FlashAttention 3), the attention math itself then runs in FP8, and the queries are quantized too.

Below 8 bits the layout of the values matters. KIVI (arXiv 2402.02750) studied the element distributions of real KV caches and found that keys have a few channels with large values while values do not, so keys should be quantized per channel (one scale per channel, shared across tokens) and values per token. With that split it stores the cache in 2 bits without tuning; the authors report almost the same quality with 2.6 times less peak memory (weights included), up to 4 times larger batches and 2.35 to 3.47 times the throughput. DeepSeek-V4.1-Flash stores its main KV in a 4-bit floating-point format trained in with quantization-aware training, and keeps its sliding window KV in FP8 because it is more sensitive (chapter 4.8).

W4A8KV4: QServe and the dequantization tax

Why does 4-bit weight-only quantization (W4A16) speed up a single user but not a busy server? QServe (MIT, arXiv 2405.04532) measured the answer: existing INT4 methods spend 20% to 90% extra runtime dequantizing weights or partial sums on the GPU's slower CUDA cores, which dominates once the batch is large enough to be compute-bound (chapter 2.5). Its QoQ algorithm ("quattuor-octo-quattuor", 4-8-4) uses 4-bit weights, 8-bit activations and a 4-bit KV cache, with progressive quantization so that the W4A8 matmul can run on INT8 tensor cores with cheap dequantization, and SmoothAttention to keep 4-bit KV accurate. Against TensorRT-LLM the authors report 1.2 to 1.4 times the throughput for Llama-3-8B and 2.4 to 3.5 times for Qwen1.5-72B on A100 and L40S. The lesson is general: a format helps only if the kernel can use it without moving work onto slow units.

7. Measuring quality

The production standard is no measurable quality loss. Three checks, from cheapest to most meaningful:

  1. Perplexity on held-out text. Perplexity is e raised to the average loss per token: how "surprised" the model is by real text. Lower is better; compare quantized against original on the same text and window length. Cheap and sensitive, but a small perplexity change can hide a large change on hard tasks.
  2. Standard benchmarks (for example with lm-evaluation-harness): MMLU-style knowledge, GSM8K-style math, coding. Long-context and reasoning tasks are often the first to degrade.
  3. Your own evals on real prompts from your product. This is the one that decides.
Watch out: noise

Scores vary between runs, especially with sampling. Measure the original model's spread over several seeds first. A quantized score inside that spread is not a regression; one outside it is, even if it looks small.

If quality drops, the levers, in order: a finer granularity (per-channel, then smaller groups), a better algorithm (RTN to GPTQ or AWQ), skipping sensitive layers, a better calibration set, a higher-precision format (FP4 to FP8), and finally QAT.

8. Expert layer

Quantization-aware training and native low-precision models

QAT simulates the low precision during training ("fake quantization": quantize then dequantize in the forward pass), so the weights settle where rounding hurts least. Some labs now release models trained or post-trained this way, for example GPT-OSS with MXFP4 expert weights and Kimi K2 Thinking with INT4 weights. For those, the low-precision checkpoint is the original, not an approximation.

GGUF k-quants and very low bit widths

GGUF (chapter 3.6) uses two-level block scales: small sub-blocks each have a scale, and those scales are themselves quantized with a scale per super-block. Mixed "dynamic" recipes keep sensitive tensors at higher precision and push others very low, so the average can be under 2 bits per weight. BitNet b1.58 goes further with ternary weights (−1, 0, 1) trained from scratch, which turns matmuls into additions. These matter most for local and edge inference.

Accumulation precision

Low-precision inputs still need high-precision sums (chapter 1.3, section 8). The DeepSeek-V3 report measured that FP8 matmul accumulation on its H800 (Hopper) GPUs keeps only about 14 bits, with relative errors up to nearly 2%, so it promotes partial sums to FP32 on CUDA cores every 128 elements to stay accurate. Kernel libraries handle this, but it explains why "FP8 everywhere" is not free.

Two more ways around outliers

QuaRot (arXiv 2404.00456) multiplies the hidden state by a random orthogonal (Hadamard) rotation that leaves the model's output unchanged but spreads outlier channels across all channels, so weights, activations and KV can all be quantized to 4 bits without keeping any channel in high precision; the authors report at most 0.47 WikiText-2 perplexity loss for 4-bit Llama-2-70B. SqueezeLLM (arXiv 2306.07629) keeps the outliers instead: a dense low-bit part with non-uniform levels chosen by sensitivity, plus a small sparse matrix holding outliers and sensitive weights in full precision.

Packing and kernels

A 4-bit weight is not addressable on its own: kernels pack eight of them into one 32-bit word and unpack them in registers before the 16-bit matmul. AWQ's odd packing order exists so one instruction can unpack two values at once. Marlin, Machete and similar kernels fuse the unpack, scale and matmul; this fused work is why W4A16 gains shrink as the batch grows (chapter 5.4 explains kernel fusion).

9. Common mistakes

  • Expecting 2 times speed from halving the bits. Expect 30% to 50% per level, and check where your workload sits on the roofline.
  • Using weight-only INT4 for a high-throughput, large-batch service and wondering why it is no faster than FP16.
  • Judging quality on perplexity alone, or on one benchmark run without measuring noise.
  • Calibrating on generic web text and serving code, or another language.
  • Turning on an FP8 KV cache without calibrated scales and without re-running long-context evals.
  • Quantizing lm_head, the MoE router or the embedding table in a first attempt.
  • Comparing an FP8 run on an H100 with a BF16 run on another GPU and crediting the difference to quantization.

Dynamic per-token scales do even better here, and the two combined come within about 1% of the reference. This is why production FP8 recipes use dynamic per-token activation scales, and why INT8 W8A8 relied on smoothing.

Part E: serve a 4-bit model (T4)

On a Colab T4, start vLLM twice and compare the startup log lines for model memory and KV cache size, then run the same short benchmark against each (chapter 3.1, Part D):

vllm serve Qwen/Qwen2.5-1.5B-Instruct --dtype half --max-model-len 4096
vllm serve Qwen/Qwen2.5-1.5B-Instruct-AWQ --max-model-len 4096

Predict first: how much smaller are the weights, and how many more KV tokens fit? Then measure single-request tokens per second and throughput at 32 concurrent requests. Explain with section 5 why the gap is larger at concurrency 1 than at 32. On the T4 (compute capability 7.5), FP8 checkpoints would run only as weight-only W8A16 (section 5), so this lab uses AWQ.

11. In the real world

How teams use quantization
  • Hosted APIs on Hopper and Blackwell commonly serve FP8 weights and activations, often with an FP8 KV cache, after checking evals against the BF16 original.
  • Model providers publish FP8, AWQ, GPTQ and NVFP4 checkpoints next to the BF16 ones, so most teams never run a quantizer themselves.
  • Very large MoE models (DeepSeek, Kimi, GPT-OSS) ship in FP8, INT4 or MXFP4 so a single 8-GPU node can hold them.
  • Local inference (llama.cpp, Ollama, LM Studio) runs almost entirely on 4-bit-class GGUF files.
  • Quality-critical domains stay in BF16 or FP8 and get their speed from the lossless techniques in the rest of Part 4.

12. Check yourself

13. Summary

  • Decode gains from fewer bytes; prefill gains only when the matmul itself runs in low precision. Expect 30% to 50% per precision level, not the full bit ratio.
  • Quantizers map values to codes with a scale (and maybe a zero point). Granularity and clipping decide how outliers hurt.
  • Weights are easy and static; activations have outlier channels and need per-token dynamic scales or smoothing.
  • GPTQ corrects rounding errors with the remaining weights; AWQ protects channels with large activations; SmoothQuant moves outliers from activations into weights.
  • FP8 (W8A8 plus FP8 KV) is the production default on Hopper and newer; 4-bit weight-only suits small-batch and memory-limited serving; NVFP4 and MXFP4 need Blackwell.
  • Quantize weights first, then activations, then the KV cache; keep attention math, lm_head and routers in high precision.
  • Prove quality with perplexity, benchmarks and your own evals, compared against the original's noise.

Notes on sources

  • The day 13 README of 100 Days of Inference quotes 3.9 PFLOP/s FP8 and 1.98 PFLOP/s FP16 for the H100. Those are the with-sparsity figures; the dense figures used in this book are about 1,979 and 989 TFLOP/s. The ratio (2 times) is the same.
  • The Grootendorst guide says weights with smaller values in the Hessian are more important. In GPTQ's framework it is the other way round for the Hessian itself (large diagonal entries mean the output is more sensitive to that weight); small values in the inverse Hessian mark important weights, which the guide also says correctly.
  • AI Systems Performance Engineering calls SmoothQuant "calibration-free". It is training-free, but it uses a small calibration set to find the activation maxima that set the smoothing factors.
  • The Kiely book advises against integer formats for quality-sensitive production work. Many production deployments do use INT4 weight-only (AWQ, GPTQ) successfully; treat the advice as "evaluate integer formats carefully", which section 7 does.
