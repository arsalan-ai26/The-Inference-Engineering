Part 6 · Production inference infrastructure · Chapter 6.9

Fault tolerance, security and incident response

GPUs fail, networks drop, engines crash, and deploys go wrong. An inference service has to keep answering anyway, lose as little work as possible when a replica dies mid-stream, and recover quickly. It also has to keep tenants apart, protect prompts and model weights, and resist abuse. This chapter covers how GPU clusters actually fail, how to detect and remove bad nodes, what happens to in-flight requests and their KV caches when a replica dies, retry and degradation strategies, chaos testing, how to run an incident, and the security risks specific to LLM inference, including prompt-cache timing leaks.

Before you start: skip check
  1. A replica dies after streaming 60 of 100 tokens. What are the options for that request?
  2. What does Xid 79 in a kernel log mean, and what should happen to the node?
  3. How can a shared prefix cache leak one customer's prompt to another?
Answers
  1. Fail it and let the client retry; restart it from scratch on another replica (the 60 tokens are wasted, and a streaming client must discard what it showed); or resume it elsewhere by sending the prompt plus the 60 tokens and generating the remaining 40 (costs a longer prefill; the KV itself died with the GPU unless it was copied to another tier).
  2. "GPU has fallen off the bus": the GPU is no longer reachable over PCIe. Drain the node and take it out of service; NVIDIA's catalog recommends a bare-metal restart and contacting support if it repeats.
  3. Cache hits return the first token faster. An attacker who sends prompts that share a prefix with someone else's cached prompt can tell from the timing whether that prefix was recently sent. Isolate caches per tenant (for example a per-tenant cache salt).

1. How GPU clusters fail

Large operators publish their failure data, and the numbers are sobering:

  • Llama 3 training (about 16,000 H100 GPUs, 54 days): 419 unexpected interruptions, about one per 50,000 GPU-hours. Faulty GPUs (148 interruptions) and GPU HBM3 memory (72) were the top two causes, followed by software bugs and network switches and cables.
  • Meta's research clusters (RSC-1 and RSC-2): failure rates change constantly, from about 2.5 to 17.5 failures per node-day across the cluster in different periods; RSC-1's average was 6.5 failures per thousand node-days. Jobs of 4,000 GPUs saw a mean time to failure of about 10 hours. The most common attributed causes were the backend network, file system mounts and GPUs (mostly memory errors, PCIe errors and GPUs falling off the bus).

For inference, the same rates apply per GPU. Mean time to failure scales as 1 ÷ (number of nodes × failure rate per node), so a 2-node replica fails about twice as often as a 1-node replica, and a fleet of hundreds of replicas sees failures daily.

2. Detecting and removing bad nodes

Meta's clusters run health checks on every node every five minutes: GPU accessible, NVLink errors, uncorrectable ECC, failed row remaps, PCIe and InfiniBand link errors, missing file system mounts. A node that fails a check is removed from scheduling until fixed. Two of their lessons:

  • One bad node spoils the bunch. Without checks, the same defective node is picked again and again, and jobs fail in a loop.
  • New checks reveal hidden failures. Adding a check often makes the failure rate appear to rise, because a problem that was always there is now visible.

For an inference service, layer the checks:

  1. Liveness: is the engine process alive? Restart it if not.
  2. Readiness: is the model loaded and is the replica accepting requests? Remove it from routing if not (chapter 6.2).
  3. Node health: Xid events, ECC counts, NVLink and PCIe errors from DCGM. Drain the node on critical errors.
  4. End-to-end probe: a tiny real generation (a few tokens of a fixed prompt) every few seconds. It catches a replica that is "ready" but stuck or producing garbage.
  5. Passive checks: the router stops sending to a replica as soon as requests to it fail, without waiting for the next probe.

3. What happens to in-flight requests

When a replica dies, everything in its GPU memory is gone: the weights (reloaded on restart) and the KV cache of every request it was serving. Each in-flight request has four possible fates:

StrategyHowCostNotes
FailReturn an error; client decidesNone for the serverThe user sees an error; fine for batch clients with their own retries
RestartRouter resends the original request to another replicaAll tokens already generated are wasted; full prefill againA streaming client has already shown part of an answer; the new answer may differ (sampling)
Resume by recomputeResend prompt + tokens generated so far, ask for the restA longer prefill; no generated tokens wastedThe stream continues seamlessly; the continuation is a valid sample but not necessarily what the dead replica would have produced
Resume by KV transferAnother replica loads the request's KV from a copy outside the dead GPUTransfer time; needs KV already written to CPU, disk or a remote storePossible with tiered KV caches and connectors (chapter 4.4); cannot recover KV that existed only on the failed GPU

Retries need care:

  • Retry budgets and backoff. Limit retries per request (for example 2) and across the fleet (for example retries at most 10% of traffic), with exponential backoff and random jitter. Otherwise a partial outage turns into a retry storm that overloads the healthy replicas.
  • Idempotency. Retrying a generation is safe; retrying an agent's tool call that sends an email or charges a card is not. Agent harnesses need idempotency keys for side effects.
  • Multi-node replicas fail as a unit: one bad GPU takes down the whole tensor- or pipeline-parallel group. Restart the group together (LeaderWorkerSet's all-or-nothing restart, chapter 6.7) and keep spare capacity.
Interactive: how often does something break?
Expected replica failures from a per-node failure rate. Defaults use Meta RSC-1's average (6.5 failures per thousand node-days); Llama 3's rate, one per 50,000 GPU-hours, is about 3.8 per thousand node-days for 8-GPU nodes.

4. Graceful degradation

When capacity drops faster than the autoscaler can replace it (chapter 6.3 showed GPU replicas take minutes), keep the most important traffic working:

  • Shed load by priority (chapter 6.4): reject or queue batch and free-tier traffic first, with clear 429 or 503 responses and a Retry-After header.
  • Reduce work per request: lower the maximum output length, disable expensive features, route long-context requests to a dedicated pool.
  • Fall back to a smaller model or another region or provider, if the product can accept it (chapter 6.5).
  • Circuit breakers: stop calling a dependency that keeps failing, so requests fail fast instead of piling up.

5. Chaos testing

Recovery that has never been tested usually does not work. Chaos engineering injects failures on purpose, in staging and then carefully in production. Chaos Mesh, a Kubernetes-native tool, defines failures as resources (killing pods, adding network delay or loss, stressing CPU and memory) and can orchestrate them in workflows with status checks. Inference-specific experiments:

  • Kill a replica mid-stream; measure failed requests, retry success and time to full capacity (the lab does this).
  • Add network delay between router and replicas, or between prefill and decode workers (chapter 4.6).
  • Force a GPU out-of-memory with a request near the context limit.
  • Bad rollout: deploy a canary with a broken chat template; does chapter 6.6's correctness monitoring catch it, and does rollback work?
  • Cache degradation: flush or disable the prefix cache; how far do TTFT and cost rise, and do autoscaling and alerts react?

6. Running an incident

Google's incident management follows the Incident Command System, with clear roles:

  • Incident commander: holds the overall state, assigns roles, decides. Holds every role not yet delegated.
  • Operations lead: the only person (or team) changing the system during the incident.
  • Communications lead: regular updates to stakeholders and users.
  • Planning lead: longer-term tasks: bugs, handoffs, tracking temporary changes to revert later.

The commander keeps a living incident document with a timeline. Declare incidents early (it is cheaper to cancel one than to start one late), hand off command explicitly at shift changes, and write a blameless postmortem afterwards.

Worked example: a first-cause timeline

TTFT p99 alert fires at 14:05. Timeline built from metrics, deploy logs and Xid logs:

  • 13:40 config deploy lowers gpu-memory-utilization from 0.90 to 0.85 on all replicas (audit log).
  • 13:41 to 13:50 replicas restart in a rolling update; the KV pool is about 7% smaller, because it gets what is left after weights and activations (for an 8B model on an 80 GB GPU; chapter 3.3).
  • 13:55 afternoon traffic rises; num_requests_waiting climbs, preemptions start.
  • 14:02 node 17 logs Xid 79; its replica drops out, remaining replicas take the extra load.
  • 14:05 alert. First cause: the config change that shrank the KV pool; the GPU failure was a coincidental trigger that removed the remaining headroom.

The first symptom (the alert) and the most visible event (the GPU failure) are not the first cause. Lining up changes, saturation metrics and hardware events on one timeline finds it.

Runbooks: for each likely incident (replica crash loop, GPU failure, TTFT regression after a deploy, quality regression, traffic spike, provider outage), write the symptoms, the dashboards and queries to check, the safe mitigations (roll back, drain, shed load, scale out) and who to escalate to.

7. Security for inference

Securing an inference service is first like securing any containerized service: encryption in transit and at rest, container security, network and access controls, workload isolation and third-party penetration testing. Three assets need attention: user data (prompts and outputs), model weights (often a trade secret) and the infrastructure itself (GPUs and model access are targets for abuse). The simplest step: do not store prompts and outputs unless you need to. Compliance regimes such as SOC 2 Type II and HIPAA require your providers to be compliant too, and data residency rules can require processing in specific countries (chapter 6.5).

Risks specific to LLM serving

  • Prompt-cache timing leaks. A cache hit makes TTFT measurably faster. Gu et al. audited 17 API providers in late 2024: 8 cached prompts, and 7 shared the cache globally across all users, so an attacker could in principle detect whether another user had recently sent a prompt with a given prefix. They disclosed the results to the providers before publishing. Mitigation: per-tenant (per-organization or per-user) caches. vLLM supports a per-request cache_salt that is mixed into the hash of the first block, so only requests with the same salt share cached blocks.
  • Tenant isolation beyond the cache: separate LoRA adapters and fine-tuned models per tenant, no cross-tenant data in logs or traces, rate limits and quotas per tenant.
  • Unbounded consumption (OWASP LLM10): very long prompts, maximum output lengths and many parallel streams exhaust GPUs and budgets. Enforce limits on input length, output length, concurrency and tokens per minute per key.
  • Supply chain (LLM03): load weights from safetensors, not pickle (chapter 3.1); avoid trust_remote_code for untrusted repositories; pin and sign container images.
  • Weight protection: restrict who can read weight storage, encrypt it, log access; confidential computing (chapter 6.7) protects weights on hosts you do not control.

8. Expert layer

Why "resume by recompute" is usually the right default

Prefill is fast per token compared with decode (chapter 2.5), so re-prefilling the prompt plus 60 generated tokens costs much less than generating 60 tokens again, and the user sees no gap in the stream beyond one TTFT. KV transfer is faster still, but only if the KV was already copied off the GPU, which costs bandwidth on every request to protect against rare failures. Systems that already move KV (disaggregated prefill and decode, tiered caches) get it nearly for free.

Correlated failures

Failures are not independent: a top-of-rack switch takes out every node under it; a bad driver rollout hits every node at once; Meta saw a spike of InfiniBand link failures from a handful of nodes. Spread replicas across racks and failure domains, roll out drivers and firmware like code (canaries, chapter 6.5), and size headroom for the largest correlated loss, not one node.

9. Common mistakes

  • Health checks that only test whether the process is alive.
  • Unlimited retries without backoff, turning a partial failure into a full outage.
  • Retrying agent tool calls with side effects.
  • Restarting one pod of a multi-node replica instead of the whole group.
  • A global prefix cache shared across tenants.
  • Logging full prompts by default, or sending them to third-party tracing tools.
  • Never testing recovery until a real failure.

10. Lab

Goal: kill a replica mid-stream and measure what three retry policies do. Then write runbooks.

Part A: fault injection with two replicas

Two fake engine replicas (FastAPI, streaming tokens, with prefill time that grows with prompt length) sit behind a client-side router with active health checks every 0.5 s and passive checks on errors. Requests arrive at 10 per second for 12 s (500-word prompts, 100 output tokens). At 4 s, replica B is killed with SIGKILL; at 7 s it restarts with a 2 s model-load delay. Three policies: none (fail), restart (resend from scratch to the other replica) and resume (send prompt plus the tokens received so far, ask for the rest).

Predict first: how many requests fail with no retries, and which policy has the best p99?

# replica.py: one fake engine replica
import asyncio, json, os, time
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse
time.sleep(float(os.environ.get("STARTUP_S", "0")))       # model load time on (re)start
app = FastAPI(); active = 0
@app.get("/health")
async def health(): return {"ok": True}
@app.post("/v1/completions")
async def completions(req: Request):
    body = await req.json()
    n_in = len(body["prompt"].split()); n_out = body["max_tokens"]
    async def gen():
        global active
        active += 1
        try:
            await asyncio.sleep(0.02 + n_in * 0.0002 * (1 + active / 8))   # prefill
            for i in range(n_out):
                await asyncio.sleep(0.01 * (1 + active / 16))                # decode step
                yield f"data: {json.dumps({'choices': [{'text': ' tok'}]})}\n\n"
            yield "data: [DONE]\n\n"
        finally:
            active -= 1
    return StreamingResponse(gen(), media_type="text/event-stream")
# chaos.py: router, retry policies and the failure schedule (run next to replica.py)
import asyncio, os, random, signal, subprocess, sys, time, httpx
PORTS = [8101, 8102]
def start(port, startup=0.0):
    env = dict(os.environ, STARTUP_S=str(startup))
    return subprocess.Popen([sys.executable, "-m", "uvicorn", "replica:app", "--port", str(port), "--log-level", "error"],
                            env=env, stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL)
async def wait_ready(port):
    async with httpx.AsyncClient() as c:
        while True:
            try:
                if (await c.get(f"http://127.0.0.1:{port}/health")).status_code == 200: return
            except Exception: pass
            await asyncio.sleep(0.1)

class Router:
    def __init__(self): self.healthy = set(PORTS); self.i = 0
    def pick(self, avoid=None):
        c = sorted(p for p in self.healthy if p != avoid) or sorted(self.healthy) or PORTS
        self.i += 1; return c[self.i % len(c)]
    async def prober(self):                                  # active health checks every 0.5 s
        async with httpx.AsyncClient(timeout=0.3) as c:
            while True:
                for p in PORTS:
                    try: ok = (await c.get(f"http://127.0.0.1:{p}/health")).status_code == 200
                    except Exception: ok = False
                    (self.healthy.add if ok else self.healthy.discard)(p)
                await asyncio.sleep(0.5)

async def request(client, router, policy, prompt_words=500, out=100):
    prompt = " ".join(["w"] * prompt_words); got = wasted = tries = 0; t0 = time.perf_counter(); port = None
    while tries < 3:
        tries += 1; port = router.pick(avoid=port)
        if policy == "resume" and got:
            body = {"prompt": prompt + " tok" * got, "max_tokens": out - got}
        else:
            body = {"prompt": prompt, "max_tokens": out}; wasted += got; got = 0
        try:
            async with client.stream("POST", f"http://127.0.0.1:{port}/v1/completions", json=body) as r:
                async for line in r.aiter_lines():
                    if line.startswith("data: {"): got += 1
            if got >= out: return True, time.perf_counter() - t0, wasted, tries
        except Exception:
            router.healthy.discard(port)                     # passive health check
        if policy == "none": break
    return False, time.perf_counter() - t0, wasted + got, tries

async def scenario(policy, rate=10, duration=12, kill_at=4, restart_at=7, startup=2.0):
    procs = {p: start(p) for p in PORTS}
    for p in PORTS: await wait_ready(p)
    router = Router(); probe = asyncio.create_task(router.prober()); random.seed(1)
    async with httpx.AsyncClient(timeout=30) as client:
        t_start = time.perf_counter(); tasks = []; killed = restarted = False
        while (now := time.perf_counter() - t_start) < duration:
            if now > kill_at and not killed: procs[8102].send_signal(signal.SIGKILL); killed = True
            if now > restart_at and not restarted: procs[8102] = start(8102, startup); restarted = True
            tasks.append(asyncio.create_task(request(client, router, policy)))
            await asyncio.sleep(random.expovariate(rate))
        res = await asyncio.gather(*tasks)
    probe.cancel()
    for p in procs.values(): p.kill()
    ok = [r for r in res if r[0]]; lat = sorted(r[1] for r in ok)
    print(f"{policy:7s} requests {len(res)}  failed {len(res)-len(ok):3d}  retried {sum(r[3]>1 for r in res):3d}  "
          f"tokens wasted {sum(r[2] for r in res):5d}  p50 {lat[len(lat)//2]:.2f} s  p99 {lat[int(.99*len(lat))]:.2f} s")
    await asyncio.sleep(1)

async def main():
    for policy in ["none", "restart", "resume"]:
        await scenario(policy)
asyncio.run(main())
What we measured (CPU, about 45 s)
none    requests 122  failed  12  retried   0  tokens wasted   583  p50 2.49 s  p99 3.27 s
restart requests 122  failed   0  retried  12  tokens wasted   580  p50 3.20 s  p99 5.20 s
resume  requests 122  failed   0  retried  12  tokens wasted     0  p50 2.74 s  p99 3.53 s

The 12 requests in flight on replica B when it died failed with no retries; their 583 already-streamed tokens were lost. The passive check removed B immediately, so no new requests failed. Restarting from scratch saved all 12 but wasted the same tokens and raised p99 to 5.2 s (those requests started over, on a replica now carrying all the load). Resuming saved all 12, wasted nothing, and kept p99 at 3.5 s. (The none latencies look best only because the 12 failures are excluded.) Try next: remove the passive check and count how many extra requests fail before the active probe notices; set startup to 30 s; double the rate so one replica cannot carry the load alone.

Part B: on real GPUs

Repeat Part A with two vLLM replicas of a small model behind a router (chapter 6.4) on one or two GPUs. Kill one with kill -9 mid-stream, and measure recovery time (until the restarted replica passes readiness: its cold start, chapter 6.2). Then run a request near the context limit to provoke an out-of-memory error and observe how the engine reports it. Expect the restart to take tens of seconds to minutes, dominated by weight loading and CUDA graph capture.

Part C: runbooks and a seeded incident

Write runbooks for the three incidents you consider most likely for your deployment. Then have a partner seed one (for example: lower gpu-memory-utilization and kill a replica during a load test) without telling you, and run the incident with roles, a living document and a first-cause timeline.

Part D: a cache timing test

On your own vLLM server with prefix caching on: send a random 2,000-token prompt from "user A", then from "user B" send prompts that share the first 1,000 tokens or none, 20 times each, and compare TTFT. Repeat with a different cache_salt per user. Expect a clear TTFT gap without salts and none with them.

11. In the real world

Reliability and security in practice
  • Large clusters run node health checks every few minutes and drain nodes automatically.
  • Inference gateways retry with budgets and backoff; some resume streams on another replica.
  • API providers scope prompt caches to an organization or user after the timing audits.
  • Regulated customers require zero retention of prompts, regional processing and compliant providers.

12. Check yourself

13. Summary

  • Expect failures: about one per 50,000 GPU-hours in Llama 3 training; failure rates vary over time and scale with the number of nodes.
  • Layer health checks (liveness, readiness, node health, end-to-end probes, passive) and drain bad nodes automatically.
  • A replica's death loses its KV; resume by recompute is a good default, KV transfer if KV is already tiered; use retry budgets, backoff and idempotency.
  • Degrade gracefully, test recovery with chaos experiments, and run incidents with clear roles and first-cause timelines.
  • Isolate prompt caches per tenant, limit consumption, keep prompts out of logs, and protect weights and the supply chain.
