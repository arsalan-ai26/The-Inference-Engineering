Linear algebra for LLMs

An LLM is mostly one operation repeated billions of times: multiply a grid of numbers by another grid of numbers. This chapter teaches the four ideas you need to read model code and estimate its cost: vectors, the dot product, matrix multiplication and tensor shapes. You will count the work of a real model layer by the end.

Level: beginner Time: 3 to 4 hours with the lab Needs: basic Python Compute: Colab CPU is enough
Before you start: skip check

If you can answer all three, skim this chapter and go to the lab:

  1. What is the shape of A @ B if A is [32, 4096] and B is [4096, 14336]?
  2. How many floating-point operations (FLOPs) does that multiply take?
  3. Two vectors have a dot product of 0. What does that tell you?
Answers
  1. [32, 14336]. The inner sizes (4096) must match and disappear.
  2. 2 × 32 × 4096 × 14336 ≈ 3.76 billion FLOPs.
  3. They are perpendicular (orthogonal). Neither vector points at all in the other's direction.

1. Why an inference engineer needs this

When a model reads a token, it turns the token into a list of numbers. Every layer then multiplies that list by tables of learned numbers called weights. The output of one layer is the input of the next.

So the cost of running a model is mostly the cost of these multiplications. If you can count them, you can predict how long a request takes, how much memory it needs and which GPU you need. Every later chapter uses these counts.

You do not need proofs, determinants or eigenvalues for this work. You need to know the shapes of things and how to count the work.

2. Vectors: a list of numbers with a meaning

Definitions

Scalar: one number, for example 0.7.

Vector: an ordered list of numbers, for example [0.2, −1.3, 0.5]. The number of items is its dimension or length.

Element: one item in a vector. In code, v[0] is the first element.

You can think of a vector in two ways. Both are useful.

  • As an arrow. A 2-dimensional vector [3, 2] is an arrow from the origin to the point (3, 2). It has a direction and a length.
  • As a description. Each element measures one feature. A house could be [rooms, area, age]. In an LLM, each token becomes a vector with thousands of elements. Llama 3.1 8B uses 4,096. No single element has a simple name, but together they encode what the token means in its context.

Two basic operations act element by element:

[1, 2, 3] + [10, 20, 30] = [11, 22, 33] 2 × [1, 2, 3] = [2, 4, 6]

Adding vectors joins two descriptions. Scaling a vector makes it longer or shorter without changing its direction. Transformers add vectors all the time: the "residual stream" you meet in chapter 1.5 is a running sum of vectors.

The length (or norm) of a vector is the square root of the sum of its squared elements. The length of [3, 4] is √(9 + 16) = 5.

3. The dot product: how much two vectors agree

The dot product takes two vectors of the same length and gives one number. Multiply the matching elements, then add the results:

a · b = a₁b₁ + a₂b₂ + ... + aₙbₙ
Worked example

a = [1, 2, 3] and b = [4, −5, 6].

a · b = (1 × 4) + (2 × −5) + (3 × 6) = 4 − 10 + 18 = 12.

Cost: 3 multiplications and 2 additions. For vectors of length n, the cost is n multiplications and n − 1 additions, so about 2n operations.

The geometric meaning is the important part. The dot product also equals:

a · b = |a| × |b| × cos(angle between a and b)
  • Large and positive: the vectors point in a similar direction.
  • Zero: the vectors are perpendicular. They share nothing.
  • Negative: they point in opposite directions.

If you divide by both lengths, you get the cosine similarity, a score from −1 to 1 that ignores length and measures only direction. Search engines, RAG systems and embedding models use it to find similar text. Inside a transformer, attention (chapter 2.2) uses raw dot products to decide which earlier tokens matter to the current one.

4. Matrices: many vectors in a grid

Definitions

Matrix: a 2-D grid of numbers with rows and columns. A matrix with m rows and n columns has shape [m, n].

Weight matrix: a matrix of learned numbers inside a model layer.

Transpose: the same matrix with rows and columns swapped. Shape [m, n] becomes [n, m]. Written Aᵀ, or A.T in code.

A useful way to see a matrix: a stack of vectors. A batch of 32 tokens, each a 4,096-element vector, is a matrix of shape [32, 4096]. Each row is one token.

A weight matrix is also a stack of vectors. Each column is a "detector": a direction in the vector space. Multiplying a token vector by the matrix asks each detector, with a dot product, "how much does this token point your way?"

5. Matrix multiplication: many dot products at once

To multiply A [m, k] by B [k, n]:

  1. Take row i of A (length k).
  2. Take column j of B (length k).
  3. Their dot product is the output element at row i, column j.
  4. Do this for every row i and every column j.

The result has shape [m, n]. The inner sizes must match, because a dot product needs two vectors of the same length. The inner size k "disappears" into the sums.

[m, k] @ [k, n] → [m, n] the two k's must be equal
Interactive: build a matmul one cell at a time
Each step computes one output cell as the dot product of a row of A (indigo) and a column of B (amber). The counter adds 2k operations per cell.

Counting the work: 2 × m × n × k

The output has m × n cells. Each cell is a dot product of length k, which costs k multiplications and about k additions. So:

FLOPs of a matmul = 2 × m × n × k

A FLOP is one floating-point operation: one multiply or one add. GPU makers count a fused multiply-add as 2 FLOPs, which matches this formula. (FLOP/s, with a lower-case s, is FLOPs per second: a speed. Do not confuse them.)

Worked example: one layer of a real model

Llama 3.1 8B has a hidden size of 4,096. Its MLP block first multiplies each token by an "up" matrix of shape [4096, 14336].

For one token: [1, 4096] @ [4096, 14336] → [1, 14336]. FLOPs = 2 × 1 × 14,336 × 4,096 ≈ 117 million.

For a batch of 32 tokens: [32, 4096] @ [4096, 14336] → [32, 14336]. FLOPs ≈ 3.76 billion. The work grows in a straight line with the number of tokens.

Counting the data: bytes moved

Work is half the story. The computer must also read A and B from memory and write the result. With 2 bytes per number (the BF16 format from chapter 1.3):

bytes ≈ (m × k + k × n + m × n) × bytes per number

For the one-token example, the weight matrix alone is 4,096 × 14,336 × 2 bytes ≈ 117 MB. You read 117 MB to do 117 million FLOPs: about 1 FLOP per byte. For 32 tokens you read almost the same 117 MB and do 32 times the work: about 32 FLOPs per byte.

This ratio, work per byte, is called arithmetic intensity. It explains most of LLM performance. A GPU can do hundreds of FLOPs in the time it reads one byte, so a matmul with a low ratio leaves the math units waiting for data. Chapter 2.5 develops this into the roofline model. For now, remember one fact: a batch of tokens reuses the same weights, so batching raises the work per byte.

6. Tensors and shapes

Definitions

Tensor: a grid of numbers with any number of dimensions. A scalar has 0, a vector 1, a matrix 2. LLM code uses 3-D and 4-D tensors all the time.

Shape: the size of each dimension, written as a list. [2, 8, 4096] means 2 × 8 × 4,096 numbers.

Batched matmul: a matmul on the last two dimensions, done independently for every index of the dimensions in front.

Model code names dimensions with letters. You will see these constantly:

LetterMeaningLlama 3.1 8B example
BBatch: number of sequences processed together1 to hundreds
T (or S, L)Tokens in each sequenceup to 131,072
D (or C, d_model)Hidden size: length of each token vector4,096
HNumber of attention heads32
d (or d_head)Size of each head128
VVocabulary size128,256

A linear layer in PyTorch takes an input of shape [B, T, D] and acts on the last dimension only. It treats B × T as "many rows". So [2, 8, 4096] @ [4096, 14336] gives [2, 8, 14336], and the FLOPs are 2 × (2 × 8) × 14,336 × 4,096. The rule: multiply all leading dimensions together to get m.

Try it: predict the shape
  1. x is [4, 100, 4096]. W is [4096, 1024]. Shape of x @ W?
  2. q is [4, 32, 100, 128] and k is [4, 32, 100, 128]. Shape of q @ k.transpose(-2, -1)?
  3. How many FLOPs is the product in question 2?
Answers
  1. [4, 100, 1024].
  2. k transposed on the last two dims is [4, 32, 128, 100]. The product is [4, 32, 100, 100]: one 100 × 100 score grid per sequence per head. You will meet this grid again as the attention matrix in chapter 2.2.
  3. There are 4 × 32 = 128 separate matmuls, each [100, 128] @ [128, 100]. FLOPs = 128 × 2 × 100 × 100 × 128 ≈ 328 million.

Broadcasting is the rule that lets you add a smaller tensor to a bigger one. A bias of shape [14336] added to [2, 8, 14336] is copied along the leading dimensions. Read shapes from the right: dimensions must be equal, or one of them must be 1 (or missing). Chapter 1.4 practises this.

7. Putting it together: the matmuls inside one model

Almost all parameters of a transformer live in a few weight matrices per layer. For Llama 3.1 8B, each of the 32 layers has:

MatrixShapeParameters
Query projection4096 × 409616.8 M
Key projection4096 × 10244.2 M
Value projection4096 × 10244.2 M
Output projection4096 × 409616.8 M
MLP gate4096 × 1433658.7 M
MLP up4096 × 1433658.7 M
MLP down14336 × 409658.7 M
Per layer218.1 M

32 layers × 218.1 M ≈ 6.98 B. The input embedding table and the output head (each 128,256 × 4,096 ≈ 0.53 B) bring the total to about 8.03 B. Small parts such as normalization weights add almost nothing.

Now the key result. Each parameter takes part in one multiply and one add per token. So:

FLOPs per token ≈ 2 × number of parameters

For Llama 3.1 8B, that is about 16 GFLOPs per token. (The input embedding is a table lookup, not a matmul, and attention adds work that grows with context. Chapter 2.5 refines this. The rule is still the standard first estimate.)

What the number means

A 1,000-token prompt into Llama 3.1 8B needs about 16 TFLOPs. An NVIDIA H100 does about 989 TFLOP/s of dense BF16 math at its peak. So the prompt needs at least 16 ms of pure math, and in practice somewhat more. You just estimated a latency from a shape table.

8. Expert layer

Why matmul order and layout matter

A matmul's FLOP count does not depend on how you loop, but its speed does. A GPU splits the output into tiles and loads each tile of A and B into fast on-chip memory once, then reuses it many times. Tiling raises the effective work per byte read from main memory. Chapter 5.4 teaches this. The fact to keep now: shapes that are multiples of 64 or 128 usually run faster, because they fill the tiles exactly.

Low-rank structure

A [k, n] matrix can be approximated as the product of [k, r] and [r, n] with a small r. This cuts parameters from k × n to r × (k + n). LoRA fine-tuning (chapter 7.3) and the compressed KV cache of multi-head latent attention (expert layer of chapter 2.4) both use this idea.

Matrix-vector vs matrix-matrix

When m = 1, a matmul is a matrix-vector product (GEMV). It reads the full weight matrix to do only 2 FLOPs per weight. Generating one token for one user is a chain of GEMVs, which is why it is limited by memory speed, not math speed. Many users at once turn GEMVs back into matrix-matrix products (GEMM). This is the core reason LLM servers batch requests (chapter 3.2).

9. Common mistakes

  • Counting a matmul as m × n × k FLOPs. Each multiply has an add: use 2 × m × n × k.
  • Forgetting the leading dimensions. For [B, T, D] inputs, m = B × T.
  • Confusing FLOPs (an amount of work) with FLOP/s (a speed).
  • Reading a shape from the left when broadcasting. Broadcasting aligns dimensions from the right.
  • Assuming a bigger FLOP count always means slower. At small m, reading the weights takes longer than the math.

10. Lab

Goal: count FLOPs by hand, then measure them, and see that small matmuls waste the hardware.

Setup: open a new Google Colab notebook. A CPU runtime is enough for Parts A to C. Part D needs a GPU: choose Runtime, then Change runtime type, then T4 GPU.

Part A: dot product and cosine by hand, then in code

Predict first: for a = [1, 2, 3] and b = [4, −5, 6], what are a · b and the cosine similarity? Then run:

import numpy as np
a = np.array([1., 2., 3.]); b = np.array([4., -5., 6.])
dot = sum(x * y for x, y in zip(a, b))          # your own loop
print(dot, a @ b)                               # both should be 12.0
cos = dot / (np.linalg.norm(a) * np.linalg.norm(b))
print(round(cos, 3))
Expected output

12.0 twice, then 0.366. The vectors point in a broadly similar direction (angle about 68 degrees).

Part B: write a matmul with loops

Write matmul(A, B) with three nested loops. Do not use @. Count the multiply-adds as you go.

def matmul(A, B):
    m, k = A.shape; k2, n = B.shape
    assert k == k2, "inner sizes must match"
    C = np.zeros((m, n)); flops = 0
    # TODO: fill C[i, j] with the dot product of row i of A and column j of B
    # and add 2 to flops for every multiply-add
    return C, flops

A = np.random.randn(3, 4); B = np.random.randn(4, 2)
C, f = matmul(A, B)
print(np.allclose(C, A @ B), f, 2 * 3 * 2 * 4)   # True 48 48
Solution 
    for i in range(m):
        for j in range(n):
            s = 0.0
            for p in range(k):
                s += A[i, p] * B[p, j]
                flops += 2
            C[i, j] = s

Part C: measure FLOP/s and the effect of shape

Predict first: the three shapes below have very different FLOP counts. Write down the FLOPs of each. Which will reach the highest GFLOP/s, and why?

import time
def bench(m, k, n, reps=5):
    A = np.random.randn(m, k).astype(np.float32)
    B = np.random.randn(k, n).astype(np.float32)
    A @ B                                         # warm-up
    t = time.perf_counter()
    for _ in range(reps): A @ B
    dt = (time.perf_counter() - t) / reps
    flops = 2 * m * n * k
    print(f"[{m}x{k}] @ [{k}x{n}]  {flops/1e9:8.3f} GFLOP  {dt*1e3:8.2f} ms  {flops/dt/1e9:7.1f} GFLOP/s")

bench(1, 4096, 4096)      # one token through a 4096x4096 layer
bench(32, 4096, 4096)     # 32 tokens
bench(2048, 4096, 4096)   # 2048 tokens
What you should see

The FLOPs are 0.034, 1.07 and 68.7 GFLOP. Time grows much more slowly than FLOPs from m = 1 to m = 32, because the cost at m = 1 is mostly reading the 64 MB weight matrix (FP32) and loop overhead. GFLOP/s rises with m. This is the "work per byte" effect from section 5, measured on your own machine. Exact numbers depend on the CPU Colab gives you.

Part D: the same on a GPU

import torch
dev = "cuda"
def gbench(m, k, n, dtype=torch.float16, reps=20):
    A = torch.randn(m, k, device=dev, dtype=dtype); B = torch.randn(k, n, device=dev, dtype=dtype)
    for _ in range(3): A @ B
    torch.cuda.synchronize(); t = time.perf_counter()
    for _ in range(reps): A @ B
    torch.cuda.synchronize(); dt = (time.perf_counter() - t) / reps
    print(f"m={m:5d}  {2*m*n*k/dt/1e12:6.2f} TFLOP/s  {dt*1e6:8.1f} us")

for m in [1, 8, 32, 128, 512, 2048, 8192]:
    gbench(m, 4096, 4096)

A T4's data sheet lists 65 TFLOP/s of FP16 tensor math. Find the m where you get closest to it. Plot TFLOP/s against m. Keep this plot: it is the shape of every batching curve in this book.

Watch out

GPU work runs asynchronously. Without torch.cuda.synchronize() the timer stops before the GPU finishes, and you will report impossible speeds.

Part E: count a real model

Load the config of an open model and recompute its parameter count from shapes. Compare with the official number.

from transformers import AutoConfig
c = AutoConfig.from_pretrained("Qwen/Qwen2.5-0.5B")       # no login needed
D, F, L, V = c.hidden_size, c.intermediate_size, c.num_hidden_layers, c.vocab_size
hd = D // c.num_attention_heads; kv = c.num_key_value_heads * hd
per_layer = D*D + 2*D*kv + D*D + 3*D*F                     # q, k, v, o, gate, up, down
emb = V * D * (1 if c.tie_word_embeddings else 2)
print(D, F, L, V, kv)
print(f"{(L*per_layer + emb)/1e9:.3f} B parameters (official: 0.49 B)")
Notes

Your estimate should land within a few percent of 0.49 B. The small gap is biases on the Q, K and V projections and the normalization weights, which this formula skips. Qwen2.5-0.5B ties its input and output embeddings, so the table is counted once.

11. In the real world

Where these counts are used
  • Capacity planning: teams estimate GPUs needed from 2 × parameters × tokens per second, then divide by the GPU's real (not peak) FLOP/s.
  • Model choice: a model with half the parameters needs about half the FLOPs per token, so it can serve about twice the traffic on the same hardware, all else equal.
  • Libraries: every linear layer in PyTorch calls a vendor matmul library (cuBLAS on NVIDIA). Engine teams tune shapes and batch sizes so these calls hit the fast tile sizes.
  • Embeddings and search: vector databases rank documents by dot product or cosine similarity, at millions of comparisons per query.

13. Summary

  • A vector is a list of numbers. In an LLM, every token becomes one vector of the hidden size.
  • The dot product multiplies matching elements and adds them. It measures how much two vectors agree. Cosine similarity is the same, divided by the lengths.
  • A matmul [m, k] @ [k, n] gives [m, n] and costs 2 × m × n × k FLOPs.
  • Bytes moved ≈ (mk + kn + mn) × bytes per number. Work per byte rises with m because the weights are shared.
  • For [B, T, D] inputs, m = B × T.
  • A transformer's FLOPs per token ≈ 2 × parameters. Llama 3.1 8B ≈ 16 GFLOPs per token.
