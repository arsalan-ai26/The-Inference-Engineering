Profiling

A benchmark tells you how fast a system is; a profile tells you why. Profilers record every operator, kernel launch, memory copy and synchronization with timestamps, so you can see which kernels take the time, where the GPU sits idle, and what the CPU was doing meanwhile. This chapter shows how to use the PyTorch profiler, what Nsight Systems and Nsight Compute add, how to read a trace and turn it into a diagnosis with the three regimes of chapter 5.1, and how to profile a real engine.

Before you start: skip check
  1. A trace shows the GPU stream with many short kernels separated by gaps, and the CPU busy the whole time. Which regime?
  2. What does Nsight Compute tell you that Nsight Systems does not?
  3. Why should you not report latency numbers measured while the profiler was running?
Answers
  1. Overhead-bound: the GPU waits for the CPU to launch work.
  2. What happens inside one kernel: achieved memory and compute throughput as a share of peak, occupancy, cache hit rates, stall reasons. Nsight Systems shows the timeline across the whole program.
  3. Profiling adds overhead (recording, shapes, stacks), which changes timings, especially for small kernels and CPU-side work. Profile to find causes; benchmark separately to measure.

1. Benchmark first, then profile

Benchmarking gives the numbers (for example p90 TTFT = 350 ms); profiling shows where each millisecond went. Most inference engineers using a mature engine mainly configure and benchmark. Profiling becomes essential when you contribute to an engine, write your own serving code, adopt a new model or hardware generation, or a benchmark result does not match your estimate from first principles (chapter 2.5). A large gap between the estimate and the measurement is the best reason to profile.

2. The PyTorch profiler

import torch
from torch.profiler import profile, record_function, ProfilerActivity

acts = [ProfilerActivity.CPU, ProfilerActivity.CUDA]
with torch.no_grad():
    model(ids)                                        # warm up outside the profile
    with profile(activities=acts, record_shapes=True) as prof:
        with record_function("prefill"):              # a named range in the trace
            out = model(ids, use_cache=True)
        with record_function("decode_step"):
            model(next_token, past_key_values=out.past_key_values, use_cache=True)

print(prof.key_averages().table(sort_by="self_cuda_time_total", row_limit=12))
prof.export_chrome_trace("trace.json")                # open at ui.perfetto.dev

The table has one row per operator (or kernel), summed over calls. Key columns:

  • Self time: time spent in the operator itself, excluding operators it called. Sort by self CUDA time to find the kernels that take the GPU's time.
  • Total time: including children. A record_function range's total shows the cost of a whole phase.
  • # of calls: often the most revealing column. Hundreds of calls of a cheap operator mean launch overhead; check the count against the model's structure (for example, 4 matmuls per layer per pass).

For long-running programs, pass a schedule (wait, warm-up, active steps) and an on_trace_ready handler so only a few steps are recorded. Options such as profile_memory and with_stack are useful but add overhead.

3. Reading a trace

Open the exported trace in Perfetto (or Chrome's trace viewer). You will see rows (tracks) on a shared time axis:

  • CPU thread: Python and PyTorch operators as nested bars, with CUDA API calls such as cudaLaunchKernel and cudaStreamSynchronize at the bottom of each stack.
  • GPU stream: the kernels that actually ran, and memory copies. Arrows (flows) link each launch on the CPU to the kernel it started.

Then ask, in this order:

  1. Is the GPU stream continuous? Gaps between kernels mean the GPU waited. If the CPU row is busy with launches during the gap, it is launch or Python overhead; if the CPU is inside cudaStreamSynchronize or a .item(), it is a synchronization (chapter 5.3).
  2. Which kernels take the time? Kernel names reveal their type: GEMMs contain names like gemm, cutlass, xmma or nvjet; attention contains flash, fmha or the backend's name; element-wise kernels mention elementwise or vectorized; Triton kernels carry generated names starting with triton_.
  3. Is each heavy kernel near its roofline? Divide the bytes it must move by its time (for memory-bound kernels) or its FLOPs by its time (for compute-bound ones) and compare with peak (chapters 2.5 and 5.1). A GEMM at 30% of peak bandwidth in decode is a lead; at 85% it is done.
  4. What runs on the CPU between steps? Scheduling, sampling, detokenization: anything that delays the next launch.

4. Nsight Systems and Nsight Compute

Nsight Systems is the tool for whole-program timelines with low overhead, including multiple processes and GPUs, NCCL collectives, and memory copies. Typical use:

nsys profile -t cuda,nvtx,osrt -o decode_trace python serve_one_request.py
nsys stats decode_trace.nsys-rep          # text summaries: top kernels, API calls

Add NVTX ranges (torch.cuda.nvtx.range_push("prefill") / range_pop(), or record_function) to label phases. In the GUI, look for the same things as in section 3: gaps on the GPU row, long CUDA API calls on the CPU row, and whether communication overlaps with compute.

Nsight Compute profiles individual kernels, replaying each one several times to collect hardware counters. Its "speed of light" section reports achieved memory and compute throughput as a percentage of peak, which tells you immediately whether a kernel is memory- or compute-limited and how close it is. Further sections show occupancy and its limiter (chapter 5.2), cache hit rates, and warp stall reasons (waiting for memory, for a barrier, for an instruction). Use it on one or two kernels you already know matter; it is far too slow to run on a whole model.

ncu --set full -k regex:gemm -c 5 -o gemm_report python one_forward_pass.py

5. Profiling a serving engine

Engines run the model in worker processes, so a profiler around your client script sees nothing. vLLM has built-in support: start the server with a profiler configuration and trigger recording with the benchmark tool or HTTP endpoints.

vllm serve Qwen/Qwen2.5-1.5B-Instruct \
  --profiler-config '{"profiler": "torch", "torch_profiler_dir": "./vllm_profile"}'
curl -X POST http://localhost:8000/start_profile
# ... send two or three requests ...
curl -X POST http://localhost:8000/stop_profile    # flushes traces; can take a while

Each worker writes a trace and a summary table, viewable in Perfetto. Send only a few requests: traces grow fast. vLLM's documentation recommends Nsight Systems for low-overhead performance work and the PyTorch profiler for richer debugging information, and warns that profiling is for developers, never for production serving.

6. A profiling workflow

  1. Estimate. Compute the expected step time from bytes and FLOPs (chapter 2.5).
  2. Benchmark. Measure the real step time without the profiler.
  3. Profile a small, representative run. Warm up first; record a few steps of both prefill and decode at the batch sizes you serve.
  4. Classify. Overhead (gaps), memory (bandwidth-bound kernels below peak), compute (GEMMs below peak FLOP/s).
  5. Change one thing. Remove a sync, fuse kernels, capture a CUDA graph, change a kernel backend, raise the batch.
  6. Benchmark again, then re-profile to confirm the trace changed the way you expected.

7. Expert layer

CUDA graphs hide kernels from the CPU view

With CUDA graphs (chapter 5.7), the CPU launches one graph and the GPU runs many kernels; the PyTorch profiler may show only the graph launch on the CPU side. Nsight Systems can trace individual kernels inside graphs (with graph tracing enabled at node level), at some extra overhead. When comparing eager and graph runs, compare GPU-side time per step.

Profiling multi-GPU runs

With tensor or expert parallelism, look at each rank's timeline side by side. A rank that finishes its compute early and waits in an all-reduce or all-to-all reveals load imbalance (for example, a hot expert in chapter 4.5). Communication kernels (NCCL) that do not overlap with compute are the usual target.

Clocks and warm-up

GPUs change clock speeds with load and temperature; the first iterations also include compilation, autotuning and memory allocation. Always warm up, record steady-state steps, and for kernel-level measurements consider locking clocks (on machines where you are allowed to), as Nsight Compute does by default.

8. Common mistakes

  • Profiling the first iteration and optimizing compilation or allocation time.
  • Reporting latency from a profiled run.
  • Sorting by total time instead of self time and chasing parent operators.
  • Profiling only prefill (or only decode) when the workload is a mix.
  • Running Nsight Compute on a whole model and waiting hours.
  • Wrapping the client script with a profiler while the model runs in an engine's worker process.

9. Lab

Goal: profile a small model's prefill and decode, name the top kernels and why they cost the most, and find the overhead.

Part A: an operator table (CPU, under a minute)

import torch
from torch.profiler import profile, record_function, ProfilerActivity
from transformers import AutoModelForCausalLM, AutoTokenizer
dev = "cuda" if torch.cuda.is_available() else "cpu"
MID = "Qwen/Qwen2.5-0.5B-Instruct"
model = AutoModelForCausalLM.from_pretrained(
    MID, dtype=torch.float16 if dev == "cuda" else torch.float32).to(dev).eval()
tok = AutoTokenizer.from_pretrained(MID)
ids = tok("The quick brown fox " * 64, return_tensors="pt").input_ids.to(dev)   # about 300 tokens
acts = [ProfilerActivity.CPU] + ([ProfilerActivity.CUDA] if dev == "cuda" else [])
with torch.no_grad():
    model(ids)                                              # warm up
    with profile(activities=acts, record_shapes=True) as prof:
        with record_function("prefill"):
            out = model(ids, use_cache=True)
        nxt = out.logits[:, -1:].argmax(-1)
        with record_function("decode_step"):
            model(nxt, past_key_values=out.past_key_values, use_cache=True)
key = "self_cuda_time_total" if dev == "cuda" else "self_cpu_time_total"
print(prof.key_averages().table(sort_by=key, row_limit=12))
prof.export_chrome_trace("trace.json")

Before reading the table, predict: how many matmul calls should there be? (Qwen2.5-0.5B has 24 layers; its Q, K and V projections have biases, the other four projections do not; there is one output head; the program runs two forward passes.)

What we measured on CPU, and why
Name                                   Self CPU %   Self CPU   # of Calls
aten::mm                                   85.72%     1.271s          194
aten::addmm                                 4.10%    60.8ms           144
aten::_scaled_dot_product_flash_attention_for_cpu   2.71%   40.2ms     48
aten::mul                                   1.86%    27.5ms           442
prefill (range)                             1.25%    18.6ms             1
aten::silu                                  0.86%    12.8ms            48
decode_step (range)                         0.64%     9.5ms             1

Matmuls dominate prefill (86% self time): they hold almost all the FLOPs. The counts check out: addmm = 3 biased projections × 24 layers × 2 passes = 144; mm = 4 unbiased projections × 24 × 2 + 2 output heads = 194. The decode step took about 101 ms in total against about 1.38 s for prefill of 300 tokens, much more than 1/300 of it: per token, decode is far less efficient. Element-wise ops (mul with 442 calls) are cheap individually but numerous: on a GPU, their launches become the overhead.

Part B: the GPU trace (T4)

Run Part A on a T4 and open trace.json in Perfetto. In the decode step: measure the GPU's busy time against the step's wall time; find the three kernels with the most self CUDA time and name their type (GEMM, attention, element-wise); and find a gap and the CPU activity during it. Then batch 32 sequences into the decode step and compare. Write a three-line diagnosis using chapter 5.1's regimes.

What to expect

For a 0.5B model at batch 1 on a T4, the decode step's GPU row is mostly gaps: kernels take a few microseconds each, and the CPU spends longer launching them. GEMM kernels still lead self CUDA time, followed by attention and element-wise kernels. At batch 32 the kernels lengthen but the gaps barely change, so the GPU busy fraction rises: the overhead is amortized. This is the motivation for CUDA graphs in chapter 5.7.

Part C (optional): Nsight Systems

If nsys is available on your machine, profile the same script with nsys profile -t cuda,nvtx,osrt and run nsys stats on the result. Compare the top kernels list with the PyTorch profiler's. Which tool showed the CPU-side gaps more clearly?

Part D: profile vLLM (T4)

Start vLLM with the profiler configuration from section 5, send one short and one long request between start_profile and stop_profile, and open the worker trace. Find a prefill step and a decode step. Are decode steps replayed from CUDA graphs (look for graph launches and dense kernel sequences)? Compare the decode step's GPU row with your Part B trace.

10. In the real world

Profiling in practice
  • Engine teams profile every new model architecture and GPU generation; many performance pull requests start with a trace showing a gap or a slow kernel.
  • Platform teams keep profiling scripts for their standard models and rerun them after engine upgrades to catch regressions.
  • Kernel authors live in Nsight Compute's speed-of-light and stall-reason views.

12. Summary

  • Benchmark to measure, profile to explain; profile when measurements disagree with first-principles estimates.
  • The PyTorch profiler gives operator tables and timelines; Nsight Systems gives low-overhead system timelines; Nsight Compute explains single kernels.
  • Read traces for gaps (overhead or synchronization), top kernels (by self time), and each heavy kernel's distance from its roofline.
  • Profile engines through their own hooks (vLLM's profiler configuration) with a few requests.
  • Estimate, benchmark, profile, change one thing, repeat.
