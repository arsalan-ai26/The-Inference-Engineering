Part 5 · GPUs, hardware and kernels · Chapter 5.2

GPU architecture

You do not need to design chips to be an inference engineer, but you need a working picture of what is inside one. Every number in Parts 2 to 4 (FLOP/s, bandwidth, ops:byte, why FlashAttention tiles, why fusion helps) comes from the structure described here: many streaming multiprocessors, each with tensor cores and a little fast memory, all sharing a large, slower main memory. This chapter walks through that structure from the outside in, using the H100 as the reference, and notes what Blackwell changes.

1. The big picture

A CPU has a few powerful cores built to finish one sequence of instructions as fast as possible. A GPU has a large number of simpler units built to run one operation on thousands of pieces of data at once. For neural networks, which are mostly large matrix multiplications, the GPU's design wins by a wide margin.

An H100 SXM is, from the outside in:

  • 132 streaming multiprocessors (SMs), the independent compute units. A B200 has 148.
  • A shared L2 cache of 50 MB.
  • 80 GB of HBM3 (high-bandwidth memory) stacked next to the chip, at about 3.35 TB/s.
  • NVLink ports to other GPUs (about 450 GB/s each way) and a PCIe link to the host CPU (about 64 GB/s each way on PCIe 5).

2. Inside a streaming multiprocessor

Each SM is split into 4 identical sub-partitions. Each sub-partition has:

  • a warp scheduler that issues one instruction per cycle for one warp;
  • 32 FP32 CUDA cores (plus integer and FP64 units) for ordinary arithmetic;
  • one tensor core, a unit that multiplies small matrix tiles in one step;
  • a register file of 16,384 32-bit registers (64 KB).

The 4 sub-partitions share the SM's L1 cache / shared memory: 256 KB of on-chip SRAM, of which up to about 228 KB can be used as programmer-controlled shared memory. Special function units (for exponentials, sines and similar) sit alongside.

Definitions

Thread: one instance of a kernel's code with its own registers. Warp: 32 threads that execute the same instruction together (SIMT: single instruction, multiple threads).

Thread block (CTA): a group of threads (up to 1,024) that run on one SM and can share its shared memory and synchronize with each other. Grid: all the blocks of one kernel launch. Chapter 5.3 covers this programming model.

Shared memory (SMEM): fast on-chip memory shared by the threads of one block. Registers: the fastest storage, private to each thread.

Where the FLOPs are

The tensor cores provide almost all of the headline FLOP/s: on an H100, about 990 TFLOP/s in BF16 from tensor cores against about 67 TFLOP/s in FP32 from CUDA cores (chapter 5.1). Counting backwards, each tensor core does roughly 1,024 BF16 FLOPs per clock cycle, about one 8 × 8 × 8 matrix multiply. Every generation has made tensor cores larger and faster, and that has changed how they must be fed:

GenerationTensor core fed byNotable additions for inference
Ampere (A100, 2020)One warp (mma instructions)BF16, TF32, 2:4 structured sparsity, asynchronous copies
Hopper (H100, H200, 2022)A warpgroup of 4 warps (wgmma), operands in shared memoryFP8; the Tensor Memory Accelerator (TMA) for bulk asynchronous copies; thread block clusters and distributed shared memory
Blackwell (B200, B300, 2024)Operands in a new Tensor Memory (TMEM), 256 KB per SM; one MMA can span 2 SMsFP4, MXFP8, MXFP4, NVFP4 with hardware block scaling; NVLink 5

The trend matters for kernels: the bigger the tensor core, the harder it is to keep busy, and the more kernels must use asynchronous copies, warp specialization and pipelining (FlashAttention-3 and 4, chapter 4.2). This is why each new GPU generation needs new kernels before it reaches its potential.

3. The memory hierarchy

Data moves through layers that trade size for speed. The closer to the tensor cores, the faster and smaller:

NVIDIA does not publish L2 bandwidth; the figure is the measurement quoted in the JAX scaling book. Aggregate SMEM bandwidth estimates vary by source; what matters is that it is several times HBM.

Every optimization in Part 4 is about this hierarchy. Weights and the KV cache live in HBM, so decode is limited by HBM bandwidth. FlashAttention keeps tiles in shared memory and registers so the score matrix never reaches HBM. Fusion keeps intermediate results in registers instead of writing them to HBM. Quantization shrinks what must cross the HBM boundary.

4. Hiding latency with many warps

A read from HBM takes hundreds of clock cycles to arrive. A CPU hides latency with large caches and by guessing ahead. A GPU hides it with parallelism: each SM keeps up to 64 warps (2,048 threads) resident, with their registers already loaded. When a warp stalls on a memory read, the scheduler issues an instruction from another warp that is ready, in the next cycle, with no context-switch cost. With enough warps in flight, the memory system always has requests outstanding and the cores always have work.

Occupancy is the number of resident warps as a share of the maximum. It is limited by whichever resource runs out first: registers per thread, shared memory per block, or threads per block. Higher occupancy hides latency better, but not always: kernels that keep more data in registers and shared memory (like FlashAttention) deliberately run at lower occupancy and hide latency with asynchronous copies instead.

Interactive: what limits occupancy on an H100 SM
Per SM: 65,536 registers, 2,048 threads, 32 blocks, about 228 KB of shared memory. Choose a kernel's resource use and see how many warps fit. (Real allocation rounds registers and shared memory up to fixed sizes; this ignores that.)

5. Three hardware habits kernels must respect

  • Coalesced memory access. When the 32 threads of a warp read 32 neighbouring addresses, the hardware combines them into a few wide transactions. Scattered addresses turn into many separate transactions and waste bandwidth. Data layouts (row-major vs column-major, KV cache layouts) are chosen so that warps read contiguous memory.
  • Warp divergence. All 32 threads in a warp run the same instruction. If an if sends half of them one way and half the other, the warp runs both paths one after the other, with half its threads idle each time. Kernels avoid data-dependent branches in inner loops.
  • Shared memory bank conflicts. Shared memory is split into 32 banks. If several threads of a warp hit different addresses in the same bank, the accesses are serialized. Kernel authors pad or swizzle tile layouts to avoid this.

6. Beyond one GPU

  • NVLink and NVSwitch connect the 8 GPUs of a node all-to-all at full bandwidth: about 450 GB/s each way per H100 (NVLink 4), about 900 GB/s per B200 (NVLink 5). GB200 NVL72 systems extend one NVLink domain to 72 GPUs.
  • InfiniBand or RoCE connect nodes, typically one 400 Gb/s (about 50 GB/s) network card per GPU, with newer 800 Gb/s cards arriving.
  • Grace CPUs (GH200, GB200) connect to their GPUs with NVLink-C2C at up to 900 GB/s in total, far faster than PCIe, which makes CPU memory a much faster KV offload tier (chapter 4.4).

Chapter 4.5 used these numbers to choose parallel layouts; chapter 5.5 compares GPU generations and other accelerators.

7. Expert layer

Asynchrony is the new programming model

On Hopper and Blackwell, the fastest kernels split warps into roles: "producer" warps issue TMA copies from HBM into shared memory, "consumer" warpgroups run tensor-core MMAs on data that already arrived, and the two overlap through barriers in shared memory. Blackwell adds tensor memory and 2-SM MMAs, so even the accumulator lives outside registers. Libraries such as CUTLASS, CuTe and ThunderKittens exist largely to make this tractable (chapter 5.8).

Clocks, power and the spec sheet

Peak FLOP/s assume the boost clock. Under sustained heavy load a GPU may lower its clock to stay within power and temperature limits, so a long benchmark can be slower than a short one. Spec sheets also often list FLOP/s "with sparsity" (2:4 structured sparsity, twice the dense figure); dense numbers are what inference normally gets.

Not only NVIDIA

AMD's Instinct GPUs use the same broad structure under different names (compute units, wavefronts of 64 threads on CDNA, LDS for shared memory, Infinity Fabric for links). TPUs use a few very large matrix units with a big software-managed memory (VMEM) instead of many small SMs. The concepts in this chapter transfer; the numbers and the kernel tricks do not.

8. Common mistakes

  • Comparing GPUs on sparse FLOP/s figures.
  • Assuming a kernel tuned for an H100 is fast on a B200 (or runs at all).
  • Thinking more threads always means faster; resource limits and register spills can make the opposite true.
  • Ignoring memory layout: a transposed tensor that forces scattered reads can halve bandwidth.
  • Treating L2 as a place to keep weights; it holds a tiny fraction of a model and is managed by hardware.

Part B: device properties and a cache cliff

import torch, time
dev = "cuda" if torch.cuda.is_available() else "cpu"
if dev == "cuda":
    p = torch.cuda.get_device_properties(0)
    print(p.name, "SMs:", p.multi_processor_count, "memory GB:", round(p.total_memory / 1e9, 1),
          "L2 MB:", getattr(p, "L2_cache_size", 0) / 1e6, "compute capability:", f"{p.major}.{p.minor}")
def sync():
    if dev == "cuda": torch.cuda.synchronize()
for kib in [64, 256, 1024, 4096, 16384, 65536, 262144]:     # size of ONE tensor
    n = kib * 1024 // 4
    a = torch.randn(n, device=dev); b = torch.empty_like(a)
    reps = max(10, int(2e9 // (8 * n)))
    b.copy_(a); sync()
    t = time.perf_counter()
    for _ in range(reps): b.copy_(a)
    sync(); s = (time.perf_counter() - t) / reps
    print(f"working set {2*kib:>7} KiB  {2*n*4/s/1e9:7.1f} GB/s")

Predict where the bandwidth will change: on a CPU, where the working set (source plus destination) leaves the last-level cache; on a T4, where it exceeds the 4 MB L2.

What we measured on CPU, and what to expect on a T4

On a 2-core CPU: 52, 71 and 123 GB/s for working sets of 128 KiB, 512 KiB and 2 MiB (in cache), then a cliff to 47, 37, 24 and 20 GB/s from 8 MiB up (main memory). On a T4 the large sizes should approach its 320 GB/s HBM bandwidth (often 70% to 90% of it). Small sizes are dominated by launch overhead (chapter 5.1), so the L2 effect is hard to see with this simple timer; time many copies inside one CUDA graph, or use the profiler of chapter 5.6, to see it.

Part C: occupancy by hand

A kernel uses 128 threads per block, 96 registers per thread and 48 KB of shared memory per block, on an H100 SM. How many blocks fit, what limits them, and what is the occupancy? Then change it to 40 KB of shared memory and recompute. Check with the widget.

Answer

Threads: 2,048 ÷ 128 = 16 blocks. Registers: 65,536 ÷ (96 × 128) = 5.3, so 5 blocks. Shared memory: 228 ÷ 48 = 4.75, so 4 blocks. Shared memory limits it to 4 blocks = 16 warps = 25% occupancy. With 40 KB: 228 ÷ 40 = 5.7, so 5 blocks; now registers and shared memory both allow 5 blocks = 20 warps = 31%.

10. In the real world

Why this matters on the job
  • Hardware selection uses bandwidth and memory for decode-heavy work and tensor-core FLOP/s for prefill-heavy work (chapter 5.5).
  • Kernel and engine releases lag new GPU generations because kernels must be rewritten for new tensor-core interfaces (TMA, wgmma, TMEM).
  • Debugging slow kernels starts from this chapter's vocabulary: occupancy, coalescing, bank conflicts, register spills (chapter 5.6).

12. Summary

  • A GPU is many SMs (132 on an H100) sharing an L2 cache and HBM; each SM has 4 sub-partitions with a warp scheduler, CUDA cores, a tensor core and registers, and shared on-chip SRAM.
  • Tensor cores provide nearly all FLOP/s; each generation makes them larger and harder to feed (wgmma and TMA on Hopper, TMEM on Blackwell).
  • Memory runs from registers and shared memory (fast, tiny) through L2 to HBM (large, slower) and host memory over PCIe; optimizations are about staying high in this hierarchy.
  • Many resident warps hide latency; occupancy is limited by registers, shared memory and threads.
  • Coalescing, divergence and bank conflicts are the everyday hardware rules kernels follow.
