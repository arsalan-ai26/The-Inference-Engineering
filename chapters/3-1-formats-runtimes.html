Part 3 · Inference engines and serving · Chapter 3.1

Model formats and runtimes

A trained model is a folder of files. Turning it into a fast, shared service takes two decisions: how the weights are stored and loaded, and what program runs the forward pass. This chapter covers the file formats (safetensors, ONNX, engine files), the ways to execute a model (eager PyTorch, compiled graphs, TensorRT), why a plain PyTorch server collapses under many users, and how to read an inference engine's metrics.

Answers
  1. Pickle can run arbitrary Python code while it loads. Safetensors stores only a JSON header and raw tensor bytes, so loading cannot execute code.
  2. Capturing the model's computation as a graph, optimizing it for one target (fusing operations, choosing kernels, planning memory) and producing code that runs it with less overhead.
  3. It waits for the 15 requests in front of it to finish completely, so its TTFT becomes about 15 full generation times.

1. What a model release contains

Open any model repository on Hugging Face and you find the same set of files:

FileWhat it holdsWho reads it
config.jsonArchitecture: layers, hidden size, heads, KV heads, RoPE settings, vocabulary size, data typeThe engine, to build the model and size the KV cache
model-00001-of-00004.safetensors …The weights, split into shards of a few GBThe weight loader
model.safetensors.index.jsonWhich tensor lives in which shardThe weight loader
tokenizer.json, tokenizer_config.jsonVocabulary, merges, special tokens, often the chat template (chapter 2.1)The API server
generation_config.jsonDefault sampling settings and stop tokens (chapter 1.2)The API server

The config and weights describe what the model is. They say nothing about how fast it runs. That depends on the program that executes it.

2. Weight files: pickle vs safetensors

PyTorch's own format (torch.save, files ending in .bin or .pt) uses Python's pickle. Pickle stores Python objects, and loading a pickle can run any Python code the file contains. A malicious checkpoint can therefore run commands on your server. Recent PyTorch versions default to a restricted "weights only" mode, but the format itself remains unsafe.

Safetensors was designed to remove this risk and to load fast. Its layout is simple:

  • Safe: the loader only parses JSON and copies bytes.
  • Fast: the file can be memory-mapped: the operating system maps it into the process's address space and reads pages only when they are touched. A tensor can be read without loading the whole file, and without an extra copy in CPU memory.
  • Lazy and partial: a loader can read just the tensors one GPU needs, which matters when a model is split across GPUs (chapter 4.5).

Safetensors is now the default for open model releases. The data still has to travel from disk to CPU memory to the GPU. For large models, disk and network speed usually set the load time (section 8).

3. How the forward pass is executed

The same weights can be run in very different ways:

ModeHow it worksStrengthWeakness
PyTorch eagerPython runs each operation in turn; each launches one or more GPU kernelsFlexible, easy to debug, any modelPython and launch overhead per operation; no cross-operation fusion
torch.compileCaptures the Python code as a graph, fuses operations, generates kernels (often in Triton); can use CUDA graphsLarge speed-ups with little code changeCompile time; some Python features force "graph breaks"; custom kernels stay opaque calls
ONNX + ONNX RuntimeExport a graph of standard operators plus weights; a runtime executes it on many hardware typesPortable across vendors and languagesNot every PyTorch operation exports; LLM-specific features (paged KV, continuous batching) are not built in
TensorRTCompile a graph into an "engine" for one GPU type: fuse layers, pick precisions, benchmark kernels for each shapeVery fast on NVIDIA GPUsEngine is tied to the GPU architecture and TensorRT version; build step required
LLM inference engines (vLLM, SGLang, TensorRT-LLM)Hand-written model code plus fused kernels, plus a scheduler and KV cache managerBuilt for many concurrent usersModel must be supported by the engine

4. What "compiling" a model means

Compiling has three steps, whatever the tool:

  1. Capture. Record the sequence of tensor operations as a graph, with shapes and data types.
  2. Optimize. Rewrite the graph: fuse chains of element-wise operations into one kernel (chapter 5.4), remove unused work, pick the fastest kernel for each shape, choose precisions, and plan where every intermediate tensor lives in memory.
  3. Lower. Generate code for the target hardware and package it so it can be launched with little overhead, for example as a CUDA graph: a recorded sequence of kernel launches replayed with a single call (chapter 5.7).

Why it helps LLMs: decode at small batch runs hundreds of small kernels per token. Eager mode pays a CPU launch cost for each, and the GPU waits between them (the overhead-bound regime of chapter 2.5). Fusion reduces the number of kernels and memory round trips; CUDA graphs remove most of the launch cost.

Watch out: "compiling cannot help with custom kernels"

You may read that torch.compile is of limited use for LLMs because it cannot fuse custom kernels such as FlashAttention. It is true that a custom kernel stays an opaque call inside the graph. But the compiler still fuses everything around it (normalization, RoPE, activation, residual adds) and can capture the whole step in CUDA graphs. vLLM, for example, uses torch.compile on its model code alongside its custom attention kernels.

5. Why a plain PyTorch server breaks under load

The quickest way to serve a model is a web endpoint that calls model.generate(). It works for one user. With many, it fails in four ways:

  1. Queueing. If requests run one at a time, the n-th user waits for every request ahead of it to finish. Time to first token grows linearly with the queue.
  2. Wasted batching. If you batch requests together the simple way, every request in the batch waits for the longest one, and short prompts are padded to the longest prompt. GPU work is wasted on padding, and finished requests hold their slot (chapter 3.2).
  3. Memory. Each request's KV cache is allocated separately and grows by copying. Memory fragments and is reserved for the worst case (chapter 2.4, section 7), so far fewer requests fit.
  4. Overhead. Eager Python decode at small batch leaves the GPU idle between kernels.
Interactive: one-at-a-time vs an engine that batches
A simple model of a burst of requests arriving together. "Sequential" serves them one at a time. "Batched" runs all of them in every decode step (continuous batching, chapter 3.2), with a step time that grows slowly with batch (chapter 2.5). Prefill is ignored to keep the picture clear.

6. What an inference engine adds

An LLM inference engine is the answer to all four problems. Chapters 3.2 to 3.4 open each part; here is the map:

  • The API server handles HTTP, the chat template, tokenization and streaming, often in a separate process so the GPU loop is never blocked by networking.
  • The scheduler decides, at every step, which requests run and how many tokens each processes (chapter 3.2).
  • The KV cache manager hands out fixed-size memory blocks to requests as they grow (chapter 3.3).
  • The model runner executes one forward pass for the whole batch with fused, compiled kernels, then samples the next tokens.

7. The OpenAI-compatible server

vLLM, SGLang and TensorRT-LLM all offer the same HTTP interface as OpenAI's API, so any OpenAI client library works by changing the base URL. The endpoints you will use:

EndpointUse
POST /v1/chat/completionsChat: messages in, the engine applies the chat template
POST /v1/completionsRaw text prompt in, no template
GET /v1/modelsWhich models the server holds; a quick readiness check
GET /healthLiveness for load balancers and orchestrators
GET /metricsPrometheus metrics (section 9)
from openai import OpenAI
client = OpenAI(base_url="http://localhost:8000/v1", api_key="unused")
r = client.chat.completions.create(model="Qwen/Qwen2.5-0.5B-Instruct",
        messages=[{"role": "user", "content": "One fact about GPUs."}], max_tokens=60)
print(r.choices[0].message.content, r.usage)

Engines add their own parameters on top (for example vLLM accepts top_k, min_p and structured-output options in the request body). Their exact names differ between engines, which matters if you switch engines behind one API.

8. Load time and cold start

When an engine starts, it must:

  1. Download the weights if they are not on local disk (often the slowest step).
  2. Read the safetensors shards and copy weights to the GPU.
  3. Measure memory with a test forward pass, then reserve the KV cache pool (chapter 2.4).
  4. Compile and capture CUDA graphs for common batch sizes.

Steps 3 and 4 explain why a vLLM server takes noticeably longer to become ready than a plain from_pretrained. In production this cold start time decides how fast you can add capacity (chapter 6.3). Teams cut it with local model caches, faster loaders that stream shards in parallel, and caching compiled artifacts between starts.

9. Reading engine metrics and request state

Inside an engine, each request moves through a few states:

A request waits until the scheduler admits it, runs (prefill then decode), and finishes. If KV memory runs out, the engine can preempt a running request: free its blocks and put it back in the queue to recompute later (chapter 3.3).

The /metrics endpoint exposes these states and timings in Prometheus format. The most useful vLLM metrics:

MetricMeaningWhat to watch for
vllm:num_requests_runningRequests in the current batchStuck at a low value under heavy load: a limit such as max-num-seqs or memory
vllm:num_requests_waitingRequests queued, not yet admittedGrowing steadily: the server is over capacity
vllm:kv_cache_usage_percShare of KV blocks in useNear 100% with preemptions: memory-limited
vllm:num_preemptionsRequests evicted for lack of memoryAny steady rise wastes compute on recomputation
vllm:time_to_first_token_secondsTTFT histogramLong tail: queueing or long prefills
vllm:inter_token_latency_secondsTime between output tokensSpikes when long prefills share steps with decodes (chapter 3.2)
vllm:request_queue_time_secondsTime spent waiting before runningThe queueing part of TTFT
vllm:prompt_tokens, vllm:generation_tokensCounters of tokens processedRate of these = input and output throughput
vllm:prefix_cache_queries, vllm:prefix_cache_hitsPrefix cache lookups and hitsHit rate = hits ÷ queries (chapter 3.5)

Names from the current vLLM metrics documentation. Older versions used gpu_cache_usage_perc for KV usage; check your version.

10. Expert layer

Transformers v5 and the reference role

Hugging Face transformers v5 went PyTorch-only, simplified tokenization to one backend, added packaged optimized kernels, and introduced transformers serve, an OpenAI-compatible server for evaluation-style workloads. Its stated aim is to be the reference model definition that engines such as vLLM and SGLang stay compatible with, not to replace them. Some engines can even run a transformers model definition directly as a fallback for architectures they do not implement natively.

TensorRT engine portability

A TensorRT engine is built for one GPU architecture and TensorRT version. Newer TensorRT versions offer a hardware-compatibility mode that builds engines able to run across several recent architectures, at some speed cost. Plan engine builds into your deployment pipeline, one per GPU type.

Graph capture and dynamic shapes

LLM serving has shapes that change every step: the number of sequences and tokens in the batch. Engines capture CUDA graphs for a set of batch sizes and pad to the nearest one, and keep the parts that vary most (attention over paged KV) outside or in "piecewise" graphs. This is the main reason compiled serving is an engineering problem, not just a compiler flag.

Exporters and other runtimes

Hugging Face Optimum exports models to ONNX and other backends (for example optimum-cli export onnx --model gpt2 gpt2_onnx/) and runs them with ONNX Runtime and vendor runtimes. Modular's MAX is another graph compiler and runtime aimed at portable performance across GPU vendors. For LLM serving at scale, these are less common than the engines of this Part, but they matter for edge, CPU and non-NVIDIA deployments.

11. Common mistakes

  • Loading .bin checkpoints from untrusted sources.
  • Benchmarking a plain generate() server and concluding the GPU is too slow.
  • Reading GPU-Util or memory use as load. An engine reserves memory at start; use num_requests_running, num_requests_waiting and KV usage instead.
  • Forgetting compile and CUDA-graph capture time when planning how fast new replicas can start.
  • Assuming request parameters are portable between engines. Check each engine's extras.

Part B: read a safetensors header by hand

import json, struct
from huggingface_hub import hf_hub_download
path = hf_hub_download("Qwen/Qwen2.5-0.5B-Instruct", "model.safetensors")
with open(path, "rb") as f:
    n = struct.unpack("<Q", f.read(8))[0]            # 8-byte little-endian header length
    header = json.loads(f.read(n))
print("header bytes:", n, " tensors:", len(header) - ("__metadata__" in header))
for name in list(header)[:6]:
    print(name, header[name] if name == "__metadata__" else (header[name]["dtype"], header[name]["shape"], header[name]["data_offsets"]))

from safetensors import safe_open
with safe_open(path, framework="pt") as f:              # read ONE tensor without loading the file

print(t.shape, t.dtype)

Part C: eager vs compiled decode

import torch, time
from transformers import AutoModelForCausalLM, AutoTokenizer
name = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(name)
m = AutoModelForCausalLM.from_pretrained(name, torch_dtype=torch.float16).cuda().eval()
ids = tok("Write a haiku about memory bandwidth.", return_tensors="pt").to("cuda")

def run(label, **kw):
    m.generate(**ids, max_new_tokens=16, do_sample=False, **kw)       # warm-up (and compile)
    torch.cuda.synchronize(); t = time.perf_counter()
    out = m.generate(**ids, max_new_tokens=128, min_new_tokens=128, do_sample=False, **kw)
    torch.cuda.synchronize(); dt = time.perf_counter() - t
    print(f"{label:10s} {128/dt:6.1f} tok/s")

run("eager")
m.generation_config.cache_implementation = "static"    # fixed-shape cache, needed for compiling
m.forward = torch.compile(m.forward, mode="reduce-overhead", fullgraph=True)
run("compiled")

Predict first: from chapter 2.5, the bandwidth ceiling for this model on a T4 is about 320 tokens per second. Where will eager and compiled land? If compilation fails on your library versions, note the error; the static-cache and compile options change between transformers releases.

Part D: 16 users, naive server vs vLLM

First a deliberately naive server that runs one request at a time:

%%writefile naive_server.py
import json, threading, torch
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
from transformers import AutoModelForCausalLM, AutoTokenizer
name = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(name)
m = AutoModelForCausalLM.from_pretrained(name, torch_dtype=torch.float16).cuda().eval()
lock = threading.Lock()                                    # one generate() at a time
class H(BaseHTTPRequestHandler):
    def do_POST(self):
        body = json.loads(self.rfile.read(int(self.headers["Content-Length"])))
        ids = tok(body["prompt"], return_tensors="pt").to("cuda")
        with lock, torch.inference_mode():
            out = m.generate(**ids, max_new_tokens=body["max_tokens"], min_new_tokens=body["max_tokens"], do_sample=False)
        n = out.shape[1] - ids.input_ids.shape[1]
        self.send_response(200); self.end_headers()
        self.wfile.write(json.dumps({"usage": {"completion_tokens": n}}).encode())
    def log_message(self, *a): pass
ThreadingHTTPServer(("0.0.0.0", 8001), H).serve_forever()

%%writefile load.py

url, users = sys.argv[1], int(sys.argv[2])
def one(i):
    t = time.perf_counter()
    r = requests.post(url, json={"model": "Qwen/Qwen2.5-0.5B-Instruct", "prompt": f"Story number {i}:",
                                 "max_tokens": 128, "min_tokens": 128, "ignore_eos": True}).json()

t0 = time.perf_counter()

lat = sorted(r[0] for r in res)

13. In the real world

How teams choose
  • Most LLM deployments ship safetensors weights straight into an engine (vLLM, SGLang or TensorRT-LLM) and skip ONNX entirely.
  • TensorRT and ONNX Runtime remain common for image, video, speech and smaller non-LLM models, and for non-NVIDIA or edge targets.
  • Monitoring scrapes /metrics into Prometheus and Grafana. Alerts use queue length, KV usage, preemptions and TTFT percentiles, not GPU-Util.
  • Security reviews require safetensors and pinned model revisions for any third-party model.

14. Check yourself

15. Summary

  • A model release is config, sharded safetensors weights, tokenizer and generation defaults.
  • Safetensors is a JSON header plus raw bytes: safe, memory-mappable and partially loadable. Pickle can execute code.
  • Execution modes range from eager PyTorch to compiled graphs, ONNX Runtime, TensorRT and LLM engines.
  • Compiling means capture, optimize, lower; for LLM decode the big wins are fusion and CUDA graphs.
  • Plain generate() servers fail under load through queueing, padded batches, fragmented KV memory and overhead. Engines fix all four.
  • Watch running, waiting, KV usage, preemptions, TTFT and ITL in /metrics.
