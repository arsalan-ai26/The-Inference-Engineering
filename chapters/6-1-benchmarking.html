Benchmarking

Every claim in this book about speed and cost ends in a number, and in production that number comes from a benchmark. A good benchmark answers one question: how many requests per second can this system serve while meeting its latency targets, on traffic like ours? Getting that answer right is harder than it looks: tools define metrics differently, averages hide the tail, and synthetic traffic flatters caches and speculators. This chapter defines the metrics precisely, shows how to design a load test, how to find the saturation point, and how to read published benchmarks critically.

  1. Two tools report different "tokens per second" for the same run. Name one reason.
  2. Why is mean TTFT a poor target?
  3. What is goodput?
Answers
  1. They count over different time windows (first request to last response, or whole benchmark duration), include or exclude warm-up requests, or count input tokens too.
  2. A few very slow requests, the ones users notice and complain about, barely move the mean. Targets are set on percentiles such as p95 or p99.
  3. The rate of requests (or tokens) completed while meeting all latency targets. Requests that miss their SLO do not count.

1. The metrics, precisely

Chapter 2.4 introduced TTFT, TPOT and E2E latency. Benchmarks add throughput and percentiles, and tools differ in the details, so write down which definition you use.

MetricDefinitionWatch for
TTFT (time to first token)From sending the request to receiving the first token with contentIncludes queueing, prefill and network. Grows with prompt length and load.
ITL (inter-token latency)Time between consecutive output tokensReport percentiles: one stall shows up in p99 ITL, not in the mean.
TPOT (time per output token)(E2E − TTFT) ÷ (output tokens − 1) for one requestSome tools call this ITL; some include TTFT in the average, which mixes prefill into a decode metric.
E2E latencyFrom sending the request to receiving the last tokenDominated by output length for long answers.
Output tokens per second, systemAll output tokens ÷ measurement windowWindow choice matters: first request to last response vs whole run; warm-up and cool-down included or not.
Tokens per second, per userOutput tokens ÷ E2E for one request; approaches 1 ÷ TPOT for long outputsFalls as load rises while system throughput rises.
Requests per secondCompleted requests ÷ windowMeaningless without the sequence lengths.
GoodputRequests per second that meet every SLOThe number to optimize (chapter 3.2).
Worked example: one streamed request

A request is sent at t = 0. The first token arrives at 0.35 s, the 200th and last at 6.32 s. TTFT = 0.35 s. E2E = 6.32 s. TPOT = (6.32 − 0.35) ÷ 199 = 30 ms. Tokens per second for this user: 200 ÷ 6.32 = 31.6, close to 1 ÷ TPOT = 33 because the answer is long.

Watch out: tools disagree

NVIDIA's GenAI-Perf and Ray's LLMPerf, for example, differ in whether ITL averages include the first token and in the time window for system throughput; NVIDIA observed that start-up and tear-down overheads can be a third of a short single-concurrency run. Use one tool for comparisons, state its definitions, and never compare numbers across tools without checking.

2. Percentiles and why averages mislead

Latency distributions in serving are skewed: most requests are fast, a few are much slower (they arrived during a long prefill, waited in a queue, or were preempted). The p50 (median) describes the typical user; p95 and p99 describe the unhappy ones, and at scale "1% of requests" is many users per minute. SLOs are written on percentiles: for example "p95 TTFT under 1 s and p95 TPOT under 50 ms at 20 requests per second".

  • Measure enough requests for the percentile you report: p99 from 100 requests is one request.
  • Report percentiles per metric separately; the request with the worst TTFT is often not the one with the worst TPOT.
  • Never average percentiles across runs or replicas; merge the raw samples and recompute.

3. Designing a load test

The best benchmark is real traffic: shadowing copies production requests to the system under test without returning its answers to users. When that is not possible, match production on every dimension that changes performance:

  • Sequence lengths: the distribution of input and output lengths (ISL and OSL), not just averages. Long tails matter: a few 30K-token prompts change everything.
  • Request contents: real prompts, so prefix-cache hit rates (chapter 4.4) and speculative acceptance (chapter 4.3) are realistic. Random tokens make both look worse; one repeated prompt makes caching look perfect.
  • Arrival pattern: real traffic arrives randomly (often modelled as Poisson) and in bursts, not as a fixed number of clients waiting politely.
  • Parameters: temperature, max tokens, stop conditions, structured output, reasoning effort, as in production. Forcing every request to its maximum length (ignore end-of-sequence) is useful for steady measurements but changes the length distribution.

Two ways to apply load

  • Fixed concurrency (closed loop): N clients, each sending a new request as soon as its previous one finishes. Easy to reason about, and it never overloads the server, because slower responses slow the clients down. Good for capacity curves at a given batch.
  • Fixed request rate (open loop): requests arrive on a schedule regardless of how the server is doing. This is how users behave; when the server falls behind, queues grow and latency explodes. Use it to find the real saturation point.

Find the knee

Sweep the request rate upward. Throughput first rises with load; past saturation, it flattens while queueing makes latency climb steeply. The useful operating point is below the knee, where the SLO percentiles still hold.

5. Benchmarking practice

  1. Baseline first. Record the current system with a fixed configuration before changing anything.
  2. Change one thing at a time, in the system and in the benchmark. Test optimizations alone and together: some interfere (speculative decoding at large batch, chapter 4.3).
  3. Warm up, then measure a steady state long enough for stable percentiles; repeat runs and report the spread.
  4. Control the environment: same GPU type and count, engine version, model revision, precision, and client location. Run the client close to the server, or measure network latency separately.
  5. Check quality on a task set alongside speed; a faster but wrong system is not an improvement.
  6. Keep the artifacts: command lines, configs, raw per-request results. You will need them when someone asks why a number changed.

6. Reading published benchmarks

Vendor and third-party benchmarks are useful for orientation, not for decisions. For every number, find:

  • Model, precision (BF16, FP8, FP4) and whether quality was checked.
  • Hardware: GPU type and count, form factor, interconnect.
  • Engine and version, parallel layout, speculative decoding on or off.
  • Workload: ISL/OSL, concurrency or rate, cache hit rates, output forced to max length or not.
  • Which metric: per-user or per-system throughput, per GPU or per node, at what latency.

Independent sites such as Artificial Analysis publish API and hardware benchmarks with a stated methodology; read the methodology page first. Throughput per GPU at a fixed per-user speed (an interactivity target) is the most useful single comparison across hardware, because it reflects the latency-throughput trade-off instead of hiding it.

7. Expert layer

Coordinated omission

A closed-loop client that waits for each response before sending the next silently stops sending when the server stalls, so the stall barely appears in its latency samples. Open-loop (fixed-rate) clients avoid this; when using closed-loop tools, compute latency from the intended send time, not the actual one.

The latency-throughput frontier

Instead of a single number, plot per-user tokens per second (x) against system tokens per second per GPU (y) over a sweep of concurrency, for each configuration. The upper-right frontier shows the best trade-offs; configurations below it are dominated. Hardware and engine comparisons in this form are much harder to game.

Benchmarking agents and multi-call workloads

Agent workloads chain many dependent calls with growing prefixes (chapter 6.8). Per-call TTFT and throughput miss what users feel: total task time. Replaying recorded agent traces, with their real inter-call gaps and cache reuse, is the closest equivalent to shadowing.

8. Common mistakes

  • Benchmarking with one prompt repeated (perfect cache hits) or random tokens (no hits, no speculative acceptance).
  • Reporting mean latency only.
  • Only closed-loop tests, so the system never shows its behaviour under overload.
  • Comparing numbers from different tools or definitions.
  • Running the client on a busy machine far from the server.
  • Measuring during warm-up, compilation or autoscaling.
  • Quoting peak throughput at a latency nobody would accept.

Part B: a streaming benchmark client (CPU, with a mock server)

The mock server below behaves like an engine: prefill grows with prompt length and every step slows as more requests share the GPU. Run it with uvicorn mock_server:app --port 8000, then run the client.

# mock_server.py
import asyncio, json
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse
app = FastAPI(); active = 0
@app.post("/v1/completions")
async def completions(req: Request):
    body = await req.json()
    n_in = len(body["prompt"].split()); n_out = body.get("max_tokens", 64)
    async def gen():
        global active
        active += 1
        try:
            await asyncio.sleep(0.02 + n_in * 0.0002 * (1 + active / 8))   # prefill
            for i in range(n_out):
                await asyncio.sleep(0.01 * (1 + active / 16))               # decode step
                yield f"data: {json.dumps({'choices': [{'text': f' t{i}', 'index': 0}]})}\n\n"
            yield "data: [DONE]\n\n"
        finally:
            active -= 1
    return StreamingResponse(gen(), media_type="text/event-stream")
# bench_client.py
import asyncio, time, random, sys
from openai import AsyncOpenAI
client = AsyncOpenAI(base_url=sys.argv[1] if len(sys.argv) > 1 else "http://localhost:8000/v1", api_key="x")
MODEL = sys.argv[2] if len(sys.argv) > 2 else "mock"

async def one(prompt, max_tokens):
    t0 = time.perf_counter(); ttft = None; times = []
    stream = await client.completions.create(model=MODEL, prompt=prompt, max_tokens=max_tokens, stream=True)
    async for chunk in stream:
        now = time.perf_counter()
        if chunk.choices and chunk.choices[0].text:
            if ttft is None: ttft = now - t0
            times.append(now)
    # TODO: compute the inter-token latencies from times, and the E2E latency
    return ttft, itl, e2e, len(times)

async def run(rate, n=60, prompt_words=500, out=64):
    random.seed(0); tasks = []
    prompt = " ".join(["word"] * prompt_words)
    t_start = time.perf_counter()
    for _ in range(n):
        tasks.append(asyncio.create_task(one(prompt, out)))
        await asyncio.sleep(random.expovariate(rate))          # open loop: Poisson arrivals
    res = await asyncio.gather(*tasks)
    dur = time.perf_counter() - t_start
    ttft = sorted(r[0] for r in res); itl = sorted(x for r in res for x in r[1])
    p = lambda xs, q: xs[min(len(xs) - 1, int(q * len(xs)))]
    print(f"rate {rate}/s TTFT p50 {p(ttft,.5)*1e3:.0f} p99 {p(ttft,.99)*1e3:.0f} ms  "
          f"ITL p50 {p(itl,.5)*1e3:.1f} p99 {p(itl,.99)*1e3:.1f} ms  "
          f"throughput {sum(r[3] for r in res)/dur:.0f} tok/s")

async def main():
    for rate in [1, 4, 8, 16]:
        await run(rate)
asyncio.run(main())

10. In the real world

Benchmarking in production teams
  • Release gates: teams rerun a fixed benchmark suite on every engine or model upgrade and block regressions in goodput or p99 latency.
  • Capacity planning uses the measured knee per replica to size fleets (chapter 6.5).
  • Shadow traffic validates big changes (new hardware, disaggregation) on real request mixes before cutover.
  • Procurement asks vendors for frontier curves on the team's own workload, not headline numbers.

12. Summary

  • Define metrics precisely (TTFT, ITL, TPOT, E2E, system and per-user throughput, goodput) and use one tool's definitions consistently.
  • Use percentiles; averages hide the tail users feel.
  • Match production on lengths, contents, arrival pattern and parameters; shadow real traffic when you can.
  • Sweep the request rate with open-loop load to find the knee, and operate below it at your SLOs.
  • Read published benchmarks with a checklist: model, precision, hardware, engine, workload, metric, latency.
