Part 5 · GPUs, hardware and kernels · Chapter 5.8

Expert depth: writing high-performance kernels and kernel compilers

Most inference engineers select kernels; some write them. This chapter is for when you need to: a new GPU generation, a new number format, a new attention variant or MoE layout that no library supports yet. It explains how a fast matrix multiply is built, layer by layer, from a naive kernel at 1% of peak to one within a few percent of cuBLAS; the patterns specific to inference kernels; the tools and languages used to write them today; how kernel compilers such as Triton turn short programs into GPU code; and how to test and benchmark kernels so you can trust the result.

Before you start: skip check
  1. Why does computing a larger output tile per block make a GEMM faster?
  2. What problem does split-K solve?
  3. Why is a decode-time GEMM (a few rows times a large weight matrix) hard to make fast?
Answers
  1. A BM × BN tile loads BM + BN rows and columns per K step but does BM × BN multiply-adds with them: arithmetic intensity grows with tile size, so the tensor cores wait less for memory.
  2. When M and N are small, there are too few output tiles to fill all SMs. Split-K also divides the K dimension among blocks, which compute partial sums that are then added.
  3. It is memory-bound: the whole weight matrix must be read for very little math. Speed comes from reading weights at full bandwidth with enough blocks in flight (and from quantized weights), not from tensor-core tricks.

1. When to write a kernel

Writing and maintaining kernels is expensive: they are tied to GPU generations, shapes and formats (chapter 5.4). Good reasons to do it:

  • A new operation with no fast implementation: a new attention variant, a quantization format, a routing scheme for MoE.
  • A fusion that compilers cannot find and that matters at your scale (for example dequantize + GEMM, or all-reduce + norm).
  • A new GPU generation whose features libraries do not yet use.
  • A profile (chapter 5.6) showing one kernel far from its roofline on your real shapes.

Before writing one, check the engine's existing kernels, recent releases of FlashInfer, CUTLASS, DeepGEMM and similar libraries, and whether torch.compile already fuses the pattern.

2. Anatomy of a fast GEMM

A matrix multiply C = A × B of shape [M, K] × [K, N] does 2MNK FLOPs. At large sizes it is compute-bound in principle; the whole art is to keep the math units fed. Simon Boehm's worklog makes the steps concrete for an FP32 GEMM of size 4,092 on an A6000 (about 30 TFLOP/s FP32 peak):

StepIdeaReported speed
1. NaiveOne thread per output element; reads rows and columns straight from global memoryabout 0.3 TFLOP/s
2. Coalesced loadsArrange threads so a warp reads consecutive addresses (chapter 5.2)about 2.0
3. Shared-memory tilingEach block loads tiles of A and B into shared memory and reuses themabout 2.2
4. 1D block tilingEach thread computes several outputs, reusing values held in registersabout 8.6
5. 2D block tilingEach thread computes an 8 × 8 patch: much higher arithmetic intensity per loadabout 16
6. Vectorized loadsWide (128-bit) loads; transpose A in shared memoryabout 19
9. AutotuningSearch tile sizes per GPUabout 20
10. Warp tilingAn extra tiling level per warp for register and scheduling localitywithin a few % of cuBLAS at sizes 2,048 and 4,096

The lesson behind the numbers: each step raises reuse at one level of the memory hierarchy (global memory, shared memory, registers), which raises arithmetic intensity at that level (chapter 2.5). A production tensor-core GEMM on Hopper or Blackwell adds:

  • Tensor-core MMA instructions (mma on Ampere, wgmma on Hopper, tcgen05 with tensor memory on Blackwell) instead of FMA on CUDA cores.
  • Asynchronous copies and pipelining: TMA (or cp.async) copies the next K tiles into shared memory while tensor cores work on the current ones, using several buffers ("stages").
  • Warp specialization: producer warps load, consumer warpgroups compute.
  • Swizzled layouts in shared memory to avoid bank conflicts, and tile rasterization (the order in which output tiles are visited) to improve L2 reuse.
  • Persistent kernels with tile schedulers (including Stream-K) to balance work across SMs and avoid wave quantization (chapter 5.1).
  • Epilogues that apply bias, activation, scaling or quantization before writing the output (chapter 5.4).

cuBLAS itself is not one kernel but hundreds: it picks among many implementations by shape, and adds split-K plus a reduction kernel when the output is too small to fill the GPU.

Interactive: tile size and arithmetic intensity
For one block computing a BM × BN output tile, each K step loads BM × BK values of A and BK × BN of B and does 2 × BM × BN × BK FLOPs. The intensity with respect to global memory (ignoring cache reuse between blocks) must exceed the GPU's ops:byte ratio for the tile to be compute-bound.

4. Languages and libraries

  • CUDA C++, with inline PTX for the newest instructions: full control, most effort. Read the SASS (the GPU's machine code) with cuobjdump when performance surprises you.
  • CUTLASS 3 and CuTe: NVIDIA's C++ template library for GEMMs and convolutions, built on CuTe's layout algebra, which describes how tensors map to threads, warps and memory. FlashAttention-3 uses it.
  • CuTe-DSL: the same concepts from Python, with much faster compile times; FlashAttention-4 is written in it.
  • Triton: block-level programming in Python with an MLIR-based compiler; the default for portable kernels and the target of torch.compile (chapter 5.4).
  • Tile-based DSLs from research groups, such as ThunderKittens (tiles of registers and shared memory as first-class objects) and TileLang, aim for near-hand-written performance with much less code.
  • Other ecosystems: HIP and Composable Kernel on AMD (Triton also targets AMD), Pallas for TPUs and GPUs in JAX.

5. How a kernel compiler works: Triton as an example

A Triton kernel is a short Python function. Getting from it to fast GPU code takes several stages:

  1. Front end: the decorated Python function is parsed into Triton IR (an MLIR dialect) with block-level operations: loads, stores, dot, reductions.
  2. Specialization: tl.constexpr values (block sizes, flags) and argument properties (for example pointer alignment) are baked in; each combination is a separate compiled kernel, cached on disk.
  3. GPU lowering: TritonGPU IR assigns layouts: which thread and warp holds which part of each block, how data is staged through shared memory, where to insert asynchronous copies and software pipelining (the num_stages parameter), and how tl.dot maps to the target's MMA instructions.
  4. Back end: LLVM IR, then PTX, then the GPU binary (cubin) via NVIDIA's assembler; on AMD, the AMDGPU backend.
  5. Autotuning (@triton.autotune): run several configurations (block sizes, num_warps, num_stages) on the real shapes and keep the fastest.

Graph compilers sit one level up: TorchInductor decides what to fuse in a whole model and emits Triton for each fused group (chapter 5.7). AI-assisted kernel writing (benchmarks such as KernelBench evaluate models on producing correct, fast kernels) is an active area; generated kernels need the same testing discipline as hand-written ones.

6. Testing and benchmarking kernels

  • Correctness first: compare against a high-precision reference (FP32 or FP64 PyTorch) on many shapes, including odd sizes that exercise masks, with tolerances appropriate to the precision. Test edge cases: zero-length inputs, maximum sizes, unusual strides.
  • Benchmark carefully: warm up; time many runs with CUDA events or triton.testing.do_bench; flush the L2 cache between runs when measuring memory-bound kernels, or the second run reads from cache; report achieved bandwidth or FLOP/s against the roofline, not just milliseconds.
  • Use real shapes: the shapes of your models at your batch sizes, for both prefill and decode. A kernel that wins at 4,096 × 4,096 may lose at 8 × 4,096.
  • Check numerics end to end: run a model-level evaluation (perplexity or task accuracy, chapter 4.1) with the new kernel, not only unit tests.

7. Expert layer

Layouts are the heart of modern kernels

Most of the difficulty in Hopper and Blackwell kernels is not math but layout: how a tile is arranged in global memory, how TMA copies it into a swizzled shared-memory layout, how MMA instructions expect operands, and where accumulators live (registers or tensor memory). CuTe's layout algebra (shape, stride and composition) exists to make these mappings composable and checkable.

Low-precision GEMMs need careful accumulation

FP8 and FP4 GEMMs apply block scales and must accumulate in higher precision. DeepSeek promoted partial sums to FP32 every 128 elements on H800 (chapter 4.1); Blackwell applies microscaling scales in hardware. Kernel authors decide where scales are applied (per tile, in the epilogue) and how to keep accuracy without losing speed.

From kernels to megakernels

As individual kernels approach their rooflines, the remaining time in small-batch decode is between kernels: launches, synchronizations and pipeline bubbles at kernel boundaries. Megakernels fuse an entire forward pass into one persistent kernel that schedules its own work on the GPU, overlapping the end of one layer with the start of the next. They are hard to write and maintain, but research systems have shown sizable latency reductions for small-batch decode.

8. Common mistakes

  • Benchmarking a memory-bound kernel without flushing L2, so data comes from cache.
  • Testing only power-of-two sizes and missing mask bugs.
  • Comparing against an eager PyTorch baseline instead of the best existing kernel.
  • Tuning tile sizes on one GPU and shipping them to another.
  • Accumulating in low precision to save registers.
  • Writing a kernel for a pattern the compiler or engine already fuses.

Part B: intensity by hand

For BM = BN = 128, BK = 32 in BF16, compute the bytes loaded and FLOPs per K step, and the intensity. Is this tile compute-bound on an H100 in BF16? In FP8? What about BM = 16 (a decode-like M)?

Answer

Loads: (128 × 32 + 32 × 128) × 2 bytes = 16,384 bytes. FLOPs: 2 × 128 × 128 × 32 = 1,048,576. Intensity 64 FLOPs per byte with respect to global memory, below the H100's 295 for BF16: the kernel relies on L2 reuse between neighbouring tiles (good rasterization) and on larger tiles (for example 128 × 256) to approach peak. With FP8 values the bytes halve (128 FLOPs per byte) but the target ratio doubles (590). With BM = 16 the intensity is about 14: hopelessly memory-bound, which is why decode GEMMs are optimized for bandwidth instead.

10. In the real world

Who writes kernels
  • Hardware vendors (cuBLAS, cuDNN, CUTLASS, TensorRT-LLM kernels; AMD's AITER and Composable Kernel).
  • Model labs release kernels with their models (DeepSeek's FlashMLA, DeepGEMM and DeepEP).
  • Engine teams write Triton and CUDA kernels for new models, formats and fusions.
  • Research groups build attention kernels (FlashAttention, FlashInfer) and new DSLs (ThunderKittens, TileLang).

11. Check yourself

12. Summary

  • Write kernels for new operations, formats, hardware or fusions that matter at your scale, and only after checking existing libraries and compilers.
  • Fast GEMMs climb the memory hierarchy: coalescing, shared-memory tiles, register tiles, vectorized loads, warp tiles, then tensor-core MMAs, asynchronous pipelines, warp specialization and persistent scheduling.
  • Inference adds its own patterns: skinny and mixed-precision GEMMs, grouped GEMMs for MoE, paged decode attention, communication fusion, and megakernels.
  • Triton compiles block-level Python through MLIR stages to GPU code, with specialization and autotuning; CUTLASS, CuTe and CuTe-DSL give finer control.
  • Test against high-precision references on real and odd shapes, benchmark with warm-up and cache flushes, and report results against the roofline.
