Part 5 · GPUs, hardware and kernels · Chapter 5.3

The CUDA execution model

Chapter 5.2 described the hardware. This chapter describes how software uses it: a program on the CPU launches kernels, each kernel runs as a grid of thread blocks, and the CPU and GPU work asynchronously, talking through queues called streams. Most performance surprises in inference engines (idle GPUs, mysterious stalls, slow small models) come from this model, not from the math. You will write two small kernels, see how a launch maps onto the hardware, and learn to find hidden CPU-GPU synchronizations using timing alone.

1. Kernels, threads, blocks and grids

A kernel is a function that runs on the GPU. When the CPU launches it, it says how many threads to start, arranged in two levels:

  • a block of threads (up to 1,024), which runs on one SM and can share that SM's shared memory and synchronize internally;
  • a grid of blocks, which can be very large and is spread over all the SMs as they become free.

Every thread runs the same code. It finds out which piece of data is its own from built-in variables:

global index i = blockIdx.x × blockDim.x + threadIdx.x

Here is the classic first kernel in CUDA C++, and the same kernel in Python with Numba. Both compute out = a × x + y.

// CUDA C++
__global__ void scale_add(const float* x, const float* y, float* out, float a, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;   // which element is mine?
    if (i < n) out[i] = a * x[i] + y[i];            // guard the overhang
}
// launch from the CPU: enough blocks of 256 threads to cover n
scale_add<<<(n + 255) / 256, 256>>>(x, y, out, 2.0f, n);

The launch says nothing about which SM runs which block. The hardware's block scheduler hands blocks to SMs as resources free up, many blocks per SM at a time (chapter 5.2's occupancy), in no guaranteed order. That is why blocks cannot wait for each other inside a kernel: correctness must not depend on block order.

2. Cooperating inside a block: shared memory and barriers

Element-wise kernels need no cooperation. Most interesting kernels do: a sum, a softmax, a tile of a matrix multiply. Threads in a block cooperate through shared memory and a barrier, __syncthreads(), which makes every thread in the block wait until all have reached it.

A block sum is the standard example: each thread loads one value into shared memory, then the block repeatedly adds the upper half onto the lower half (128 → 64 → ... → 1), with a barrier after every round so no thread reads a slot before it is written. Thread 0 writes the block's partial sum. A second small step adds the partial sums. Part A of the lab runs this kernel. Softmax, RMSNorm and attention kernels are built from the same pattern: a reduction (max, sum of squares, sum of exponentials) followed by an element-wise step.

Watch out

A __syncthreads() inside an if that only some threads take can hang the block. Barriers must be reached by every thread of the block.

3. The CPU and GPU work asynchronously

When PyTorch runs y = x @ w on a GPU, the CPU does not wait for the multiply. It checks shapes, picks a kernel, puts a launch command on a queue and returns immediately with a tensor whose values do not exist yet. The GPU takes commands from the queue in order and runs them. In a healthy program the CPU runs far ahead, the queue is never empty, and the GPU never waits.

Definitions

Host / device: the CPU and its memory / the GPU and its memory.

Stream: an ordered queue of GPU work. Work in one stream runs in order; work in different streams may overlap. PyTorch uses one default stream per device unless told otherwise.

Synchronization: the CPU waits until the GPU has finished queued work. Explicit (torch.cuda.synchronize()) or implicit (any operation that needs a GPU value on the CPU).

CUDA event: a marker recorded in a stream; the time between two events is GPU time, measured on the GPU.

That is launch-bound decode, and the fix is fewer launches (fusion, chapter 5.4) or recording the whole sequence once and replaying it (CUDA graphs, chapter 5.7).

4. Hidden synchronizations

Any operation whose result the CPU needs right now forces it to wait for the GPU to finish all queued work. After that, the GPU's queue is empty and it idles until the CPU launches more. In a decode loop, one such call per step can cost a large share of throughput. Common triggers:

  • tensor.item(), .tolist(), .cpu(), .numpy(), print(tensor).
  • Python control flow on a GPU value: if (x > 0).any(): calls bool() on a GPU tensor.
  • Dynamic shapes: operations whose output size depends on GPU data, such as boolean-mask indexing x[mask], torch.nonzero, slicing with a GPU tensor x[:gpu_n], or repeat_interleave without output_size. The CPU must learn the size before it can allocate the output.
  • Copies from pageable (non-pinned) CPU memory to the GPU, and many allocator calls when memory is fragmented.

Engines avoid these by keeping decisions on the GPU (masking instead of indexing), constructing simple tensors directly on the device instead of copying them, deciding shapes on the CPU from information it already has, and doing CPU bookkeeping for step n + 1 while the GPU runs step n. PyTorch can flag synchronizations: torch.cuda.set_sync_debug_mode("warn") (experimental, and it does not catch every case).

Timing GPU code correctly

start, end = torch.cuda.Event(enable_timing=True), torch.cuda.Event(enable_timing=True)
start.record()
y = model(x)                      # queued on the stream
end.record()
torch.cuda.synchronize()          # wait until the end event has happened
print(start.elapsed_time(end), "ms of GPU time")

Always warm up first (the first call compiles kernels, allocates memory and fills caches), and time many repetitions.

5. What a kernel launch costs, and how engines avoid paying it

Each launch costs CPU time (PyTorch dispatch, argument setup, the driver call) and some GPU-side latency, on the order of microseconds in total. A transformer layer in eager PyTorch launches dozens of kernels; a 32-layer model, over a thousand per decode step. For large batches that is noise; for batch 1 on a fast GPU it can be most of the step (chapter 2.4's GPT-2 lab showed this).

Three remedies, in increasing order of effect:

  1. Fewer, larger kernels: fusion, by hand or by compiler (chapter 5.4).
  2. Less CPU work per launch: a compiled graph instead of Python (torch.compile, chapter 5.7).
  3. CUDA graphs: record the whole sequence of kernels for a step once, then replay it with a single launch. vLLM and SGLang capture graphs for a set of batch sizes and replay them every decode step (chapters 3.4 and 5.7).

6. Expert layer

Streams for overlap

Work in separate streams can overlap: a copy of the next request's data, a KV block transfer (chapter 4.6) or an all-reduce (chapter 4.5) on one stream while compute runs on another. Engines and communication libraries (NCCL) use dedicated streams for this. Overlap needs pinned host memory for copies and care with dependencies, expressed with events between streams.

Persistent kernels and megakernels

Instead of one launch per operation, a persistent kernel launches once with exactly as many blocks as the GPU can hold and loops over work items itself. Pushed to the limit, a "megakernel" runs an entire forward pass in one launch with its own on-GPU scheduler. Research systems have shown large latency gains for small-batch decode this way; it trades flexibility and engineering effort for the last microseconds.

Thread block clusters (Hopper and newer)

Hopper adds a level between block and grid: a cluster of blocks scheduled together on nearby SMs that can read each other's shared memory (distributed shared memory). Large GEMM and attention kernels use clusters to share loaded tiles and cut HBM traffic.

7. Common mistakes

  • Timing without synchronizing, or without warm-up.
  • Calling .item() or printing a GPU tensor in a hot loop.
  • Boolean-mask indexing on the GPU in a decode path (dynamic shapes).
  • Forgetting the if (i < n) guard and reading past the end of a buffer.
  • A barrier inside a branch that not every thread takes.
  • Assuming blocks run in order, or that two blocks can wait for each other.

Part A: two kernels in Numba (CPU simulator, then T4)

Numba compiles Python functions into CUDA kernels. On a machine without a GPU, set NUMBA_ENABLE_CUDASIM=1 before importing Numba to run the same code in a slow CPU simulator, which is handy for checking logic. On a T4, leave it unset.

import numpy as np, math
from numba import cuda, float32

@cuda.jit
def scale_add(x, y, out, a, n):
    i = cuda.blockIdx.x * cuda.blockDim.x + cuda.threadIdx.x   # global thread index
    if i < n:                                                   # the last block may overhang
        out[i] = a * x[i] + y[i]

TPB = 128
@cuda.jit
def block_sum(x, partial, n):
    buf = cuda.shared.array(TPB, dtype=float32)    # shared by the threads of one block
    t = cuda.threadIdx.x
    i = cuda.blockIdx.x * TPB + t
    buf[t] = x[i] if i < n else 0.0
    cuda.syncthreads()                             # all slots written
    s = TPB // 2
    while s > 0:                                   # TODO: tree reduction.
        # if t < s: add buf[t + s] into buf[t]; then a barrier for every thread; halve s
        s //= 2
    if t == 0:
        partial[cuda.blockIdx.x] = buf[0]

n = 1003                                           # small for the simulator; use 10_000_000 on a T4
x = np.random.rand(n).astype(np.float32); y = np.random.rand(n).astype(np.float32)
dx, dy = cuda.to_device(x), cuda.to_device(y)     # host to device
dout = cuda.device_array_like(x)
blocks = math.ceil(n / 256)
scale_add[blocks, 256](dx, dy, dout, np.float32(2.0), n)   # launch: [grid, block]
print("scale_add max error", np.abs(dout.copy_to_host() - (2 * x + y)).max())

blocks = math.ceil(n / TPB)
p = cuda.device_array(blocks, dtype=np.float32)
block_sum[blocks, TPB](dx, p, n)
print("block_sum", p.copy_to_host().sum(), "numpy", x.sum())
Solution 
    while s > 0:
        if t < s:
            buf[t] += buf[t + s]
        cuda.syncthreads()
        s //= 2

Measured in the simulator: scale_add maximum error 0.0; block_sum 500.2174 against NumPy's 500.2174. Now break it on purpose: move cuda.syncthreads() inside the if t < s. On a real GPU this can hang or give wrong sums; explain why from section 2.

On a T4: time scale_add for n = 10⁴, 10⁶ and 10⁸ with CUDA events (cuda.event() in Numba). Compute achieved GB/s (12 bytes per element). At which size does it approach the T4's 320 GB/s, and what dominates below that?

Part B: find the hidden synchronization (T4)

Two functions do the same GPU work; one contains a synchronization. Find which, using only the time each call takes to return (no profiler).

import torch, time
x = torch.randn(2048, 2048, device="cuda", dtype=torch.float16)
w = torch.randn(2048, 2048, device="cuda", dtype=torch.float16) / 45

def step_a(y):
    for _ in range(30):
        y = torch.relu(y @ w)
    return y

def step_b(y):
    for _ in range(30):
        y = torch.relu(y @ w)
        if y.abs().max() > 1e4:          # looks harmless
            break
    return y

for f in (step_a, step_b):
    f(x); torch.cuda.synchronize()        # warm up
    t0 = time.perf_counter(); f(x)
    t_return = time.perf_counter() - t0   # CPU time until the call returns
    torch.cuda.synchronize()
    t_total = time.perf_counter() - t0    # until the GPU has finished
    print(f.__name__, f"returns after {t_return*1e3:.2f} ms, GPU done after {t_total*1e3:.2f} ms")
What to look for, and the fix

step_a returns long before the GPU finishes: the CPU queued all 30 matmuls and left. step_b returns only when the GPU is done, and its total time is longer: the if calls bool() on a GPU tensor, so the CPU waits after every matmul and the GPU idles while the next launch is prepared. Confirm by running step_b after torch.cuda.set_sync_debug_mode("warn"). Fix: check once after the loop, or keep the decision on the GPU (for example torch.where), or check only every N steps.

9. In the real world

The execution model in engines
  • vLLM and SGLang keep the scheduler's CPU work off the GPU's critical path, prepare the next step while the current one runs, and replay CUDA graphs for decode.
  • Engine contributions often remove a single hidden synchronization or host-to-device copy; Modal described fixes of exactly this kind in open-source engines.
  • Speculative decoding and sampling code is a frequent source of dynamic shapes; contributors use sync debug modes in tests to keep it clean.

11. Summary

  • A kernel launch starts a grid of blocks of threads; each thread finds its data from blockIdx, blockDim and threadIdx and guards against overhang.
  • Blocks run on SMs in any order; threads in a block cooperate through shared memory and barriers.
  • The CPU queues work on streams and runs ahead; anything that needs a GPU value on the CPU synchronizes and leaves the GPU idle.
  • Time GPU code with synchronization or CUDA events, after warm-up.
  • Launch overhead is microseconds per kernel; fusion, compilation and CUDA graphs remove it.
