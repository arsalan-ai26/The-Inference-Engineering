Part 6 · Production inference infrastructure · Chapter 6.10

Capstone: public engine teardown

The capstone puts Parts 2 to 6 to work on one question: on one model and one GPU, how do vLLM, SGLang and TensorRT-LLM compare, and why? You design the test matrix, run a reproducible benchmark on a rented GPU for a few hours, plot throughput against interactivity and cost per million tokens, explain every difference from first principles, and publish the configs and raw results so anyone can check them. This chapter gives the method, a tested harness, the analysis, a checklist for explaining differences and a report template. The harness was tested against mock engines on CPU, so every number measured in this chapter comes from those mocks; the real comparison is yours to run on a GPU.

Level: capstone Time: 1 to 2 days, including 3 to 5 GPU-hours Needs: 3.4, 4.1, 5.6, 6.1, 6.6 Compute: one rented GPU (H100, L40S or similar)
Before you start: skip check
  1. Engine X has higher peak throughput than engine Y. Is X better?
  2. Why must every engine use the same weights, precision and chat template?
  3. Why run a correctness check before any speed measurement?
Answers
  1. Not necessarily. Peak throughput is reached at a concurrency where each user may get too few tokens per second. Compare full curves, and compare at your SLO (chapter 6.1).
  2. Otherwise you measure the difference between models or quantization recipes, not between engines. FP8 against BF16 alone changes throughput substantially (chapter 4.1).
  3. A fast engine that produces wrong output (broken template, bad kernel, wrong sampling defaults) is not a result. Chapter 6.6 showed that silent quality differences between providers of the same model are real.

1. Rules for a fair comparison

  1. Same model files and precision for every engine (for example Llama-3.1-8B-Instruct in BF16, then a second pass with the same FP8 checkpoint). If one engine needs its own conversion, record it.
  2. Same hardware and software base: one GPU type, same driver and CUDA version, the engines' official container images, pinned by version and digest. Record nvidia-smi -q (clocks, power limit, ECC, MIG off).
  3. Same workload: same prompts, same input and output lengths, same tokenizer and chat template, a fixed output length so each engine generates the same number of tokens, same sampling settings.
  4. Defaults first, then tuned. Report "out of the box" and "tuned" separately, and list every non-default flag. A tuned engine against a default one says nothing.
  5. Warm up, repeat, report spread. Discard warm-up requests (CUDA graph capture, JIT compilation, cache warm-up), run each point at least three times and report the spread.
  6. One client for all engines. Use one benchmark client against each engine's OpenAI-compatible API, so client-side metric definitions are identical (chapter 6.1 showed tools define ITL and throughput differently).
  7. Check correctness first. Golden outputs and a short task evaluation on each engine before any timing (section 4).

2. Design the test matrix

A few hours of GPU time allows a focused matrix. A good default:

DimensionValuesWhy
Model and precisionOne 7B to 8B instruct model; BF16, then FP8 if the GPU supports itFits one GPU with room for KV cache; FP8 shows quantized kernel quality
Workloads (input / output tokens)Chat 1,000 / 200; long input 8,000 / 200; long output 200 / 1,000Prefill-heavy and decode-heavy shapes favour different engines (chapter 2.5)
LoadClosed-loop concurrency 1, 2, 4, ... 128 (or 256); plus one open-loop rate sweep near the kneeConcurrency traces the full curve; open loop reveals overload a closed loop hides (chapter 6.1)
Prefix reuseOne run with a shared 2,000-token system promptPrefix caching designs differ (radix tree, hashed blocks; chapter 4.4)
Repeats3 per pointRun-to-run variation

Write down predictions before running: which engine wins at concurrency 1, which at 128, and on which workload. The predictions are what make the explanations in section 6 worth reading.

3. Launch the engines

Each engine provides an OpenAI-compatible server. Run one at a time on the same GPU, with comparable memory settings. Exact flags change between versions; check each --help for the version you pin, and record the full command.

# vLLM
vllm serve meta-llama/Llama-3.1-8B-Instruct --port 8000 \
  --max-model-len 16384 --gpu-memory-utilization 0.90

# SGLang
python3 -m sglang.launch_server --model-path meta-llama/Llama-3.1-8B-Instruct --port 8000 \
  --context-length 16384 --mem-fraction-static 0.90

# TensorRT-LLM (PyTorch backend by default); extra settings go in a YAML file via --config
trtllm-serve meta-llama/Llama-3.1-8B-Instruct --port 8000 \
  --max_seq_len 16384 --kv_cache_free_gpu_memory_fraction 0.90

Note that "0.90" does not mean the same thing in each engine: vLLM's value is the share of total GPU memory the engine may use, SGLang's is the share for weights and KV pool, and TensorRT-LLM's is the share of free memory after loading given to the KV cache. Record the resulting KV cache capacity each engine logs at start-up, and compare it: KV capacity is often the real difference at high concurrency (chapter 3.3).

4. Correctness gate

  • Golden outputs: 20 fixed prompts at temperature 0 and 64 tokens on each engine. Expect identical text for most prompts and early splits for a few (chapter 6.6 explains why near-ties flip). Many prompts diverging in the first few tokens means a template, tokenizer or kernel problem.
  • Task evaluation: a short run of a standard benchmark through each engine's API (for example GSM8K with lm-evaluation-harness's local-completions model type). Scores should agree within run-to-run noise.
  • Chat template check: render one conversation through each engine's chat endpoint and compare the token IDs it actually processed, when the engine can show them.

5. The benchmark harness

One small client measures every engine the same way: a closed-loop sweep over concurrency, one JSON line per request. The analysis turns those lines into throughput, interactivity, latency percentiles and cost. We tested the full pipeline here on three mock engines (section 7 and the widget); on a GPU, point it at the real servers.

# sweep.py: engine-agnostic closed-loop concurrency sweep; one JSON line per request
import asyncio, json, sys, time, httpx
async def one(client, url, prompt, out):
    t0 = time.perf_counter(); first = None; n = 0
    async with client.stream("POST", url, json={"model": "m", "prompt": prompt, "max_tokens": out,
                                                "stream": True, "ignore_eos": True}) as r:
        async for line in r.aiter_lines():
            if line.startswith("data: {"):
                n += 1
                if first is None: first = time.perf_counter()
    end = time.perf_counter()
    return {"ttft": first - t0, "tpot": (end - first) / max(1, n - 1), "e2e": end - t0, "out": n, "t0": t0, "end": end}

async def level(url, conc, n_req, prompt, out):
    q = asyncio.Queue(); [q.put_nowait(i) for i in range(n_req)]; res = []
    async with httpx.AsyncClient(timeout=120) as client:
        async def worker():
            while not q.empty():
                q.get_nowait(); res.append(await one(client, url, prompt, out))
        await asyncio.gather(*[worker() for _ in range(conc)])
    return res

async def main(engine, url, out_path, isl=1000, osl=100):
    prompt = " ".join(["w"] * isl)     # on real engines use real text: see the note below
    with open(out_path, "a") as f:
        for conc in [1, 2, 4, 8, 16, 32, 64]:
            await level(url, conc, conc, prompt, osl)                    # warm-up at this level
            res = await level(url, conc, max(4 * conc, 16), prompt, osl)
            for r in res: f.write(json.dumps({"engine": engine, "conc": conc, **r}) + "\n")
asyncio.run(main(sys.argv[1], sys.argv[2], sys.argv[3]))
# analyze.py: per engine and concurrency, the numbers a teardown reports
import json, sys, collections, statistics
GPU_PRICE = float(sys.argv[2]) if len(sys.argv) > 2 else 2.90      # $ per GPU-hour
rows = [json.loads(l) for l in open(sys.argv[1])]
groups = collections.defaultdict(list)
for r in rows: groups[(r["engine"], r["conc"])].append(r)
q = lambda xs, p: sorted(xs)[min(len(xs) - 1, int(p * len(xs)))]
print("engine conc  out tok/s  tok/s/user  TTFT p95  TPOT p95   $/M out")
for (eng, conc), rs in sorted(groups.items()):
    span = max(r["end"] for r in rs) - min(r["t0"] for r in rs)
    tput = sum(r["out"] for r in rs) / span                   # output tokens per second on this GPU
    user = statistics.median(1 / r["tpot"] for r in rs)      # interactivity: tokens/s each user sees
    cost = GPU_PRICE / 3600 / tput * 1e6
    print(f"{eng:6s} {conc:4d} {tput:10.0f} {user:11.1f} {q([r['ttft'] for r in rs], .95):8.2f} s "
          f"{q([r['tpot'] for r in rs], .95)*1e3:6.1f} ms  {cost:8.2f}")

Notes for real engines: use real text prompts with an exact token count (tokenize with the model's tokenizer and trim), not repeated words, because repeated tokens can trigger prefix caching or unusual attention patterns. ignore_eos is an extra parameter some servers accept; if one rejects it, remove it and rely on the counted output tokens. As a cross-check, also run vllm bench serve --backend openai --endpoint /v1/completions --host ... --port ... against each server with --save-result: two independent clients agreeing is strong evidence the numbers are right.

6. Explain every difference from first principles

A teardown is only as good as its explanations. For each gap larger than the run-to-run spread, find the mechanism and, where possible, confirm it with a profile (chapter 5.6) or by changing one flag.

Where the gap appearsLikely causes to checkHow to confirm
Concurrency 1 to 4 (latency regime)CPU overhead per step, CUDA graph coverage, sampling and detokenization cost, attention kernel for small batchesNsight Systems trace: gaps between kernels (chapters 5.3, 5.7); engine flags that disable CUDA graphs
Middle of the curveScheduler policy: chunked-prefill token budget, how prefills and decodes mix (chapter 3.2)Inter-token latency spikes when prefills arrive; change the token budget
High concurrency (throughput regime)KV cache capacity (memory settings, block size), maximum batch size, preemptions, matmul and attention kernel efficiency at large batchEngine logs and metrics: running vs waiting requests, KV usage, preemptions (chapter 3.1)
TTFT at high loadQueueing once the batch limit is reached; prefill speed; HTTP front-end limitsServer-side queue time vs client TTFT (chapter 6.6)
Long-input workloadPrefill kernels (FlashAttention or FlashInfer versions, chapter 4.2), chunk sizePrefill time per token at concurrency 1
Prefix-reuse workloadPrefix cache design, hit rate, evictionHit-rate metrics; TTFT with caching on and off
FP8 runQuantized GEMM kernels and which layers stay in higher precision (chapter 4.1)Kernel names and times in a profile

An example of a mechanism you may meet: at high concurrency a single Python serving process can become host-bound, with one event loop parsing every request and writing every streamed chunk. TensorRT-LLM's server documentation says this is why trtllm-serve now runs 8 HTTP front-end processes by default. If one engine's TTFT climbs while its GPU shows idle gaps, check the front end before the kernels.

7. Reading the results

Plot each engine as a curve: x-axis tokens per second per user (interactivity, 1 ÷ TPOT), y-axis output tokens per second per GPU (throughput). Moving right along an engine's curve means fewer concurrent users; the curve that lies above and to the right of the others is better at every operating point. Curves often cross. Then apply your SLO: a minimum tokens per second per user (and a TTFT limit) picks one point on each curve, and the engine with the highest throughput there wins for that SLO, at a cost per million tokens of GPU price ÷ throughput.

Interactive: Pareto curves and an SLO
These curves come from the pipeline test on three mock engines on a CPU (A: fast steps that slow down quickly with batch size; B: slower steps that scale better; C: like A but limited to 16 running requests). They are not vLLM, SGLang or TensorRT-LLM results. They show how to read a real teardown.

In the mock test, A wins at low concurrency (fastest per-user speed), B wins at high concurrency (highest throughput), and C stops scaling at 16 running requests: its throughput stays flat while TTFT grows to 3.7 s at concurrency 64, because extra requests just queue. A real teardown shows the same kinds of pattern, for real reasons from the table in section 6.

8. Publish it

A teardown others can trust includes:

  • Hardware (GPU, host CPU, memory, cloud and region), driver, CUDA, engine versions and container digests.
  • The exact launch commands and config files, and the KV capacity each engine reported.
  • The workload generator, prompts (or the seed and dataset), the client and its version.
  • Raw per-request results (the JSON lines), the analysis script and the plotting script.
  • Correctness gate results.
  • Plots: Pareto curves per workload, TTFT and TPOT percentiles against concurrency, cost per million tokens at your SLO.
  • Explanations for each difference, with the evidence (profiles, metrics, flag changes), and a list of what you did not test.

Budget: at the H100 price in chapter 6.5 ($2.90 per hour), four hours costs about $12. Script everything before renting, test the scripts on a mock or a small GPU, and shut the instance down as soon as the raw results are copied off.

9. Common mistakes

  • Different precisions or model files across engines.
  • Comparing one engine's tuned config with another's defaults.
  • Reporting a single peak-throughput number.
  • No warm-up, so CUDA graph capture and compilation land in the measurements.
  • Prompts made of repeated tokens, or identical prompts that hit the prefix cache.
  • Different output lengths because one engine stops at end-of-sequence earlier.
  • Explaining differences by reputation ("engine X is optimized") instead of evidence.

10. Lab: the capstone

Part A: run the pipeline on mock engines

Before renting a GPU, run the whole pipeline on a CPU with mock engines. The mock engine streams tokens with a decode step time that grows with the number of running requests, a prefill time per prompt token, and a maximum batch size:

# mock_engine.py: a stand-in "engine" for testing the harness without a GPU
import asyncio, os
from fastapi import FastAPI, Request
from fastapi.responses import StreamingResponse
STEP = float(os.environ["STEP_MS"]) / 1000          # decode step time at batch 1
SLOW = float(os.environ["SLOW"])                    # slowdown per extra running request
PRE = float(os.environ["PREFILL_US_PER_TOK"]) / 1e6 # prefill time per prompt token
MAXB = int(os.environ["MAX_BATCH"])                 # requests that can run at once; the rest queue
app = FastAPI(); sem = asyncio.Semaphore(MAXB); running = 0
@app.post("/v1/completions")
async def completions(req: Request):
    body = await req.json(); n_in = len(body["prompt"].split()); n_out = body["max_tokens"]
    async def gen():
        global running
        async with sem:
            running += 1
            try:
                await asyncio.sleep(n_in * PRE * (1 + running * SLOW))
                for _ in range(n_out):
                    await asyncio.sleep(STEP * (1 + running * SLOW))
                    yield 'data: {"choices": [{"text": " t"}]}\n\n'
                yield "data: [DONE]\n\n"
            finally:
                running -= 1
    return StreamingResponse(gen(), media_type="text/event-stream")
# run_mock.sh
declare -A CFG=( [A]="STEP_MS=8 SLOW=0.03 PREFILL_US_PER_TOK=40 MAX_BATCH=64"
                 [B]="STEP_MS=12 SLOW=0.012 PREFILL_US_PER_TOK=25 MAX_BATCH=64"
                 [C]="STEP_MS=8 SLOW=0.02 PREFILL_US_PER_TOK=40 MAX_BATCH=16" )
port=8301
for e in A B C; do
  env ${CFG[$e]} python3 -m uvicorn mock_engine:app --port $port --log-level error & pid=$!
  sleep 2
  python3 sweep.py $e http://127.0.0.1:$port/v1/completions results.jsonl
  kill $pid; port=$((port+1))
done
python3 analyze.py results.jsonl 2.90

Part B: the real run

  1. Design your matrix (section 2) and write your predictions.
  2. Rent one GPU. Pull the three engines' official images at pinned versions.
  3. For each engine: launch, record the start-up log (KV capacity, CUDA graph sizes), run the correctness gate, run the sweep for each workload three times, copy the results off, stop the engine.
  4. Profile one point where engines differ most (Nsight Systems, a few seconds of steady state).
  5. Analyze: Pareto plots, percentile plots, cost at your SLO. Explain each difference with evidence.
  6. Publish the repository and report.

Part C: the report

Structure: question and predictions; setup and versions; correctness gate; results per workload (plots and table); explanations; what surprised you and what your predictions got wrong; limitations; how to reproduce. Keep the conclusion conditional: "for this model, GPU, workload and SLO, engine X gave the lowest cost per million tokens, because ...".

11. In the real world

How teams use engine comparisons
  • Platform teams rerun a teardown like this whenever a major engine version, model family or GPU arrives, because rankings change often.
  • Engine projects publish their own benchmarks; independent ones with published configs are the ones to trust.
  • Public benchmark sites (chapter 6.1) compare providers end to end; a teardown explains the engine-level reasons behind such differences.

12. Check yourself

13. Summary

  • Same weights, precision, hardware, workload and client for every engine; defaults and tuned configs reported separately; warm-up and repeats.
  • Correctness first, then curves across concurrency for several workload shapes.
  • Read Pareto curves at your SLO, convert to cost per million tokens, and explain each gap with evidence: CPU overhead, CUDA graphs, scheduler, KV capacity, kernels, prefix caching, front ends.
  • Publish everything needed to reproduce the result.
