Specialized inference workloads

The same engine serves very different workloads, and each one stresses a different part of it. A reasoning model writes tens of thousands of tokens and fills the KV cache; a batch job cares only about tokens per dollar; a vision model spends its prefill on image tokens; an RL trainer needs fresh weights in the engine every few minutes; a diffusion model has no tokens at all. This chapter profiles eight workloads side by side, shows for each which earlier technique matters most and what to measure, and gives a method for defining a workload and its SLO before choosing anything.

Before you start: skip check
  1. A reasoning model averages 16,000 output tokens per request. What runs out first on an 8B model on one H100: compute or KV memory?
  2. For an overnight batch job of 10 million prompts, which SLO do you set?
  3. Why is an image costly for a vision-language model even when the text prompt is short?
Answers
  1. KV memory. At about 128 KB per token, 16,000 tokens is about 2.1 GB per request, so roughly 24 requests fill a 50 GB KV pool, far below the batch size at which decode would become compute-bound (chapter 2.5).
  2. A deadline for the whole job (for example done by 6 a.m.) and a cost per million tokens; per-request latency does not matter. Use offline inference with large batches.
  3. The vision encoder must run, and the image becomes hundreds to thousands of tokens of prefill and KV cache, more than the text itself (chapter 3.7).

1. Define the workload before the system

For each workload write down five things; they decide almost every later choice:

  1. Shape: input and output length distributions, shared prefixes, media per request.
  2. Arrival: interactive (open-loop, bursty), batch (all at once), or in a training loop.
  3. SLO: TTFT and TPOT percentiles, a job deadline, or rollout throughput.
  4. Quality target: the evaluation and the acceptable regression for any optimization (chapter 7.6).
  5. Cost target: cost per request, per million tokens, or per training step.

3. Vision-language and multimodal

Images and video pass through a vision encoder whose output becomes media tokens in the language model's context (chapter 3.7). Serving levers in vLLM:

  • limit_mm_per_prompt caps images or videos per request, which bounds the worst-case memory a request can claim.
  • Precomputed embeddings (enable_mm_embeds): pass encoder outputs instead of raw images, so the encoder can run elsewhere or be cached across requests that reuse the same image.
  • Video token pruning (--video-pruning-rate): drop a fraction of video tokens after the encoder, cutting prefill time and KV use at some cost in accuracy.
  • Encoder work competes with prefill and decode; disaggregated designs give the encoder its own GPUs (the omni-modality pipelines of chapter 3.7).

4. Reasoning models

Reasoning models write a thinking section before the answer; vLLM's reasoning parsers split it into a separate reasoning field (formerly reasoning_content; clients reading the old name silently get nothing). Whether thinking is on is model-specific: Qwen3 thinks by default (disable with enable_thinking=False in the chat template arguments), while some other models need it switched on. Serving consequences:

  • KV grows during decode. Each request's cache keeps growing for minutes, so the KV pool, not compute, limits concurrency. Preemptions and recomputation appear under load (chapter 3.3). FP8 KV cache and models with GQA or MLA help most.
  • Thinking budgets. vLLM's thinking_token_budget sampling parameter forces the end-of-thinking marker once the budget is reached, optionally with a transition phrase so the answer follows naturally. Budgets turn an unbounded cost into a bounded one; evaluate quality at each budget.
  • Long-tail latency. Hugging Face measured SmolLM3's thinking mode at a median of about 16,000 tokens on AIME25 with a fat tail, against about 2,000 without thinking: plan capacity for the tail, not the median.
  • Speculative decoding (chapter 4.3) helps the long decode at low concurrency; structured outputs apply only after reasoning if the parser separates them.
  • Architecture changes the bill. DeepSeek-R1 (arXiv 2501.12948) created this workload. Qwen3 (arXiv 2505.09388) put thinking and non-thinking modes and a thinking budget in one model, so one deployment sees both short and very long outputs. MiniMax-M1 (arXiv 2506.13585) shows why attention design matters here: with mostly linear attention layers, its report states it uses less than half of DeepSeek-R1's FLOPs at a 64K-token generation and about a quarter at 100K (chapter 2.7).

5. Batch and offline inference

When nobody waits for individual answers, optimize tokens per dollar. vLLM's offline LLM class takes a whole list of prompts and schedules them with continuous batching at the largest batch memory allows, without an HTTP server. The lab measures the basic trade-off: batch 16 gave 6.3 times the total throughput of batch 1, while each request got 2.6 times slower. Other levers: sort or group prompts by length, share prefixes (put the common instructions first), use the cheapest hardware that fits, run in troughs of interactive traffic (chapter 6.5), and choose quantization by quality per dollar. Completion time for a job ≈ total tokens ÷ throughput, so measure throughput at the batch size you will use.

6. RL rollout inference

In RL (chapter 7.4) the engine generates rollouts inside the training loop. verl, an open implementation of the HybridFlow design, connects trainers (PyTorch FSDP, Megatron-LM) with rollout engines (vLLM, SGLang) through modular interfaces. Differences from serving:

  • Weights change every step or few steps: the engine needs fast in-place weight updates, and its caches (prefix cache, CUDA graphs) must stay valid.
  • The tail sets the pace in synchronous training: one very long rollout holds the whole step. Asynchronous and partial rollouts trade some on-policyness for throughput.
  • Numerics matter: the sampler's log-probabilities feed the loss; track the trainer-sampler gap or use batch-invariant kernels (chapter 7.6).
  • Colocation: sharing GPUs between trainer and engine (TRL's colocate mode, verl's hybrid engine) needs memory handoff between phases.

7. Diffusion inference

Diffusion models refine noise into an image or video over a number of steps; each step is a large, compute-bound forward pass of a U-Net or diffusion transformer. Hugging Face Diffusers lists the levers: run in reduced precision (FP16 or BF16, and TF32 matmuls on Ampere and later); use scaled dot-product attention, which picks FlashAttention or memory-efficient kernels automatically; compile the heavy components (U-Net or transformer, VAE) with torch.compile; and combine techniques. The largest lever is fewer steps (better schedulers, distilled few-step models), which trades quality for time: measure quality at each step budget, as chapter 3.7 described for serving systems such as SGLang Diffusion and vLLM-Omni.

8. Expert layer

Mixed workloads on one fleet

Interactive chat, long reasoning requests and batch jobs on the same replicas interfere: long decodes hold KV blocks, long prefills stall decodes (chapter 3.2), batch traffic fills queues. Production systems separate them by pool (routing by expected length or model mode), by priority (batch yields to interactive, chapter 6.4), or by time (batch in troughs), and measure each class against its own SLO.

Encoder caching for repeated media

Many multimodal workloads reuse the same image or document across turns. Caching encoder outputs by a hash of the media (and the processor settings) avoids re-encoding, the multimodal analogue of prefix caching; it needs the same safety rules (scope to model and processor version, and to tenant, chapter 6.9).

9. Common mistakes

  • One SLO for all workloads on a shared fleet.
  • Planning reasoning capacity from median output length.
  • Reading reasoning_content after the field was renamed.
  • Running batch jobs through the interactive endpoint at small batch sizes.
  • No limit on media per request.
  • RL rollouts with a different chat template or numerics from training.

10. Lab

Part A: throughput-first vs latency-first

import torch, time
from transformers import AutoTokenizer, AutoModelForCausalLM
name = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(name); tok.padding_side = "left"
model = AutoModelForCausalLM.from_pretrained(name, dtype=torch.float32).eval()
prompt = tok.apply_chat_template([{"role": "user", "content": "Summarize the benefits of unit tests in one paragraph."}],
                                 tokenize=False, add_generation_prompt=True)
for bs in [1, 4, 16]:
    enc = tok([prompt] * bs, return_tensors="pt", padding=True)
    with torch.no_grad():
        model.generate(**enc, max_new_tokens=4, do_sample=False)              # warm-up
        t = time.perf_counter()
        model.generate(**enc, max_new_tokens=64, min_new_tokens=64, do_sample=False, pad_token_id=tok.eos_token_id)
        dt = time.perf_counter() - t
    print(f"batch {bs}: {bs*64/dt:.1f} tok/s total, {64/dt:.1f} tok/s per request")

Predict first: how much does total throughput grow from batch 1 to batch 16, and what happens to each request's speed?

What we measured (2 CPU cores)
batch  1:    8.7 output tok/s total,   8.7 tok/s per request,   7.4 s per batch
batch  4:   18.1 output tok/s total,   4.5 tok/s per request,  14.1 s per batch
batch 16:   54.8 output tok/s total,   3.4 tok/s per request,  18.7 s per batch

Total throughput grew 6.3 times while each request slowed 2.6 times: the trade batch jobs make on purpose. On a GPU the curve is far steeper at first, because decode at batch 1 is memory-bound (chapter 2.5); with vLLM's offline LLM.generate on thousands of prompts, expect total throughput tens of times higher than batch 1.

11. In the real world

In practice
  • Providers offer cheaper batch APIs for latency-tolerant work and route reasoning modes to pools sized for long outputs.
  • Multimodal products cap media, cache encoder outputs and size encoder capacity separately.
  • RL teams run engines inside training with asynchronous rollouts and weight sync.

13. Summary

  • Define shape, arrival, SLO, quality target and cost target before choosing a system.
  • Each workload stresses a different resource: grammar checks, adapters, encoders, prefixes, KV growth, batch throughput, weight sync or denoising steps.
  • Reasoning: plan KV for the tail, use thinking budgets. Batch: maximize batch size and minimize cost. Multimodal: limit and cache media. RL: fast weight sync, async rollouts, matched numerics. Diffusion: fewer steps, lower precision, compiled kernels.
