Case study: DeepSeek's inference stack, from V3 to DeepInfer

DeepSeek publishes its model architectures, its kernels, its cluster designs, its serving layout and its production numbers, and in October 2026 it open-sourced DeepInfer, the engine behind its own API. Reading these releases in order is the quickest way to see how the techniques of Parts 2 to 6 fit together in one system. This chapter follows the stack from DeepSeek-V3 (December 2024) through the February 2025 kernel releases, DeepSeek Sparse Attention in V3.2, the one-million-token V4, and V4.1-Flash, whose global KV cache is 890 bytes per token. It ends with DeepInfer itself: what it contains, how each feature maps to an earlier chapter, and what is still missing for a complete service.

Level: expert Time: 4 hours with the lab Needs: 2.4, 2.6, 4.2, 4.3, 4.5, 4.6, 6.7 Compute: CPU for Parts A and B; SM100 or Ascend 950 for Part C
Before you start: skip check
  1. DeepSeek-V4.1-Flash activates 16B parameters per token in decode. Why only 8B in prefill?
  2. Why does DeepInfer run prefill with the smallest expert parallel group that fits, and decode with the largest?
  3. DeepSeek's V4.1 service keeps the global KV cache on SSD for at least 72 hours but keeps sliding window KV only for minutes, in host memory. Why treat the two differently?
Answers
  1. Its causal encoder-decoder design projects the decoder layers' global KV from the last encoder layer's output, so prefill runs only the 20 encoder layers over the prompt (plus a short replay of the last tokens through the decoder).
  2. Prefill already has a large batch per expert, so a small group balances load better and moves less data over NVLink. Decode has a small batch per expert, so a wide group (64 to 128 GPUs) gives each expert more tokens and each GPU fewer weights to read.
  3. Global KV is reused over hours and days (long-tail reuse); sliding window KV is reused only inside an active session and is dead once the next turn starts. A cheap approximate rebuild (SWA bounded replay) covers the misses.

1. Why one lab's stack is worth a chapter

Most frontier labs publish a model card and benchmark scores. DeepSeek also publishes the parts an inference engineer needs: per-token KV sizes, the hardware constraints behind each architectural choice, the kernels (FlashMLA, DeepEP, DeepGEMM, DeepSelect, TileKernels), the file system behind its KV cache (3FS), the deployment layout of its service with a day of production statistics (chapter 6.7), and now the engine (DeepInfer). Each release answers a question the previous one created, so reading them in order shows a design being pushed against its bottleneck, then the next bottleneck, for two years.

The thread to follow is the KV cache. Every generation shrinks it along a different dimension, and every shrink changes where the cost of serving goes: from HBM capacity, to prefill compute, to SSD capacity and I/O.

Definitions used throughout

Global KV: the KV cache of attention that spans the whole context (in DeepSeek-V4 and later, the compressed main KV plus the lightning indexer's keys). Its size grows with the sequence length and it lives in HBM while a request runs.

Persistent KV: the part of the KV cache stored after a request ends (on SSD or in host memory) so later requests with the same prefix can skip prefill (chapter 4.4).

Scale-up domain: the set of GPUs connected by the fast in-node or in-rack fabric (NVLink, or Huawei's unified bus); a supernode is a large one, such as a 64-GPU or 72-GPU rack.

2. DeepSeek-V3 (December 2024): the base design

V3 is a 671B-parameter mixture-of-experts model with 37B parameters active per token. Its inference-relevant choices, each covered earlier in the book:

  • Multi-head latent attention (MLA), chapters 2.4 and 4.2: one 512-value latent plus a 64-value RoPE key per token per layer, 70,272 bytes per token in BF16.
  • DeepSeekMoE, chapter 2.6: one shared expert that every token uses plus 256 fine-grained routed experts, 8 active per token, balanced by a bias term instead of an auxiliary loss.
  • Multi-token prediction (MTP), chapter 4.3: a one-layer module trained with the model that predicts an extra token, reused at serving time as a draft.
  • FP8 training with fine-grained block scales, chapters 1.3 and 4.1, which makes FP8 serving the native precision rather than a quantization.
  • DualPipe, a bidirectional pipeline schedule that overlaps forward and backward computation with communication in training.

The ISCA 2025 paper "Insights into DeepSeek-V3" explains why the model looks like this, from the hardware side. Three of its arguments matter for serving:

  • Memory first. Its Table 1 puts V3's KV cache at 70.272 KB per token against 327.680 KB for Qwen-2.5 72B (GQA) and 516.096 KB for Llama-3.1 405B. MLA is what lets a 671B model hold long contexts.
  • Interconnect sets the speed limit of MoE decode. With one expert per GPU and about 32 tokens per expert, dispatch in FP8 and combine in BF16 over 400 Gb/s InfiniBand take 120.96 µs per layer; with two micro-batches overlapped that gives 61 × 241.92 µs = 14.76 ms per token, about 67 tokens per second, as a theoretical ceiling. On a GB200 NVL72 domain at 900 GB/s the same arithmetic gives about 0.82 ms. The paper calls this purely theoretical; the point is that decode speed for wide MoE is a network number.
  • Node-limited routing. H800 NVLink gives about 160 GB/s usable against about 40 GB/s effective per InfiniBand NIC, so V3 groups its 256 experts into 8 node-sized groups and sends each token to at most 4 nodes. A token crosses InfiniBand once per node and is forwarded over NVLink inside it.

The same paper reports that the MTP module's second-token acceptance rate is 80% to 90% in practice, which raises generation speed by 1.8 times. Fire-Flyer AI-HPC (SC'24) covers the cluster underneath: 10,000 PCIe A100 GPUs reaching performance close to DGX-A100 at half the cost and 40% less energy, with HFReduce for all-reduce and 3FS for storage. The common argument of both papers: co-designing the model and software with cheaper hardware beats buying the most expensive interconnect.

Expert layer: the hardware wish list

Sections 3 to 6 of "Insights into DeepSeek-V3" end with requests to hardware vendors: higher-precision accumulation in FP8 tensor cores and native fine-grained scaling; communication compression (their LogFMT format); a single fabric that merges scale-up and scale-out with hardware offload of forwarding; lower-latency networks (they compare InfiniBand and RoCE and use InfiniBand GPUDirect Async); better error detection; faster CPU to GPU links; and memory-centric designs such as DRAM stacked on logic. Read it next to chapter 5.5: many of these requests shaped the hardware that V4.1 now runs on.

4. DeepSeek-V3.2 (late 2025): sparse attention

V3.2 added DeepSeek Sparse Attention (DSA, chapter 4.2): a small lightning indexer scores every earlier token and each query attends to only the top 2,048. Core attention cost falls from growing with T² to growing with T × k, while the indexer still scores every pair but cheaply (it can run in FP8). Serving it needed three new pieces: indexer logit kernels in DeepGEMM, sparse attention kernels in FlashMLA, and a fast top-k, which became DeepSelect. The DeepSelect README describes it as the top-k kernel for DSA in V3.2, V4 and V4.1 and for the sampler, on CUDA and Ascend, with 2 to 20 times the speed of torch.topk, measured as effective memory bandwidth at top-k 512.

DSA did not shrink the KV cache; V3.2's global KV is 48,068 bytes per token in the V4.1 report's Figure 1(b). It shrank the attention compute of long contexts. The next two generations went after memory.

5. DeepSeek-V4 (April 2026): one million tokens

V4 is two MoE models: V4-Pro (1.6T parameters, 49B active, 61 layers) and V4-Flash (284B, 13B active, 43 layers), both with a one-million-token context, pre-trained on more than 32T tokens with the Muon optimizer (chapter 7.7) and manifold-constrained hyper-connections (mHC, chapter 2.7). The attention is new.

Definitions

Compressed Sparse Attention (CSA): DeepSeek-V4's attention that first compresses the KV of every m tokens into one entry (m = 4 in both V4 models, using learned weights over overlapping windows), then applies DSA so each query attends to only the top-k compressed entries (512 in V4-Flash, 1,024 in V4-Pro).

Heavily Compressed Attention (HCA): V4's second attention type, which compresses the KV of every m′ tokens into one entry (m′ = 128) and attends densely to all of them, with no sparse selection.

V4 interleaves CSA and HCA layers. In both, each compressed entry serves as key and value (shared-KV multi-query attention, chapter 2.4), with a grouped output projection to keep the large concatenated head output cheap. Both also keep a sliding window branch of the last 128 uncompressed tokens (a query cannot see inside its own compressed block otherwise), and an attention sink. The report's efficiency section adds three precision choices: the KV entries are stored in FP8 except the RoPE dimensions in BF16 (nearly half of pure BF16), the lightning indexer computes in FP4, and the top-k is smaller than V3.2's.

The result, from the report's introduction, at a one-million-token context: V4-Pro needs 27% of V3.2's single-token inference FLOPs (in FP8-equivalent FLOPs) and 10% of its KV cache; V4-Flash needs 10% of the FLOPs and 7% of the KV. Against a BF16 GQA baseline with 8 KV heads of size 128, V4's KV cache is about 2%.

What V4 changed in the inference framework

The report says the framework "largely inherits from that of DeepSeek-V3", with a new KV layout. Hybrid attention breaks PagedAttention's assumption that every layer stores the same thing per token (chapter 3.3): CSA layers store one entry per 4 tokens, HCA layers one per 128, the indexer has its own dimensions, and sliding window layers keep only a window. V4 splits the cache in two:

  • A classical paged KV cache for CSA and HCA, where each block covers lcm(m, m′) original tokens, so one block holds a whole number of entries of both kinds. The sparse attention kernel is co-designed with this layout so blocks can hold different token counts per layer without losing speed.
  • A state cache with one fixed-size slot per request, holding the sliding window KV and the tail tokens not yet ready for compression. The report treats this part like the state of a state space model (chapter 2.7): bounded, and dependent only on the current position.

For the on-disk prefix cache, compressed CSA and HCA entries are stored as they are. Sliding window KV is about 8 times larger because it is uncompressed and in every layer, so the report gives three options: store it all (no recompute, but write-heavy on SSDs), checkpoint it every p tokens, or store none and recompute. Exact recompute needs the last nwin × L tokens, because each layer's window depends on the previous layer's window.

6. DeepSeek-V4.1-Flash (September 2026): KV compression to the limit

The V4.1-Flash report opens with the workload: long-horizon agents make contexts long and input-heavy, sparse attention has already cut attention compute, so storage and data movement of the KV cache are now the bottleneck (chapter 6.8). V4.1-Flash is a 552B-parameter multimodal MoE (plus 196B parameters of Engram, a sparsely accessed conditional memory) with a one-million-token context. Three changes do the work.

Definitions

Causal encoder-decoder (CED): V4.1-Flash's layout of its 40 layers into a 20-layer causal encoder and a 20-layer decoder, where the decoder layers' global KV is projected from the last encoder layer's hidden state instead of each layer's own. Prefill needs only the encoder, so it activates 8B parameters per token against 16B in decode.

Compressed Sparse Attention 2 (CSA2): V4.1's attention, in which layers share global KV and top-k selections. Each layer is statically Full (computes its own KV and selection), Reindex (reuses an earlier layer's KV but selects again) or Reuse (reuses both).

SWA bounded replay: rebuilding a missing sliding window KV state approximately by recomputing only the last nwin tokens (128) and truncating the window to that replayed segment, instead of the nwin × L tokens an exact rebuild needs.

  • CED cuts prefill compute. The report says it is inspired by YOCO (Microsoft, 2024), in which the upper half of the layers reuses the KV cache of the lower half, and calls the reduction "nearly half" of prefill computation. Each layer still computes its own sliding window KV, so the decoder's windows need a short replay (next item).
  • CSA2 cuts KV storage. Shared global KV removes duplicate storage across layers; reused selections remove indexer work; a hierarchical sparse indexer in the decoder lets later indexers search only a candidate pool chosen by an earlier one. V4.1 drops HCA and uses CSA2 throughout, with a simplified compressor (no overlapping windows).
  • FP4 main KV. The main KV cache is trained with quantization-aware training into an E2M1 format with one E4M3 scale per 16 channels (NVFP4 without its global scale); the indexer uses MXFP4. The sliding window KV stays in FP8 because it is sensitive to quantization.

Together, CSA2 and FP4 bring the global KV to 890 bytes per token, about a quarter of V4-Flash's 3,514. SWA bounded replay then lets the service stop persisting sliding window KV at all, which brings the persistent KV to about one eighth of V4-Flash's. The report adds that extending the context 256 times, from 4K to 1M tokens, raises V4.1-Flash's decode FLOPs per token by only a quarter.

Bounded replay in practice

Bounded replay is used twice, and both uses accept an approximation that the report says has negligible quality impact (it also simulates the replay in post-training):

  • Encoder replay on a cache hit. The prefix cache now depends only on global KV. If the sliding window state for the hit prefix is missing, the last 128 tokens of the prefix are recomputed together with the new suffix, rebuilding only the window.
  • Decoder replay on every prefill. The decoder never stores its window state, and an exact rebuild would run 20 layers over the last 2,560 tokens. Instead every prefill runs the last 128 prompt tokens through the decoder; the result is used for decode only and never enters the prefix cache. The DeepInfer Q&A says this nearly halves total prefill computation.

7. DeepInfer (October 2026): the engine

DeepInfer is "the high-performance inference framework that powers DeepSeek's large-scale production services". The open-source release, read at commit a679bb8 (3 November 2026), provides offline inference with the core features for serving at scale, for one model: DeepSeek-V4.1-Flash (checkpoint DeepSeek-V4.1-Flash-1017, also served by the deepseek-flash API model). It is Apache-2.0 and, in its own words, "originally built primarily on vLLM, with additional inspiration from SGLang and TensorRT-LLM". It runs on NVIDIA SM100 GPUs (CUDA 13) and Huawei Ascend 950 NPUs (CANN 9.2), with Python 3.12 and GCC 13 or newer. Hopper GPUs are not supported, so most readers will read this section rather than run it.

The README also lists what a complete service needs that the release does not include: a KV cache system, vision encoder, prefill and decode disaggregation ("most required engine functionality is already implemented"), and load balancing across data-parallel replicas. The deployment Q&A in the repository (doc/inference_deployment_qa.md, version 0.2) describes those missing parts as DeepSeek runs them, and is the most detailed public account of a frontier service. Its main points follow; every number is DeepSeek-reported.

The V4.1-Flash service as the DeepInfer Q&A describes it: disaggregated vision encoder (VE), prefill and decode pools, four load balancers, and separate stores for block KV and sliding window KV.

  • Scale. One cluster serves 155 trillion tokens per day, with revenue of US$38 per GPU-hour at the off-peak price.
  • Parallelism. Prefill on ordinary 8-GPU machines with EP2 to EP8 (data parallel attention of the same size), the smallest that HBM allows. Decode on 64- to 128-GPU supernodes with EP64 to EP128 ("Wide-EP"). Vision encoders on one cheaper GPU each. No tensor parallelism and, for now, no context parallelism: in their measurements CP was up to 5% slower end to end, worsened expert load balance, and was not needed because V4.1 keeps tail TTFT acceptable even on a full cache miss. The smallest efficient unit is 64 prefill GPUs plus 64 decode GPUs (a roughly 1:1 ratio).
  • Expert load balancing. Prefill: 4 redundant experts per GPU, a 100-step load window, re-placement every 1,000 steps; measured slowest-to-mean load ratio 1.074 at EP4. Decode: 1 redundant expert per GPU (7 experts per GPU at EP64 after rounding), a 1,000-step window, re-placement every 10,000 steps; ratio 1.090.
  • Prefill scheduling. Requests are bucketed by total context (under 16K, 16K to 64K, 64K to 256K, 256K and over); engines pull work by remaining compute quota; each step's chunk size is solved from a time budget with a fitted quadratic cost model of new tokens and cached prefix length, capped at 32,768 tokens. There is no prefix-affinity routing, because every prefill machine can read every prefix from shared storage.
  • Decode routing. A global decode load balancer evens out two quantities per GPU at once: request count (batch size) and total KV length (attention cost). Overall, load balancing reaches about 80% of a perfectly balanced offline benchmark.
  • KV storage. In-flight KV and per-sequence state in HBM; sliding window KV in host memory on the machine that produced it, found through an in-memory directory and pulled over a 400G network on a cross-machine hit; block KV (main KV and indexer keys) on a dedicated 3FS cluster with 10+2 erasure coding, about 100 PiB of SSD, a TTL of 3 days for agent traffic and 7 days for chat traffic, about 14.4 TB of logical KV per online GPU. Only 20 layers × 134 tokens × 528 bytes = 1,415,040 bytes of sliding window state is saved per sequence.
  • Speculative decoding. In production the draft model proposes 5 tokens; a confidence head predicts each one's acceptance; the scheduler sorts drafts by expected acceptance and verifies the prefix set that maximizes throughput on a profiled cost curve. On their Open-PerfectBlend data this cuts verified tokens per step by about 30% with nearly the same accepted length, for 4% to 7% more throughput at the production point of about 60 sequences per GPU (table below).
  • Failure handling. In wide EP one failed GPU stops the whole instance; the platform restarts it with an EP size equal to the healthy GPUs it receives. A decode engine being shut down gets a one-minute grace period, then forwards unfinished requests with their KV to other engines.

A toy model, not DeepSeek's cost curve. A batch of requests each has 5 draft tokens; draft i survives with probability pi. A verify step costs a fixed overhead plus a per-token cost for every draft verified. Dynamic verification keeps only the draft tokens whose expected gain beats their cost.

Two engine details are worth knowing before you read the code (chapter 8.2 maps it). The scheduler, block manager and cost estimator are C++ (csrc/engine/) behind Python bindings, rather than Python as in vLLM. And asynchronous scheduling interacts with speculation: when step N+1 is scheduled, step N's confidences have not returned, so the CPU fixes only the total verification budget and a TileLang kernel on the GPU assigns each request's length.

The repository also ships benchmarks. The README's Pareto charts were measured on 4 SM100 GPUs for prefill (EP4, 128K context, bounded replay) and 64 for decode (EP64, 128K context, three draft tokens with 75% per-token acceptance assumed). Read from the charts, approximately: prefill reaches about 87,000 non-cached input tokens per second per GPU with 32,768-token batches at about 375 ms per step; decode reaches about 15,700 output tokens per second per GPU at 64 requests per GPU and about 246 tokens per second per user. These are DeepSeek-reported and not independently reproduced; note that the decode metric counts every draft token at the assumed acceptance.

Read across, the bottleneck moves. V3 made KV small enough for long contexts and made decode a network problem, answered with wide EP. V3.2 made long-context attention compute affordable. V4 shrank KV by compressing the sequence dimension and storing in lower precision. V4.1 shrank it along the layer dimension and in precision again, and attacked the prefill compute that input-heavy agents create. The engine and the service followed each step: a heterogeneous cache layout, storage tiers matched to reuse patterns, and schedulers that model compute cost instead of counting tokens.

9. Expert layer

Why decode runs on 64 to 144 GPUs per unit

With 6 or 8 of several hundred experts active per token, a decode batch of a few hundred requests gives each expert only a handful of tokens per GPU, so expert matmuls read their weights to do almost no work (chapter 2.5). Spreading experts over a wide group gives each GPU fewer experts and each expert more tokens. The DeepInfer Q&A adds the limit: past about EP32 the fused MoE kernel stops gaining, because once memory bandwidth is no longer the bottleneck, wider groups add communication and synchronization. It also notes that jobs sharing NVLink in a supernode interfere, so one EP group uses the whole supernode.

What others built on DSA

Lookahead Sparse Attention (FlashMemory-DeepSeek-V4, arXiv 2606.09079) trains a neural memory indexer as a dual encoder, without loading the backbone, and keeps only the KV chunks a query will need in GPU memory. The authors report an average KV footprint of 13.5% of the full-context baseline with equal or slightly better accuracy, and at 1M tokens 0.30 times the per-token decode compute, 90% less GPU KV cache, and 2.8 times throughput in prefill-decode disaggregated serving on 8 H20 GPUs. LongCat Sparse Attention (Meituan, arXiv 2608.01662) targets the lightning indexer's own O(L²) cost and its scattered memory access with streaming-aware indexing (contiguous KV layouts for coalesced reads), cross-layer indexing and hierarchical coarse-to-fine indexing; V4.1's hierarchical sparse indexer and index reuse follow the same direction.

Tree speculation on compressed attention

Tree speculation (chapter 4.3) verifies several branches from a shared prefix in one pass. On V4-Flash this is hard because CSA and HCA compress KV online: branches that diverge from a shared prefix compress into different states. The authors of arXiv 2609.24698 add branch-aware causal verification, temporary state isolation and a state refresh along the accepted path. At a budget of 8 draft tokens the accepted length rises to about 2.83 to 3.41 from 2.39 to 2.84 for linear drafts, with throughput gains of up to about 18.5%; beyond some budget throughput plateaus while accepted length keeps rising. Any model with compressed, sparse or stateful context will meet the same problem.

10. Common mistakes

  • Quoting the February 2025 service numbers (H800, 144-GPU decode units, 56% cache hits) as DeepSeek's current deployment.
  • Comparing per-token KV sizes across generations without saying which part is counted: global KV, the window state, the indexer, or all of them.
  • Expecting DeepInfer to run on H100 or H200: the release targets SM100 and Ascend 950, and current FlashMLA has dropped Hopper.
  • Treating DeepInfer as a complete service: the KV cache system, disaggregation and replica load balancing are not in the release.
  • Reading the README's decode throughput as delivered tokens: it counts drafts at an assumed acceptance rate.
  • Assuming bounded replay is exact. It is an approximation the model was trained to tolerate; outputs depend on where the cache hit landed.

A single one-million-token V3 session needs 70 GB, so 64 of them need 4.5 TB, a rack's worth of HBM. The same 64 sessions of V4.1-Flash need 57 GB, under one GPU. That is the change that makes million-token agents a serving product rather than a demo, and it is why the cost moved to prefill compute and SSD capacity. Two caveats: weights and the per-sequence window state also take HBM, and V4-Pro's figure is from a ratio at exactly 1M tokens, not a per-token size.

Part B: revenue per GPU-hour (CPU)

Use the DeepSeek API's deepseek-flash prices (served by V4.1-Flash-1017), checked on 7 November 2026: per million tokens off-peak, $0.003 cache-hit input, $0.15 cache-miss input, $0.60 output; peak rates are double. Combine them with the benchmark throughputs from section 7.

price = {"hit": 0.003, "miss": 0.15, "out": 0.60}   # USD per 1M tokens, off-peak (peak is 2x), checked 7 Nov 2026

dspark_tps  = 14_466   # tokens/s/rank, dynamic-length verification at 60 seqs/rank (Q&A table)
for name, tps, p in [("prefill GPU (cache-miss input)", prefill_tps, price["miss"]),
                     ("decode GPU (chart)", decode_tps, price["out"]),
                     ("decode GPU (DSpark table)", dspark_tps, price["out"])]:
    tok_h = tps * 3600
    print(f"{name:32s} {tok_h/1e6:6.1f} M tokens/GPU-hour -> ${tok_h/1e6*p:5.2f} off-peak, ${2*tok_h/1e6*p:5.2f} peak")

# 1P:1D is the ratio the Q&A gives; one pair of GPUs earns:

A fully busy pair of one prefill and one decode GPU earns about $40 per GPU-hour off-peak, the same size as the $38 DeepSeek reports. Do not read utilization from that match: the published figure includes cache-hit revenue, idle and peak hours, and the chart throughputs are benchmark points, not production averages. Two things the numbers do show: prices are set close to what the engine can produce per GPU, and a cache hit is billed at 2% of a miss, so the 3FS cluster's job is to turn expensive prefill into almost free input. Compare chapter 6.7's 2025 calculation, where the assumed cost was $2 per H800-hour.

Part C: run DeepInfer (SM100 or Ascend 950; expected, not measured)

On an 8-GPU SM100 node: build with DEEPINFER_ACCELERATOR=nvidia ./build.sh, run python examples/offline_inference.py --ep 8, then python examples/benchmark.py with its defaults (64 decode requests, 32,768-token context, 4,096 non-cached tokens, five draft tokens). Then sweep: bash examples/sweep/run_sweep.sh prefill pe-128k 131072 and the decode sweep with three draft tokens. Expect prefill throughput to rise and flatten with batch size and decode throughput to fall per user as requests grow, as in the README charts; on 8 GPUs (EP8) decode throughput per GPU should be well below the EP64 chart, which is the Wide-EP effect the Q&A shows. 12. In the real world

Where this stack shows up
  • Open engines (vLLM and SGLang, chapter 3.7) integrate FlashMLA, DeepEP and DeepGEMM as backends; DeepInfer itself started from vLLM.
  • Other labs' models reuse the parts: MLA layers in Kimi Linear's hybrid (chapter 2.7), DSA-style indexing in LongCat Sparse Attention, redundant experts in DeepEP-based expert balancing work from Moonshot (MoonEP) and others.
  • Chinese accelerators are first-class targets: FlashMLA, DeepEP, DeepGEMM, TileKernels and DeepSelect all ship Ascend 950 backends, and DeepInfer supports both platforms.
  • Agent platforms are the workload the V4.1 design is priced for: long, input-heavy contexts with high prefix reuse.

14. Summary

  • DeepSeek's releases show one design pushed against its bottleneck for two years: KV memory, then attention compute, then KV storage and prefill compute.
  • V3: MLA (70 KB per token), fine-grained MoE, MTP, FP8; decode speed for wide MoE is set by the interconnect.
  • V3.2: DSA cut long-context attention compute; V4: CSA and HCA compressed the sequence dimension, 10% of V3.2's KV at 1M tokens for V4-Pro.
  • V4.1-Flash: CED halves prefill, CSA2 shares KV across layers, FP4 main KV; 890 bytes of global KV per token; bounded replay removes window KV from persistent storage.
  • DeepInfer packages the kernels, attention DP with wide EP and EPLB, DSpark, bounded replay, asynchronous scheduling, batch invariance and structured outputs; the KV cache system and load balancers are described but not released.

Notes on sources

  • DeepSeek-V4, V4.1-Flash, DeepInfer, DeepSelect, TileKernels and the three related papers post-date the training data of the models that wrote this chapter. Every statement about them comes from the arXiv pages (full HTML for V4 and V4.1-Flash, abstracts for the others), the GitHub READMEs and the DeepInfer Q&A, read on 7 November 2026.
  • The DeepInfer README's benchmark figures are charts without tables; the prefill and decode throughputs used here are read from them and are approximate.
  • The README's environment variables call bounded replay "YOCO"; the V4.1-Flash report states that CED is inspired by YOCO, which is why the two are linked here.
  • The DeepEP README no longer has the separate normal and low-latency mode tables of 2025; version 2 merged both into EPBuffer. Older descriptions of two modes (including chapter 4.5) describe version 1.
  • The DeepInfer Q&A refers to a Zhihu blog post for the overall architecture; it was not used here, so the KV cache and load balancer details are only those the Q&A states. The V4-Flash serving layout was not found in the sources.
  • The report's V3.2 figure (48,068 bytes per token, exactly 788 bytes per layer over 61 layers) is smaller than chapter 2.4's 70,272 bytes for V3's latent in BF16, although V3.2 adds an indexer. The report does not break the figure down; a lower storage precision for the latent would explain it, but that is not confirmed from the source.
