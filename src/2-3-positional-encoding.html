Positional information

Attention, as built in chapter 2.2, cannot tell "dog bites man" from "man bites dog". Something must tell the model where each token is. Modern LLMs do it by rotating the query and key vectors, a method called RoPE. This chapter explains why it works, how it sets a model's context limit, and how serving engines stretch that limit.

1. The problem: attention is order-blind

Look at the attention formula again: softmax(QKᵀ/√d)V. Each score is a dot product of two token vectors. Nothing in it says which token came first. If you shuffle the input tokens, every token gets the same output as before, just in a new place. Mathematically, attention without positions is permutation-equivariant.

The causal mask (chapter 2.2) adds a little order information, because token 5 sees 5 tokens and token 50 sees 50. But it does not tell the model how far apart two specific tokens are. Language depends heavily on order and distance, so the model needs explicit position information.

2. First solution: add a position vector

The original transformer and GPT-2 add a position vector to each token's embedding before the first layer:

x_i = token_embedding[id_i] + position_embedding[i]
  • Sinusoidal (original transformer): fixed sine and cosine waves of many frequencies. Not learned.
  • Learned (GPT-2, BERT): a second embedding table with one row per position. GPT-2 has 1,024 rows of 768.

Learned absolute positions have a hard limit: position 1,025 has no row. GPT-2 simply cannot read longer input. Both kinds also encode absolute position, while language mostly cares about relative position: "the word two places before me" matters more than "the word at position 4,817".

3. RoPE: encode position as a rotation

Rotary position embedding (RoPE) takes a different route. It does not add anything to the embeddings. Inside every attention layer, it rotates each query and key vector by an angle that depends on the token's position.

Start with two dimensions. Treat the first two elements of q as a point on a plane. For a token at position m, rotate that point by the angle m × θ. Do the same to k at position n with angle n × θ. Now use one property of rotations:

rotate(q, mθ) · rotate(k, nθ) = q · rotate(k, (n − m)θ)

The dot product depends only on the difference n − m. Move both tokens 100 places later, and the score is identical. So attention scores become a function of the content and the relative distance only, which is what language needs.

A query (indigo) at position m and a key (amber) at position n, rotated by m·θ and n·θ. Change both positions by the same amount with the "shift both" slider: the angle between them, and so the dot product, stays the same.

Many frequencies

A real head has d = 128 dimensions, not 2. RoPE splits them into 64 pairs and gives each pair its own rotation speed:

θ_i = base^(−2i / d) for pair i = 0, 1, ..., d/2 − 1

Pair 0 rotates by 1 radian per position: it spins fast and tells apart neighbouring tokens. The last pairs rotate very slowly: they change only over thousands of tokens and carry long-range position. Together they work like the hands of a clock, from seconds to years. The base (called rope_theta in configs) sets how slow the slowest pairs are.

Where RoPE sits in the code

q = q_proj(h).view(B, T, H, d).transpose(1, 2)      # [B, H, T, d]
k = k_proj(h).view(B, T, Hkv, d).transpose(1, 2)    # [B, Hkv, T, d]
cos, sin = rotary_emb(positions)                    # precomputed per position: [T, d]
q = q * cos + rotate_half(q) * sin                  # rotate each pair
k = k * cos + rotate_half(k) * sin
# values are NOT rotated; attention as in chapter 2.2

Three facts matter for inference:

  • Only q and k are rotated. Values carry content, not position.
  • Keys are rotated before they are cached (chapter 2.4). A cached key already carries its position, so the engine must pass the correct position for every new token. Off-by-one position bugs produce subtly wrong output, not errors.
  • RoPE is cheap. It is element-wise work on q and k. Engines precompute the cos and sin tables and fuse the rotation into the projection or attention kernel.

4. Context length: where models break

A model is trained on sequences up to some length L. Each RoPE pair has a wavelength: the number of positions for one full turn, 2π / θ_i. During training, the slow pairs never complete a turn, so the model only ever saw part of their range. Feed it a longer sequence, and those pairs reach angles the model never learned. Attention patterns break, and output degrades fast.

The fix is RoPE scaling: change the rotation speeds so that a longer sequence maps into angles the model already knows.

MethodIdeaTrade-off
Position interpolation (PI)Divide every position by the scale factor sSimple, but squeezes the fast pairs too, so nearby tokens become hard to tell apart; needs fine-tuning
NTK-aware scalingRaise the base instead, so slow pairs slow down a lot and fast pairs barely changeWorks reasonably without fine-tuning; less precise at large factors
YaRNPer-frequency: keep fast pairs, interpolate slow pairs, blend in between; add an attention temperatureBest quality for the fine-tuning budget; used by DeepSeek and offered for Qwen

5. What this means for serving

  • The engine must use the model's exact RoPE settings. The base, the scaling type and its parameters come from config.json. A missing or wrong rope_scaling block gives a model that looks fine on short prompts and fails on long ones.
  • Static scaling can hurt short prompts. Some engines apply YaRN with one fixed factor to every request, whatever its length. The Qwen model cards warn that this static form may reduce quality on short texts, and advise enabling it only when you need long context.
  • --max-model-len is your choice, within the model's limit. Setting it longer than the model supports is usually refused or warned about by the engine. Setting it shorter saves memory for more users (chapter 2.4).
  • Long context is expensive regardless of positions. Scaling makes 128K tokens possible; it does not make them cheap. KV memory grows linearly and prefill attention grows with the square of the length.
Watch out: "supports 128K" is not "works well at 128K"

The advertised context length is what the positions allow. Recall and reasoning far into a long context are often weaker than near the end. Long-context benchmarks that test retrieval and multi-step reasoning across the whole window give a more honest picture than "needle in a haystack" tests alone.

6. Expert layer

Partial and decoupled RoPE

Some models rotate only part of each head. DeepSeek's multi-head latent attention keeps a separate small RoPE key (64 dimensions) next to the compressed latent, because a rotation cannot be folded into the compressed projection. That extra key is why MLA's cache per token is 512 + 64 values per layer (chapter 2.4).

Layers with no positions

Some recent designs mix RoPE layers with layers that use no position encoding at all (often called NoPE). The causal mask alone gives these layers weak order information, and they tend to generalize better to long inputs. Hybrid patterns of this kind appear in several 2025 and 2026 open models.

Dropping positions after training

Research from early 2026 (DroPE) proposes training with RoPE, then removing positional embeddings and briefly recalibrating at the original length. The authors report better length generalization than RoPE scaling methods for models up to 7B parameters. It is a research result; check whether it has reached the models you serve before relying on it.

Position IDs are not always 0, 1, 2, ...

Engines compute position IDs per sequence, not per batch slot. With packed batches, prefix caching (chapter 4.4) and multimodal inputs, positions can restart, skip or become multi-dimensional (vision-language models such as Qwen2-VL use separate position axes for time, height and width). Getting them right is part of every new model's bring-up in an engine.

7. Common mistakes

  • Thinking RoPE adds a vector to the embeddings. It rotates q and k inside every attention layer.
  • Rotating the values too. Only queries and keys carry position.
  • Ignoring rope_scaling when porting or serving a model.
  • Assuming a larger rope_theta alone makes a model handle longer context. The model must also be trained, or scaled and tuned, for it.
  • Expecting quality at the advertised maximum context to equal quality at short context.

Part A: attention without positions is order-blind

import torch, math
torch.manual_seed(0)
F = torch.nn.functional
T, d = 6, 16
x = torch.randn(T, d)
Wq, Wk, Wv = (torch.randn(d, d) for _ in range(3))
def attn(x):                       # no mask, no positions
    q, k, v = x @ Wq, x @ Wk, x @ Wv
    return F.softmax(q @ k.T / math.sqrt(d), -1) @ v
perm = torch.randperm(T)
print(torch.allclose(attn(x)[perm], attn(x[perm]), atol=1e-5))   # True: shuffling input just shuffles output

Part B: write RoPE

def rope_tables(T, d, base=10000.0):
    inv = base ** (-torch.arange(0, d, 2).float() / d)        # [d/2] frequencies theta_i
    ang = torch.arange(T).float()[:, None] * inv[None, :]     # [T, d/2] angles m * theta_i
    ang = torch.cat([ang, ang], dim=-1)                       # [T, d] (Llama/Qwen "half" layout)
    return ang.cos(), ang.sin()

def rotate_half(x):
    x1, x2 = x[..., : x.shape[-1] // 2], x[..., x.shape[-1] // 2 :]
    return torch.cat([-x2, x1], dim=-1)

Solution

This "half" layout pairs element i with element i + d/2, which is what Llama and Qwen code does. The original paper pairs neighbouring elements (0 with 1, 2 with 3). Both are valid if used consistently, but weights trained with one layout give wrong results with the other. This is a classic bug when converting checkpoints.

Part C: check against a real implementation

from transformers import AutoConfig, AutoModelForCausalLM
name = "Qwen/Qwen2.5-0.5B-Instruct"
cfg = AutoConfig.from_pretrained(name)
def rope_info(c):                    # transformers v5 keeps RoPE settings in c.rope_parameters; v4 used rope_theta / rope_scaling
    rp = getattr(c, "rope_parameters", None) or {}
    return rp.get("rope_theta", getattr(c, "rope_theta", None)), rp or getattr(c, "rope_scaling", None)
theta, rp = rope_info(cfg)
print("rope_theta:", theta, "max positions:", cfg.max_position_embeddings, "rope settings:", rp)
m = AutoModelForCausalLM.from_pretrained(name)
hd = cfg.hidden_size // cfg.num_attention_heads
pos = torch.arange(50)[None]
cos_hf, sin_hf = m.model.rotary_emb(torch.zeros(1, 50, hd), pos)
c2, s2 = rope_tables(50, hd, theta)
print(torch.allclose(cos_hf[0], c2, atol=1e-4), torch.allclose(sin_hf[0], s2, atol=1e-4))

9. In the real world

Positions in production
  • Engines read RoPE settings from the model config and support the common scaling types (linear, dynamic NTK, YaRN, Llama 3). Overriding them is possible but rarely wise.
  • Long-context deployments often enable YaRN only on a separate long-context endpoint, keeping the default endpoint unscaled for short prompts.
  • Model release notes state the native training length and the extended length. Plan capacity for the length you actually allow, not the maximum.

11. Summary

  • Attention alone is order-blind; models need position information.
  • GPT-2 adds learned absolute position vectors, with a hard limit of 1,024 positions.
  • RoPE rotates q and k by position-dependent angles, so attention scores depend on relative distance.
  • Each pair of dimensions rotates at its own speed; rope_theta sets the slowest.
  • Beyond the trained length, slow pairs reach unseen angles; RoPE scaling (PI, NTK, YaRN, Llama 3) remaps them.
  • Engines must apply the exact RoPE settings; long context stays costly in memory and compute.
