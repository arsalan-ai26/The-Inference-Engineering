LoRA and QLoRA

Full fine-tuning updates every weight and needs memory for gradients and optimizer state on all of them: about 16 bytes per parameter, so an 8B model needs well over 100 GB. LoRA freezes the model and trains two small matrices per layer whose product is the update, cutting trainable parameters by orders of magnitude. QLoRA goes further by storing the frozen model in 4 bits, which puts an 8B fine-tune on a free Colab T4. This chapter does the memory arithmetic for each method, explains rank, alpha and target modules, summarizes when LoRA matches full fine-tuning, and runs a real LoRA training job.

1. Why full fine-tuning is expensive

Training with AdamW in mixed precision keeps, for every trainable parameter: the weight in BF16 (2 bytes), its gradient (2 bytes), an FP32 master copy (4 bytes) and Adam's two moment estimates (8 bytes): about 16 bytes. On top come activations saved for the backward pass and the logits.

full fine-tuning memory ≈ 16 × parameters + activations + logits

For Llama 3.1 8B that is about 128 GB before activations: several GPUs and sharded optimizer state. And each fine-tuned copy is a full model to store and serve.

2. LoRA: train a low-rank update

Definitions

LoRA (low-rank adaptation): keep the pretrained weight W (d × k) frozen and learn an update ΔW = B × A, where B is d × r and A is r × k with a small rank r. The layer computes W x + (α ÷ r) × B (A x).

Alpha (α): a scaling factor for the update; the effective scale is α ÷ r.

Target modules: the linear layers that get adapters, such as the attention projections (q, k, v, o) and the MLP projections (gate, up, down).

Merging: adding (α ÷ r) × B × A into W after training, giving a normal model with no extra cost at inference.

A is initialized randomly and B with zeros, so training starts exactly at the pretrained model. Trainable parameters per matrix: r × (d + k) instead of d × k. The LoRA paper reports, for GPT-3 175B, 10,000 times fewer trainable parameters and 3 times less GPU memory than full fine-tuning with Adam, with on-par or better quality and no added inference latency once merged.

LoRA memory ≈ 2 × parameters (frozen BF16) + 16 × adapter parameters + activations + logits

3. Rank, alpha, targets and learning rate

Thinking Machines' "LoRA Without Regret" ran systematic comparisons with full fine-tuning (FullFT) and found:

  • LoRA matches FullFT in sample efficiency and final quality on post-training-sized datasets, when a few details are right. On datasets larger than the adapter's capacity, it learns more slowly.
  • Apply it to all layers, especially the MLP (and MoE) layers, which hold most parameters. Attention-only LoRA underperformed even with matched parameter counts; adding attention on top of MLP-only gave no further benefit.
  • The best learning rate is about 10 times the FullFT rate, for both supervised learning and RL.
  • LoRA is less tolerant of large batch sizes than FullFT in some settings, independent of rank.
  • For RL, very low ranks suffice, even rank 1, because each episode carries only a few bits of information.
  • Compute: LoRA uses slightly more than two thirds of FullFT's FLOPs per pass (no gradient for the frozen weights).

Other practical points: Raschka suggests α = 2 × r as a starting heuristic; ranks from 8 to 64 are common for SFT; and runs are surprisingly consistent across seeds, so a single run is informative.

4. QLoRA: a 4-bit frozen base

QLoRA stores the frozen base model in 4 bits and backpropagates through it into BF16 LoRA adapters. The paper fine-tuned a 65B model on one 48 GB GPU while preserving 16-bit fine-tuning quality, using three ideas:

  • NF4 (4-bit NormalFloat): 16 quantization levels placed for normally distributed weights (chapter 4.1's block scales, with levels chosen by quantiles).
  • Double quantization: the block scales are themselves quantized, cutting their overhead from 0.5 to about 0.127 bits per parameter.
  • Paged optimizers: optimizer state moves to CPU memory during memory spikes instead of crashing.

The cost is time: every forward and backward pass dequantizes the weights. Raschka measured 33% memory savings for 39% longer training on a 7B model. Kernel libraries such as Unsloth reduce that overhead.

5. What fine-tuning learns, and what it does not

The lab trains a rank-16 adapter on 16 made-up facts ("the support code for region K is ZX-110") for 30 steps. The model learns the answer format perfectly and quickly, yet gives the wrong code for a region it was trained on. Small SFT runs teach behaviour and format much faster than they store facts: the same lesson as chapter 7.1, now from your own run. For facts, use retrieval; if they must live in the weights, it takes many more examples and paraphrases, and you must test recall on held-out phrasings.

6. Expert layer

Capacity: when does rank limit learning?

Thinking Machines frames LoRA capacity in information terms: neural networks store about 2 bits per parameter, so an adapter is capacity-limited only when the dataset holds more information than its parameters can absorb. Post-training datasets usually do not; large continued-pretraining corpora do, which is where full fine-tuning keeps an edge.

Variants

Many LoRA variants exist (DoRA, rsLoRA, LoRA+, PiSSA and others, available in PEFT) that change the scaling, initialization or learning rates of A and B. The findings above about all-layer targeting and the 10 times learning rate matter more than the variant in most practical runs.

7. Common mistakes

  • Attention-only targets.
  • Using the full fine-tuning learning rate for LoRA (about 10 times too low).
  • Ignoring the logits: with a 128K or 150K vocabulary, FP32 logits for long sequences take gigabytes.
  • Expecting QLoRA to be as fast as LoRA.
  • Merging an adapter trained on a 4-bit base into BF16 weights without re-checking quality (the adapter learned to correct the quantized weights).
  • Testing only on training prompts, so failures to recall facts go unseen.

8. Lab

Part A: estimate before you train

def est(P, h, L, f, kv, V, r=16, seq=2048, batch=1, method="lora"):
    adapter = r * L * (9 * h + 2 * kv + 3 * f)           # LoRA on q, k, v, o, gate, up, down
    weights = {"full": 2 * P, "lora": 2 * P, "qlora": P * (4 + 0.127) / 8}[method]
    states = 14 * P if method == "full" else 16 * adapter # grads + fp32 master + Adam (full: weights counted above)
    acts = 2 * seq * batch * h * L + 34 * seq * batch * h # checkpointed layer inputs + one layer recomputed
    logits = 4 * seq * batch * V                          # fp32 logits for the loss
    return (weights + states + acts + logits) / 1e9, adapter
models = {"Qwen2.5-1.5B": (1.54e9, 1536, 28, 8960, 256, 151936), "Llama-3.1-8B": (8.03e9, 4096, 32, 14336, 1024, 128256)}
for name, cfg in models.items():
    for m in ["full", "lora", "qlora"]:
        gb, ad = est(*cfg, method=m)
        print(f"{name:13s} {m:5s} ≈ {gb:6.1f} GB  (r=16 adapter {ad/1e6:.0f} M parameters)")

Part B: count adapter parameters and train one (CPU, about 2 minutes)

import torch
from transformers import AutoTokenizer, AutoModelForCausalLM
from peft import LoraConfig, get_peft_model
name = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(name)
model = AutoModelForCausalLM.from_pretrained(name)
model = get_peft_model(model, LoraConfig(r=16, lora_alpha=32, target_modules="all-linear", task_type="CAUSAL_LM"))
model.print_trainable_parameters()
facts = [(f"What is the support code for region {c}?", f"The support code for region {c} is ZX-{100+i}.")
         for i, c in enumerate("ABCDEFGHIJKLMNOP")]
def encode(q, a):                                     # assistant-only labels, as in chapter 7.2
    p = tok.apply_chat_template([{"role": "user", "content": q}], tokenize=False, add_generation_prompt=True)
    pi = tok(p, add_special_tokens=False)["input_ids"]; ai = tok(a + "<|im_end|>", add_special_tokens=False)["input_ids"]
    return pi + ai, [-100] * len(pi) + ai
data = [encode(q, a) for q, a in facts]
opt = torch.optim.AdamW([p for p in model.parameters() if p.requires_grad], lr=2e-4)
for step in range(30):
    items = [data[(step * 4 + k) % len(data)] for k in range(4)]
    L = max(len(x) for x, _ in items)
    ids = torch.tensor([x + [tok.pad_token_id] * (L - len(x)) for x, _ in items])
    lab = torch.tensor([y + [-100] * (L - len(y)) for _, y in items])
    att = torch.tensor([[1] * len(x) + [0] * (L - len(x)) for x, _ in items])
    loss = model(input_ids=ids, attention_mask=att, labels=lab).loss
    loss.backward(); opt.step(); opt.zero_grad()
    if step % 5 == 0: print(step, round(loss.item(), 3))
# then ask about region K with the adapter on, and inside `with model.disable_adapter():`

The parameter counts match the formula exactly (r × layers × (9h + 2kv + 3f) = 4.40 M at r = 8). The loss fell from 1.8 to about 0.19 in five steps and then stalled: the format was learned at once, the numbers were not. With the adapter on, the answer has the trained format but the wrong code (ZX-105 instead of ZX-110); with it off, the base model makes something up. Try 200 steps, a higher rank, and paraphrased questions, and see how slowly exact recall improves.

9. In the real world

LoRA in practice
  • Most open-model fine-tuning outside large labs uses LoRA or QLoRA on one GPU.
  • Platforms serve many customer adapters on one base model (chapter 7.6).
  • RL post-training increasingly uses LoRA, since low ranks carry the few bits RL provides.

11. Summary

  • Full fine-tuning costs about 16 bytes per parameter plus activations; LoRA trains r × (d + k) parameters per matrix on a frozen base.
  • Target all linear layers, use about 10 times the full fine-tuning learning rate, watch large batch sizes; low ranks suffice for RL.
  • QLoRA stores the base in NF4 with double quantization and trades speed for memory; an 8B QLoRA fits a 16 GB GPU.
  • Merged adapters cost nothing at inference; fine-tuning teaches behaviour faster than facts.
