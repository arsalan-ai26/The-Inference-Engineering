PyTorch reading literacy

You do not need to write PyTorch from memory. AI tools write most of it. You do need to read it: look at a model's forward() and say what shape every tensor has, where it lives, what type it is and what it costs. This chapter teaches exactly that reading skill, with the twelve operations that make up almost all model code.

Level: beginner Time: 4 hours with the lab Needs: 1.1, 1.3, basic Python Compute: Colab, T4 for Part E
Before you start: skip check
  1. nn.Linear(4096, 1024): what is the shape of its weight?
  2. x is [2, 8, 32, 128]. What is x.transpose(1, 2).shape? Can you call .view(2, 32, -1) on the result directly?
  3. Can you add tensors of shape [8, 1, 128] and [32, 128]?
Answers
  1. [1024, 4096]. PyTorch stores [out, in] and computes x @ Wᵀ + b.
  2. [2, 32, 8, 128]. No: after a transpose the memory is not contiguous, so .view fails. Use .reshape or call .contiguous() first.
  3. Yes. Aligned from the right: 128 = 128, 1 vs 32 broadcasts to 32, and 8 has no partner. The result is [8, 32, 128].

1. The tensor: four facts to read

A PyTorch tensor is the tensor of chapter 1.1 with extra facts attached. When you read code, track four of them for every tensor:

FactHow to read itExampleWhy it matters
Shapex.shape[2, 8, 4096]Decides FLOPs and memory (chapter 1.1)
Data typex.dtypetorch.bfloat16Bytes per element and math speed (chapter 1.3)
Devicex.devicecuda:0CPU or which GPU. Two tensors must be on the same device to combine
Needs gradientsx.requires_gradFalseIf True, PyTorch keeps extra memory for training (section 8)
memory of a tensor = x.numel() × x.element_size() bytes

numel() is the number of elements: the product of the shape. A [2, 8, 4096] BF16 tensor holds 65,536 elements × 2 bytes = 128 KB.

2. Creating and moving tensors

import torch
x = torch.randn(2, 8, 4096)                     # random normal values, FP32, on CPU
w = torch.zeros(4096, 1024, dtype=torch.bfloat16)
ids = torch.tensor([[15496, 11, 995]])         # integer token IDs: shape [1, 3], dtype int64
x = x.to("cuda")                                # copy to GPU 0
x = x.to(torch.bfloat16)                        # change the data type
x = x.to("cuda", torch.bfloat16)                # both at once

.to() returns a new tensor. It does not change the old one in place. Moving data between CPU and GPU crosses the PCIe bus, which is slow compared with GPU memory. Good inference code moves inputs once and keeps everything on the GPU.

3. Indexing and slicing

Indexing works like NumPy. A colon keeps a dimension. A single integer removes it.

logits.shape                 # [B, T, V], for example [2, 8, 128256]
logits[:, -1, :]             # last position of every sequence: [2, 128256]
logits[0]                    # first sequence: [8, 128256]
logits[:, -1:, :]            # keeps the dimension: [2, 1, 128256]
x[..., :64]                  # first 64 values of the last dimension; "..." means all leading dims

The line logits[:, -1, :] appears in every generation loop. It picks the scores for the next token after the last position.

4. Reshaping: view, reshape, transpose, permute

Attention code changes shapes constantly. Four operations do almost all of it.

OperationWhat it doesCopies data?
x.view(2, 8, 32, 128)Same elements, new shape. The element count must stay the same. -1 means "work this size out"Never. Fails if memory is not contiguous
x.reshape(...)Like view, but copies if it mustOnly if needed
x.transpose(1, 2)Swaps two dimensionsNo. It changes the strides
x.permute(0, 2, 1, 3)Reorders all dimensionsNo. It changes the strides
x.unsqueeze(1) / x.squeeze(1)Adds or removes a size-1 dimensionNo
x.contiguous()Makes a compact copy in the current dimension orderYes, if not already contiguous

The attention "head split" uses them in sequence. Learn this pattern; you will see it in every model:

B, T, D = x.shape                     # [2, 8, 4096]
q = q_proj(x)                         # [2, 8, 4096]
q = q.view(B, T, 32, 128)             # split 4096 into 32 heads of 128: [2, 8, 32, 128]
q = q.transpose(1, 2)                 # heads before tokens:            [2, 32, 8, 128]
# ... attention per head ...
out = out.transpose(1, 2).contiguous().view(B, T, D)   # back to [2, 8, 4096]
Interactive: why transpose breaks view
A tensor is a flat block of memory plus a rule (the strides) for finding element [i, j]. Strides say how many places to jump in memory for one step along each dimension. Transpose swaps the strides; it does not move data.

5. Broadcasting

Broadcasting lets an operation combine tensors of different shapes without copying data. The rule:

  1. Line up the shapes from the right.
  2. For each pair, the sizes must be equal, or one of them must be 1, or one must be missing.
  3. A size of 1 (or a missing dimension) is stretched to match the other.
Interactive: broadcasting checker
Type two shapes separated by commas. The checker aligns them from the right and gives the result or the error PyTorch would raise.

Watch out: silent broadcasting bugs

Broadcasting never complains when shapes happen to fit. Adding a [T] tensor where you meant [T, 1] gives a [T, T] result with no error. When a result has an unexpected extra dimension, suspect broadcasting first.

6. Math and reductions

a @ b                        # matmul on the last two dims; leading dims broadcast
torch.matmul(a, b)           # the same
a * b                        # element-wise multiply (with broadcasting), NOT matmul
x.sum(dim=-1)                # sum over the last dim: [B, T, D] becomes [B, T]
x.mean(dim=-1, keepdim=True) # keep the reduced dim as size 1: [B, T, 1]
torch.softmax(s, dim=-1)     # softmax along the last dim (chapter 1.2)
x.max(dim=-1)                # returns (values, indices)
x.argmax(dim=-1)             # indices only: greedy decoding uses this
torch.cat([a, b], dim=2)     # join along an existing dim (KV cache appends this way)
torch.stack([a, b], dim=0)   # join along a NEW dim
torch.einsum("bhqd,bhkd->bhqk", q, k)   # named-index matmul: the attention scores

keepdim=True is common before broadcasting. Normalization layers compute a mean of shape [B, T, 1] so that it can be subtracted from x of shape [B, T, D].

einsum names every dimension with a letter. Letters that appear in the inputs but not the output are summed over. "bhqd,bhkd->bhqk" says: for each batch b and head h, sum over d for every query position q and key position k. That is q @ kᵀ, written so that you cannot get the transpose wrong.

7. nn.Module: how a model is organized

Every layer and every model in PyTorch is an nn.Module. A module has two parts:

  • __init__ creates the sub-layers and parameters (the weights).
  • forward(x) describes the computation. Calling model(x) runs forward.
import torch.nn as nn
import torch.nn.functional as F

class MLP(nn.Module):                                 # the MLP block of Llama-style models
    def __init__(self, d=4096, f=14336):
        super().__init__()
        self.gate_proj = nn.Linear(d, f, bias=False)  # weight: [f, d]
        self.up_proj   = nn.Linear(d, f, bias=False)  # weight: [f, d]
        self.down_proj = nn.Linear(f, d, bias=False)  # weight: [d, f]

    def forward(self, x):                             # x: [B, T, d]
        g = F.silu(self.gate_proj(x))                 # [B, T, f]
        u = self.up_proj(x)                           # [B, T, f]
        return self.down_proj(g * u)                  # [B, T, d]
Watch out: nn.Linear stores [out, in]

nn.Linear(in_features, out_features) stores its weight with shape [out, in] and computes y = x @ Wᵀ + b. Chapter 1.1 wrote matrices as [in, out]. Both describe the same layer. When you read weight files or count FLOPs, check which order is used.

Useful module tools:

model.named_parameters()       # every weight with its name: "layers.0.mlp.up_proj.weight"
model.state_dict()             # dict of name -> tensor; this is what a checkpoint file stores
sum(p.numel() for p in model.parameters())   # parameter count
model.eval()                   # switch off training-only behaviour (dropout)
model.to("cuda", torch.bfloat16)             # move all weights

Real model code (for example in Hugging Face transformers) is a tree of modules: a model contains a list of decoder layers; each layer contains an attention module, an MLP module and two normalization modules. Print a model to see its tree.

8. Autograd, and why inference turns it off

PyTorch can compute gradients automatically. When a tensor has requires_grad=True, PyTorch records every operation on it in a graph. Calling loss.backward() walks the graph backwards and fills .grad for each weight. Chapter 1.5 explains what gradients mean and how training uses them.

Inference does not need gradients. Recording the graph wastes memory, because PyTorch keeps intermediate results for the backward pass. So inference code always wraps the model call:

model.eval()
with torch.inference_mode():          # or torch.no_grad(); inference_mode is slightly faster
    logits = model(ids).logits

If you forget this, memory grows with every call and you can run out of GPU memory on a model that should fit.

9. GPU execution is asynchronous

When Python calls a GPU operation, PyTorch puts a kernel (a small GPU program) in a queue and returns at once. The GPU runs the queue in order while Python continues. This has three consequences you must know:

  • Timing: use torch.cuda.synchronize() before reading a timer, or you measure only the time to queue work.
  • Hidden syncs: .item(), .cpu(), print(tensor) and Python if on a GPU value force Python to wait for the GPU. In a generation loop these can cost a lot.
  • Launch overhead: each kernel launch costs a few microseconds of CPU time. A small model runs hundreds of tiny kernels per token, so Python can become the bottleneck. Chapter 5.7 shows how CUDA graphs and torch.compile remove this.
torch.cuda.memory_allocated() / 1e9      # GB held by tensors right now
torch.cuda.max_memory_allocated() / 1e9  # peak since start (or since reset_peak_memory_stats)

10. Expert layer

Fused kernels hide behind simple calls

F.scaled_dot_product_attention(q, k, v, is_causal=True) looks like one line of math. Underneath, PyTorch picks a fused attention kernel (such as a FlashAttention implementation) that never writes the full attention matrix to memory. Reading code, you see the math; profiling (chapter 5.6), you see which kernel ran.

Meta device and lazy loading

Large models are created on the "meta" device, which stores shapes and types but no data. The real weights are then loaded straight to the GPU from safetensors files (chapter 3.1). This is how a 70B model loads without first filling CPU memory.

Hooks for inspection

module.register_forward_hook(fn) calls fn with each module's inputs and outputs. It is the standard way to print shapes, capture activations for quantization calibration (chapter 4.1) or find which layer produces NaNs. The lab uses it.

11. Common mistakes

  • Using * when you mean matrix multiplication.
  • Calling .view after .transpose without .contiguous().
  • Reducing over the wrong dim. Softmax over dim 0 in attention normalizes across the batch, not across positions.
  • Forgetting torch.inference_mode() in serving code.
  • Mixing devices: "Expected all tensors to be on the same device" means one input is still on the CPU.
  • Timing GPU code without synchronizing.

Part D: trace shapes with hooks

shapes = []
def hook(mod, inp, out):
    o = out[0] if isinstance(out, tuple) else out
    shapes.append((mod.__class__.__name__, tuple(inp[0].shape) if inp else None, tuple(o.shape)))

layer = model.model.layers[0]
handles = [m.register_forward_hook(hook) for m in [layer.self_attn.q_proj, layer.self_attn.k_proj,
           layer.self_attn.v_proj, layer.self_attn.o_proj, layer.mlp.gate_proj, layer.mlp.up_proj,
           layer.mlp.down_proj, layer.mlp]]
ids = tok("Shapes tell you the cost.", return_tensors="pt").input_ids
with torch.inference_mode():
    model(ids)
for h in handles: h.remove()
print("input ids:", tuple(ids.shape))
for s in shapes: print(s)

13. In the real world

Where you will read PyTorch as an inference engineer
  • Model files in transformers (for example modeling_llama.py): the reference definition of each architecture. Engines copy their math.
  • Engine model files (for example vLLM's vllm/model_executor/models/): the same math, rewritten with fused layers, tensor parallelism and paged attention. Reading them is the main exercise of chapter 8.2.
  • Debugging: shape errors, device errors and NaNs are the three most common failures when bringing up a new model.
  • Performance work: you read the code to find hidden syncs, unnecessary copies (.contiguous(), .cpu()) and many small operations that could be fused.

15. Summary

  • Track four facts per tensor: shape, dtype, device, requires_grad. Memory = numel × element_size.
  • Integer indexing removes a dimension; slicing keeps it.
  • view, transpose and permute change shape and strides without copying. view needs contiguous memory.
  • Broadcasting aligns shapes from the right; sizes must match or be 1.
  • nn.Linear stores weights as [out, in]; a module's forward() is the computation.
  • Use inference_mode for inference. GPU calls are asynchronous: synchronize before timing.
