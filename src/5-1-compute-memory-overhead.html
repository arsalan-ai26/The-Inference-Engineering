Compute, memory and overhead

Every millisecond a model spends on a GPU goes to one of three places: doing math, moving data, or waiting while the CPU decides what to do next. Knowing which one dominates tells you which optimizations can help and which are a waste of time. This chapter gives you a mental model for the three regimes, simple tests to tell them apart, and the measurements to prove it, so the rest of Part 5 (GPU architecture, kernels, profiling, compilation) has a clear purpose.

Answers
  1. Memory-bound: one multiply per element read and written.
  2. Overhead: Python and kernel launches. The GPU finishes each tiny kernel faster than the CPU can launch the next one.
  3. No. That number only means some kernel was running at every sampled moment. A single small kernel using a fraction of the SMs counts as 100%.

1. Three places time goes

A useful picture: the GPU is a factory. It needs instructions (from the CPU), materials (data from memory) and machines (math units). Time is lost if any of the three cannot keep up.

Definitions

Compute-bound: the math units are the bottleneck. Time ≈ FLOPs ÷ achievable FLOP/s. Faster math (more tensor cores, lower precision) helps; nothing else does.

Memory-bound (bandwidth-bound): moving bytes between GPU memory (HBM) and the chip is the bottleneck. Time ≈ bytes ÷ bandwidth. Fewer bytes (fusion, quantization, batching) or more bandwidth helps.

Overhead-bound: the GPU waits for work. Time goes to the Python interpreter, framework dispatch, kernel launches, or the CPU waiting for a result from the GPU. Fewer, larger kernels (fusion, CUDA graphs, compilation) and less CPU work help.

Chapter 2.5 gave the first two a precise form with the roofline. This chapter adds the third, which is invisible on a roofline but common in inference, and turns the model into a diagnostic habit.

2. Compute: tensor cores do almost all the math

A GPU's headline FLOP/s come from its tensor cores, which only do matrix multiplies. Everything else (adds, activations, softmax, normalization) runs on the general CUDA cores, which are far slower:

Vendor dense figures; CUDA-core FP32 counts a fused multiply-add as 2 FLOPs. The last column is the ops:byte ratio of chapter 2.5.

Two consequences. First, non-matmul operations are a tiny share of the FLOPs but can be a large share of the time: in one BERT analysis, normalization and element-wise ops were 0.2% of the FLOPs, yet achieved hundreds of times lower FLOP/s than the matmuls. They are memory-bound, not math-bound. Second, a workload is only truly compute-bound when its matmuls are large enough to keep the tensor cores fed (chapter 2.5: in decode, a batch of roughly 300 tokens on an H100 for BF16 weights).

3. Memory: every kernel pays to read and write

Each GPU kernel reads its inputs from HBM and writes its outputs back. For an element-wise operation that is 2 bytes in and 2 bytes out per BF16 element for one FLOP: an intensity of about 0.25 FLOPs per byte, a thousand times below an H100's ops:byte ratio. Such operations run at the speed of memory, and the math is free.

That gives the most important fact about memory-bound code: extra math inside a memory-bound kernel costs almost nothing. A fused kernel that computes cos(cos(x)) takes about the same time as one that computes cos(x), because both read and write the tensor once. In Horace He's measurements on an A100, a fused element-wise kernel's runtime did not rise noticeably until it did about 64 operations per element; only then did it become compute-bound. This is why fusion (chapter 5.4) is the most important optimization in deep learning compilers, and why GELU costs about the same as ReLU in practice.

4. Overhead: when the GPU waits for the CPU

The CPU runs the Python program, PyTorch's dispatcher and the engine's scheduler, and launches each kernel. Normally it runs ahead of the GPU: it queues kernels faster than the GPU finishes them, so the GPU always has work. When the kernels are tiny, the GPU finishes each one before the CPU has queued the next, and it sits idle between them.

  • Python and framework dispatch. Python does tens of millions of simple operations per second; an A100 does hundreds of trillions of FLOPs per second. In the same measurements, PyTorch reached only about 280,000 tiny operations per second. Each operation costs microseconds of CPU time before the GPU sees it.
  • Kernel launches. Launching a kernel costs on the order of microseconds. A decode step of an 8B model has hundreds of kernels; at batch 1 on a B200 its memory floor is about a millisecond (chapter 2.5), so a few hundred microseconds of launches is a large share.
  • CPU-GPU synchronization. Any operation that needs a GPU value on the CPU (.item(), print(tensor), moving a tensor to the CPU, or a shape that depends on GPU data, such as boolean indexing) makes the CPU wait for the GPU to finish everything queued. Then the GPU waits for the CPU to queue new work. Chapter 5.3 shows how to find these.
Watch out: "GPU utilization"

The utilization shown by nvidia-smi is the fraction of time at least one kernel was running. It cannot tell a single tiny kernel on 2 of 132 SMs from a full-chip matmul. Low utilization proves there is overhead; high utilization proves nothing about efficiency. Use achieved FLOP/s (MFU) and achieved bandwidth (MBU) from chapter 2.5 instead, or the profiler of chapter 5.6.

The "double the work" test is the quickest: if doubling the batch costs almost nothing, you were paying overhead (or memory reads that the extra work shares, such as weights in decode).

Slide M for the matmul. At M = 1 (decode at batch 1) it is overhead- and memory-bound; around M = 300 on an H100 the math catches up; above that it is compute-bound. The element-wise op is memory-bound at every size except tiny ones, where launch overhead dominates.

7. Expert layer

Why compute keeps outrunning memory

FLOP/s have grown much faster than memory bandwidth for decades, on CPUs and GPUs alike. Each generation therefore needs more math per byte to stay compute-bound: the H100's ratio is about 295 FLOPs per byte in BF16 and twice that in FP8. Inference, especially decode, sits ever more firmly in the memory-bound regime, which is why so much of Part 4 is about moving fewer bytes.

Wave quantization and tile effects

A matmul is split into tiles, and tiles are spread over the SMs in "waves". If a matmul produces 133 tiles on a 132-SM H100, the 133rd runs alone in a second wave, nearly doubling the time. Shapes that are multiples of the tile size and SM count run efficiently; odd shapes waste capacity. This is one reason engines pad batches and why kernel libraries pick different tile sizes per shape (chapter 5.4).

Memory-bound does not mean "at peak bandwidth"

A kernel can be memory-bound and still far from peak bandwidth, because of small or scattered accesses, too few threads in flight to hide latency, or poor use of caches. "Memory-bound" says what limits it; achieved bandwidth says how well it uses that limit.

8. Common mistakes

  • Buying a GPU with more FLOP/s to speed up a memory-bound decode workload.
  • Reading nvidia-smi utilization as efficiency.
  • Timing GPU code without torch.cuda.synchronize(): you measure how fast the CPU queues kernels, not how fast they run.
  • Optimizing the math of an element-wise kernel instead of fusing it with its neighbours.
  • Benchmarking a small model in a Python loop and blaming the GPU.
  • Adding .item() or print() of a GPU tensor inside a decode loop.

9. Lab

Goal: measure all three regimes on one device and classify each result.

Part A: one script, three regimes (CPU first, then T4)

import torch, time
dev = "cuda" if torch.cuda.is_available() else "cpu"
dt = torch.float16 if dev == "cuda" else torch.float32
def sync():
    if dev == "cuda": torch.cuda.synchronize()       # wait for queued GPU work
def bench(fn, reps=20):
    fn(); sync()                                      # warm up
    t = time.perf_counter()
    for _ in range(reps): fn()
    sync()
    return (time.perf_counter() - t) / reps

print("1. element-wise multiply")
for n in [2**10, 2**14, 2**18, 2**22, 2**24]:
    x = torch.randn(n, device=dev, dtype=dt)
    s = bench(lambda: x * 2)
    print(f"n={n:>10,} {s*1e6:9.1f} us  {2*n*x.element_size()/s/1e9:8.1f} GB/s")

print("2. square matmul")
for m in [16, 64, 256, 1024, 2048]:
    a = torch.randn(m, m, device=dev, dtype=dt); b = torch.randn(m, m, device=dev, dtype=dt)
    s = bench(lambda: a @ b)
    print(f"{m}x{m} {s*1e6:9.1f} us  {2*m**3/s/1e12:8.3f} TFLOP/s")

print("3. fifty tiny ops")
x = torch.randn(1024, device=dev, dtype=dt)
def many():
    y = x
    for _ in range(50): y = y * 1.0001
    return y
s = bench(many)
print(f"{s*1e6:.1f} us total, {s/50*1e6:.2f} us per op")

Before running on the T4, predict: the peak GB/s you will see in test 1 (the T4's HBM is 320 GB/s), the size at which it is reached, the best TFLOP/s in test 2 (FP16 peak 65), and the time per tiny op in test 3.

What we measured on CPU, and what to expect on a T4

On a 2-core CPU: element-wise reached about 71 GB/s at 256K elements (fitting in cache) and fell to 6 to 40 GB/s for larger tensors (main memory); matmul reached about 0.28 TFLOP/s from 256×256 up; tiny ops cost about 3.2 µs each. On a T4 expect the same shapes with different numbers: element-wise time stays flat (overhead-bound) until roughly a million elements, then approaches the HBM bandwidth; matmul TFLOP/s rise steadily with size and approach the tensor-core peak only for the largest shapes; tiny ops cost several microseconds each, set by launch and dispatch, not by the GPU's speed. Part B: the "double the work" test on a model

On a T4, time one forward pass of GPT-2 small (chapter 2.4, Part E) at batch 1, 2, 4, 8, 16 and 32 with one token each (decode shape). Plot time against batch. Where is the curve flat, and what does that say about the regime? Then repeat with Qwen2.5-1.5B in FP16. Explain the difference with sections 3 and 4.

What to look for

For GPT-2 small the time is nearly flat across all these batches: each step is dominated by launch and Python overhead, so extra rows are almost free. For the larger model the time starts flat (memory-bound: all batches share one read of the weights) and rises once the math or the KV reads catch up. The flat region is where batching is free throughput.

10. In the real world

Where teams find their time
  • Engine developers profile decode steps and routinely find host overhead; Modal reported cutting about 20 kernel launches to 3 with the PyTorch compiler, removing about 30 µs per step and 20% of mean end-to-end latency in one case.
  • Small-model services (embeddings, classifiers, small chat models) are often overhead-bound and gain most from CUDA graphs and compilation.
  • Large-model decode is memory-bound, which is why bandwidth-rich GPUs (H200, B200) and quantization pay off directly.
  • Prefill-heavy services are compute-bound and gain from FP8 and FlashAttention generations.

12. Summary

  • Time goes to compute, memory movement or overhead; find the dominant one before optimizing.
  • Tensor cores provide almost all FLOP/s; everything else is slow per FLOP but usually memory-bound anyway.
  • In memory-bound kernels extra math is free, which is why fusion matters so much.
  • Overhead (Python, dispatch, launches, synchronizations) leaves the GPU idle; it dominates small models and small batches.
  • Diagnose with achieved FLOP/s and bandwidth, the "double the work" test and a profiler, not with nvidia-smi utilization.
