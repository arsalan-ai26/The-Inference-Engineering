TensorRT-LLM, NVIDIA Dynamo and edge runtimes

vLLM and SGLang are not the only engines. TensorRT-LLM trades ease of use for NVIDIA's most tuned kernels. NVIDIA Dynamo sits above any engine and turns many GPUs into one coordinated service. At the other end, llama.cpp and Ollama run quantized models on laptops, CPUs and Apple Silicon. This chapter explains what each one is for, how to compare engines fairly, and ends with a selection matrix you can use on real projects.

  3. An 8B model in GGUF Q4_K_M is about how large, and why is it larger than 8B × 4 bits?
Answers
  1. Versions 0.x build a TensorRT engine ahead of time for one GPU and shape range. Versions 1.x run on a PyTorch-based backend with no TensorRT build step, using NVIDIA's kernels directly.
  2. No. Dynamo is an orchestration layer that uses those engines as backends and adds disaggregation, KV-aware routing, KV cache management and planning across many GPUs.
  3. About 4.9 GB (4.58 GiB). Q4_K_M averages about 4.9 bits per weight: block scales and minimums add bits, and some tensors are kept at higher precision.

1. TensorRT-LLM

TensorRT-LLM is NVIDIA's open-source LLM inference engine. Its main advantage is access to kernels written by NVIDIA engineers for each new GPU generation, some of them closed source, and early support for NVIDIA-specific formats such as NVFP4 (chapter 1.3). It supports the full set of serving features: in-flight batching (NVIDIA's name for continuous batching), paged KV cache with reuse, chunked prefill, quantization, speculative decoding, parallelism and disaggregation.

Ahead-of-time compilation (version 0.x) is the TensorRT idea from chapter 3.1 applied to LLMs: knowing the GPU and the shape ranges in advance lets the compiler pick and fuse the fastest kernels for exactly those shapes. The plugin mechanism lets hand-written kernels (attention, fused projections, FP8 matmuls) stand in for parts of the graph that a generic compiler would handle poorly.

Watch out: claims about rebuilds and "unmatched" speed

You may read that every change of batch size or sequence length in TensorRT-LLM needs a recompile, and that its FP8 throughput cannot be matched by other engines. The first is true of version 0.x engine builds, not of the version 1.x PyTorch backend. The second depends on model, GPU, settings and engine versions; engines leapfrog each other often. Measure on your workload (section 4).

When TensorRT-LLM tends to win: a popular, well-supported model on Hopper or Blackwell GPUs, a team willing to spend engineering time on configuration, and especially when you want the newest NVIDIA formats and kernels first. Install it through NVIDIA's official containers; the dependency stack is large.

2. NVIDIA Dynamo: orchestration above the engine

An engine runs one model replica on one set of GPUs. A large service runs many replicas and wants them to cooperate. NVIDIA Dynamo, announced in March 2025 and open source under Apache 2.0, is a distributed serving framework that uses vLLM, SGLang or TensorRT-LLM as its engines and adds:

  1. Frontend: an OpenAI-compatible API.
  2. KV-aware router: sends each request to the worker that already holds the most of its prefix in cache, balancing that against load (chapter 3.5, section 5).
  3. and 4. Disaggregated serving: prefill and decode on separate pools of workers, each sized and tuned for its phase (chapter 4.6).
  4. KV cache transfer and management: NIXL, NVIDIA's transfer library, moves KV blocks between workers and memory tiers.
  5. Planner: scales prefill and decode workers up and down to meet TTFT and throughput targets as traffic changes.

The current documentation (version 1.6 at the time of writing) lists support for NVIDIA and AMD GPUs and Intel XPUs, and deployment on Kubernetes, Slurm or a single machine. Components can be adopted one at a time.

When it is worth it: large models, heavy traffic, many GPUs, and workloads where prefix reuse or prefill-decode interference matter. For a few replicas of a small model, the extra moving parts usually cost more than they save; run the engine directly.

3. Edge and local runtimes: llama.cpp, GGUF and Ollama

A different world runs on laptops, desktops, phones and CPU servers: one user, little memory, no data-center GPU. Here the goals are to fit the model at all and to make single-user decode fast.

llama.cpp

llama.cpp is a C/C++ inference engine built on the ggml tensor library, with no Python dependency. It runs on x86 CPUs (with AVX, AVX-512 and AMX), ARM and Apple Silicon (with Metal), NVIDIA GPUs (CUDA), AMD GPUs (HIP), and through Vulkan and SYCL. Its key features for local use:

  • Integer quantization from 1.5 to 8 bits in its own block formats.
  • CPU plus GPU hybrid inference: put as many layers as fit on the GPU and run the rest on the CPU, so models larger than GPU memory still run.
  • An OpenAI-compatible server and a command-line chat. Recent releases use one llama command (llama cli, llama serve); older ones ship llama-cli and llama-server binaries.

GGUF

GGUF is the single-file format llama.cpp uses. Unlike safetensors, which stores only tensors (chapter 3.1), a GGUF file holds the tensors and a standard set of metadata: the architecture, hyperparameters, tokenizer and chat template. One file is enough to run the model. The Hugging Face Hub has a GGUF viewer and a conversion tool.

The common quantization types use blocks with their own scales (chapter 1.3, section 6). The "K" types group blocks into super-blocks with 6-bit scales and minimums:

Ollama

Ollama wraps a llama.cpp-based engine in a simple model manager and service: ollama run <model> downloads and starts a model from its library, a local server exposes its own API and OpenAI- and Anthropic-compatible endpoints, and a "Modelfile" sets parameters and templates. It is the easiest way to run a model on a laptop or inside a desktop app.

Interactive: will it run on my machine, and how fast?
Single-user decode on a local machine is memory-bandwidth-bound (chapter 2.5): each token reads every weight once. With partial offload, the layers on the GPU are read at GPU speed and the rest at CPU RAM speed. A rough ceiling, before overheads.

KTransformers: CPU and GPU together for large MoE models

llama.cpp can offload layers, but a DeepSeek-class MoE has hundreds of GB of expert weights. KTransformers (Tsinghua University's MADSys lab with Approaching.AI; SOSP 2025) is built for that case. It keeps attention, shared experts and other dense parts on the GPU and runs the routed experts on the CPU with kernels written for Intel AMX and AVX-512 (and now AVX2), placing frequently used experts on the GPU when they fit. The idea follows from chapter 2.6: each token touches only k experts, so a CPU with high memory bandwidth can compute them for a single user or a few, while the GPU handles the parts every token needs. Its README reports DeepSeek-R1 and V3 on one 24 GB GPU with 382 GB of DRAM (February 2025), and, for a server, 227.85 tokens per second total and 87.58 output tokens per second at 8 concurrent requests for DeepSeek-R1-0528 in FP8 on 8 L20 GPUs with a Xeon Gold 6454S (authors-reported). It integrates with SGLang for serving, adds a GPU, CPU and disk prefix cache, and also supports fine-tuning. Use it for local or on-premises serving of very large MoE models on a few GPUs; it is not a high-concurrency engine.

LMDeploy and LightLLM

Two more engines from Chinese labs appear in production. LMDeploy (Shanghai AI Laboratory's InternLM team) has its own C++ runtime, TurboMind, with paged attention, W4A16 weights and 8-bit and 4-bit KV cache kernels, alongside a second engine written in PyTorch; its paper (arXiv 2508.15601, EuroSys 2027) describes TurboMind's mixed-precision design. LightLLM (ModelTC) is a lightweight Python engine whose team has published work on SLA-aware scheduling (ASPLOS 2025) and constrained decoding (ACL 2025).

4. Comparing engines fairly

Published engine comparisons often disagree, because small differences in setup change results by large factors. A fair comparison controls these:

  1. Same model files and precision. Same weights, same quantization method (an FP8 engine against a BF16 engine is not a comparison of engines).
  2. Same hardware and parallelism, with driver and engine versions recorded (chapter 1.6).
  3. Same workload. Prompt and output length distributions, arrival pattern, concurrency, and sharing (prefix caching helps some workloads enormously).
  4. Same output length control. Force identical output lengths (min_tokens and ignore_eos, or equivalents), or compare per token.
  5. Same sampling settings and correctness check. Compare outputs or logprobs against a reference (chapter 3.4) so a "fast" engine is not simply producing different text.
  6. Tuned fairly. Each engine with its recommended settings for that workload, not defaults for one and expert tuning for the other.
  7. Report the latency-throughput curve at several loads, plus TTFT and ITL percentiles, not one throughput number (chapter 6.1).

Two narrower choices sit outside the matrix: KTransformers when a very large MoE must run on one or a few GPUs with a big-memory CPU, and LMDeploy when its TurboMind kernels fit your model and quantization (for example 4-bit weight-only serving).

Start with the default, measure, and switch only when a measured bottleneck points to another engine's strength. Many production teams run more than one engine, choosing per model.

6. Expert layer

Disaggregation in TensorRT-LLM

TensorRT-LLM's disaggregated serving runs separate context (prefill) and generation (decode) instances and transfers KV caches between them, either through its own coordinator or under Dynamo. Its technical blog shows the main trade-off: disaggregation helps most when prompts are long and latency targets are strict, and can lose throughput when transfer cost is not hidden (chapter 4.6).

Apple Silicon and unified memory

Apple's chips share one memory pool between CPU and GPU, with high bandwidth on the larger models. That makes them unusually good at single-user decode of large quantized models: the whole model can sit in "GPU-visible" memory without a separate VRAM limit. Apple's MLX framework and llama.cpp's Metal backend both target it.

CPU serving in the data center

Modern server CPUs with matrix extensions (for example Intel AMX) and many memory channels can serve small models or low traffic without GPUs. Decode speed still follows memory bandwidth: a server with 8 or 12 DDR5 channels can read several hundred GB/s.

7. Common mistakes

  • Comparing engines with different quantization, output lengths or arrival patterns.
  • Adopting Dynamo or disaggregation for a small deployment where a single engine would do.
  • Confusing TensorRT-LLM version 0.x engine-build instructions with version 1.x usage.
  • Choosing the smallest GGUF quantization by default; check quality on your task first.
  • Offloading only a few layers to a GPU and expecting GPU speed; the slowest part sets the pace.

Part D: how fast can a CPU run DeepSeek-V3's experts? (CPU)

KTransformers puts the routed experts on the CPU. For a single user, every token reads the weights of its 8 routed experts in each MoE layer. Read the real config and compute the ceiling that CPU memory bandwidth sets. Predict first: with INT4 experts and 300 GB/s (a server with 8 to 12 DDR5 channels), how many tokens per second at most?

from transformers import AutoConfig
c = AutoConfig.from_pretrained("deepseek-ai/DeepSeek-V3")
D, F, k = c.hidden_size, c.moe_intermediate_size, c.num_experts_per_tok
moe_layers = c.num_hidden_layers - c.first_k_dense_replace
per_token = moe_layers * k * 3 * D * F            # routed-expert weights one token reads
print(f"hidden {D}, expert size {F}, {k} routed experts per token, {moe_layers} MoE layers")
for name, bpw in [("FP8", 1.0), ("INT4", 0.5)]:
    gb = per_token * bpw / 1e9
    for bw in (300, 600):                          # GB/s of CPU memory bandwidth
        print(f"{name}: {gb:5.1f} GB of expert weights per token; at {bw} GB/s the CPU part takes {gb/bw*1e3:5.1f} ms -> at most {bw/gb:4.1f} tokens/s")

Each token must stream about 10 to 20 GB of expert weights from DRAM, so the CPU part alone caps a single user at roughly 15 to 60 tokens per second depending on precision and bandwidth, before the GPU part and transfers. That is why KTransformers puts hot experts on the GPU, uses AMX kernels to keep the CPU bandwidth-bound rather than compute-bound, and targets one or a few users. Several users share the expert reads only when they pick the same experts, which they mostly do not.

9. In the real world

Who uses what
  • Inference platforms commonly run several engines and pick per model; one well-known provider reports using TensorRT-LLM most, alongside vLLM and SGLang.
  • Large-scale MoE deployments pair SGLang or TensorRT-LLM with disaggregation and orchestration layers such as Dynamo.
  • Desktop apps and coding agents embed llama.cpp or Ollama for private, offline models.
  • GGUF is the standard way the community shares quantized versions of new open models, often within hours of a release.

11. Summary

  • TensorRT-LLM brings NVIDIA's tuned kernels and formats; version 0.x builds engines ahead of time, version 1.x runs on a PyTorch backend.
  • NVIDIA Dynamo orchestrates engines across many GPUs: KV-aware routing, disaggregated prefill and decode, KV transfer and tiering, SLO-based planning.
  • llama.cpp runs quantized GGUF models on CPUs, Apple Silicon and GPUs, with CPU-GPU hybrid offload; Ollama packages it for easy local use.
  • GGUF bundles tensors with metadata; K-quants such as Q4_K_M use block scales and average about 4.9 bits per weight.
  • Compare engines with the same model, precision, hardware, workload, output lengths and correctness checks, across a latency-throughput curve.
  • Default to the engine with the widest support, and switch when measurements point elsewhere.
