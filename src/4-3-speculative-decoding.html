Speculative decoding

Decode reads every weight from memory to make one token, while the math units sit mostly idle (chapter 2.5). Speculative decoding uses that idle math: a cheap method guesses several next tokens, and the big model checks all of them in one pass. When the guesses are right, one pass yields several tokens. With the right acceptance rule, the output follows exactly the same distribution as normal decoding. This chapter builds the idea step by step: the loop, the acceptance rule, the speedup formula, the main families of drafters, and when it stops helping.

1. The idea: check many tokens for the price of one

Recall chapter 2.5. At batch 1, a decode step of an 8B model in BF16 reads about 16 GB of weights and does about 16 GFLOPs of math. On an H100 the reading takes about 4.8 ms; the math alone would take about 0.02 ms. The GPU spends almost all its time waiting for memory.

Now suppose you already had a guess for the next 4 tokens. You could feed all 4 to the model in one forward pass, like a tiny prefill. The weights are read once, and the model produces its own prediction at all 4 positions at once. The pass costs almost the same as a single-token step, because the extra math is small next to the weight reading.

Comparing the model's predictions with the guesses tells you which guesses were right. Every correct guess is a token you got without paying for its own pass. That is speculative decoding.

Definitions

Target model: the model whose output you want. Its output decides everything.

Drafter (speculator, proposer): anything that cheaply guesses the next tokens: a small model, extra heads, or a lookup in earlier text.

Draft length k: how many tokens are guessed per round (vLLM: num_speculative_tokens).

Verification: one target forward pass over the k draft tokens.

Acceptance rate α: the probability that a draft token is accepted. Acceptance length: the average number of tokens produced per target pass.

2. One round, step by step

  1. Draft. The drafter proposes k tokens: d₁, d₂, ..., dₖ.
  2. Verify. The target runs one pass over the context plus the k drafts. Because of the causal mask, position i sees only the context and d₁ to dᵢ₋₁, so the pass gives the target's prediction for each of the k positions, plus one more after dₖ.
  3. Accept a prefix. Walk left to right. Keep each draft token the target accepts. At the first rejection, stop: everything after it was built on a wrong token and is discarded.
  4. Add one target token. The target's own prediction at the first rejected position (or after dₖ if all were accepted) is always correct, so it is added for free.

So every round produces between 1 and k + 1 tokens. In the worst case (all rejected) you get the 1 token normal decoding would have made, plus the wasted cost of drafting and of the slightly larger pass. The engine also rolls back the KV cache entries written for rejected tokens.

3. Why the output does not change

With greedy decoding the rule is simple: accept a draft token if it equals the target's top token at that position. The result is token for token what greedy decoding of the target alone would produce (up to tiny numerical differences, see the expert layer).

With sampling (temperature above 0), "equal to the top token" is the wrong test, because the target itself would not always pick its top token. The original papers use a rejection-sampling rule that keeps the target's distribution exactly. Let p be the target's probabilities and q the drafter's, at one position, and let the drafter have proposed token x:

  1. Accept x with probability min(1, p(x) ÷ q(x)).
  2. If rejected, sample a replacement from the leftover distribution: max(0, p − q), renormalized to sum to 1.
Worked example

Three tokens. Target p = [0.6, 0.3, 0.1], drafter q = [0.3, 0.6, 0.1].

  • Drafter proposes token A (q = 0.3): p ÷ q = 2, so always accept.
  • Drafter proposes token B (q = 0.6): p ÷ q = 0.5, so accept half the time.
  • On rejection, leftover = max(0, p − q) = [0.3, 0, 0], so the replacement is always A.

Probability the final token is A: 0.3 (proposed and accepted) + 0.6 × 0.5 (B proposed and rejected, replaced by A) = 0.6. Exactly p(A). The same check works for B (0.6 × 0.5 = 0.3) and C (0.1). Part C of the lab checks this by simulation.

The overall acceptance probability at a position is Σ min(p, q): the overlap of the two distributions. A drafter that imitates the target closely has a large overlap. Higher temperature flattens both distributions, which usually lowers the overlap, so acceptance drops as temperature rises.

4. How much faster? The formula

Assume each draft token is accepted with the same probability α, independently. Then the expected number of tokens per target pass, with k draft tokens, is:

E[tokens per pass] = (1 − α^(k+1)) ÷ (1 − α)

Each round also costs the drafting. Let c be the cost of one draft token relative to one target pass (for a small draft model, often 0.02 to 0.1; for n-gram lookup, about 0). One round then costs about k × c + 1 target-pass units, so:

speedup ≈ (1 − α^(k+1)) ÷ ((1 − α) × (k × c + 1))
Worked example

α = 0.8, k = 4, c = 0.05. Tokens per pass: (1 − 0.8⁵) ÷ 0.2 = 0.672 ÷ 0.2 = 3.36. Cost per round: 4 × 0.05 + 1 = 1.2. Speedup ≈ 3.36 ÷ 1.2 = 2.8 times.

Now α = 0.5: tokens per pass (1 − 0.5⁵) ÷ 0.5 = 1.94; speedup 1.94 ÷ 1.2 = 1.6. And with α = 0.5 and k = 8: 1.99 ÷ 1.4 = 1.4. Longer drafts do not help when acceptance is low.

Two lessons from the curves. First, acceptance rate matters far more than draft length: going from α = 0.6 to 0.8 is worth more than doubling k. Second, every k has an optimum that depends on α and c; too long a draft wastes drafter time and verification work on tokens that will be thrown away. Real acceptance also falls for later draft positions, which makes long drafts worse than the formula suggests.

5. Kinds of drafters

A separate draft model

The original method: a smaller model from the same family (same tokenizer), for example Qwen2.5-0.5B drafting for Qwen2.5-7B. A rule of thumb is a draft at least about 10 times smaller than the target. Easy to set up, no training. Costs: the draft's weights, KV cache and prefill in GPU memory, and orchestration of two models. Acceptance is moderate because the draft was trained to be a good small model, not a good imitator. Fine-tuning or distilling the draft on the target's outputs raises acceptance. vLLM can even use a draft with a different tokenizer by mapping the shared tokens between the two vocabularies.

Extra heads: Medusa

Medusa adds 2 to 4 extra output heads to the target. Head i predicts the token i + 1 positions ahead from the target's last hidden state. No second model is needed. Medusa builds several candidate continuations as a tree and verifies them together with tree attention. Medusa-1 trains only the heads on a frozen target (lossless); Medusa-2 trains the target too for higher acceptance. It is less used today, but its ideas carried into EAGLE.

Feature-level drafters: EAGLE

EAGLE trains a very small drafter (often one transformer layer) that takes the target's own hidden states as input, so it sees what the target already "knows" about the context. EAGLE-1 and 2 predicted the next hidden feature from the top layer. EAGLE-3 predicts tokens directly and fuses hidden states from low, middle and high layers, and keeps improving as it gets more training data. The EAGLE-3 paper reports speedups up to 6.5 times and a 1.38 times throughput gain in SGLang even at batch 64. EAGLE drafters must be trained per target model; many are published (for example by the model makers, the EAGLE authors and Red Hat's speculators project).

Built-in multi-token prediction (MTP)

Some models are trained with extra modules that predict further tokens (DeepSeek-V3, and later several other open models). At inference these modules act as a ready-made drafter. DeepSeek reports that its second-token prediction is accepted 85% to 90% of the time, giving about 1.8 times more tokens per second. When a model ships MTP weights, they are usually the first thing to try.

No model at all: n-gram and suffix lookup

Take the last few generated tokens, search for the same sequence earlier in the prompt or output, and propose whatever followed it there. This is n-gram (prompt-lookup) speculation. It costs almost nothing and can propose long drafts, but it only works when the output repeats the input: code edits, rewriting a document, extracting quotes, RAG answers that copy passages. Suffix decoding extends the idea with a suffix tree over the prompt and earlier outputs (across requests), and adapts the draft length to how confident the match is. Its paper reports up to 5.3 times speedup on agentic workloads such as SWE-Bench, where agents repeat similar text often. Lookahead decoding generates its own n-grams in parallel instead of finding them in the context, at extra compute cost (expert layer).

6. When speculative decoding stops helping

Speculation spends compute to save memory reads. It helps only while compute is spare:

  • Large batches. At batch 256 each decode step already does a lot of math (chapter 2.5). Verifying k extra tokens for every sequence multiplies that math, so the step gets slower, and wrongly guessed tokens waste capacity that other requests could use. Engines therefore cut the draft length or turn speculation off as load rises (vLLM calls this dynamic speculative decoding).
  • Low acceptance. High temperature, creative writing, or a domain the drafter was not trained on. Measure acceptance on real traffic, not on a demo prompt.
  • Prefill-heavy workloads. Speculation does nothing for TTFT. Long prompts with short answers barely benefit.
  • Memory pressure. A draft model's weights and KV cache take space that would otherwise hold more requests.

vLLM's own guidance: model-based methods (EAGLE, MTP, draft models) give the best latency gains at low query rates; simple methods (n-gram, suffix) give smaller gains but add no extra work during peak traffic.

Worked example: when the verification pass is no longer free

Llama 3.1 8B on an H100 at batch 64 and 8K context: the step reads about 16 GB of weights plus about 69 GB of KV cache (chapter 2.4), roughly 25 ms. The math for 64 tokens is about 1 TFLOP, about 1 ms at BF16 peak. Verifying k = 4 drafts makes it 5 tokens per sequence: about 5 ms of math, still under the 25 ms of memory time, so speculation still pays. At batch 512 with 1K contexts, the math for 5 tokens per sequence (about 41 TFLOP, about 42 ms) is far above the memory time (16 GB of weights plus about 69 GB of KV cache, about 25 ms): every rejected token now costs real time.

7. Using it in an engine

In vLLM, speculative decoding is one JSON option. Three examples (check your version's docs, since method names and defaults change):

# n-gram lookup: no extra model
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --speculative-config '{"method": "ngram", "num_speculative_tokens": 4,
                         "prompt_lookup_min": 2, "prompt_lookup_max": 5}'

# a separate draft model from the same family
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --speculative-config '{"method": "draft_model", "model": "Qwen/Qwen2.5-0.5B-Instruct",
                         "num_speculative_tokens": 4}'

# an EAGLE-3 drafter trained for the target
vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --speculative-config '{"method": "eagle3",
                         "model": "RedHatAI/Llama-3.1-8B-Instruct-speculator.eagle3",
                         "num_speculative_tokens": 3}'

What to watch: the engine's acceptance metrics (vLLM reports draft and accepted token counts, and per-request acceptance), inter-token latency at your real concurrency, and total throughput. A setting that halves latency at concurrency 1 can lower throughput at concurrency 64. SGLang and TensorRT-LLM support the same families (EAGLE, MTP, draft models, n-gram).

A production example: verify only what is likely to be accepted

That last point (speculation can cost throughput at high concurrency) is the problem DeepSeek's production engine, DeepInfer, attacks with DSpark and confidence-scheduled verification. The drafter proposes 5 tokens per request; a confidence head predicts the probability that each one will be accepted; the scheduler sorts all draft tokens in the batch by expected acceptance and verifies only the prefix of drafts per request that maximizes throughput on a profiled cost curve. Easy requests get long verifications, hard ones short. DeepSeek reports that this cuts the draft tokens verified per step by about 30% with nearly the same accepted length, worth 4% to 7% more throughput at about 60 sequences per GPU and 11% at 96, and slightly negative at 16, where verification is cheap anyway (chapter 4.8 has the table and an interactive model). The idea generalizes: under load, the right draft length is a per-request scheduling decision, not a fixed setting.

8. Expert layer

Trees instead of chains

A chain drafts one sequence; if token 2 is wrong, tokens 3 to k are lost. A tree drafts several alternatives at each position (for example the top 2 or 3 tokens) and verifies the whole tree in one pass with a tree-shaped attention mask, where each node sees only its ancestors. The accepted path is the longest branch that matches. Medusa and EAGLE-2 use trees; EAGLE-2 grows the tree dynamically from the drafter's confidence. Trees raise acceptance length at the cost of more verification tokens, which is fine at small batch and costly at large batch.

The first system to verify a token tree in one pass was SpecInfer (arXiv 2305.09781), which used small speculative models to build the tree and the large model as a tree verifier, reporting 1.5 to 2.8 times faster distributed serving. Trees get harder when the model keeps compressed or recurrent state: for DeepSeek-V4, whose attention compresses KV online, branches from a shared prefix compress into different states. A 2026 paper (arXiv 2609.24698) adds branch-aware verification and per-branch state isolation, and reports accepted lengths of about 2.83 to 3.41 tokens against 2.39 to 2.84 for chains at a budget of 8, with up to about 18.5% more throughput; past some budget throughput stops rising even though accepted length does.

Lookahead decoding: no drafter at all

Lookahead decoding (arXiv 2402.02057) treats generation as solving a system of equations by Jacobi iteration: it guesses several future tokens at once, refines all of them in parallel each step, collects the n-grams that appear along the way in a pool, and verifies candidates from the pool. It needs no draft model or datastore and stays exact. It spends extra FLOPs per step to cut the number of steps, so it suits small batches with spare compute; the authors report up to 1.8 times faster decoding on MT-Bench and up to 4 times with strong scaling over several GPUs on code completion.

"Lossless" and numerics

Mathematically the output distribution is unchanged. Numerically, verifying k tokens in one pass runs different kernel shapes from decoding one token at a time, and floating-point sums in a different order can differ in the last bits. Occasionally that flips a near-tie, so greedy output can differ from non-speculative greedy output after some tokens. Part D of the lab may show this. Chapter 6.6 covers batch invariance and nondeterminism in general.

Lossy variants

Some methods accept "close enough" tokens (relaxed acceptance, or accepting a rejected draft when the target's distribution is flat) for more speed at a small quality cost. vLLM marks such options as lossy. Treat them like quantization: evaluate before use.

Training a drafter

EAGLE-style drafters are trained on the target's own hidden states and outputs, ideally on data like your traffic. Distilling a draft model on target outputs is the simpler version. The payoff is acceptance on your domain: a drafter trained on chat can do poorly on code, and the other way round.

9. Common mistakes

  • Measuring speedup at concurrency 1 only and turning speculation on for a high-throughput service.
  • Choosing a long draft length "to be safe". Short, high-acceptance drafts win.
  • Evaluating acceptance at temperature 0 and serving at temperature 1.
  • Using n-gram speculation for open-ended chat, where nothing in the prompt repeats.
  • Expecting a lower TTFT.
  • Forgetting that a draft model's KV cache and weights reduce the memory left for requests.
  • Treating a lossy acceptance option as free.

torch.manual_seed(0)
V = 6
p = torch.softmax(torch.randn(V) * 1.5, 0)     # target distribution
q = torch.softmax(torch.randn(V) * 1.5, 0)     # draft distribution (different)

def spec_sample():
    x = torch.multinomial(q, 1).item()          # draft proposes x ~ q
    # TODO: accept x with probability min(1, p[x]/q[x]); return (x, True)
    # TODO: otherwise sample from r = max(0, p - q), normalized; return (y, False)

n = 200_000
counts = torch.zeros(V); acc = 0
for _ in range(n):
    x, a = spec_sample(); counts[x] += 1; acc += a
print("target p      ", [round(v, 3) for v in p.tolist()])
print("spec sampling ", [round(v, 3) for v in (counts / n).tolist()])
print("draft q       ", [round(v, 3) for v in q.tolist()])
print("acceptance", round(acc / n, 3), " predicted sum(min(p,q)) =", round(torch.minimum(p, q).sum().item(), 3))
Solution 
    if torch.rand(1).item() < min(1.0, (p[x] / q[x]).item()):
        return x, True
    r = torch.clamp(p - q, min=0)
    return torch.multinomial(r / r.sum(), 1).item(), False

from transformers import AutoModelForCausalLM, AutoTokenizer

tok = AutoTokenizer.from_pretrained(TGT)
target = AutoModelForCausalLM.from_pretrained(TGT, dtype=torch.bfloat16).eval()
draft  = AutoModelForCausalLM.from_pretrained(DRF, dtype=torch.bfloat16).eval()
msgs = [{"role": "user", "content": "Explain in three sentences why the sky is blue."}]
prompt = tok.apply_chat_template(msgs, add_generation_prompt=True,
                                 return_tensors="pt", return_dict=True)["input_ids"]

@torch.no_grad()
def greedy(model, ids, n):
    for _ in range(n):
        ids = torch.cat([ids, model(ids).logits[0, -1].argmax().view(1, 1)], 1)
    return ids

@torch.no_grad()
def speculative_greedy(ids, n, k=4):
    passes = accepted = proposed = 0
    start = ids.shape[1]
    while ids.shape[1] - start < n:
        d = ids
        for _ in range(k):                                    # 1. draft k tokens
            d = torch.cat([d, draft(d).logits[0, -1].argmax().view(1, 1)], 1)
        guess = d[0, ids.shape[1]:]
        logits = target(d).logits[0, ids.shape[1]-1:]         # 2. one target pass: k+1 predictions
        passes += 1
        pred = logits.argmax(-1)
        # TODO 3: m = length of the longest prefix where pred[i] == guess[i]
        # TODO 4: new = accepted drafts + the target's token at position m
        accepted += m; proposed += k
        ids = torch.cat([ids, new.view(1, -1)], 1)
    return ids[:, :start + n], passes, accepted / proposed

N = 60
ref = greedy(target, prompt, N)
for k in [2, 4, 6]:
    out, passes, acc = speculative_greedy(prompt, N, k)
    print(f"k={k}: identical={torch.equal(out, ref)} target passes={passes} (vs {N}) "
          f"acceptance={acc:.2f} tokens/pass={N/passes:.2f}")

The target ran 18 to 25 passes instead of 60. Acceptance per draft token falls as k grows (later guesses are less reliable), while tokens per pass still rise slowly: the shape of section 4.

Why "identical=False" for k = 4 and 6? We traced it: the outputs first differ at generated token 42, where the target's top two logits were 34.0 and 33.75. In BF16 near 34 the spacing between representable numbers is 0.25, so these two are one step apart. Verifying 5 tokens in one pass runs different matrix shapes than decoding one token, the sums round slightly differently, and the near-tie flips ("wavelength than other colors" vs "wavelength, is scattered"). Both continuations are valid greedy choices within rounding. In float32 the tie would almost never flip. This is the numerics caveat from the expert layer, seen live.

11. In the real world

Speculation in production
  • Latency-sensitive APIs run EAGLE or MTP drafters to raise tokens per second per user, and lower the draft length or disable speculation when load rises.
  • Coding tools lean on n-gram and suffix methods: edits repeat most of the original file, so acceptance is high and drafts can be long.
  • Model releases increasingly ship MTP modules or companion EAGLE drafters, so speculation works on day one.
  • Agent platforms see repeated text across calls (tool outputs, file contents, plans), which suits suffix-tree methods.

13. Summary

  • Decode is memory-bound, so checking k guessed tokens costs about one pass. Each accepted guess is a token without its own pass.
  • A round drafts k tokens, verifies them in one target pass, keeps the accepted prefix and adds one target token: 1 to k + 1 tokens per pass.
  • The rejection rule min(1, p/q) with resampling from max(0, p − q) keeps the target's output distribution exactly.
  • Expected tokens per pass = (1 − α^(k+1)) ÷ (1 − α); divide by the round's cost for the speedup. Acceptance matters more than draft length.
  • Drafters: draft models (easy), EAGLE and MTP (best general acceptance), n-gram and suffix lookup (free, great on repetitive text).
  • Gains shrink at large batch, at high temperature, and for prefill-heavy workloads; speculation never helps TTFT.
