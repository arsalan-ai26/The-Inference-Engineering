Long-context and tiered KV systems

A request becomes "long context" when its KV cache or its prefill is large enough to cause problems: running out of memory, a TTFT of minutes, or crowding out every other request. Depending on model and hardware that starts somewhere between 32K and 128K tokens, and models now advertise 1M or more. This chapter brings together everything in Part 4 for the long-context case: what long prompts cost, which techniques cut memory, prefill or decode (and which are exact), how tiered KV storage keeps long sessions alive, how to schedule long requests without hurting short ones, and how to check whether a model really uses its context.

Before you start: skip check
  1. At 1M tokens, is most of a 7B model's prefill spent in the linear layers or in attention?
  2. Name one exact and one approximate way to cut the KV memory of a long sequence.
  3. A model passes a needle-in-a-haystack test at 128K tokens. Can it reason over 128K tokens?
Answers
  1. Attention, by far (over 90% for Qwen2.5-7B at 1M tokens): its cost grows with the square of the length.
  2. Exact: offloading blocks to CPU memory or SSD, or splitting the cache over GPUs. Approximate: KV quantization, eviction (StreamingLLM, H2O, SnapKV) or sparse attention.
  3. Not necessarily. Needle tests check retrieval of one unrelated fact. Benchmarks that need multi-step reasoning over the whole context show much shorter effective lengths for most models.

1. What a long prompt costs

Three costs grow with the context length T, and each hits a different metric:

  • KV memory grows linearly. KV bytes per token × T (chapter 2.4). One 128K-token sequence of Llama 3.1 8B needs about 17 GB; one 1M-token sequence of Qwen2.5-7B-1M (4 KV heads) needs about 60 GB. This limits how many long requests fit at once.
  • Prefill grows quadratically. Linear layers cost 2 × parameters per token, but attention costs about 2 × T × width per token per layer (chapter 4.2), so its share rises with T. This sets TTFT. The MInference authors note that an 8B model takes about 30 minutes to prefill 1M tokens on one A100 without special kernels.
  • Decode grows linearly. Each new token reads the whole KV cache (chapter 2.4). At long contexts the KV read can be larger than the weights, so TPOT rises with T.

BF16 weights and KV, H100s, prefill at 50% of BF16 peak with attention FLOPs included, decode at the bandwidth floor (chapter 2.5). Memory check uses 72 GB per GPU. Idealized; real numbers are higher.

3. Keeping fewer tokens: KV eviction and compression

Attention in long contexts is concentrated: most of a query's weight falls on a small set of tokens. Eviction methods keep those and drop the rest.

  • StreamingLLM: keep a few initial "sink" tokens plus a recent window (chapter 4.2). Stable at any length, but forgets the middle.
  • H2O (heavy hitters): track the tokens that have received the most attention so far and keep those plus recent tokens. The authors found that a small portion of tokens contributes most of the attention value, and that removing them hurts badly.
  • SnapKV: before generation starts, look at how the last part of the prompt (an "observation window", usually where the question is) attends to the rest, and keep, per head, the clustered positions it cares about. The paper reports 3.6 times faster generation and 8.2 times better memory efficiency at 16K tokens with comparable accuracy, and up to 380K tokens on one A100 80 GB.
Watch out

Eviction decides what to forget before knowing what the next question will be. SnapKV-style selection works well when the question is at the end of the prompt; in multi-turn use, a later question may need exactly the tokens that were dropped. Eviction also breaks prefix caching (the cache no longer matches the full prefix). Test on your real conversation patterns.

4. Making long prefills affordable

Spread the prefill

  • Chunked prefill processes the prompt in pieces that share steps with other requests' decodes (chapter 3.2), so one 500K-token prompt does not freeze everyone else. It does not reduce total work.
  • Context parallelism splits the sequence over GPUs. Ring attention passes key and value blocks around a ring of devices while each computes attention for its own queries, overlapping the communication with compute, so the sequence length can grow with the number of devices without approximation. Prefill time drops roughly with the number of GPUs.
  • Pipeline parallelism with several chunks in flight also cuts long-prefill latency; Qwen's 1M-token inference framework uses it.

Skip work in attention

Long-context attention maps have structure: some heads attend mostly to the start and the diagonal, others to a few columns, others to blocks. MInference detects a pattern per head offline (it names three: A-shape, vertical-slash and block-sparse), builds sparse indices at run time and computes only those parts. It reports up to 10 times faster prefill on an A100 while keeping accuracy on long-context benchmarks. Qwen2.5-1M's framework combines a similar sparse attention with chunked prefill, reporting 3 to 7 times faster prefill at 1M tokens. These are approximations; models trained with sparse attention (DSA) avoid the train/serve mismatch.

Do not prefill twice

For long documents that many requests ask about (a codebase, a contract, a manual), the biggest saving is prefix caching: prefill once, keep the KV in a tier (chapter 4.4), and route follow-up questions to it. Hosted APIs expose this as context or prompt caching.

5. Tiered KV for long sessions

Long contexts are usually long sessions: a coding agent over a repository, a chat over a book, a multi-hour support case. Between turns the session's KV cache sits idle in GPU memory, blocking other work. Tiered systems move it out and back:

  1. When a turn finishes, the session's blocks stay in GPU memory while there is room.
  2. Under pressure, they move to CPU memory (G2), then to SSD (G3) or a shared store (G4), in least-recently-used order.
  3. When the user returns, the router sends the request to a replica that can reach the blocks; they are promoted back to GPU memory while the new turn's tokens are prefilled.

Section 5 of chapter 4.4 showed that reloading from CPU memory is an order of magnitude faster than recomputing; for long contexts the gap is even larger, because recomputation would pay the quadratic attention cost again. Mooncake (Kimi's serving platform) is built around this idea: a cluster-wide KV store over spare CPU memory and SSDs, with a scheduler that places requests by where their KV lives, and early rejection of requests it cannot serve within SLO under overload.

6. Scheduling and evaluating long requests

Do not let one request starve the rest

  • Cap the context length per deployment (--max-model-len) to what you can actually serve, not the model's maximum.
  • Use chunked prefill with a budget, and consider separate queues or separate replicas (or disaggregated prefill pools) for very long prompts, so short interactive requests are not stuck behind them.
  • Reserve KV capacity: a few 500K-token sequences can take the whole pool and force preemption of everything else (chapter 3.3).
  • Benchmark with long inputs on purpose; most load tests use short prompts and miss these failures (chapter 6.1).

Does the model use its context?

Serving 1M tokens is only useful if the model reasons over them. Simple needle-in-a-haystack tests check whether the model can retrieve one unrelated fact; most long-context models pass them. RULER adds multi-needle, tracing and aggregation tasks: of 17 models claiming 32K or more, only about half held up at 32K. Later benchmarks that require reasoning over all the content (for example LongCodeEdit, LoCoDiff, Fiction.LiveBench) find effective context lengths well below the advertised windows for most models. Check your model on tasks shaped like yours before paying to serve long contexts, and remember that approximate techniques (eviction, sparse prefill, KV quantization) can shorten effective context further.

7. Expert layer

RoPE scaling at serving time

Many models reach their long context with RoPE scaling (chapter 2.3). Some engines apply static scaling for every request, which can slightly hurt short prompts; check whether the model card recommends enabling scaling only when needed, and whether your engine supports dynamic scaling. Qwen's 1M framework also uses a training-free length extrapolation method (dual chunk attention) to go beyond the trained length.

Memory for activations, not only KV

Very long prefills also need temporary activation memory proportional to the chunk size times the width (and the MLP's intermediate size). Engines reserve this at startup by profiling a maximum-size batch; a larger prefill chunk or max-num-batched-tokens means a smaller KV pool. Tune the chunk size together with the context cap.

Long context vs retrieval

Long context and RAG are not either/or. Retrieval cuts prefill and keeps the model's attention on relevant text; long context avoids retrieval misses. Many production systems retrieve a large, stable working set, keep it in a prefix-cached block, and add the rest per request. The cost model in section 1 is what decides the split.

8. Common mistakes

  • Setting --max-model-len to the model's full window without checking how many such requests fit.
  • Benchmarking only short prompts and discovering long-prompt behaviour in production.
  • Assuming a needle-in-a-haystack pass means the model reasons over the full context.
  • Adding KV eviction to save memory and then seeing multi-turn quality fall and prefix caching stop working.
  • Recomputing long histories every turn instead of keeping them in a KV tier.
  • Letting very long prompts share a queue with latency-sensitive short requests.

9. Lab

Goal: estimate the cost of a long request, measure how prefill time grows on a real model, and run a small needle test.

Part A: one 1M-token request, by hand

Qwen2.5-7B-Instruct-1M: 28 layers, 4 KV heads of size 128, width 3,584, about 7.6 billion parameters, BF16. For one 1M-token (1,048,576) prompt compute: KV size; prefill FLOPs (linear plus causal attention); prefill time on 8 H100s at 50% MFU; and the decode step floor on those 8 GPUs at batch 1.

Answer

KV per token: 2 × 28 × 4 × 128 × 2 = 57,344 bytes; for 1M tokens 60 GB. Linear: 2 × 7.6 × 10⁹ × 1.05 × 10⁶ ≈ 1.6 × 10¹⁶. Attention: 28 × 2 × (1.05 × 10⁶)² × 3,584 ≈ 2.2 × 10¹⁷, about 93% of the total. Total about 2.36 × 10¹⁷ FLOPs; at 8 × 989 × 0.5 ≈ 3,956 TFLOP/s: about 60 s. Decode floor: (15.2 GB weights + 60 GB KV) ÷ (8 × 3.35 TB/s) ≈ 2.8 ms per token, if the weights and KV are split evenly. A minute of TTFT is why sparse prefill and caching matter at this length.

Part B: measure prefill growth (CPU, a few minutes)

import torch, time
from transformers import AutoModelForCausalLM, AutoTokenizer
MID = "Qwen/Qwen2.5-0.5B-Instruct"
tok = AutoTokenizer.from_pretrained(MID)
model = AutoModelForCausalLM.from_pretrained(MID, dtype=torch.float32).eval()
for n in [1024, 2048, 4096, 8192]:
    ids = torch.randint(1000, 20000, (1, n))
    with torch.no_grad():
        t = time.time(); model(ids, logits_to_keep=1); dt = time.time() - t
    print(f"prefill {n} tokens: {dt:.2f} s ({n/dt:.0f} tokens/s)")

Predict first: if prefill were purely linear, tokens per second would stay constant. What do you expect, and from what length should the attention term show? (Qwen2.5-0.5B: 24 layers, width 896, about 0.5 billion parameters.)

What we measured, and why
prefill 1024 tokens:  3.74 s (273 tokens/s)
prefill 2048 tokens:  7.99 s (256 tokens/s)
prefill 4096 tokens: 19.77 s (207 tokens/s)
prefill 8192 tokens: 49.88 s (164 tokens/s)

Tokens per second fall as the prompt grows: doubling the length more than doubles the time. For this small model, attention is about 2 × 24 × T × 896 FLOPs per token against about 1 GFLOP for the linear layers, so at 8K it is already about a quarter of the math, and on a CPU the attention also moves a lot of memory. On a GPU the same curve appears at longer lengths. Extrapolate: at this rate, what would 128K tokens take?

Part C: a small needle test (CPU, about 10 minutes; faster on a T4)

import random
random.seed(0)
filler = ["The committee reviewed the quarterly report and noted steady progress.",
          "Weather in the region stayed mild for most of the season.",
          "Several teams shared updates on their ongoing projects.",
          "The library extended its opening hours during the exam period."]
def haystack(n_tokens, depth, code):
    sents, total = [], 0
    while total < n_tokens:
        s = random.choice(filler); sents.append(s); total += len(tok(s).input_ids)
    sents.insert(int(len(sents) * depth), f"The secret access code is {code}.")
    return " ".join(sents)
for n in [1000, 4000, 8000]:
    for depth in [0.1, 0.5, 0.9]:
        code = str(random.randint(10000, 99999))
        msgs = [{"role": "user", "content": haystack(n, depth, code) +
                 "\n\nWhat is the secret access code? Answer with the number only."}]
        ids = tok.apply_chat_template(msgs, add_generation_prompt=True,
                                      return_tensors="pt", return_dict=True)["input_ids"]
        with torch.no_grad():
            out = model.generate(ids, max_new_tokens=8, do_sample=False)
        ans = tok.decode(out[0, ids.shape[1]:], skip_special_tokens=True)
        print(n, depth, "found" if code in ans else "missed", repr(ans.strip()), code)
What we measured, and why

All nine found: 1K, 4K and 8K tokens with the code at 10%, 50% and 90% depth. Even a 0.5B model retrieves a single unrelated fact. That is the point of section 6: a pass on this test says little about reasoning over the whole context. The harder variants in "Extend it" are where small models, and many large ones, start to fail.

Extend it: make the task harder in the RULER style. Insert three codes for three different teams and ask for the code of the team mentioned second; or ask for the sum of two codes. Watch accuracy fall long before the context limit.

10. In the real world

Long context in production
  • Coding agents and document products keep long working sets in prefix-cached, tiered KV, and route returning sessions to where their cache lives.
  • Providers cap context length per deployment and price long-context and cached tokens separately.
  • Model makers increasingly build long context into the architecture (MLA, hybrids, trained sparse attention) because inference-time approximations alone cost quality.
  • Kimi's Mooncake and similar systems make the KV cache, not the GPU, the central resource the scheduler manages.

12. Summary

  • Long contexts cost linear KV memory, quadratic prefill and linear decode growth; each hits a different metric.
  • Apply exact techniques first (chunked prefill, FlashAttention, prefix caching, offload, parallelism, disaggregation), then long-context architectures, then approximations with evaluation.
  • Eviction (StreamingLLM, H2O, SnapKV) and sparse prefill (MInference) save a lot but can lose information.
  • Tiered KV keeps long sessions alive cheaply; reloading beats recomputing.
  • Cap context per deployment, isolate very long requests, and benchmark with long inputs.
  • Effective context is often much shorter than advertised; test on tasks like yours.
