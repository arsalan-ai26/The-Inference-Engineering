Tokenization and embeddings

Models do not read text. They read integers. The tokenizer turns text into a list of token IDs, and the embedding table turns each ID into a vector. Both steps look simple, but they set how many tokens a request costs, how fast it runs, how fair the price is across languages, and a whole class of serving bugs. This chapter covers both.

  2. The same paragraph is 30 tokens in English and 90 tokens in Hindi for one model. Name two effects on serving.
  3. Why can decoding one token at a time print "�" when streaming?
Answers
  1. Words give a huge vocabulary and cannot handle new words. Characters give very long sequences. Subwords keep the vocabulary manageable and sequences short, and any text can still be encoded.
  2. Any two: 3 times the prefill compute, 3 times the KV cache memory, slower time to first token, a higher price for the same content, less room in the context window.
  3. Byte-level tokenizers can split one multi-byte character across tokens. A single token may hold only part of a UTF-8 character, which cannot be shown until the rest arrives.

1. The problem: text is not numbers

A neural network works on vectors (chapter 1.5). Text is a string of characters. We need a fixed, reversible way to cut text into pieces and give each piece a number. This is tokenization.

There are three ways to cut:

UnitVocabulary sizeSequence lengthProblem
Whole wordsMillions (every word form, name, typo)ShortUnknown words cannot be encoded
Characters or bytes256 bytes, or about 150,000 Unicode charactersVery long (4 to 5 times words)Long sequences cost more compute and memory
SubwordsAbout 30,000 to 260,000MediumSplits depend on the training data

All current LLMs use subwords. Common words become one token. Rare words are split into pieces: GPT-2's tokenizer splits "Kubernetes" into K, uber, net, es. Any text can still be encoded, because the smallest pieces are single bytes.

Definitions

Token: one piece of text in the tokenizer's vocabulary.

Token ID: the integer for a token. The model only ever sees IDs.

Vocabulary: the full table of tokens and their IDs.

Encode / decode: text to IDs, and IDs back to text.

2. Byte pair encoding (BPE)

The most common method is byte pair encoding. Training a BPE tokenizer is a simple loop:

  1. Start with every text split into single bytes (or characters).
  2. Count every pair of neighbouring pieces in the training text.
  3. Merge the most frequent pair into one new token. Record the merge.
  4. Repeat until the vocabulary reaches the target size.

To encode new text, apply the recorded merges in the same order. No neural network is involved, and the result is deterministic.

Real tokenizers add three refinements:

  • Byte-level base: GPT-2, Llama 3 and Qwen start from the 256 possible bytes, so any input, even emoji or binary noise, can be encoded.
  • Pre-tokenization: before BPE runs, a regular expression splits text into chunks such as words, numbers and punctuation, so merges never cross those boundaries. A leading space usually stays attached to the word that follows it. GPT-2's tokens show it as "Ġ": Ġhello is " hello".
  • Special tokens: reserved tokens that are never produced from normal text, such as end-of-text, chat role markers and tool-call markers (section 5).

Other methods exist. WordPiece (BERT) is similar to BPE but picks merges by a likelihood score. SentencePiece is a library that treats text as a raw stream, including spaces, and supports BPE and a "unigram" method. For serving, the differences matter less than the vocabulary each model ends up with.

3. Same text, different token counts

Each model family has its own tokenizer. The same text can need very different numbers of tokens. These counts were measured with the real tokenizers:

"The quick brown fox jumps over the lazy dog."10101010

Hindi: "नमस्ते, आप कैसे हैं?"3211*209
"12345678 + 87654321"81018n/a

Counts exclude special tokens. *BERT uncased strips accents and diacritics during normalization, so its low count loses information. o200k is the tokenizer used by recent OpenAI models, measured with the tiktoken library.

Three lessons:

  1. Language matters. GPT-2 needs over 3 times more tokens for the Hindi sentence than a large multilingual vocabulary does. More tokens means more compute, more KV cache, a higher price and less usable context for the same meaning.
  2. Code and whitespace matter. Older tokenizers waste tokens on runs of spaces in indented code. Newer ones have tokens for common indentation.
  3. Numbers are a design choice. Qwen splits every digit into its own token, which helps arithmetic but makes numbers longer. GPT-2 groups digits in irregular chunks.
Watch out: tokens per second is not comparable across models

A model with a larger vocabulary may need 20% fewer tokens for the same text. Its "tokens per second" can look lower while it delivers words just as fast. Compare throughput in tokens of the same tokenizer, or in characters or words, when models differ.

4. Vocabulary size: a trade-off

Why not use a huge vocabulary? Because the vocabulary size V appears twice in the model:

  • The embedding table has V rows of hidden size D.
  • The output head (chapter 1.2) is a [D, V] matmul run for every generated token, followed by a softmax over V values.
Interactive: the cost of the vocabulary
Embedding and output-head parameters, and the output head's share of the FLOPs per token. Assumes the rest of the model is fixed. "Tied" means the embedding table and output head share one matrix.

For a small model, the vocabulary can be a large share of all parameters. Qwen2.5-0.5B has 151,936 × 896 ≈ 136 M embedding parameters: over a quarter of the model. That is why small models often tie their embedding and output weights. For large models, the share is small, and a larger vocabulary pays for itself by shortening sequences.

A detail you will notice in configs

Qwen2.5's tokenizer has 151,665 entries, but its config says vocab_size: 151936. The embedding table is padded with unused rows to a size that divides nicely, so that matmul shapes fit GPU tiles (chapter 1.1, expert layer). Engines must handle these extra rows: they can never be sampled, because no real token maps to them.

5. Special tokens and chat templates

A chat model does not see "messages". It sees one long token sequence. A chat template turns a list of messages into that sequence, using special tokens to mark roles. For Qwen2.5, a single user message "Hi" becomes:

<|im_start|>system
You are Qwen, created by Alibaba Cloud. You are a helpful assistant.<|im_end|>
<|im_start|>user
Hi<|im_end|>
<|im_start|>assistant

Note that the template added a default system prompt the user never typed. The model was trained with this exact format, so it expects it. Llama 3, Mistral, DeepSeek and others each use different markers.

The template is stored with the tokenizer (in tokenizer_config.json or a separate template file) as a small Jinja program. Serving engines apply it when you call the chat API. Getting it wrong is one of the most common causes of "the model is worse on our server than in the demo":

  • A missing or wrong template: the model sees plain text and rambles.
  • A wrong end-of-sequence token: generation never stops, or stops too early.
  • Tool-calling markers that the engine does not parse back into structured calls (chapter 3.5).

6. Tokenization inside a server

Tokenization runs on the CPU, before and after the GPU work:

  • Cost. Fast tokenizers (written in Rust) encode millions of characters per second. Usually this is small next to GPU time, but for very long prompts or very high request rates it can become noticeable. Some engines run tokenization in separate processes so it does not block the GPU loop.
  • Incremental detokenization. When streaming, the server turns each new token ID into text. Two problems: a token may hold only part of a multi-byte UTF-8 character, and some tokenizers change how a token prints depending on its neighbours (for example the leading space). Engines keep a small window of recent tokens and emit only text that is complete and stable.
  • Stop strings. A stop string such as "\n\nUser:" may arrive spread over several tokens, so the server checks the decoded text, not single tokens.

7. Embeddings: from ID to vector

After tokenization, each ID selects one row of the embedding table, a [V, D] matrix of learned numbers (chapter 1.5). For token IDs of shape [B, T], the result is [B, T, D].

embeddings = E[ids] shape [B, T] → [B, T, D]

Mathematically this equals multiplying a one-hot vector (all zeros except a 1 at the token's ID) by E. In practice, engines do a direct row lookup: no multiplication, just a memory read of T × D values. It is one of the cheapest steps in the model.

During training, tokens that appear in similar contexts get similar rows. So the embedding space has structure: related tokens point in similar directions, and cosine similarity (chapter 1.1) measures it. This is only the starting point. Every transformer layer adds information from the context, so the vector for "bank" in "river bank" ends up very different from "bank" in "bank loan" after a few layers. Those context-aware vectors are what embedding models for search return.

8. One thing embeddings lack: position

The same token ID always gives the same embedding row, wherever it appears. "dog bites man" and "man bites dog" give the same set of vectors. Something must add order. GPT-2 adds a second learned table indexed by position. Modern models instead rotate the query and key vectors inside attention (RoPE). Chapter 2.3 covers both. Chapter 2.2 first explains attention itself.

9. Expert layer

Tokenizer fertility and fair pricing

"Fertility" is the average number of tokens per word for a language. High-fertility languages pay more per sentence on token-priced APIs, see slower responses and fit less text in the context window. Multilingual model builders grow the vocabulary partly to reduce this gap.

Token healing and prompt boundaries

If a prompt ends in the middle of what would normally be one token (for example, it ends with "http:" and the model usually sees "://" as one token), the model sees an unusual split and may continue badly. Some libraries "heal" this by backing up one token and constraining the next token to start with the removed text.

Glitch tokens

Some tokens exist in the vocabulary but were almost never seen in training, because the tokenizer was trained on different data from the model. Their embeddings stay close to random, and prompts containing them can make a model behave strangely. They are a reminder that the tokenizer and the model are trained separately.

Tokenizer-free and byte-level models

Research models that read raw bytes avoid tokenizer problems, but sequences become several times longer. Some designs group bytes into dynamic "patches" inside the model to win back the length. These are not yet common in production serving.

10. Common mistakes

  • Estimating cost from word count. Measure tokens with the model's own tokenizer.
  • Using one model's tokenizer to count tokens for another model.
  • Forgetting the chat template and special tokens when counting prompt length. The default system prompt alone can add dozens of tokens.
  • Decoding streamed tokens one at a time and printing "�" for non-English text.
  • Assuming len(tokenizer) equals config.vocab_size. The embedding table is often padded.

Part E: embeddings are a lookup

import torch
from transformers import AutoModelForCausalLM
m = AutoModelForCausalLM.from_pretrained("openai-community/gpt2")
E = m.transformer.wte.weight                     # [50257, 768]
ids = torch.tensor(g("king queen man woman apple").input_ids)
rows = E[ids]                                    # lookup
onehot = torch.nn.functional.one_hot(ids, E.shape[0]).float()
print(torch.allclose(rows, onehot @ E, atol=1e-6))   # same result, far more work

cos = torch.nn.functional.cosine_similarity
for a, b in [(0, 1), (2, 3), (0, 4)]:
    print(g.decode(ids[a]), g.decode(ids[b]), round(cos(rows[a], rows[b], dim=0).item(), 3))

n = lambda mod: sum(p.numel() for p in mod.parameters())
emb = n(m.transformer.wte) + n(m.transformer.wpe)
attn = sum(n(b.attn) for b in m.transformer.h); mlp = sum(n(b.mlp) for b in m.transformer.h)
total = n(m)
print(f"embeddings {emb/total:.1%}  attention {attn/total:.1%}  mlp {mlp/total:.1%}")

Raw input embeddings are noisy, so do not expect perfect analogies. Related pairs should still score higher than unrelated ones. Then check the parameter split.

What the split should be

For GPT-2 small (124 M), embeddings are about 31.6%, attention about 22.8% and the MLP about 45.5%, with layer norms near 0%. (The output head shares the embedding table, so it adds nothing.)

12. In the real world

Tokens in production
  • Pricing: hosted APIs bill per input and output token. The same request costs different amounts on models with different tokenizers.
  • Context limits are in tokens, including the chat template and system prompt.
  • Serving engines ship the tokenizer and chat template with the model and run tokenization in CPU worker processes. vLLM and SGLang both apply the model's chat template on their chat endpoints and let you override it.
  • Debugging: when a self-hosted model behaves differently from its hosted version, compare the exact token IDs sent to the model first.

14. Summary

  • Tokenizers split text into subword tokens; BPE builds the vocabulary by merging frequent pairs, starting from bytes.
  • Token counts differ by tokenizer, language, code style and numbers. Always count with the model's own tokenizer.
  • Vocabulary size trades a bigger embedding table and output head against shorter sequences.
  • Chat templates and special tokens turn messages into one sequence; a wrong template breaks quality and stopping.
  • Servers tokenize on the CPU and detokenize incrementally for streaming.
  • Embedding is a row lookup: [B, T] IDs become [B, T, D] vectors. Position is not in it yet.
