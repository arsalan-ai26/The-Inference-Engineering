Remote GPU machines and a reproducible setup

Real inference work happens on GPUs you rent by the hour and reach over SSH. This chapter teaches the practical skills: get a machine, connect to it safely, check that the driver, CUDA and PyTorch fit together, serve a model over HTTP, watch the GPU while it works, and record the setup so you can rebuild it exactly.

Level: beginner Time: 3 hours, plus about 1 hour of rented GPU time Needs: a terminal and basic shell commands Compute: free Colab or Kaggle first, then optional paid GPU
Before you start: skip check
  1. nvidia-smi says "CUDA Version: 12.4". Is the CUDA 12.4 toolkit installed?
  2. How do you reach a web server on port 8000 of a remote GPU box from your laptop, without opening the port to the internet?
  3. Name three things you must record so that someone else can rebuild your exact benchmark setup.
Answers
  1. Not necessarily. That line is the highest CUDA version the installed driver supports. The toolkit may be missing or a different version.
  2. An SSH tunnel: ssh -L 8000:localhost:8000 user@host, then open http://localhost:8000 on your laptop.
  3. Any three of: GPU model and driver version, CUDA version of the PyTorch build, exact package versions, model name and revision, engine flags, container image digest.

You need a GPU for most labs in this book. Start free. Rent only when a lab needs more memory or a newer GPU.

Watch out: the meter keeps running

A rented GPU bills while it is on, even when it does nothing. Stop or delete the machine when you finish. Set a spending limit or an auto-shutdown if the provider offers one. Persistent disks may also bill after the machine stops.

2. SSH: your connection to the machine

SSH (Secure Shell) opens an encrypted terminal on a remote machine. GPU providers almost always use key-based login: you keep a private key on your laptop, and you give the provider the matching public key.

# 1. Make a key pair once (press Enter to accept the default path; set a passphrase)
ssh-keygen -t ed25519 -C "gpu-work"
# 2. Show the PUBLIC key; paste it into the provider's SSH key settings
cat ~/.ssh/id_ed25519.pub
# 3. Connect (the provider shows the user, host and port)
ssh -p 22 ubuntu@203.0.113.10

Never share the private key (the file without .pub). Save each machine in ~/.ssh/config so you can type a short name:

Host gpu
    HostName 203.0.113.10
    User ubuntu
    Port 22
    IdentityFile ~/.ssh/id_ed25519
    LocalForward 8000 localhost:8000      # tunnel for the model server (section 5)

Now ssh gpu connects and opens the tunnel.

3. The software stack: driver, CUDA, PyTorch

Four layers sit between your Python code and the GPU. Most setup failures come from a mismatch between them.

Definitions

Driver: the low-level software that talks to the GPU. It is installed on the machine by the provider. It sets the highest CUDA version you can use.

CUDA runtime: the libraries that programs call to run work on the GPU. PyTorch wheels bundle their own copy, so you do not need to install CUDA separately to use PyTorch.

CUDA toolkit: the compiler (nvcc) and headers. You need it only to compile CUDA code yourself, for example some custom kernels or packages built from source.

Compute capability: a version number for the GPU's architecture. T4 is 7.5, A100 8.0, L4 8.9, H100 9.0, B200 10.0. Software must include code compiled for your GPU's capability.

The two rules

  1. Driver must be new enough for the CUDA runtime. The "CUDA Version" that nvidia-smi prints must be equal to or higher than torch.version.cuda. Within one major version (for example 12.x), CUDA's minor-version compatibility often lets a slightly newer runtime run on an older driver, but some features may fail. A newer major version (for example a 13.x build on a 12.x driver) does not work without NVIDIA's separate forward-compatibility package.
  2. The build must support your GPU. New GPUs need recent builds (Blackwell needs CUDA 12.8 or newer builds). New CUDA releases also drop old GPUs: CUDA 13 removed support for Maxwell, Pascal and Volta (compute capability below 7.5).
Interactive: will this combination work?
Pick what nvidia-smi shows, the PyTorch build you plan to install and your GPU. The checker applies the two rules above. It is a guide, not a guarantee: always confirm with the test in section 4.

4. Check a new machine in five minutes

Run these on every new machine before you install anything else. Save the output; it is the first part of your setup record.

nvidia-smi                                   # GPU model, driver version, max CUDA, memory, processes
nvidia-smi --query-gpu=name,compute_cap,memory.total,driver_version --format=csv
nvcc --version 2>/dev/null || echo "no CUDA toolkit (fine for most inference)"
python3 --version
df -h ~ ; free -g ; nproc                      # disk, RAM, CPU cores: models need disk space
python3 -c "import torch; print(torch.__version__, torch.version.cuda, torch.cuda.is_available(), torch.cuda.get_device_name(0))"

Then prove that the GPU really computes, not just that PyTorch can see it:

python3 - <<'EOF'
import torch, time
x = torch.randn(8192, 8192, device="cuda", dtype=torch.float16)
for _ in range(3): x @ x
torch.cuda.synchronize(); t = time.perf_counter()
for _ in range(10): x @ x
torch.cuda.synchronize(); dt = (time.perf_counter() - t) / 10
print(f"{2 * 8192**3 / dt / 1e12:.1f} TFLOP/s FP16")
EOF

Compare with the GPU's data sheet (chapter 1.1, lab Part D). A result far below it points to a throttled, shared or misconfigured GPU.

5. Serve a model and stream tokens

An inference server loads a model once, then answers many HTTP requests. vLLM and SGLang both offer an OpenAI-compatible API: the same request format as OpenAI's API, so standard client libraries work. Chapter 3.1 explains what happens inside. Here you just run one.

# On the GPU machine, inside tmux
python3 -m venv ~/venv && source ~/venv/bin/activate
pip install vllm                      # installs a matching torch build
vllm serve Qwen/Qwen2.5-0.5B-Instruct --port 8000 --max-model-len 4096
# On a T4 (no BF16 support), add:  --dtype half

When the log says the server is ready, send a streaming request from another terminal (or from your laptop through the SSH tunnel):

curl -N http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "Qwen/Qwen2.5-0.5B-Instruct",
       "messages": [{"role": "user", "content": "Explain a GPU in two sentences."}],
       "max_tokens": 100, "stream": true}'

The reply arrives as server-sent events: lines that start with data:, each holding a small JSON piece with the next few characters. The stream ends with data: [DONE]. Streaming is how chat apps show text as it is generated. The time until the first piece is the TTFT you will meet in chapter 2.4.

The same request in Python, with timing:

import time, json, requests
t0 = time.perf_counter(); first = None; n = 0
with requests.post("http://localhost:8000/v1/chat/completions", stream=True, json={
        "model": "Qwen/Qwen2.5-0.5B-Instruct", "stream": True, "max_tokens": 200,
        "messages": [{"role": "user", "content": "Write a short poem about GPUs."}]}) as r:
    for line in r.iter_lines():
        if not line.startswith(b"data: ") or line == b"data: [DONE]":
            continue
        delta = json.loads(line[6:])["choices"][0]["delta"].get("content", "")
        if delta:
            first = first or time.perf_counter(); n += 1
total = time.perf_counter() - t0
print(f"time to first token {1000*(first - t0):.0f} ms, {n} chunks in {total:.2f} s")

6. Watch the GPU while it works

# one line per second: utilization, memory, power, temperature, clocks
nvidia-smi --query-gpu=timestamp,utilization.gpu,memory.used,power.draw,temperature.gpu,clocks.sm \
           --format=csv -l 1
# compact rolling view
nvidia-smi dmon -s pucm

Run the monitor in one tmux pane and send requests from another. Watch three things change: memory jumps when the server starts (it reserves the KV cache pool), utilization and power rise during a request, and both fall back when it ends. Under many parallel requests, power rises much more than under one: that is batching at work (chapter 3.2).

7. Containers

A container packs an exact set of user-space software (Python, CUDA runtime, PyTorch, the engine) into one image. The driver stays on the host. The NVIDIA Container Toolkit connects containers to the host's GPUs and driver.

# after installing Docker and the NVIDIA Container Toolkit on the host
docker run --rm --gpus all nvidia/cuda:12.8.0-base-ubuntu24.04 nvidia-smi    # test GPU access
docker run --gpus all -p 8000:8000 --ipc=host \
  -v ~/.cache/huggingface:/root/.cache/huggingface \
  vllm/vllm-openai:latest --model Qwen/Qwen2.5-0.5B-Instruct

--ipc=host (or a large --shm-size) gives the container enough shared memory, which PyTorch uses for communication between processes. Mounting the Hugging Face cache stops every new container from downloading the model again. For reproducible work, replace latest with an exact version tag, and record the image digest.

8. A reproducible setup

Performance numbers mean nothing without the setup that produced them. Driver, library and engine versions can each change results by large amounts. Record everything in a file next to your results.

cat > setup_record.sh <<'EOF'
#!/bin/bash
# Usage: bash setup_record.sh > setup.txt
echo "date: $(date -u +%FT%TZ)"
nvidia-smi --query-gpu=name,compute_cap,memory.total,driver_version,power.limit --format=csv,noheader
python3 -c "import torch, sys; print('python', sys.version.split()[0]); print('torch', torch.__version__, 'cuda', torch.version.cuda)"
python3 -c "import vllm; print('vllm', vllm.__version__)" 2>/dev/null
pip freeze | grep -i -E "^(torch|vllm|transformers|flashinfer|xformers|triton|sglang)"
EOF
bash setup_record.sh

Also record, for every experiment:

  • The model name and its revision (the commit hash on Hugging Face). Model repositories change; --revision pins one version.
  • The full engine command line, including every flag.
  • The benchmark command and its settings: prompt lengths, output lengths, concurrency.
  • The container image tag and digest, if you used one.

Pin Python packages with exact versions (pip freeze > requirements.txt, or a lock file from a tool such as uv). Then a new machine can be rebuilt with one command.

9. Expert layer

Persistence mode and clocks

On data-center GPUs, nvidia-smi -pm 1 keeps the driver loaded so the first CUDA call is not slow. Benchmarks sometimes lock clocks for stable numbers (nvidia-smi -lgc). Rented machines may not allow these settings. Whatever you do, record it.

Multi-GPU topology

nvidia-smi topo -m shows how GPUs connect: through NVLink (fast) or only PCIe (slower). Tensor parallelism (chapter 4.5) across GPUs without NVLink can be much slower. Check the topology before you rent a multi-GPU machine for a parallel lab.

Model download and cold start

A 16 GB model takes minutes to download and seconds to load. Production systems pre-download models to fast local disks or shared caches, and measure "cold start" time as a first-class metric (chapter 6.2). Set HF_HOME to a large disk on rented machines; the default home directory is often small.

MIG and GPU sharing

A100, H100 and newer data-center GPUs support Multi-Instance GPU (MIG): one physical GPU split into isolated smaller GPUs, each with its own memory and compute. Some cheap rentals are MIG slices. nvidia-smi -L shows whether you have a full GPU or a slice.

10. Common mistakes

  • Reading the "CUDA Version" in nvidia-smi as the installed toolkit.
  • Installing the CUDA toolkit to "fix" PyTorch. PyTorch wheels bring their own runtime; the usual fix is a wheel that matches the driver.
  • Running long jobs without tmux, then losing them when Wi-Fi drops.
  • Opening a model server port to the whole internet instead of using an SSH tunnel.
  • Filling the small root disk with model downloads.
  • Reporting benchmark numbers without the versions and flags that produced them.
  • Leaving a rented GPU running overnight.

11. Lab

Goal: do the full workflow once: machine, check, serve, stream, monitor, record.

Part A: free path (Colab or Kaggle)

  1. Open a T4 notebook. Run the checks of section 4 in cells (prefix shell commands with !).
  2. Predict first: what will torch.version.cuda print, and will it be lower or higher than the CUDA version in nvidia-smi?
  3. Run the FP16 matmul test. Write down the TFLOP/s and compare with the T4's 65 TFLOP/s peak.
  4. Run setup_record.sh and save the output.

Part B: serve and stream (Colab, Kaggle or rented)

In a notebook, start the server in the background and poll until it is ready:

!pip install -q vllm
import subprocess, time, requests
log = open("vllm.log", "w")
srv = subprocess.Popen(["vllm", "serve", "Qwen/Qwen2.5-0.5B-Instruct", "--port", "8000",
                        "--max-model-len", "4096", "--dtype", "half"], stdout=log, stderr=log)
for _ in range(120):
    try:
        if requests.get("http://localhost:8000/v1/models").ok: print("ready"); break
    except Exception: pass
    time.sleep(5)
!tail -n 20 vllm.log

In the log, find the line that reports the KV cache size or the maximum concurrency. Write down the number; chapter 2.4 explains it. Then run the streaming Python client from section 5. Record the time to first token.

If vLLM fails to install or start on the free GPU, note the error and do this part on a rented GPU. Free environments change often, and package versions on them are not under your control.

Part C: watch the GPU under load

import concurrent.futures as cf
def one(i):
    return requests.post("http://localhost:8000/v1/completions", json={
        "model": "Qwen/Qwen2.5-0.5B-Instruct", "prompt": f"Story {i}:", "max_tokens": 256}).json()["usage"]
mon = subprocess.Popen("nvidia-smi --query-gpu=timestamp,utilization.gpu,memory.used,power.draw --format=csv -l 1 > gpu.csv", shell=True)
for users in [1, 16]:
    t = time.perf_counter()
    with cf.ThreadPoolExecutor(users) as ex:
        usage = list(ex.map(one, range(users)))
    dt = time.perf_counter() - t
    toks = sum(u["completion_tokens"] for u in usage)
    print(f"{users:2d} users: {toks} tokens in {dt:.1f} s = {toks/dt:.0f} tokens/s")
    time.sleep(3)
mon.terminate()
!cat gpu.csv | tail -n 40

Predict first: will 16 users get about 16 times the total tokens per second of 1 user, more, or less? Then compare power draw in the two phases in gpu.csv.

Part D (optional, paid): a rented GPU over SSH

  1. Rent the cheapest single GPU with at least 24 GB (for example an L4 or A10) for one hour.
  2. Add your SSH key, connect with a ~/.ssh/config entry that forwards port 8000.
  3. Repeat Parts A to C in tmux. Open http://localhost:8000/v1/models in your laptop's browser through the tunnel.
  4. Copy gpu.csv and setup.txt back with rsync.
  5. Delete the machine. Check the provider's billing page to confirm it stopped.

12. In the real world

How teams run GPUs
  • Development happens on a rented single GPU or a shared cluster node, reached over SSH or through remote editors (for example VS Code Remote-SSH).
  • Production runs engines in containers on Kubernetes or a managed platform, with the driver on the host and the GPU operator managing devices (chapter 6.2).
  • Benchmarks published by engine teams always list GPU, driver, engine version and flags. Results that omit them cannot be compared.
  • Cost control: idle GPUs are the most common waste. Teams use auto-shutdown, scale-to-zero and spot instances (chapter 6.5).

14. Summary

  • Start on free T4 notebooks; rent GPUs by the hour for engines, newer hardware and benchmarks; always shut them down.
  • Use SSH keys, an SSH config, tmux for long jobs, tunnels for ports, rsync for files.
  • Stack: driver (host) → optional toolkit → PyTorch with bundled CUDA runtime → your code. The driver's CUDA version must cover the build, and the build must support the GPU.
  • Check a new machine with nvidia-smi, torch.cuda and a quick matmul benchmark.
  • vLLM serves an OpenAI-compatible API with streaming; watch memory, utilization and power while it runs.
  • Record GPU, driver, versions, model revision and flags with every result.
