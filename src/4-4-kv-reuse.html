Prefix caching and KV reuse at scale

Chapter 3.5 showed how one engine reuses the KV cache of a shared prefix: block hashes in vLLM, a radix tree in SGLang. This chapter treats reuse as a system-wide optimization. It covers what a cache hit is worth in time and money, how prompt design makes or breaks hits, where to keep the cache when GPU memory is full (CPU memory, SSD, a shared network store), when loading a saved cache beats recomputing it, and how routing across replicas decides whether the cache helps at all.

Before you start: skip check
  1. Your system prompt starts with "Current time: {now}". What happens to the prefix cache?
  2. Is it faster to reload 10,000 tokens of Llama 3.1 8B KV cache from CPU memory, or to recompute them on an H100?
  3. Four replicas, round-robin routing, each user chats for ten turns. Roughly what share of turns can hit the cache?
Answers
  1. Every request has a different first block, so nothing after it can ever match. The hit rate is close to zero.
  2. Reload. 10,000 tokens × 128 KiB is about 1.3 GB, about 26 ms over a 50 GB/s host link. Recomputing is about 160 TFLOP, about 330 ms at half the H100's BF16 peak.
  3. About one in four: a turn hits only if it lands on the replica that served an earlier turn of the same chat, and with round robin that is mostly luck.

1. What a cache hit is worth

A prefix cache hit skips prefill for the matched tokens. That saves three things:

  • Latency. TTFT drops roughly in proportion to the cached share of the prompt. The llm-d team measured a 10,000-token prompt to Qwen3-32B: 4.3 s TTFT the first time, 0.6 s the second time.
  • GPU time, so throughput. Prefill compute that is skipped is free for other requests. Under load this raises total throughput, not only TTFT.
  • Money. Hosted APIs price cached input tokens far below uncached ones (the llm-d post quotes a 10 times difference for one major API at the time it was written). Self-hosted, the saving shows up as fewer GPUs for the same traffic.
Worked example: an agent loop

An agent makes 20 calls per task. Each call re-sends a 4,000-token system prompt with tool definitions plus a history that grows by 1,500 tokens per call, and produces about 150 tokens. Total prompt tokens over the task: 20 × 4,000 + 1,500 × (0 + 1 + ... + 19) = 80,000 + 285,000 = 365,000. With perfect prefix caching, each call prefills only its new tokens: 4,000 once plus 1,500 per call after the first, about 32,500 in total. Prefill work drops about 11 times. Production agent traces with input-to-output ratios above 100 to 1 are common, which is why the KV cache hit rate is often called the most important metric for agent serving.

2. Prompt design decides the hit rate

A prefix match stops at the first token that differs (chapter 3.5). Everything after it is recomputed, even if the rest is identical. So the order of content in the prompt matters more than any engine setting.

  1. Stable first, variable last. System prompt, then tool definitions, then shared documents, then the conversation, then the new message. User names, timestamps and request IDs go at the end, or nowhere.
  2. Make "stable" truly byte-stable. Same whitespace, same tool order, same JSON key order, same document order. Serializing a dict whose key order changes between processes silently kills hits.
  3. Watch the chat template. Templates can insert content you did not write. Some insert today's date into the system prompt by default; the date changes once a day and every cache entry before it becomes useless at midnight. Many reasoning-model templates drop earlier turns' reasoning from the history. The engine cached turn 1 with its reasoning; turn 2's prompt shows turn 1 without it, so the cache matches only up to the end of turn 1's prompt. Part B of the lab shows this with a real template.
  4. Append, do not edit. Agent frameworks that rewrite or summarize the middle of the history break the prefix at the edit point. Editing at the end keeps the cache.
  5. RAG ordering. If retrieved documents change order between queries, the shared prefix ends at the first document. Sorting retrieved chunks in a stable order (for example by document ID) can help, when quality allows.

3. Measuring reuse

  • Hit rate in tokens, not requests. A request that hits 90% of a 10,000-token prompt saves far more than one that hits 50% of a 200-token prompt. vLLM reports cache queries and hits in tokens (chapter 3.1); hit tokens ÷ queried tokens is the hit rate.
  • TTFT by cache state. A healthy cached workload shows two TTFT populations: hits (fast) and misses (slow). If p50 TTFT moves while the hit rate falls, check prompt changes first.
  • Eviction pressure. Under load, free KV memory shrinks and cached blocks are evicted (chapter 3.5). The hit rate falls exactly when it matters most. That is the main reason to extend the cache beyond GPU memory.

4. Where the cache can live

GPU memory is the fastest place for KV blocks and the smallest. Below it are tiers that are slower but much larger:

TierMemoryBandwidth to the GPU (approximate)Size (approximate)
G1GPU memory (HBM)Terabytes per secondTens to hundreds of GB
G2CPU memory (host DRAM)Tens to hundreds of GB/sHundreds of GB to TB
G3Local SSDAbout 5 to 10 GB/sTerabytes
G4Networked storageGigabytes per secondTens of TB and more; shared by all replicas

The usual policy keeps hot blocks in G1, moves blocks that would otherwise be evicted down to G2 (and G3), and promotes them back on a hit. A shared G4 store adds something the others cannot: every replica can find a prefix any replica computed, and the cache survives a replica being restarted or scaled down. Systems with a fast CPU to GPU link (for example GB200, where the Grace CPU connects over NVLink-C2C) make G2 especially attractive.

Tools

  • vLLM's OffloadingConnector: copies completed KV blocks to pinned CPU memory (and optionally to secondary tiers such as a file system), and promotes them back on a hit. Configured through --kv-transfer-config.
  • LMCache: a KV caching layer for vLLM and SGLang that stores caches in CPU memory, disk or remote stores, shares them across engine instances, and also moves KV for prefill/decode disaggregation (chapter 4.6).
  • NVIDIA Dynamo's KV Block Manager (KVBM): APIs for moving KV blocks among G1 to G4 (chapter 3.6).
  • Mooncake: Moonshot AI's KV-cache-centric architecture for its Kimi service, which pools the cluster's spare CPU memory and SSDs into a distributed KV cache. Its paper reports handling 75% more requests on real workloads.

5. Load or recompute?

Reusing a cache from a lower tier is only worth it if moving the bytes is faster than prefilling the tokens again. Both costs grow linearly with the number of tokens, so compare per token:

load time per token = KV bytes per token ÷ tier bandwidth
recompute time per token ≈ 2 × parameters ÷ (GPU FLOP/s × MFU)
Interactive: load from a tier, or recompute?
Per-token costs for one replica. Recompute uses an H100's BF16 peak (989 TFLOP/s) times the MFU you choose, per GPU. Attention FLOPs are ignored, so recompute is really even slower at long contexts.

The pattern holds broadly: reloading from CPU memory beats recomputation by an order of magnitude; local SSD is roughly break-even to a few times better; a slow network store can lose to recomputation for small models but wins for large ones, where recomputing costs far more FLOPs per KV byte. Compact caches (GQA, MLA, FP8 KV) make every tier more attractive, because fewer bytes stand in for the same tokens. Real systems also overlap loading with computing other layers, which hides part of the load time.

The bytes moved can also be made smaller than the cache itself. CacheGen (arXiv 2310.07240, the University of Chicago group behind LMCache) encodes a KV cache into a compact bitstream using its statistical properties, and changes the compression level of different parts when network bandwidth drops, so loading stays fast enough to beat recomputing. The authors report 3.5 to 4.3 times smaller KV caches and 3.2 to 3.7 times less delay to fetch and process contexts, with negligible quality impact. It is the step from "cache tiers" to "KV streaming" that LMCache and disaggregated systems build on.

6. Routing decides whether the cache helps

Every replica has its own cache. A request only hits if it lands on a replica that holds its prefix. Ordinary load balancers (round robin, least connections) are blind to this and scatter related requests. Options, from simplest:

  • Session or hash affinity: hash the user, session or system-prompt ID to a replica. Simple and effective, but hot customers overload "their" replica.
  • Approximate prefix-aware routing: the router remembers which replica it sent each prefix to and predicts where it is cached.
  • Precise prefix-aware routing: replicas publish events every time a block is stored or evicted; the router keeps a live index of which blocks are on which replica (and in which tier) and scores each replica by how much of the request's prefix it holds. The score is combined with load, so a hot replica does not get swamped.

The llm-d benchmark (8 vLLM pods on 16 H100s, 150 simulated enterprise customers with 6,000-token contexts) compared these: precise prefix-aware scheduling reached a p90 TTFT of 0.54 s against over 31 s for the approximate scheduler and over 90 s for cache-blind ones, with about twice the throughput of cache-blind routing. Part D of the lab reproduces the shape of this result in a small simulator. Chapter 6.4 covers routers, queues and fairness in depth.

7. Beyond exact prefixes

Prefix caching only reuses an exact prefix, because each token's keys and values depend on every token before it and on its position (chapter 2.3). RAG breaks this constantly: the same document appears in different prompts at different positions after different documents. CacheBlend reuses each document's precomputed KV wherever it appears and recomputes only a small subset of tokens to repair the cross-attention between chunks, keeping quality close to full prefill. LMCache implements this kind of non-prefix reuse. It is an approximation: evaluate it on your own data before relying on it.

Shared prefixes inside one decode batch: Hydragen

Prefix caching saves the prefill of a shared prefix. During decode, though, every sequence in the batch still reads the prefix's KV from HBM separately, one matrix-vector product per sequence. Hydragen (arXiv 2402.05099) splits attention into two parts: attention over the shared prefix, computed for all sequences at once by stacking their queries into one matrix-matrix product, and attention over each sequence's own suffix. The two partial results are merged exactly with the same softmax-rescaling trick as Flash-Decoding (chapter 4.2, section 7). The prefix KV is read once per step instead of once per sequence, and the prefix part runs on tensor cores. FlashInfer calls this cascade attention. vLLM had a cascade attention path for shared prefixes but has since removed it (at the commit chapter 8.2 reads, only a deprecated flag remains), so check your engine before counting on it. The saving, computed:

kv = 131_072                 # bytes per token, Llama 3.1 8B in BF16 (chapter 2.4)
B, P, S = 64, 4_000, 500     # sequences in the batch, shared prefix tokens, own tokens per sequence
plain = B * (P + S) * kv     # every sequence reads its own copy of the prefix KV
hydra = (P + B * S) * kv     # prefix KV read once for all 64 queries, suffixes separately
print(f"KV read per decode step: plain {plain/1e9:.1f} GB, shared-prefix {hydra/1e9:.1f} GB, {plain/hydra:.1f}x less")
print(f"at 3.35 TB/s (H100): {plain/3.35e12*1e3:.1f} ms vs {hydra/3.35e12*1e3:.1f} ms of KV reading per step")
What we computed

With 64 sequences sharing a 4,000-token prefix, the KV bytes read per step drop 8 times; the longer the shared prefix and the larger the batch, the bigger the gain. The authors report up to 32 times end-to-end throughput for CodeLlama-13B, and that growing the shared prefix from 1K to 16K tokens costs Hydragen under 15% of its throughput at large batch while baselines lose over 90%. The pattern to look for: many requests in flight at once with the same long system prompt or document (agents, few-shot evaluation, parallel sampling).

8. Expert layer

Cache capacity is a sizing decision

Engines size the GPU KV pool from free memory after weights (chapter 2.4). In TensorRT-LLM, for example, free_gpu_memory_fraction = 0.8 on a 180 GB B200 with 100 GB of weights and buffers gives a 64 GB pool. A large, mostly idle pool is a cache; under load it is working memory. Plan the CPU tier so that the working set of hot prefixes (system prompts, active sessions, popular documents) fits there.

Isolation and security

A shared cache can leak: if one tenant's request gets a faster TTFT because another tenant's prompt is cached, timing reveals that the other prompt existed. Multi-tenant systems can scope cache keys per tenant (vLLM supports a cache salt in the request, chapter 3.5). Chapter 6.9 returns to this.

The same machinery serves disaggregation

Moving KV blocks between GPU, CPU, disk and network is exactly what prefill/decode disaggregation needs to move a request from a prefill GPU to a decode GPU. LMCache, Mooncake and Dynamo do both. Chapter 4.6 builds on this.

9. Common mistakes

  • Putting timestamps, user IDs or request IDs at the start of the prompt.
  • Reporting the hit rate in requests instead of tokens.
  • Assuming prefix caching only helps TTFT; it frees prefill compute for everyone.
  • Scaling out replicas behind a round-robin balancer and watching the hit rate fall.
  • Pure affinity routing with no load cap, so one busy customer saturates one replica.
  • Offloading to a slow network store for a small model, where recomputation is faster.
  • Changing the chat template or tool definitions in a deploy and not expecting a cold-cache period.

Part B: prompt layout with a real template (CPU, seconds)

This implements block hashing (chapter 3.5) over real Qwen3 token IDs and serves three requests with two layouts. Then it shows what a reasoning model's chat template does to multi-turn reuse.

from transformers import AutoTokenizer
import hashlib
tok = AutoTokenizer.from_pretrained("Qwen/Qwen3-0.6B")
B = 16
def block_hashes(ids):
    hs, parent = [], b""
    for i in range(0, len(ids) - len(ids) % B, B):          # full blocks only
        parent = hashlib.sha256(parent + str(ids[i:i+B]).encode()).digest()
        hs.append(parent)
    return hs
cache = set()
def serve(ids):
    hs = block_hashes(ids); hit = 0
    for h in hs:
        if h in cache: hit += 1
        else: break
    cache.update(hs)
    return hit * B, len(ids)

What we measured, and why

Turn 1 left 58 tokens in the cache; turn 2's prompt is 40 tokens and shares only 18 with it. The template rendered turn 1's answer as just "391": the reasoning was removed from the history. Everything from turn 1's answer onwards must be prefilled again. With long reasoning traces and many turns this costs a lot, which is why some serving stacks and newer templates keep reasoning in the history for agent loops. Check your model's template.

Answer

KV for 32,000 tokens: 32,000 × 327,680 bytes = 10.5 GB. CPU: 10.5 ÷ 200 = 52 ms. NVMe: 1.5 s. Network: 5.2 s. Recompute: 32,000 × 2 × 70.6 × 10⁹ = 4.5 PFLOP; at 4 × 989 × 0.5 = 1,978 TFLOP/s that is about 2.3 s (more with attention FLOPs at this length). Part D: routing policies (CPU, seconds)

Four replicas, each with an LRU cache of 3,000 blocks. 40 customers share 6,000-token contexts; a few customers send most of the traffic; each query adds 1,200 unique tokens.

import random
from collections import OrderedDict
random.seed(1)
R, CAP, B = 4, 3000, 16
CUST, CTX, Q = 40, 6000, 1200

class Replica:
    def __init__(s): s.cache, s.work = OrderedDict(), 0
    def cached(s, blocks):
        n = 0
        for b in blocks:
            if b in s.cache: n += 1
            else: break
        return n
    def serve(s, blocks):
        n = s.cached(blocks)
        for b in blocks:
            s.cache[b] = True; s.cache.move_to_end(b)
        while len(s.cache) > CAP: s.cache.popitem(last=False)
        s.work += (len(blocks) - n) * B          # prefill tokens actually computed
        return n * B

def request():
    c = random.choices(range(CUST), weights=[1 / (i + 1) for i in range(CUST)])[0]
    return c, [("ctx", c, i) for i in range(CTX // B)] + [("q", random.random(), i) for i in range(Q // B)]

def run(policy, n=3000):
    reps = [Replica() for _ in range(R)]; hit = tot = rr = 0
    for _ in range(n):
        c, blocks = request()
        if policy == "round robin":    r = reps[rr % R]; rr += 1
        elif policy == "least loaded": r = min(reps, key=lambda x: x.work)
        elif policy == "hash affinity": r = reps[c % R]
        else:
            # TODO: cache-aware with a load cap. Keep replicas whose work is at most
            # 1.15 x the mean, and among them pick the one with the longest cached prefix.
            pass
        hit += r.serve(blocks); tot += len(blocks) * B
    w = [x.work for x in reps]
    return hit / tot, sum(w), max(w) / (sum(w) / R)

for p in ["round robin", "least loaded", "hash affinity", "cache-aware + load cap"]:
    h, work, imb = run(p)
    print(f"{p:24s} hit {h:5.1%}  prefill computed {work/1e6:5.2f} M tokens  busiest/mean {imb:4.2f}")
Solution 
            mean = sum(x.work for x in reps) / R
            ok = [x for x in reps if x.work <= mean * 1.15 + 1] or reps
            r = max(ok, key=lambda x: (x.cached(blocks), -x.work))

Cache-blind policies balance load but compute almost twice the prefill. Hash affinity gets the hits but overloads the replica that owns the busiest customers by 40%. Cache-aware routing with a load cap gets both. Try CAP = 1,000 (smaller caches) and R = 8: affinity matters even more.

11. In the real world

Reuse in production
  • Hosted APIs price cached input tokens far below uncached ones and document how to structure prompts to get hits.
  • Agent and coding products design prompts and history handling around the cache, because their inputs are long, repeated and mostly append-only.
  • Large deployments run prefix-aware routers (llm-d, Dynamo, SGLang's router) and tiered KV stores (LMCache, Mooncake, KVBM).
  • Kimi (Moonshot AI) built its serving platform, Mooncake, around a distributed KV cache over the cluster's CPU memory and SSDs.

13. Summary

  • A cache hit skips prefill: lower TTFT, more throughput, lower cost. Agents and chat gain the most.
  • Prompt design decides the hit rate: stable content first, byte-stable serialization, and templates that do not inject changing content or rewrite history.
  • Measure hit rate in tokens, and watch it fall under load as blocks are evicted.
  • Extend the cache to CPU memory, SSD and shared network stores; reload from CPU almost always beats recomputation, and compact caches widen the advantage.
  • Route by cache contents, balanced with load; cache-blind routing throws most of the cache away.
  • Non-prefix reuse (CacheBlend) is possible but approximate.
