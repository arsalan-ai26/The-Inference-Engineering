Evaluating and serving fine-tuned models

A fine-tune is finished only when you can show it is better on the task, no worse elsewhere, and served correctly. This chapter covers building a task evaluation and regression checks, the statistics of "is this really better?", the many ways evaluation numbers fail to reproduce, then serving: merging an adapter or keeping it separate, the precision trap in merging, serving many LoRA adapters on one base model, and keeping training and inference numerically consistent.

Level: core Time: 3 hours with the lab Needs: 6.6, 7.2, 7.3 Compute: Colab CPU (Part D: any GPU)
Before you start: skip check
  1. Your fine-tune scores 82% and the base 79% on a 100-item evaluation. Is it better?
  2. You merge a LoRA adapter into BF16 weights. Is the merged model identical to base plus adapter?
  3. Fifty customers each have their own LoRA adapter on the same 8B base. Fifty deployments, or one?
Answers
  1. Not shown. With 100 items, the 95% interval on 80% accuracy is about ±8 points, so a 3-point gap is noise. Use more items, or a paired comparison on the same items.
  2. No. Adding a small update to BF16 weights rounds it; in the lab, merged and unmerged logits differed by up to 2.7 and the top token changed on 9% of positions. Merging in FP32 matched to 1e-4. Merge in higher precision, then cast, and re-run the evaluation on the merged artifact.
  3. One. Multi-LoRA serving keeps one base model in memory and applies each request's adapter in the same batch (S-LoRA, vLLM's --enable-lora).

1. What to evaluate

Definitions

Task evaluation: a held-out set from your real use case, scored the way the product needs (exact field match, unit tests passing, a rubric).

General benchmark: a public test of broad ability (instruction following, maths, knowledge), used here to catch regressions.

Regression check: a fixed set of evaluations every new checkpoint must not get worse on.

LLM-as-a-judge: using a model to score outputs against a rubric or to compare two outputs.

  • The task evaluation decides. It must come from the same distribution as production, be held out before training, and be scored by the metric that matters.
  • General evaluations guard against forgetting (chapter 7.2): a small set of instruction following, the base model's other languages, safety behaviour, and any capability the product also relies on.
  • Vibe checks matter too. Hugging Face found that interacting with intermediate checkpoints catches problems benchmarks miss; read 20 outputs before trusting a score.
  • Serving evaluations: the same tests through the production stack (chat template, quantization, engine), since that is what users get (chapter 6.6).

Is it really better? Sample size

95% interval on an accuracy p over n items ≈ p ± 1.96 × √(p × (1 − p) ÷ n)

At 80% accuracy: ±7.8 points with 100 items, ±3.5 with 500, ±1.8 with 2,000. Comparing two models on the same items (a paired test, counting items where only one is right) is more sensitive than comparing two independent scores. For a product decision, size the evaluation to detect the smallest difference you care about.

Why evaluation numbers do not reproduce

Hugging Face's evaluation guidebook lists the usual causes, all of which apply to before-and-after comparisons of your own fine-tune:

  • Metric definitions: "exact match" may be log-likelihood or generative, prefix or full, with or without normalization (punctuation, number formats).
  • Prompt format: semantically identical multiple-choice layouts can move scores by several points; few-shot examples must be the same ones.
  • Chat template and system prompt: not using the model's template "will kill its performance".
  • Generation settings: end-of-sequence token, maximum tokens, temperature and seed.
  • Model loading: hardware, library (Transformers vs vLLM), batch size and precision all change numerics (chapter 6.6's batch invariance).

LLM judges have known biases: position (prefer the first answer), verbosity (prefer longer), self-preference (prefer their own outputs), inconsistency across samples, and weakness at spotting partial hallucinations. Mitigations: randomize positions, ask for reasoning before the score with a clear scale, use several judges, and check the judge against human labels on a sample.

2. Merge or keep the adapter?

Merged weightsSeparate adapter
Inference costSame as the base modelA small extra matmul pair per layer (in the lab, about 14% at batch 1 on CPU, negligible at batch 8)
Storage per variantA full modelMegabytes (42 M parameters for an 8B model at rank 16: about 84 MB in BF16)
Many variants on one GPUNoYes, with multi-LoRA serving
QuantizationQuantize the merged model like any other (chapter 4.1)Base quantized, adapter kept in 16-bit
Best forOne fine-tune at high volumeMany customers or tasks, frequent updates

The merge precision trap. A trained update is small relative to the weights. Added to BF16 weights (8 bits of mantissa), much of it rounds away or changes. The lab measures it: merging in FP32 reproduced the unmerged model to within 1.4 × 10⁻⁴ in the logits; merging in BF16 differed by up to 2.7 and changed the top token at 9% of positions. Merge in FP32, cast once, and evaluate the merged artifact you will ship. An adapter trained on a 4-bit QLoRA base learned to correct those quantized weights; merging it into BF16 weights is a different model and needs its own evaluation.

3. Serving many adapters

S-LoRA showed that adapters from one base model can be served together: all adapters live in CPU memory, the ones needed by running requests are fetched to the GPU, a unified paging pool holds both adapter weights (of different ranks) and KV cache blocks, and custom kernels batch requests that use different adapters. It served thousands of adapters on one GPU with up to 4 times the throughput of Hugging Face PEFT and early vLLM LoRA support.

vLLM's LoRA support today:

  • --enable-lora with --lora-modules name=path; each request names its adapter in the model field.
  • max_loras (adapters active in one batch on the GPU), max_lora_rank (largest rank allowed), max_cpu_loras (adapters cached in CPU memory).
  • Runtime loading with /v1/load_lora_adapter and /v1/unload_lora_adapter (when VLLM_ALLOW_RUNTIME_LORA_UPDATING is set), or LoRAResolver plugins that fetch an adapter from a local directory, the Hugging Face Hub or your own store such as S3 on first use.

Routing matters with many adapters: a request whose adapter is already on a replica avoids a load, so gateways route by adapter as they route by prefix (chapter 6.4). Popular adapters can be pinned; rare ones loaded on demand.

4. Train-inference mismatch

A model trained in one stack and served in another can behave differently: a different chat template, tokenizer version, sampling defaults (chapter 6.6), quantization, or simply different kernels. For RL, the mismatch is critical, because the sampler's probabilities feed the training update (chapter 7.4). vLLM and TorchTitan demonstrated bitwise-consistent RL on Qwen3-1.7B: they audited every forward kernel, used vLLM's batch-invariant kernels in both, and wrote matching backward passes. With matched numerics the KL between trainer and sampler stayed exactly 0, training reached higher reward in fewer steps, and the run was 2.4 times slower than the non-bitwise one, a cost they aim to cut.

For SFT and DPO the practical checklist is shorter: same tokenizer files, same chat template, same generation settings in evaluation and production, and a golden-output test on the serving stack (chapter 6.6).

5. Expert layer

Heterogeneous LoRA batching

In one decode step, different requests use different adapters of different ranks. Gathering each request's A and B and running one small matmul per adapter would launch many tiny kernels; S-LoRA and later Punica-style kernels instead batch the LoRA computation across adapters in one kernel (a segmented or gathered matmul), keeping the extra cost close to the merged case.

Serverless adapters

Some platforms offer per-token inference for user-uploaded LoRA adapters on shared base models (Weights & Biases, among others), billing like an API while you own the adapter: multi-LoRA serving as a product.

6. Common mistakes

  • Declaring a win on a 100-item evaluation with a 3-point gap.
  • Evaluating with a different template, prompt format or generation settings from production.
  • Merging into BF16 and shipping without re-evaluating the merged artifact.
  • One deployment per adapter when multi-LoRA serving would do.
  • max_lora_rank below an adapter's rank, so it fails to load.
  • Trusting an LLM judge without checking it against human labels.

7. Lab

Part A: is a merged adapter the same model?

import torch
from transformers import AutoModelForCausalLM
from peft import LoraConfig, get_peft_model
for dtype in [torch.float32, torch.bfloat16]:
    torch.manual_seed(0)
    m = get_peft_model(AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct", dtype=dtype).eval(),
                       LoraConfig(r=16, lora_alpha=32, target_modules="all-linear", task_type="CAUSAL_LM"))
    for n, p in m.named_parameters():                   # stand-in for a trained adapter: small non-zero B
        if "lora_B" in n: torch.nn.init.normal_(p, std=0.002)
    x = torch.randint(0, 150000, (1, 64))
    with torch.no_grad():
        a = m(x).logits.float()
        with m.disable_adapter(): b = m(x).logits.float()
        c = m.merge_and_unload()(x).logits.float()
    print(dtype, f"adapter effect {(a-b).abs().max():.2f}; merged vs unmerged {(a-c).abs().max():.1e}; "
          f"same top token {(a.argmax(-1) == c.argmax(-1)).float().mean():.0%}")

Predict first: will the merged model match the unmerged one in both precisions?

What we measured (CPU)
torch.float32   adapter effect 3.28; merged vs unmerged max diff 1.4e-04; same top token 100%
torch.bfloat16  adapter effect 3.59; merged vs unmerged max diff 2.7e+00; same top token 91%

In FP32 the merge is exact to rounding. In BF16 the merge changes the model nearly as much as the adapter itself does. Note that Transformers 5 loads this checkpoint in BF16 by default when no dtype is given, so this trap is easy to fall into.

Part B: what does an unmerged adapter cost?

import time
def timeit(m, x, reps=3):
    with torch.no_grad():
        m(x); t = time.perf_counter()
        for _ in range(reps): m(x)
    return (time.perf_counter() - t) / reps
# time the PEFT model (adapter separate) for one decode step at batch 1 and 8, and one 256-token prefill,
# then m = m.merge_and_unload() and time again

About 14% extra at batch 1 and 9% for a prefill, nothing measurable at batch 8: the adapter adds a fixed amount of small work. On a GPU, engine kernels for batched LoRA keep the overhead small; Part D measures it.

8. In the real world

In practice
  • Platforms serve thousands of customer adapters on shared base models with multi-LoRA serving and adapter-aware routing.
  • Release pipelines for fine-tunes run task, general and serving-stack evaluations on the exact artifact being deployed (chapter 6.5).
  • RL teams track and correct train-inference mismatch, and some run bitwise-consistent stacks.

9. Check yourself

10. Summary

  • Decide on a held-out task evaluation sized for the difference you care about; guard against forgetting with general checks; read outputs.
  • Control metric definitions, prompts, templates, generation settings and loading when comparing scores.
  • Merge for one high-volume fine-tune (in FP32, then cast, then re-evaluate); keep adapters separate for many variants.
  • Serve many adapters on one base with multi-LoRA serving and adapter-aware routing.
  • Keep training and serving stacks consistent; for RL, mismatch matters most.
