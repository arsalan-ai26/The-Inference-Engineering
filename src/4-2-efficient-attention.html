Efficient attention and attention kernels

Attention is the one part of a transformer whose cost grows with the context. At short contexts it is a small share of the work; at 128K tokens it is most of it. There are two kinds of fixes. Architecture fixes change what is computed or stored: fewer KV heads, compressed caches, windows, sparse selection. Kernel fixes compute exactly the same thing with far less memory traffic: FlashAttention and its decode-time relatives. This chapter covers both, and builds FlashAttention's core trick, the online softmax, with numbers you can check by hand.

Answers
  1. No. It gives the same result as standard attention (up to floating-point rounding). It only changes the order of work so the large score matrix never goes to HBM.
  2. Usually MLA. DeepSeek-style MLA stores one 576-value latent per token per layer, against 2 × 8 × 128 = 2,048 values for GQA with 8 KV heads of size 128.
  3. It splits work across query tiles and batch. In decode there is one query per sequence, so there are too few tiles to fill all SMs. Flash-Decoding also splits along the keys.

1. Why attention cost grows with context

Chapter 2.2 counted the work. For one layer and T tokens with model width d (all heads together):

  • The linear layers (QKV projection, output projection, MLP) do about 2 × parameters FLOPs per token. Their cost grows linearly with T.
  • The attention scores and weighted sum (Q Kᵀ and P V) do about 4 × T × d FLOPs per token without a mask, about half that with a causal mask. Over a whole prompt that is proportional to T²: it grows quadratically.

In decode, each new token attends to all T earlier tokens: it reads T keys and T values per layer (the KV cache, chapter 2.4). So decode attention cost grows linearly with context, and at long contexts and large batches that KV read dominates the step.

At 8K tokens attention is about 12% of prefill math. At 128K it is about two thirds. This is why every long-context model changes its attention, and why attention kernels get so much engineering.

2. Fewer keys and values: MQA, GQA and MLA

Chapter 2.4 introduced these as ways to shrink the KV cache. Here is the full picture in one place, for a model with 80 layers, 64 query heads of size 128, in BF16.

The trade-offs. MQA is smallest but loses quality, because every query head must share one key and one value. GQA is the common middle ground. MLA compresses keys and values into a low-rank latent that is expanded inside attention; it caches less than GQA-8 while keeping quality close to MHA, at the cost of extra math to expand the latent and specialized kernels. Note that MLA has no factor of 2: keys and values come from the same cached latent.

Watch out

Fewer KV heads cut the KV bytes, not the score math. Every query head still computes scores against every cached token. GQA and MLA mainly speed up decode (fewer bytes) and raise capacity (more tokens fit); they do little for long-prompt prefill.

3. Attending to fewer tokens: windows, sinks and sparse attention

Sliding windows and local/global mixes

A sliding-window layer attends only to the last W tokens. Its cache stops growing at W tokens and its cost per token is constant. Models like Gemma 2 and 3 alternate many local-window layers with a few global (full) layers, so only the global layers keep a full-length cache (chapter 2.4). Engines must store a different cache length per layer type (chapter 3.3).

Attention sinks

If you simply drop the oldest tokens from a model trained with full attention, quality collapses once the text is longer than the window. The StreamingLLM paper found why: models put large attention weight on the first few tokens regardless of their meaning, using them as a "sink" for attention that has nowhere better to go. Keeping those first few tokens' KV plus a recent window restores stable output, up to millions of tokens in their tests. It does not give the model memory of the dropped middle; it only stops the collapse. Some recent models add a learned sink value per head for the same reason.

Sparse attention: pick the tokens that matter

DeepSeek Sparse Attention (DSA), introduced with DeepSeek-V3.2, keeps the full cache but lets each query attend to only k = 2,048 selected tokens. A small, cheap "lightning indexer" (few heads, can run in FP8) scores every earlier token, and the top-k are used for real attention. Core attention cost drops from O(T²) to O(T × k); the indexer is still O(T²) but much cheaper per pair. The model is trained to work this way, first by aligning the indexer with dense attention, then by training with sparse attention. Sparse attention needs its own kernels and cache handling (vLLM lists separate sparse MLA backends).

4. The real bottleneck in standard attention: memory traffic

Before FlashAttention, attention was computed in separate steps, each a separate kernel:

  1. S = Q Kᵀ ÷ √d. Write S, a T × T matrix per head, to HBM.
  2. Read S, apply the mask and softmax, write P (another T × T matrix) to HBM.
  3. Read P and V, compute O = P V, write O.

At T = 8,192 one head's S is 67 million numbers: 134 MB in BF16, written and read twice, for each of 32 heads in each of 32 layers. The softmax and masking do very little math per byte, so these steps are memory-bound, while the GPU's fast on-chip memory sits mostly unused.

Definitions

HBM: the GPU's main memory. Large (80 GB on an H100) but comparatively slow (about 3.35 TB/s).

SRAM (shared memory): small, fast memory inside each streaming multiprocessor (SM), up to about 228 KB per SM on an H100, which has 132 SMs. Its total bandwidth is roughly an order of magnitude higher than HBM. The FlashAttention paper quotes about 19 TB/s for the A100's SRAM against 1.5 to 2.0 TB/s for its HBM.

IO-aware algorithm: one designed around the cost of moving data between memory levels, not just the number of FLOPs.

Chapter 5.2 covers the memory hierarchy in depth. For now: if the T × T matrix could stay in SRAM, the slow steps would disappear. It does not fit. The answer is to never build it whole.

5. The key trick: online softmax

Softmax needs the maximum and the sum over a whole row of scores before any output can be finished. That seems to force you to compute the whole row first. It does not. You can process a row in blocks and fix up the earlier result whenever a new block changes the maximum.

Keep three running values per query row: the maximum seen so far m, the sum of exponentials so far l (each relative to m), and an unnormalized output acc. For each new block of scores s with values v:

m_new = max(m, max(s))   c = e^(m − m_new)   l = l × c + Σ e^(s − m_new)   acc = acc × c + Σ e^(s − m_new) × v

At the end, output = acc ÷ l. The factor c rescales everything computed so far to the new maximum.

Worked example (one query, four keys, two blocks)

Scores [1, 2 | 4, 3], values [10, 20 | 30, 40] (one number each, to keep it short).

Block 1 (scores 1, 2): m = 2. l = e^(−1) + e^0 = 0.368 + 1 = 1.368. acc = 0.368 × 10 + 1 × 20 = 23.68.

Block 2 (scores 4, 3): m_new = 4, so c = e^(2 − 4) = 0.135. l = 1.368 × 0.135 + e^0 + e^(−1) = 0.185 + 1 + 0.368 = 1.553. acc = 23.68 × 0.135 + 1 × 30 + 0.368 × 40 = 3.20 + 30 + 14.72 = 47.92.

Result: 47.92 ÷ 1.553 = 30.86. Full softmax over [1, 2, 4, 3] gives weights [0.032, 0.087, 0.644, 0.237] and output 0.32 + 1.74 + 19.32 + 9.48 = 30.86. Same answer, without ever holding all four scores at once.

6. FlashAttention: tiles that never leave the chip

With online softmax, attention becomes one fused kernel:

  1. Split Q into row tiles (for example 128 queries) and K, V into column tiles.
  2. Each thread block loads one Q tile into SRAM and keeps m, l and acc for its rows in registers or SRAM.
  3. Loop over the K and V tiles: load a tile, compute that block of scores, apply the mask, update m, l and acc. With a causal mask, skip tiles that are entirely in the future.
  4. Write only the final output tile (and one log-sum-exp number per row, used by training) to HBM.

The math is the same as standard attention, slightly more because of the rescaling. What changes is memory: standard attention needs on the order of T × d + T² HBM accesses, FlashAttention on the order of T² × d² ÷ M, where M is the SRAM size. With d around 64 to 128 and M around 100 KB, that is many times fewer. Memory use also drops from quadratic to linear in T, because no T × T matrix is stored.

The original paper reports 3 times faster GPT-2 training at 1K tokens and 2.4 times on long-range benchmarks, plus the ability to train at 16K and 64K contexts that were previously impractical. Since the result is exact, every engine uses it (or a relative) by default; in PyTorch, F.scaled_dot_product_attention picks a fused kernel when one is available.

The pattern across generations: as tensor cores get faster, the non-matmul parts (softmax exponentials, rescaling, data movement) become the bottleneck, and each version hides or removes more of them.

7. Attention in decode: different problem, different kernels

Decode attention has one query token per sequence (or a few, with speculative decoding). Two consequences:

  • It is memory-bound. Each step reads the whole KV cache of every sequence and does little math per byte (chapter 2.5). The goal is to read the cache at full bandwidth.
  • There is too little parallelism along queries. FlashAttention gives each query tile to a thread block. With one query per sequence and a small batch, only a few blocks run while most of the 132 SMs idle.

Flash-Decoding: split along the keys

Flash-Decoding splits each sequence's keys and values into chunks, processes the chunks in parallel on different SMs, and has each chunk write its partial output plus one number, its log-sum-exp. A small second kernel combines the chunks, weighting each by its log-sum-exp: the same online-softmax rescaling, applied across chunks. Its authors report attention itself up to 50 times faster than FlashAttention at long context and batch 1, and up to 8 times faster end-to-end generation for very long sequences. Part C of the lab implements the combine step.

Paged, batched and specialized kernels

Serving adds more requirements: keys and values live in pages (chapter 3.3), every sequence has a different length, prefill and decode tokens share one batch (chapter 3.2), and kernels must be compatible with CUDA graphs. Libraries built for this:

  • FlashInfer: an attention engine for serving with a block-sparse view of paged KV, JIT-compiled variants and load-balanced scheduling. Its paper reports 29% to 69% lower inter-token latency than compiler backends. Used by SGLang and vLLM.
  • FlashAttention's paged variants and vLLM's Triton attention backend (which runs on older GPUs such as the T4).
  • MLA kernels (FlashMLA, CUTLASS MLA, FlashInfer MLA) and sparse MLA kernels for DeepSeek-style models.

vLLM picks a backend automatically by GPU generation and model type: on Ampere and Hopper it prefers FlashAttention, then FlashInfer, then Triton; on Blackwell it prefers FlashInfer. You can override it:

vllm serve Qwen/Qwen2.5-7B-Instruct --attention-backend FLASHINFER

8. Expert layer

Context parallelism and ring attention

A single 1M-token prefill does not fit one GPU's memory or time budget. Context (sequence) parallelism splits the sequence across GPUs; ring attention passes K and V blocks around a ring of GPUs while each computes its queries' partial results, combined with the same log-sum-exp trick. Chapter 4.5 places this among the parallelism strategies, and chapter 4.7 uses it for long context.

FP8 attention

With an FP8 KV cache, some backends run the attention matmuls in FP8 too. FlashAttention-3 handles FP8's outliers with block quantization and "incoherent processing" (multiplying by a random orthogonal matrix to spread outliers), reporting 2.6 times lower error than a baseline FP8 attention. Softmax still runs in higher precision.

Why exponentials became a bottleneck

For head size 128, each score needs about 256 matmul FLOPs (on fast tensor cores) but also one exponential (on a much slower special-function unit). On the H100 the gap is already large; on the B200 tensor-core throughput doubled while the exponential units did not. FlashAttention-4 computes some exponentials with polynomial approximations on ordinary FMA units, and only rescales the output when the maximum grows enough to matter.

Long context is also a quality question

Efficient attention lets a model accept 1M tokens; it does not make the model use them well. Evaluations that go beyond simple "needle in a haystack" retrieval often find that effective context is much shorter than the advertised window. Chapter 4.7 covers long-context serving and evaluation.

9. Common mistakes

  • Calling FlashAttention an approximation, or expecting it to change outputs.
  • Expecting GQA or MLA to speed up long-prompt prefill; they cut KV bytes, not score math.
  • Counting MLA's cache with the factor 2 for keys and values.
  • Dropping old tokens without keeping sink tokens, then blaming the model.
  • Benchmarking attention kernels with prefill shapes and deploying them for decode, or the reverse.
  • Forcing an attention backend from an old blog post on a different GPU generation.

Part B: tiled attention with online softmax (CPU, seconds)

import torch, math
import torch.nn.functional as F
torch.manual_seed(0)
T, d = 1024, 64
q, k, v = (torch.randn(T, d) for _ in range(3))

def flash(q, k, v, Br=128, Bc=128):
    out = torch.empty_like(q)
    for i in range(0, T, Br):
        qi = q[i:i+Br]
        m = torch.full((qi.shape[0], 1), float("-inf"))   # running max per row
        l = torch.zeros(qi.shape[0], 1)                    # running sum of exp
        acc = torch.zeros(qi.shape[0], d)                  # running unnormalized output
        for j in range(0, i + Br, Bc):                     # causal: skip future tiles
            kj, vj = k[j:j+Bc], v[j:j+Bc]
            s = qi @ kj.T / math.sqrt(d)
            rows = torch.arange(i, i + qi.shape[0])[:, None]
            cols = torch.arange(j, j + kj.shape[0])[None]
            s = s.masked_fill(cols > rows, float("-inf"))
            # TODO: m_new, p = exp(s - m_new), corr = exp(m - m_new)
            # TODO: update l and acc with corr, then m = m_new
        out[i:i+Br] = acc / l
    return out

ref = F.scaled_dot_product_attention(q[None], k[None], v[None], is_causal=True)[0]
print("max error", (flash(q, k, v) - ref).abs().max().item())
Solution 
            m_new = torch.maximum(m, s.amax(-1, keepdim=True))

            corr = torch.exp(m - m_new)

Part D: naive vs fused, time and memory

import time
for T2 in [1024, 2048, 4096]:
    q2, k2, v2 = (torch.randn(8, T2, 64) for _ in range(3))
    t = time.time(); torch.softmax(q2 @ k2.transpose(1, 2) / 8, -1) @ v2; tn = time.time() - t
    t = time.time(); F.scaled_dot_product_attention(q2, k2, v2); ts = time.time() - t

What we measured, and why

On a 2-core CPU: about 93 vs 25 ms at 1K, 354 vs 110 ms at 2K, 1,374 vs 358 ms at 4K; the naive score matrices take 34, 134 and 537 MB. Time grows about 4 times per doubling of T for both (quadratic math), but the naive version also allocates a quadratic matrix. On a T4 GPU (move tensors to "cuda", use float16, and call torch.cuda.synchronize() before reading the clock) the gap is larger, and the naive version runs out of memory first as T grows.

11. In the real world

Where these choices show up
  • Every serving engine uses fused, IO-aware attention by default: FlashAttention, FlashInfer or vendor kernels (cuDNN, TensorRT-LLM).
  • Model designers choose GQA, MLA, windows or sparse attention largely for inference cost: DeepSeek's MLA and DSA, Gemma's local/global layers, and hybrids from chapter 2.7.
  • New models often wait on kernel support: an attention variant without fast paged kernels serves slowly no matter how good its design.
  • Hardware generations each get new attention kernels (FA3 for Hopper, FA4 for Blackwell), and engines select them automatically.

13. Summary

  • Attention math grows with T² in prefill and its KV reads grow with T in decode; at 128K tokens it dominates.
  • MQA, GQA and MLA shrink what is cached; windows, sinks and sparse top-k shrink what is attended to.
  • Standard attention is slow because T × T matrices travel through HBM. FlashAttention tiles the work and uses online softmax, so they never leave the chip: same result, far less memory traffic, linear memory.
  • Each FlashAttention generation adapts to new hardware: better work partitioning, Hopper asynchrony and FP8, Blackwell's exponential bottleneck.
  • Decode needs different kernels: Flash-Decoding splits along keys; serving libraries such as FlashInfer handle pages, ragged batches and CUDA graphs.
