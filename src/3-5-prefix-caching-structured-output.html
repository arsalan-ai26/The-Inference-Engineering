Prefix caching, RadixAttention and structured output

Real traffic repeats itself. The same system prompt starts thousands of requests, every turn of a chat re-sends the whole history, and agents call the model again and again over a growing context. Reusing the KV cache of repeated prefixes can remove most of the prefill work. This chapter covers how engines find and keep reusable prefixes (block hashing in vLLM, the radix tree in SGLang), what makes reuse safe, and the second big SGLang idea: forcing output to follow a grammar, which is how JSON mode and tool calling work inside an engine.

Answers

  2. Only if they produce exactly the same token IDs in the same order. Reuse is by tokens (plus model, adapter and other keys), not by text meaning.

1. The problem: the same prefill again and again

Recall from chapter 2.4 that a token's keys and values depend only on the tokens before it. So if two requests start with exactly the same tokens, the KV cache for that shared start is identical. Computing it twice is pure waste. Where repeated prefixes come from:

  • System prompts and few-shot examples shared by every request of an application.
  • Multi-turn chat: turn 10 re-sends turns 1 to 9.
  • RAG: popular documents appear in many prompts.
  • Agents: each tool-use step re-sends the growing transcript.
  • Parallel sampling and evaluation: many completions or questions over one long context.

Prefill is compute-bound (chapter 2.5). Skipping it lowers time to first token directly and frees GPU time for other requests. That is why hosted APIs bill cached input tokens at a discount.

2. Block hashing (vLLM automatic prefix caching)

vLLM builds prefix caching on the paged KV cache of chapter 3.3. Each full block gets a hash computed from three things:

block hash = hash( parent block's hash , this block's token IDs , extra keys )
  • The parent hash chains every block to everything before it, so equal hashes mean equal full prefixes, not just equal blocks.
  • The token IDs of the block itself.
  • Extra keys that must also match: the LoRA adapter, hashes of images or other multimodal inputs, and an optional per-request cache salt.

The engine keeps a table from block hash to physical block. When a request arrives:

  1. Hash the prompt block by block and look each hash up, stopping at the first miss.
  2. Point the request's block table at the matching cached blocks (raising their reference counts) and schedule only the remaining tokens for prefill.
  3. After the new blocks are filled, add their hashes to the table.

When a request finishes, its blocks are not erased. Their reference counts fall to 0 and they join the free queue with their contents and hashes intact. They are evicted only when the allocator needs a free block, in least-recently-used order. So the cache uses all otherwise-idle KV memory, at no cost to normal allocation.

Since v0.11, vLLM's default hash is SHA-256, chosen to make collisions practically impossible. Faster non-cryptographic hashes are available as options, with a documented collision risk.

3. RadixAttention (SGLang)

SGLang takes a different data structure. It keeps a radix tree (a compressed prefix tree) over the token sequences of all cached requests. Each edge holds a run of tokens and points at their KV entries. Requests that share a beginning share the path from the root.

The SGLang paper reported up to 6.4 times higher throughput than earlier systems on workloads with heavy sharing (agents, few-shot, RAG, multi-turn chat, JSON decoding). Both designs now perform well; the bigger difference in practice is how each engine's scheduler and router use the cache.

4. When is reuse safe?

Prefix caching does not change outputs when it is correct, because the reused keys and values are exactly what prefill would compute. Correctness depends on the cache key covering everything that changes the KV:

Must matchWhyHow engines handle it
Exact token IDs from the startK and V depend on every earlier tokenChained block hashes or tree paths
Model weights and revisionDifferent weights give different K and VOne cache per loaded model
Tokenizer and chat templateSame text can tokenize differently; templates add tokensReuse is by token IDs, so mismatches simply miss
LoRA adapterAdapters change the projectionsAdapter ID in the extra keys
Images and other mediaPlaceholder tokens look identical for different imagesMedia hashes in the extra keys
Tenant (optional)A shared cache leaks timing: a fast TTFT reveals that someone else sent that prefixA per-tenant cache salt mixed into the first block's hash
Watch out: hash collisions

If two different prefixes ever produced the same hash, one request would silently reuse another's KV cache: wrong output, and possibly another user's data in the response. That is why vLLM moved to SHA-256 by default, and why some small engines also compare the stored token IDs after a hash match before reusing a block.

5. Eviction, churn and hit rates

The prefix cache lives in free KV memory, so its size changes with load. When many requests are running, there is little free memory, cached blocks are evicted quickly, and the hit rate falls exactly when you need it most. This is cache churn.

Interactive: hit rate vs cache size
A simulated mixed workload: a shared 600-token system prompt, RAG documents with a few very popular ones, and multi-turn sessions that grow by about 180 tokens a turn. LRU eviction over 16-token blocks.

Ways teams raise hit rates:

  • Put stable content first. System prompt, then tools, then documents, then the conversation, then the new question. Anything that changes per request (a timestamp, a user name) placed early breaks every block after it.
  • Route by prefix. Send requests that share a prefix to the same replica (chapter 6.4). A cache on replica A does nothing for a request sent to replica B.
  • Extend the cache beyond GPU memory. Offload cold blocks to CPU memory or SSD and load them back on a hit (chapter 4.7).
  • Measure. vLLM reports prefix_cache_queries and prefix_cache_hits (in tokens); the ratio is the hit rate (chapter 3.1).
Real-world case: scoring many items with one prefix

LinkedIn uses SGLang for recommendation scoring: a long member context followed by one short candidate item, with almost no output. Prefix caching alone still re-sends the member context once per item. Their "multi-item scoring" packs the member prefix and many candidate items into one prompt, with a custom attention mask so each item sees the prefix but not the other items. They added this mask to FlashInfer's attention kernels and contributed it upstream.

6. Structured output: making the model follow a grammar

Applications often need output that a program can parse: JSON matching a schema, a value from a fixed list, a date in one format, or a function call. Asking politely in the prompt works most of the time. "Most of the time" breaks production code.

Constrained decoding (also called guided decoding or structured output) guarantees the format. It builds on the logit bias of chapter 1.2:

  1. Compile. Turn the JSON schema, regular expression or grammar into an automaton: a machine that knows which characters may come next in any state.
  2. Mask. At each step, find every vocabulary token whose characters keep the automaton in a valid state. Build a bitmask over the vocabulary.
  3. Apply. Set the logits of all masked-out tokens to −∞, then sample as usual (temperature, top-p and so on still apply among the allowed tokens).
  4. Advance. Feed the chosen token's characters into the automaton.
Interactive: constrained decoding, token by token
Target schema: {"city": string, "temp": integer}. A toy model prefers some tokens (bar height). Grey tokens are blocked by the grammar in the current state. With the grammar off, the model's favourite at one step breaks the JSON.

What it costs, and how engines hide it

A vocabulary has 100,000 to 260,000 tokens, and a single token can span several grammar symbols (for example ":"). Checking every token at every step is expensive. Modern grammar engines are fast because of two ideas:

  • Precompute what does not depend on context. XGrammar splits the vocabulary into tokens whose validity can be decided ahead of time for each grammar position, and the few that must be checked at run time against the parser's stack. It caches the precomputed masks.
  • Work lazily and in parallel. LLGuidance builds its automaton lazily and walks a prefix tree of the vocabulary each step, so it starts quickly even for new schemas.

Engines then overlap mask generation with the GPU's forward pass, so the mask is ready when the logits are. An independent benchmark across vLLM and SGLang found the best choice depends on the workload: with one schema reused many times, XGrammar's precomputation and caching gave the highest throughput; with a new schema on every request, grammar compile time dominated, and the lazy approach and each engine's integration mattered more. Compiling a new grammar can add noticeable latency to the first request that uses it; vLLM's documentation warns of several seconds for complex schemas.

SGLang's paper adds jump-forward decoding with a compressed automaton: when the grammar allows only one continuation (for example the literal "temp": after a comma), the engine appends those tokens directly without running the model for each one.

Watch out: valid is not the same as correct

Constraints guarantee format, not content. Forcing a structure the model did not plan can also lower quality, for example when a schema puts the answer field before the reasoning field. Describe the schema in the prompt too, so the model's intent and the mask agree.

7. Tool calling at the inference layer

When you send tools to an OpenAI-compatible endpoint, four layers work together:

  1. API request. Tools arrive as a separate field with JSON schemas.
  2. Chat template. The model's template renders the tool definitions into the prompt in the format the model was trained on (chapter 2.1). This is why a wrong template breaks tool use.
  3. Generation. The model writes the call as text in its own format, often inside special markers such as <tool_call>...</tool_call>. With tool_choice set to "required" or to a named function, vLLM uses structured output to force a call that matches the schema. With "auto", the model decides whether to call a tool, unconstrained by default.
  4. Parsing. A model-family-specific tool parser (selected in vLLM with --tool-call-parser, with --enable-auto-tool-choice) extracts the call from the text and returns it in the structured tool_calls field. When streaming, it must emit partial calls as arguments arrive.

Each layer is a place to fail: a template that renders tools differently from training, a parser that does not match the model's markers, or arguments that are valid JSON but violate the schema when unconstrained. Tool-calling quality varies noticeably between inference providers serving the same open model, mostly for these reasons.

8. Expert layer

Programs, not prompts

SGLang began as a language for LLM programs: primitives such as gen, select and fork let one program branch into parallel calls that share a prefix. The runtime sees the whole program, so it can keep the shared prefix cached and schedule the branches together. Agent frameworks get much of the same benefit from prefix caching plus prefix-aware routing.

Positions and cached prefixes

Cached keys already carry their RoPE positions (chapter 2.3). A cached block can therefore only be reused at the same position in a new sequence. Reusing a document's KV in the middle of a different prompt, at a different offset, is not exact; research on "position-independent" caching tries to correct for this, at some quality cost.

Cache-aware scheduling trade-offs

Serving requests with the longest cached prefix first raises hit rates but can starve requests that share nothing. Engines combine cache-aware ordering with fairness limits. Across replicas, routers face the same trade-off between cache affinity and load balance (chapter 6.4).

Token-efficient formats

JSON spends many tokens on quotes, braces and repeated keys. Some projects propose compact structured notations to cut output tokens, and so decode time and cost. Measure with your model's tokenizer before switching: models are trained mostly on JSON, and an unfamiliar format can cost accuracy.

9. Common mistakes

  • Putting a timestamp, request ID or user name at the start of the system prompt, breaking every cache hit after it.
  • Measuring prefix-cache benefit on an idle server; churn under load can remove most of it.
  • Sharing one cache across tenants without a salt when timing side channels matter.
  • Using a new JSON schema per request and blaming the model for slow first tokens; check grammar compile time.
  • Assuming tool_choice: "auto" guarantees schema-valid arguments.
  • Serving a model with the wrong tool parser or chat template and concluding the model is bad at tools.

Part B: a prefix-cache simulator

This tested simulator implements block hashing with LRU eviction and a mixed workload. Read it, then predict the hit rate for each capacity before you run it.

import hashlib, random
from collections import OrderedDict

class PrefixCache:
    """Block-hash prefix cache with LRU eviction (the idea behind vLLM automatic prefix caching)."""
    def __init__(self, capacity_blocks, block_size=16, salt=""):
        self.cap, self.bs, self.salt = capacity_blocks, block_size, salt
        self.lru = OrderedDict()                       # block hash -> None, oldest first
        self.queries = self.hits = 0                   # counted in tokens

    def _hashes(self, tokens, extra=""):
        h, out = (self.salt + extra).encode(), []
        for i in range(len(tokens) // self.bs):        # only FULL blocks can be cached
            blk = tokens[i * self.bs:(i + 1) * self.bs]
            h = hashlib.sha256(h + repr(blk).encode()).digest()   # parent hash + this block's tokens
            out.append(h)
        return out

    def run(self, tokens, extra=""):
        """Process one prompt. Returns the number of prompt tokens that must be prefilled."""
        hs = self._hashes(tokens, extra)
        hit = 0
        for h in hs:                                   # longest cached prefix, block by block
            if h in self.lru:
                hit += 1; self.lru.move_to_end(h)
            else:
                break
        for h in hs[hit:]:                             # the new blocks become cached after prefill
            self.lru[h] = None; self.lru.move_to_end(h)
            while len(self.lru) > self.cap:
                self.lru.popitem(last=False)           # evict least recently used
        self.queries += len(tokens); self.hits += hit * self.bs
        return len(tokens) - hit * self.bs

def workload(seed=0, n=2000, n_docs=200, n_sessions=100):
    rnd = random.Random(seed)
    system = list(range(1000, 1600))                   # 600-token shared system prompt
    docs = [[rnd.randint(0, 50000) for _ in range(800)] for _ in range(n_docs)]
    sessions = {s: [] for s in range(n_sessions)}
    for _ in range(n):
        s = rnd.randrange(n_sessions)
        doc = docs[min(int(rnd.paretovariate(1.2)) - 1, n_docs - 1)]   # popular documents are reused
        if not sessions[s]: sessions[s] = system + doc
        sessions[s] = sessions[s] + [rnd.randint(0, 50000) for _ in range(60)]   # new user turn
        yield list(sessions[s])
        sessions[s] = sessions[s] + [rnd.randint(0, 50000) for _ in range(120)]  # model reply joins history

for cap in [200, 1000, 5000, 20000]:
    c = PrefixCache(cap); prefill = sum(c.run(p) for p in workload())
    print(f"cache {cap:6d} blocks: token hit rate {c.hits / c.queries:6.1%}  prefill tokens {prefill:,}")
What you should see

About 14%, 39%, 59% and 94% token hit rates for 200, 1,000, 5,000 and 20,000 blocks. The hit rate rises steeply once the cache can hold the active sessions' histories. Then try: (1) put a random 16-token "timestamp" at the start of every prompt and watch the hit rate collapse; (2) use a different salt per session and see what isolation costs.

URL = "http://localhost:8000/v1/chat/completions"

          "year": {"type": "integer"}, "genres": {"type": "array", "items": {"type": "string"}}},
          "required": ["title", "author", "year", "genres"]}
def ask(i, constrained):
    body = {"model": "Qwen/Qwen2.5-0.5B-Instruct", "max_tokens": 120, "temperature": 0,
            "messages": [{"role": "user", "content": f"Give book metadata as JSON with title, author, year, genres for a famous novel number {i}."}]}
    if constrained:
        body["response_format"] = {"type": "json_schema", "json_schema": {"name": "book", "schema": schema}}
    t = time.perf_counter(); r = requests.post(URL, json=body).json(); dt = time.perf_counter() - t

    try: obj = json.loads(txt); ok = all(k in obj for k in schema["required"])
    except Exception: ok = False
    return dt, ok

11. In the real world

Prefix reuse and structure in production
  • Hosted APIs offer prompt caching with a discount on cached input tokens and a limited cache lifetime. Providers tell customers to put stable content first, exactly as in section 5.
  • Agent platforms depend on prefix caching: each step re-sends a growing context, and without reuse the cost of an agent grows with the square of its steps.
  • Routers in large deployments are prefix-aware, sending related requests to the replica that holds their cache (chapter 6.4).
  • Structured output through XGrammar or LLGuidance is the default in vLLM and SGLang; JSON mode and tool calling in OpenAI-compatible servers are built on it.

13. Summary

  • Identical token prefixes have identical KV; reusing them skips compute-bound prefill and cuts TTFT.
  • vLLM hashes each full block with its parent hash and extra keys, keeps freed blocks cached, and evicts LRU. SGLang keeps a radix tree with token granularity and cache-aware scheduling.
  • Reuse is safe only when tokens, model, adapter, media and (optionally) tenant salt all match; strong hashes prevent collisions.
  • Hit rates fall under load (churn). Put stable content first, route by prefix, and offload cold blocks.
  • Structured output compiles a grammar and masks invalid tokens each step; XGrammar precomputes, LLGuidance works lazily; engines overlap masks with GPU work.
  • Tool calling = template + generation (+ constraints for required or named calls) + model-specific parser.
