Read an inference engine

Chapter 3.4 explained an engine's parts with small reference engines. This chapter goes into the real thing: vLLM's own source, about 213,000 lines in its v1 package alone. You will get a map of the codebase by process, directory, file and class; follow one request from the HTTP call to the streamed token with real function names; see where the scheduler, KV cache manager, model runner, attention backends and sampler live; and learn a method for reading and changing a large engine without getting lost.

Level: expert Time: 4 to 6 hours with the lab Needs: 3.1 to 3.5, 5.6 Compute: CPU for reading; a GPU to trace and profile
Before you start: skip check
  1. In vLLM, which process runs the scheduler, and which processes run the model?
  2. Does vLLM's scheduler have a separate prefill phase and decode phase?
  3. Where would you add a new per-step metric about preemptions?
Answers
  1. The engine core process (one per data-parallel rank) runs the scheduler and KV cache manager; one GPU worker process per GPU loads weights and runs forward passes. API server processes handle HTTP and tokenization and talk to engine cores over ZMQ sockets.
  2. No. Each request has a count of computed tokens and a count of tokens it needs; every step the scheduler assigns tokens so requests catch up, which covers chunked prefill, prefix caching and speculative decoding with one rule.
  3. In vllm/v1/core/sched/scheduler.py, where _preempt_request runs inside Scheduler.schedule, recorded through the scheduler's stats into vllm/v1/metrics, behind a configuration flag.

API servers and engine cores talk over ZMQ sockets in a many-to-many topology, so any API server can route to any engine core. This split is why chapter 6.2 warned about CPU sizing: tokenization, detokenization and streaming run on CPU in separate processes from the scheduler.

2. One request, end to end

Interactive: follow one chat request through vLLM
Step through the path a streaming chat request takes. Each step names the process, the file and the function.

The engine core step

EngineCoreProc.run_busy_loop repeats two things: _process_input_queue (take new requests and aborts from the API servers) and _process_engine_step, which calls EngineCore.step. Its body is short and worth reading in full; in outline:

scheduler_output = self.scheduler.schedule(...)                     # who runs, with how many tokens
future = self.model_executor.execute_model(scheduler_output, non_block=True)
grammar_output = self.scheduler.get_grammar_bitmask(scheduler_output)  # structured output masks
model_output = self._wait_for_output(future)
if model_output is None:
    model_output = self.model_executor.sample_tokens(grammar_output)
self._process_aborts_queue()                                         # cancellations during the step
engine_core_outputs = self.scheduler.update_from_output(scheduler_output, model_output)

Note the overlap: the grammar bitmask is computed on the CPU while the GPU runs the forward pass, and sampling happens after, so structured output costs little extra time (chapter 3.5). A variant, step_with_batch_queue, keeps several batches in flight for pipeline parallelism.

The scheduler's one rule

The comment at the top of Scheduler.schedule states the design: there is no prefill phase or decode phase; each request has num_computed_tokens and num_tokens_with_spec (prompt + output + speculative tokens), and each step the scheduler assigns tokens so the first catches up with the second, within max_num_batched_tokens. A new prompt needs many tokens (prefill, chunked if the budget is smaller); a running request needs one (decode) or several (speculative verification); a prefix-cache hit simply starts with num_computed_tokens already high. For each scheduled request, KVCacheManager.allocate_slots reserves blocks from the BlockPool; if none are free, _preempt_request evicts a running request, which returns to RequestStatus.PREEMPTED (chapter 3.3).

Request states

RequestStatus lists the life of a request: WAITING, WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR (grammar still compiling), WAITING_FOR_REMOTE_KVS (KV arriving from a prefill worker, chapter 4.6), WAITING_FOR_STREAMING_REQ, RUNNING, PREEMPTED, and finished states: stopped, length-capped, aborted, ignored, error and repetition. Every state you saw in metrics (chapter 3.1) maps to one of these.

3. How to read a large engine

  1. Start from a request, not from a directory. Find the API handler, then follow calls with "go to definition" until you reach EngineCore.step.
  2. Read the loop, then the data. The step loop is short; most complexity sits in data structures (SchedulerOutput, the input batch, attention metadata). Print one of each for a real request.
  3. Use logs and a debugger on a tiny model. Run a small model with enforce_eager=True (no CUDA graphs) and one request, and set breakpoints in schedule, execute_model and update_from_output. The offline LLM class with VLLM_ENABLE_V1_MULTIPROCESSING=0 keeps everything in one process, which makes breakpoints easy.
  4. Profile to see what matters. vLLM can capture torch profiler traces; read which kernels and CPU functions dominate (chapter 5.6).
  5. Read the design docs and blogs alongside the code: vLLM's architecture overview and Aleksa Gordic's "Inside vLLM" walk the same structure with diagrams.
  6. Pin a commit. Write file and line references with the commit hash so your notes stay valid.

4. Changing one component

Chapter 3.4 covered the plugin system for out-of-tree changes. For learning, a small in-tree change behind a flag teaches the most:

  • A metric: count preemptions per step and their victims' lengths in Scheduler, expose it through the scheduler stats in vllm/v1/metrics, and graph it under load.
  • A scheduler policy: change which request is preempted (for example the one with the most computed tokens instead of the newest), behind an environment variable, and measure preemption counts and p99 latency under memory pressure.
  • A cache rule: refuse to cache prefixes shorter than N blocks, and measure hit rate and TTFT on a workload with many short unique prompts.

Rules for the change: keep the default path unchanged, add a unit test next to the existing ones in tests/v1/core/, run the relevant existing tests, and benchmark before and after with the chapter 6.1 method.

Three lessons. First, a single-model engine trades generality for depth: no model registry or backend selector, but kernels and a scheduler tuned for one architecture's heterogeneous cache (paged blocks plus per-sequence state slots, chapter 4.8). Second, the scheduler moved to C++ and plans by estimated compute, not by token counts: FlopsEstimator counts FP8-equivalent FLOPs per request (including the bounded-replay shortcut), which is how the prefill load balancer can solve for a chunk size that fills a time budget. Third, roles are types: a prefill engine refuses to decode, so disaggregation is a deployment of two engine types rather than a feature switched on in one engine. Comments in parts of the code are in Chinese, so a translation tool helps when reading the scheduler.

6. Expert layer

Async scheduling and overlapping CPU with GPU

With asynchronous scheduling (sched/async_scheduler.py), the engine schedules step n + 1 while step n runs on the GPU, hiding scheduler CPU time (chapter 5.1's overhead regime). The cost is complexity: the scheduler must plan with outputs it has not seen yet, which is why draft tokens for speculative decoding are updated in the worker in this mode, as the comment in post_step notes.

Attention backend selection

vllm/v1/attention/selector.py chooses a backend from the model (MLA, sliding windows, Mamba layers), the hardware, the KV cache dtype and user settings. Each backend supplies a metadata builder that converts the scheduler's batch into the layout its kernel needs (block tables, sequence lengths, split points). Most "why is this slower on my GPU" questions end in this selection and metadata code.

7. Common mistakes

  • Reading directories top to bottom instead of following a request.
  • Debugging with CUDA graphs and multiprocessing on, where breakpoints do not hit.
  • Notes without a commit hash.
  • Changing default behaviour instead of adding a flag.
  • Measuring a change without a before-and-after benchmark on the same workload.

9. In the real world

In practice
  • Inference teams keep forks or plugins of vLLM and SGLang and need engineers who can read and change them.
  • Debugging production issues (chapter 3.4's silent errors, chapter 6.6's correctness bugs) ends in this code.
  • Upstream contributions start as small, flagged, measured changes like Part C.

10. Check yourself

11. Summary

  • vLLM runs API servers, engine cores and GPU workers as separate processes connected by ZMQ and an executor.
  • The engine core loop is short: schedule, execute, grammar mask, sample, update; the scheduler assigns tokens so each request catches up.
  • Most code lives in the worker and attention backends; the scheduler and KV manager are compact.
  • Read by following a request, debug on a tiny model in one process, pin the commit, change things behind flags and measure.
