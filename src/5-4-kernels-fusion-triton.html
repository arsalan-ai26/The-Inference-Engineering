Kernels, fusion and Triton

A forward pass is a sequence of GPU kernels. Which kernels run, how many there are, and how much data each one moves through HBM decide most of a model's speed once the architecture is fixed. This chapter covers the kernels an inference engine runs, where they come from (vendor libraries, open kernel libraries, compilers), why fusing kernels is the most important optimization after batching, and how to read and write simple kernels in Triton, the Python-based language that most new inference kernels and compilers now use.

Answers
  1. Softmax is memory-bound. Done step by step it reads about 5MN and writes about 3MN elements for an M × N input; fused, it reads MN and writes MN. About 4 times less traffic.
  2. One thread block. The program works on a whole block of data at once; Triton's compiler decides how the block's threads and warps split the work.
  3. Kernels hard-code hardware details: tile sizes, shared memory use, tensor-core instructions (wgmma on Hopper, tcgen05 and TMEM on Blackwell). A new generation needs re-tuned or rewritten kernels.

The GEMMs and attention hold almost all the FLOPs. The rest hold few FLOPs but each costs at least one full read and write of an activation tensor plus a launch, which is why they are the first targets for fusion.

2. Where kernels come from, and kernel selection

  • Vendor libraries: cuBLAS (and cuBLASLt) for GEMMs, cuDNN for neural network primitives including attention. Solid defaults, closed source, tuned per GPU generation.
  • Template libraries: CUTLASS and its layout layer CuTe (C++), and CuTe-DSL (Python), are NVIDIA's building blocks for custom high-performance GEMMs and attention; FlashAttention-3 and 4 are built on them.
  • Open kernel libraries: FlashAttention, FlashInfer (attention and sampling for serving), DeepGEMM (FP8 GEMMs from DeepSeek), Marlin and Machete (mixed-precision 4-bit GEMMs).
  • Compilers: torch.compile generates Triton kernels for fused element-wise and reduction chains (chapter 5.7); TensorRT builds an optimized engine per model and GPU.

Kernels are tied to hardware: tile sizes, shared memory budgets and tensor-core instructions differ between generations, and a kernel may even be shape-specific. Kernel selection, choosing the best implementation for each operation, shape and GPU, is mostly automatic: libraries run heuristics or autotuning, and engines pick backends per GPU (chapter 4.2's attention priority list). Inference engineers mostly select, not write: swapping in DeepGEMM for FP8 GEMMs on Hopper, or a different attention backend, is a configuration change that must be benchmarked and checked for support on every GPU you deploy to.

3. Kernel fusion

Fusion combines several operations into one kernel so intermediate results stay in registers or shared memory instead of going through HBM. Each removed intermediate saves a full write and a full read of a tensor, plus a launch.

Worked example: SiLU(gate) × up for one decode step

Llama 3.1 8B has an MLP width of 14,336. At batch 64 in BF16, each of the gate and up outputs is 64 × 14,336 × 2 bytes = 1.8 MB.

  • Unfused: SiLU reads gate and writes a temporary (2 passes); the multiply reads the temporary and up and writes the result (3 passes). 5 × 1.8 MB = 9.2 MB, and 2 launches.
  • Fused: read gate and up, write the result. 3 × 1.8 MB = 5.5 MB, and 1 launch.

40% less traffic for this operation, times 32 layers, every step. Small per kernel, large in total, and the same pattern repeats for RMSNorm, the residual add and RoPE.

Kinds of fusion

  • Element-wise chains: any sequence of point-wise operations becomes one pass (activation × multiply, scaling, casting). Compilers do this well.
  • Reduction plus element-wise: RMSNorm (sum of squares, then scale), softmax (max, sum of exponentials, then divide). Each row is reduced and normalized in one kernel; engines also fuse the residual add into RMSNorm.
  • GEMM epilogues: bias, activation, scaling or quantization applied to the GEMM's output tile before it is written. CUTLASS and cuBLASLt support epilogue fusion.
  • Whole algorithms: FlashAttention fuses two GEMMs, a mask and a softmax with online rescaling (chapter 4.2). Such fusions need hand-written kernels; compilers rarely find them.
Interactive: memory traffic, unfused vs fused
Bytes moved through HBM for common operation chains, and the time at the GPU's bandwidth (memory-bound, so time ≈ bytes ÷ bandwidth). Launch overhead is added per kernel.

4. Triton: kernels in Python, one block at a time

CUDA C++ asks you to program individual threads and manage shared memory, synchronization and memory coalescing yourself. Triton raises the level: you write a program that handles one block of data (a vector or a tile), using whole-block operations such as load, add, max and dot. The Triton compiler decides how the block's threads and warps divide the work, uses shared memory, and coalesces loads. You keep control of what matters most: the block size, the order of loops, and what stays on chip.

Reading a Triton kernel, line by line

@triton.jit
def softmax_kernel(out_ptr, in_ptr, in_stride, out_stride, n_cols, BLOCK: tl.constexpr):
    row = tl.program_id(0)                       # 1. one program per row
    cols = tl.arange(0, BLOCK)                   # 2. the column indices this program covers
    mask = cols < n_cols                         # 3. BLOCK is a power of 2; mask the extra
    x = tl.load(in_ptr + row * in_stride + cols, mask=mask, other=-float("inf"))   # 4. one read
    x = x - tl.max(x, axis=0)                    # 5. reductions happen on chip
    num = tl.exp(x)
    y = num / tl.sum(num, axis=0)
    tl.store(out_ptr + row * out_stride + cols, y, mask=mask)                      # 6. one write

Six things to look for in any Triton kernel: what one program covers (here a row), how indices are built, how the overhang is masked (padding with −∞ so the max ignores it), how many loads and stores touch HBM (here one each), what is reduced on chip, and which arguments are tl.constexpr (compile-time constants such as block sizes, for which Triton compiles a separate specialized kernel).

The Triton tutorial measures this kernel at about 4 times the speed of the step-by-step PyTorch version and competitive with PyTorch's own softmax kernel, with the caveat that one row must fit in one program's block. Production kernels add autotuning (@triton.autotune over block sizes and warp counts), loops over large rows, and more numerics care.

When to use what

  • torch.compile first: it fuses element-wise and reduction chains into generated Triton kernels automatically.
  • Hand-written Triton for custom fusions the compiler misses (a fused sampling step, a special normalization, a quantize-and-store), and for portability across NVIDIA and AMD GPUs. Many vLLM and SGLang kernels are Triton.
  • CUDA C++, CUTLASS or CuTe for the last 10% to 30% on the most important kernels (GEMM, attention) on the newest hardware, where Triton cannot yet express every feature.

5. Expert layer

From naive to near-cuBLAS GEMM

Simon Boehm's well-known walk-through takes a CUDA matrix multiply from a naive kernel to near cuBLAS speed in steps: coalesced global loads, shared memory tiling, then each thread computing several outputs (1D and 2D block tiling) for more reuse per load, vectorized loads, and finally warp-level tiling and autotuning. Each step raises arithmetic intensity at some level of the memory hierarchy. It is the best single exercise for understanding why GEMM libraries look the way they do (chapter 5.8).

Fusion across communication

With tensor parallelism, engines fuse the all-reduce with the following residual add and RMSNorm, or overlap GEMM tiles with sending finished tiles to other GPUs. These "compute-communication" fusions need kernels that talk to the network or NVLink directly, and are an active area in vLLM, SGLang and TensorRT-LLM.

Numerics in fused kernels

Fusion changes the order of floating-point operations, so fused and unfused results can differ in the last bits. Compute reductions in FP32 even for BF16 inputs (as the SiLU kernel in the lab does), and test fused kernels against a high-precision reference with tolerances. Chapter 6.6 discusses why this matters for reproducibility.

6. Common mistakes

  • Writing a custom kernel before checking whether torch.compile or the engine already fuses the operation.
  • Benchmarking a kernel at one shape and deploying it at another.
  • Forgetting the mask, or padding a max with 0 instead of −∞.
  • Doing reductions in BF16.
  • Swapping in a faster kernel library without checking support on every GPU generation in the fleet.
  • Counting FLOPs to judge an element-wise kernel instead of bytes.

Part B: vector add and fused softmax (CPU interpreter, then T4)

Triton has an interpreter mode for checking logic without a GPU: set TRITON_INTERPRET=1 in the environment before importing Triton (slow; correctness only). On a T4, leave it unset.

import torch, triton, triton.language as tl
dev = "cuda" if torch.cuda.is_available() else "cpu"

@triton.jit
def add_kernel(x_ptr, y_ptr, out_ptr, n, BLOCK: tl.constexpr):
    pid = tl.program_id(axis=0)
    offs = pid * BLOCK + tl.arange(0, BLOCK)
    mask = offs < n
    x = tl.load(x_ptr + offs, mask=mask)
    y = tl.load(y_ptr + offs, mask=mask)
    tl.store(out_ptr + offs, x + y, mask=mask)

def add(x, y):
    out = torch.empty_like(x); n = x.numel()
    add_kernel[(triton.cdiv(n, 1024),)](x, y, out, n, BLOCK=1024)
    return out

# softmax_kernel exactly as in section 4, then:
def softmax(x):
    M, N = x.shape
    out = torch.empty_like(x)
    softmax_kernel[(M,)](out, x, x.stride(0), out.stride(0), N, BLOCK=triton.next_power_of_2(N))
    return out

x = torch.randn(10_003, device=dev); y = torch.randn(10_003, device=dev)
print("add max error", (add(x, y) - (x + y)).abs().max().item())
a = torch.randn(64, 781, device=dev)
print("softmax max error", (softmax(a) - torch.softmax(a, dim=1)).abs().max().item())
What we measured

In the interpreter: add maximum error 0.0; softmax maximum error about 4 × 10⁻⁹. On a T4, benchmark with triton.testing.do_bench for a 4,096 × N input with N from 256 to 8,192, against torch.softmax and a step-by-step version (x - x.max(1, keepdim=True)[0], exp, divide by the sum). Convert times to GB/s with 2 × M × N × 4 bytes for the fused kernels. Expect the step-by-step version at roughly a quarter of the fused bandwidth, as section 3 predicts.

8. In the real world

Kernels in production
  • Engines ship dozens of custom fused kernels (RMSNorm with residual, rotary embedding with KV cache write, SiLU-and-multiply, quantize-on-store) next to library GEMMs and attention.
  • Model launches often come with new kernels: DeepSeek released FlashMLA, DeepGEMM and DeepEP alongside its models.
  • Triton is the common language for portable kernels across NVIDIA and AMD, and the target of PyTorch's compiler.
  • Kernel selection per GPU generation is a routine part of upgrading hardware.

10. Summary

  • A decode step runs GEMMs and attention (most FLOPs) plus many small memory-bound kernels (norms, activations, rotary, cache writes, sampling).
  • Kernels come from vendor libraries, template libraries, open kernel libraries and compilers; selection per GPU and shape is a real engineering task.
  • Fusion keeps intermediates on chip; it cut softmax traffic about 4 times and SiLU × multiply by 40% in the examples.
  • Triton programs one block at a time with masked loads and stores; the compiler handles threads, shared memory and coalescing.
  • Use the compiler first, Triton for custom fusions, and CUDA/CUTLASS for the most critical kernels on the newest hardware.
