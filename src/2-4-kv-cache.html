Autoregressive generation and the KV cache

A model writes one token at a time. Each new token needs information about every earlier token. The KV cache keeps that information in GPU memory so the model does not compute it again. This one idea sets the memory limit, the context limit and the concurrency limit of almost every LLM server.

Answers
  1. 2 × 32 × 8 × 128 × 2 = 131,072 bytes (128 KiB) per token.
  2. At small batch, each decode step is limited by reading the weights from GPU memory. The weights are read once per step for the full batch, so 4 sequences cost almost the same as 1.
  3. Each query is used only once, at the step that makes its token. Later tokens never look at old queries. Later tokens do look at old keys and values.

1. The problem

In chapter 2.2 you saw one forward pass: the model takes a sequence of tokens and gives a probability for every possible next token. To write a reply, the server must do this again and again. It picks one token, adds it to the sequence, and runs the model again. This loop is autoregressive generation: each output becomes part of the next input.

Definitions

Token step: one run of the model that makes one new token for one sequence.

Context: all tokens the model can see at a step. This is the prompt plus all tokens made so far.

Key (K) and value (V) vectors: from 2.2, each attention layer turns each token into a query, a key and a value. A token's query asks "which earlier tokens matter to me?". Every token's key answers "this is what I contain". Every token's value is "this is what I pass on if you attend to me".

Here is the problem. Because of the causal mask, the key and value of token 5 depend only on tokens 1 to 5. When the model makes token 500, the key and value of token 5 are the same as they were at step 5. A naive loop computes them again anyway, at every step, in every layer.

For a reply of N tokens, the naive loop computes K and V for 1 + 2 + 3 + ... + N = N(N+1)/2 token positions per layer. That grows with the square of N. If you keep each K and V after you compute it, you compute only N. The stored keys and values are the KV cache.

2. Prefill and decode, step by step

With a cache, generation has two phases with different behaviour.

  • Prefill: the model reads the full prompt in one forward pass. It computes K and V for all prompt tokens at the same time, writes them to the cache, and makes the first output token. Many tokens are processed in parallel, so the GPU does a lot of math per byte of weights it reads.
  • Decode: the model processes one new token per step. It computes K and V for that one token, appends them to the cache, and attends over the full cache. Very little math happens per byte that the GPU reads.

Decode is one token at a time because token t+1 depends on token t. You cannot compute token 10 before you know token 9. There is no way to run decode steps of one sequence in parallel in plain generation. (Chapter 4.3 covers speculative decoding, which guesses several tokens and checks them in one pass.)

3. What the cache stores

The cache holds one key tensor and one value tensor per layer. For one sequence, each has the shape:

[ KV heads , tokens so far , head size ]

With a batch, there is one more dimension in front for the sequence. The exact layout in memory differs by engine. The amount of data does not.

Diagram: one layer's cache with grouped-query attention
Here 8 query heads share 2 KV heads (group size 4). Only K and V are stored. Each new token adds one column to every KV head in every layer.

Three attention types decide how many KV heads there are:

Llama 3.1 70B has 64 query heads and 8 KV heads. The group size is 8, so its cache is 8 times smaller than an MHA version of the same model. That is why almost every recent open model uses GQA, or the newer MLA in the expert layer.

Why the query is not stored: the query of token t is used once, at step t, to read from the earlier tokens. Token t+1 makes its own query. Nothing ever reads an old query again, so storing it would waste memory.

4. Why the cache is exact

The cache is not an approximation. In a decoder-only transformer with a causal mask, the K and V of position i are a function of tokens 1 to i only. Later tokens cannot change them, because the mask stops position i from looking forward. So the stored value equals the value you would recompute. Your lab output checks this: the cached and uncached loops give the same tokens.

There is one small exception you may see in practice. With 16-bit numbers, a batched computation and a one-token computation can add numbers in a different order. That can change the last bit of a result, and very rarely it changes which token wins. The algorithm is exact; the floating-point arithmetic is not perfectly repeatable. If you need an exact test, run it in float32.

Position matters too. With RoPE (2.3), the rotation for position i is applied to K before it is stored. A cached key already carries its position. A new token's query is rotated for its own position. This is why the relative-position property you checked in 2.3 still holds with a cache.

5. The memory formula

For each token, each layer stores one key vector and one value vector per KV head. Multiply it out:

KV bytes per token = 2 × layers × KV heads × head size × bytes per value

The 2 is for K and V. "Bytes per value" is 2 for BF16 or FP16, 1 for FP8, 4 for FP32. Then:

KV bytes per sequence = KV bytes per token × tokens in that sequence
KV bytes total = sum over all running sequences

The weights also live on the GPU. A first estimate is parameters × bytes per weight. An 8B model in BF16 needs about 16 GB.

The weight memory is fixed. The KV memory grows with every token of every user. On a busy server, the KV cache, not the weights, often uses most of the GPU memory.

How to read the calculator:

  • Memory fraction is the share of GPU memory the engine may use. In vLLM this is --gpu-memory-utilization. The current vLLM docs (v0.33) say the default is 1.0 when the extensible KV cache is on and 0.92 otherwise. In TensorRT-LLM the similar setting is free_gpu_memory_fraction, which is a share of the memory left after weights load.
  • Runtime reserve covers activations, CUDA context, temporary buffers and CUDA graphs. Engines measure this with a test forward pass at startup. 1 to 4 GB is typical for 7B to 8B models; it grows with the max batch and max tokens per pass.
  • Max sequences is the KV pool divided by one sequence's cache. This is the concurrency ceiling set by memory alone.
  • GPUs (tensor parallel) splits weights and KV heads across GPUs (chapter 4.5 explains how). The calculator divides both evenly, which is correct while the KV head count divides by the GPU count.

GPU sizes here use the marketing numbers as decimal GB. This is slightly conservative: an "80 GB" H100 reports about 81,559 MiB, which is 85.5 GB.

7. Logical vs allocated memory

The formula gives the logical size: the bytes for tokens that exist. The memory an engine allocates can be much larger.

The simple way to store a cache is one contiguous block per sequence, sized for the maximum length. If the max length is 8,192 tokens and a request uses 200, the engine reserves 8,192 slots and fills 200. That is 1 − 200/8,192 = 97.6% of that request's reservation wasted. The engine does not know the final length when the request starts, so it must reserve for the worst case.

The vLLM paper measured existing systems of that time and found that only 20.4% to 38.2% of KV cache memory held real token states. The rest was reservation waste and fragmentation. Their fix, PagedAttention, stores the cache in small fixed-size blocks and allocates them as the sequence grows. That idea is the core of chapter 3.3. For now, keep two numbers apart:

  • Logical KV: what the formula says. Use it to think about the limits of the model and hardware.
  • Allocated KV: what the engine actually holds. Use it to explain why a server runs out of memory before your formula says it should.

The setting --max-model-len in vLLM matters here. vLLM checks at startup that at least one sequence of max length can fit. If you set a 128K max on a GPU that cannot hold one 128K cache, startup fails. Lower the max length, use an FP8 KV cache, or add GPUs.

8. What decode costs

At each decode step, the GPU must read two things from its memory (called HBM, high-bandwidth memory):

  1. All the model weights, once per step, shared by every sequence in the batch.
  2. The full KV cache of every sequence in the batch.

The math per step is small, so at small batch the time is set by how fast the GPU can read memory. This gives a floor on step time:

step time ≥ ( weight bytes + Σ KV bytes of the batch ) ÷ memory bandwidth

Chapter 2.5 turns this into the roofline model and defines MBU, the share of the bandwidth limit you actually reach. Here, use it as a lower bound. Real engines reach roughly 50% to 80% of it.

Two results follow. First, batching is cheap at first: going from 1 to 4 sequences adds KV reads but no extra weight reads. Second, long contexts are expensive: the KV term grows with context, and at long context it becomes larger than the weights.

9. TTFT, TPOT and E2E

The two phases map to the two latency numbers users feel.

Definitions

TTFT (time to first token): from request arrival to the first output token. It includes queue time and prefill. Long prompts make TTFT longer.

TPOT (time per output token): the average time between output tokens after the first. It is set by decode step time. Longer context and a bigger batch make it longer.

ITL (inter-token latency): the time between two specific tokens. TPOT is the mean of the ITLs. Benchmarks report ITL percentiles to show jitter.

E2E (end-to-end latency): the full request time.

E2E ≈ TTFT + (output tokens − 1) × TPOT

Prefill is compute-bound. Its math is about 2 × parameters × prompt tokens FLOPs (2.5 explains the 2). Llama 3.1 8B with a 2,048-token prompt needs 2 × 8.03 × 109 × 2,048 ≈ 32.9 TFLOP. An H100 SXM has about 989 TFLOP/s of dense BF16 math. At 50% use, prefill takes about 66 ms. This ignores the attention FLOPs, which are small at 2K tokens but grow with the square of the prompt length.

A chat user notices TTFT. A long-form writer notices TPOT. An agent that makes 50 calls in a row notices E2E. You tune the server for the one your users care about, and chapter 3.2 shows how engine schedulers trade them.

10. Worked examples

Example A: Llama 3.1 8B, 32 users at 8K tokens, one H100

  • KV per token: 131,072 bytes.
  • KV per sequence at 8,192 tokens: 131,072 × 8,192 = 1.07 GB (exactly 1 GiB).
  • KV for 32 sequences: 34.4 GB (32 GiB).
  • Weights in BF16: 8.03 × 109 × 2 = 16.06 GB.
  • Total: about 50.4 GB, plus a runtime reserve. It fits in 80 GB.
  • The ceiling at 0.92 memory fraction and a 2 GB reserve: (73.6 − 16.06 − 2) ÷ 1.07 ≈ 51 sequences at 8K.

Example B: Llama 3.1 70B at 128K context

  • KV per token: 327,680 bytes.
  • KV for one 131,072-token sequence: 42.9 GB.
  • Weights in BF16: about 141 GB. One full-length user needs about 184 GB before any reserve.
  • This does not fit on 2 H100s (160 GB). Options: 4 H100s, FP8 weights (about 71 GB) with an FP8 cache (21.5 GB per user), or a lower max length.

Example C: decode floor for Llama 3.1 8B on one H100

  • Batch 1, short context: 16.06 GB ÷ 3.35 TB/s ≈ 4.8 ms per step, so at most about 209 tokens per second for that user.
  • Batch 1 at 8K context: (16.06 + 1.07) GB ÷ 3.35 TB/s ≈ 5.1 ms.
  • Batch 32 at 8K context: (16.06 + 34.4) GB ÷ 3.35 TB/s ≈ 15.1 ms per step. Each user now gets at most about 66 tokens per second, but the server makes about 2,130 tokens per second in total.

Example C is the central trade of LLM serving. A bigger batch raises total throughput and lowers the speed each user sees. The KV cache is what makes the step cost grow with batch and context.

11. Errors you will meet in popular material

Several widely read explanations contain errors or simplifications that will mislead you. Each one below was checked against model configs and first principles. The References section says where each appears.

Watch out: a widely shared 70B estimate

A popular tutorial notebook estimates the KV cache of a 70B model at 32K context as about 160 GB. Two problems. The MHA formula with 64 heads gives 2 × 80 × 64 × 128 × 2 × 32,768 = 85.9 GB, not 160. And Llama 70B uses GQA with 8 KV heads, so the real number is 10.7 GB. Always read the KV head count from num_key_value_heads in the model config.

Watch out: the MHA-only formula

A well-known KV formula (2 × 2 × layers × model dimension per token) assumes MHA, where KV heads × head size equals the model dimension. For any GQA model, replace the model dimension with KV heads × head size. Always compute bandwidth examples yourself rather than copying them; typos in exponents are common.

Watch out: "the cache is as big as the model"

You may read that the cache of a 13B model can become "comparable to model size". That is true only for large batch × context products. For Llama 2 13B (MHA, 40 layers, 5,120 model dimension), one 4K-token sequence uses 3.4 GB against 26 GB of weights. You need about 8 such sequences before the cache equals the weights.

Watch out: decode attention intensity

A popular attention example gives about 62 FLOPs per byte. That figure is for computing full attention over a sequence in one pass, without a fused kernel. It does not describe decode. In decode, each query head does about 4 × head size FLOPs per cached token (one dot product with K, one weighted sum of V), and reads 4 × head size bytes of BF16 K and V per KV head. So the intensity is about 1 FLOP per byte for MHA, and about the group size for GQA because several query heads share one read. Some summary tables list 0.5 for decode attention; about 1.0 is correct for MHA.

12. Expert layer

Read this after the core is clear. Each item names where it is taught in depth.

Multi-head latent attention (MLA)

DeepSeek-V2 and V3 do not store K and V per head. They store one compressed latent vector per token per layer (512 values) plus a small shared RoPE key (64 values). At decode time they project the latent back to keys and values, or fold that projection into the query. For DeepSeek-V3: 61 × (512 + 64) × 2 bytes = 70,272 bytes per token, although the model has 671B parameters. An MHA design at that scale would be many times larger. Note the formula has no "2 ×" for K and V: one latent serves both.

Sliding-window and hybrid attention

Mistral-7B-v0.1 uses a 4,096-token sliding window: each layer attends only to the last 4,096 tokens, so the cache can be a rolling buffer that stops growing at 4,096 tokens. Gemma 2 and 3 alternate local-window layers with global layers, so only the global layers grow with context. For these models the formula applies per layer type: window layers cap at the window, global layers grow. State-space and linear-attention layers (2.7) keep a fixed-size state instead of a cache.

Shrinking the cache further

FP8 KV cache halves memory with small quality loss on most models and is common in production (chapter 4.1). Lower-bit KV quantization (KIVI, KVQuant) goes to 2 to 4 bits. Eviction methods (H2O, StreamingLLM attention sinks, SnapKV) drop tokens that get little attention; they change outputs, so they are no longer exact. Cross-layer sharing (for example, YOCO and CLA) reuses one cache for several layers.

Reuse and tiers

If two requests share a prefix, such as a system prompt, the K and V of that prefix are identical, so the server can compute them once. That is prefix caching (chapter 4.4; tiers in 4.7). When GPU memory is full, caches can move to CPU memory, local SSD or remote storage and be loaded back. Engines describe these as tiers (often called G1 GPU, G2 CPU, G3 local storage, G4 remote). Moving a cache costs bandwidth, so this only pays when the load is faster than recomputing the prefill.

13. Common mistakes

  • Using the number of attention heads instead of KV heads. Check num_key_value_heads.
  • Using hidden_size / num_attention_heads as the head size for models that set head_dim explicitly. Qwen3 and Gemma set it directly; read it.
  • Forgetting the 2 for K and V, or adding it for MLA where there is one latent.
  • Counting only the output tokens. The cache holds the prompt too.
  • Mixing GB and GiB. 32 GiB is 34.4 GB. Pick one and say which.
  • Assuming the logical size is what the engine uses. Without paging, allocated memory can be several times larger.
  • Timing GPU code without torch.cuda.synchronize(). GPU work is asynchronous, so the timer stops before the work ends.

Why is_causal only when T > 1: in a decode step the single new query may look at every cached key, so no mask is needed. In prefill (and in the no-cache loop) the queries and keys have the same length, and the causal mask stops each position from seeing later ones. Note: this simple rule is wrong if you prefill into a cache that is not empty (chunked prefill); that case needs an offset mask.

torch.cat copies the whole cache every step, so this loop does extra memory traffic that grows with length. Real engines write into memory they allocated earlier. That is fine for this lab.

    t = time.perf_counter(); r = fn(*args)
    if dev == "cuda": torch.cuda.synchronize()

Step 4: compare with the bandwidth floor

GPT-2 small in float32 has about 0.50 GB of weights. A T4 reads about 320 GB/s, so the floor is about 1.6 ms per token, or about 640 tokens per second. Your cached loop will be much slower. Find out why: the model runs about a dozen small GPU kernels per layer, and each launch from Python costs several microseconds of CPU time. At this model size the GPU waits for the CPU. This is called being launch-bound. Chapter 5.7 removes it with CUDA graphs and torch.compile.

def cache_bytes(past):
    # The cache class changed across transformers versions; this handles the common ones.
    if hasattr(past, "layers"):
        pairs = [(l.keys, l.values) for l in past.layers]
    elif hasattr(past, "key_cache"):
        pairs = list(zip(past.key_cache, past.value_cache))
    else:
        pairs = list(past)
    return sum(k.numel()*k.element_size() + v.numel()*v.element_size() for k, v in pairs)

  1. KV: 147,456 × 32,768 × 16 = 77.3 GB, plus 16.4 GB of weights. It does not fit. An FP8 KV cache halves it to 38.7 GB, which fits with room to spare (about 55 GB plus reserve). Using 2 GPUs also works.
  2. Weights about 8.0 GB. Pool at 0.92 and a 2 GB reserve: 22.08 − 8.03 − 2 ≈ 12.05 GB. One 4K sequence in BF16 KV: 0.537 GB. Max about 22 users. With an FP8 cache, about 44.
  3. 16.06 GB ÷ 131,072 bytes per token ≈ 122,500 tokens. Below that, weights dominate the step at batch 1. With a batch of 32, the crossover drops to about 3,830 tokens per sequence.

15. In the real world

How production systems use this
  • vLLM computes the KV pool at startup and logs it as the number of tokens it can hold and the max concurrency at full length. Read these two log lines on every deployment. They are the calculator output for your real setup.
  • TensorRT-LLM sizes its paged KV cache from free_gpu_memory_fraction of the memory left after weights.
  • API pricing: providers that offer prompt caching charge less for cached input tokens because the server skips that prefill. Anthropic, for example, lists cache reads at 0.1 times the base input price. Check each provider's current pricing page; these numbers change.
  • Context limits on hosted models are partly a memory decision. A provider that offers 1M-token context must hold or move that much cache per user.

16. Check yourself

17. Summary

  • Generation is a loop: one forward pass per new token. Prefill processes the prompt in one parallel pass; decode adds one token per step.
  • Keys and values of earlier tokens never change (causal mask), so the engine stores them: the KV cache. The query is not stored.
  • KV bytes per token = 2 × layers × KV heads × head size × bytes per value. GQA, MQA and MLA shrink it; FP8 halves it.
  • KV memory = bytes per token × tokens × sequences. It sets the maximum context and the number of concurrent users.
  • Engines allocate more than the logical size unless they page the cache (chapter 3.3).
  • Each decode step reads all weights plus every sequence's cache, so step time grows with batch and context. Bigger batches raise total throughput and lower per-user speed.
  • TTFT is set mostly by prefill; TPOT by decode step time; E2E ≈ TTFT + (n − 1) × TPOT.
