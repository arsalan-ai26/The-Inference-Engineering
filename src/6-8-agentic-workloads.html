Expert depth: agentic workloads and tooling

An agent calls a model in a loop: decide on an action, run a tool, append the result, call again. That loop produces traffic very unlike a chatbot's: dozens of calls per task, contexts that grow with every step, outputs of a few dozen tokens, long pauses while tools run, and bursts when agents start sub-agents. This chapter shows how agent traffic changes the serving problem, the context engineering practices that make agents fast and cheap (most of them are about the KV cache), how agent harnesses and tool protocols fit around the model, and how agents are now used to write and tune the kernels from Part 5.

  2. In an agent loop, which phase dominates: prefill or decode?
  3. What does programmatic tool calling change about the tokens that enter the context?
Answers
  1. Prefix caching only reuses tokens up to the first difference. A timestamp at the top changes on every call, so no part of the context is ever reused and every call pays full price and full prefill time.
  2. Prefill. Each call re-reads a long, growing context and writes a short action. Manus reports an average input-to-output ratio of about 100 to 1.
  3. The model writes code that calls tools in a sandbox and processes their results there; only the final, small result returns to the context, instead of every raw tool output.

1. The agent loop, seen from the server

Definitions

Agent: a program that uses a model to choose actions (tool calls) step by step until a task is done.

Tool call: a structured request from the model, such as {"name": "shell_run", "arguments": {...}}, which the program executes; the result (the observation) is added to the context.

Trajectory: the full sequence of model calls, actions and observations for one task.

Harness: the software around the model that runs the loop: prompts, tool handling, context management, sub-agents, hooks.

Each step sends the whole context so far, and the model returns a short action. Manus, a general-purpose agent, reports about 50 tool calls per typical task and an average of roughly 100 input tokens per output token. For the server this means:

Users feel the total time of the loop, which is roughly the number of steps × (TTFT + output time + tool time). With 50 steps, saving 300 ms of TTFT per call saves 15 s per task.

2. Design around the KV cache

Manus calls the KV cache hit rate "the single most important metric for a production-stage AI agent", because it sets both latency and cost. Cached input is also much cheaper through APIs: Manus cites $0.30 versus $3 per million input tokens on Claude Sonnet, a factor of 10. Their practices:

  1. Keep the prefix stable. One changed token invalidates the cache from that point on. A timestamp at the top of the system prompt breaks every call.
  2. Make the context append-only. Do not edit earlier actions or observations. Serialize deterministically: many JSON libraries do not guarantee key order, which silently changes bytes.
  3. Mark cache breakpoints where the provider requires explicit ones, at least at the end of the system prompt.
  4. Do not add or remove tools mid-task. Tool definitions sit near the front of the context, so changing them invalidates everything after. Manus keeps all tools defined and instead masks the logits of tools that are not allowed in the current state, using constrained decoding (chapter 3.5) and consistent name prefixes such as browser_ and shell_.
  5. Self-hosting: enable prefix caching and route each session to the same replica (session affinity, or prefix-aware routing, chapter 6.4).

Note the last design: dropping the oldest observations to keep the context short also breaks the prefix, because everything after the dropped part shifts. That is why Manus prefers restorable compression: replace a web page's content with its URL, or a file's content with its path, so the agent can fetch it again; and why it treats the file system as external memory.

Keeping the cache warm between calls

While a tool runs, the engine serves other requests and may evict the agent's KV blocks. On return, the agent pays full prefill again. Defences from earlier chapters: enough KV capacity for the number of concurrent agent sessions; offloading idle sessions' KV to CPU memory or disk instead of dropping it (chapter 4.4, as DeepSeek's on-disk cache in chapter 6.7); and routing that sends the next call to the replica holding the prefix. API providers keep cached prefixes only for a limited time, so very slow tools can lose the cache.

3. Context engineering beyond the cache

  • Recitation: Manus agents keep a todo.md file and rewrite it as they go, which puts the plan at the end of the context, where the model attends to it most, during a 50-step task.
  • Keep errors in the context. A failed action and its error message steer the model away from repeating it; hiding failures removes that evidence.
  • Avoid self-imposed few-shot patterns. Many near-identical steps make the model copy the pattern; small, structured variation in formatting breaks it.
  • Programmatic tool calling. Instead of one JSON tool call per step with every raw result returned to the context, the model writes code that calls tools inside a sandbox, filters and aggregates the data, and returns only the final result. For data-heavy tasks (for example a year of daily prices for ten tickers, over 2,500 data points) this keeps tens of thousands of tokens out of the context. Anthropic introduced it in its API; open-source versions exist (open-ptc-agent).
  • Fewer tools. Large tool lists confuse models and lengthen the prefix. Phil Schmid cites Vercel removing 80% of an agent's tools and getting fewer steps, fewer tokens and faster responses.

4. Harnesses, frameworks and protocols

A useful analogy from Phil Schmid: the model is the CPU, the context window is the RAM, the harness is the operating system (it curates the context, starts up with the right prompts and hooks, and provides drivers for tools), and the agent is the application. Coding CLIs such as Claude Code and Codex are specialized harnesses; SDKs such as the Claude Agent SDK, LangChain DeepAgents and Strands Agents (an open-source, model-agnostic agent loop for Python and TypeScript) let you build your own.

  • Model Context Protocol (MCP): an open standard for connecting models to tools and data. By December 2025 there were more than 10,000 active public MCP servers, and Anthropic donated MCP to the Agentic AI Foundation under the Linux Foundation, co-founded with Block and OpenAI.
  • Asynchronous (background) agents: agents that run in cloud sandboxes without a human watching, started from chat or an issue tracker. One builder's design: an orchestrator container holds secrets and creates short-lived, single-repository credentials; each agent runs in its own container with only the keys it needs. For inference this means long, unattended trajectories, many in parallel: throughput and cost matter more than per-call latency.
  • Durability over many steps: leaderboard scores barely separate models, but long tasks expose whether a model still follows instructions after 50 or 100 tool calls. Harnesses produce the logged trajectories that measure this, and that labs feed back into training.

Serving implications: harness traffic is the most cacheable traffic there is (same system prompt and tools for every user), it depends on accurate tool-call parsing (chapter 6.6's provider comparison measured exactly this), and its bursts come from sub-agents started in parallel.

5. Agents that write kernels

Kernel work (Part 5) has a clear correctness check and a measurable score, which makes it well suited to agents that try, test and retry. AMD's AgentKernelArena is an environment for this:

  • Kernel tasks: implement and optimize one operator (for example RMSNorm) in Triton, Gluon, HIP or FlyDSL. Correctness is checked against a high-precision PyTorch reference; speed is measured with cold caches and CUDA graphs (chapter 5.7) against a vendored baseline, on workloads taken from production.
  • End-to-end tasks: change the kernels of a whole serving stack while weights, precision, parallelism and serving flags stay fixed; reward comes from model correctness and serving throughput.
  • The run configuration chooses the agent (for example Claude Code), the GPU, the language and a time budget, and the environment produces reward signals that can train kernel-writing agents with reinforcement learning.

The design shows what any agent evaluation needs: a fixed task contract, an independent checker the agent cannot edit, and measurement methods that cannot be gamed (cold cache, fixed workloads).

6. Expert layer

Why agents push toward disaggregation and tiered KV

With a 100 : 1 input ratio and mostly cached prefixes, the work per call is a modest prefill of new tokens plus a short decode, but the KV that must be kept is large and lives for minutes. That combination favours separate prefill capacity, large KV pools spread across GPU, CPU and disk, and routing by cache location: exactly the llm-d and Dynamo designs of chapters 4.4 and 4.6.

Masking tools without breaking the cache

Response prefill does the masking without touching the prefix. In the Hermes format: prefill <|im_start|>assistant to let the model choose; add <tool_call> to force a tool call; add {"name": "browser_ to force a tool from one group. The tool definitions never change, so the cache survives.

7. Common mistakes

  • Timestamps, random IDs or per-user data at the top of the prompt.
  • Non-deterministic JSON serialization of tool results.
  • Loading tools dynamically mid-task.
  • Sliding-window truncation of agent context without counting the lost cache hits.
  • Round-robin routing of agent sessions across replicas.
  • Measuring agent speed by single-call TTFT rather than time per task.

8. Lab

Goal: measure what KV reuse saves on a growing context, and estimate the cache hit rate and cost of an agent workload.

Part A: re-prefill everything, or only the new tokens?

Predict first: on a CPU, how much faster is prefilling only a new 400-token step than re-prefilling a 3,500-token context?

import torch, time
from transformers import AutoModelForCausalLM, DynamicCache
torch.set_num_threads(2)
model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct", dtype=torch.float32).eval()
V = model.config.vocab_size
ctx = torch.randint(0, V, (1, 1500))         # system prompt + tools + task
cache = DynamicCache()
with torch.no_grad():
    model(ctx, past_key_values=cache, use_cache=True)
for step in range(1, 6):
    new = torch.randint(0, V, (1, 400))      # one action + observation
    full = torch.cat([ctx, new], 1)
    with torch.no_grad():
        t = time.perf_counter(); model(full, use_cache=False); t_full = time.perf_counter() - t
        t = time.perf_counter(); model(new, past_key_values=cache, use_cache=True); t_new = time.perf_counter() - t
    ctx = full
    print(step, ctx.shape[1], round(t_full, 2), round(t_new, 2))
What we measured (2 CPU cores)
 step  context  full prefill  only new tokens
    1     1900       10.70 s          3.50 s
    2     2300       14.15 s          2.90 s
    3     2700       16.62 s          2.68 s
    4     3100       18.21 s          2.63 s
    5     3500       22.74 s          3.24 s

Re-prefilling grows with the context (11 s to 23 s); prefilling only the new tokens stays around 3 s, a 7 times difference at 3,500 tokens that keeps widening as the context grows. On a GPU every number is much smaller, but the shape is the same.

Part B: token accounting for a whole task

def run(steps=50, system=3000, tools=5000, user=200, action=100, obs=1000,
        price_in=3.00, price_cached=0.30, price_out=15.00, breaks_at=None):
    ctx_prev = fresh = cached = out = 0
    ctx = system + tools + user
    for _ in range(steps):
        reusable = 0 if breaks_at == "start" else min(ctx_prev, system) if breaks_at == "tools" else ctx_prev
        cached += reusable; fresh += ctx - reusable; out += action
        ctx_prev = ctx + action
        ctx += action + obs
    return fresh, cached, out, (fresh*price_in + cached*price_cached + out*price_out) / 1e6

for label, b in [("stable prefix", None), ("timestamp at top", "start"), ("tools change", "tools")]:
    f, c, o, cost = run(breaks_at=b)
    print(f"{label:17s} input {f+c:,}  cached {c/(f+c):.1%}  in:out {(f+c)/o:.0f}:1  ${cost:.2f}")
What we computed
stable prefix, append-only   input 1,757,500 (cached 96.7%)  output 5,000  in:out  352:1  cost $0.76
timestamp at the top         input 1,757,500 (cached  0.0%)  output 5,000  in:out  352:1  cost $5.35
tool list changes each step  input 1,757,500 (cached  8.4%)  output 5,000  in:out  352:1  cost $4.95

The same 50-step task costs $0.76 with a stable prefix and about seven times more when the cache breaks every step. With 1,000-token observations the input-to-output ratio here is 352 to 1, higher than Manus's average of 100 to 1; shorter observations or fewer steps lower it.

Part C: your own agent

Take one agent you use or build. Log (or estimate) for 10 tasks: steps per task, system prompt and tool definition size, tokens per action and per observation, and seconds per tool call. Fill them into Part B, then check: where in your prompt is the first token that changes between calls? Would a self-hosted engine keep your KV through the longest tool call, given your concurrency? Estimate the cache hit rate and the saving from fixing the first cache break you find.

9. In the real world

Agents in production
  • Agent products treat the cache hit rate as a top metric and design prompts to be append-only.
  • Coding harnesses run long trajectories, increasingly as background agents in cloud sandboxes.
  • Inference platforms add session-aware routing and KV offloading for agent traffic.
  • Hardware vendors and labs build environments such as AgentKernelArena to train and evaluate kernel-writing agents.

10. Check yourself

11. Summary

  • Agent traffic is many calls per task, prefill-heavy, highly cacheable, bursty and structured.
  • The KV cache hit rate decides agent latency and cost: stable prefixes, append-only contexts, deterministic serialization, fixed tool lists with masking, session-aware routing.
  • Restorable compression, recitation and keeping errors in context improve long tasks without breaking the cache.
  • Harnesses and MCP standardize how agents use tools; programmatic tool calling keeps raw data out of the context.
  • Kernel optimization is now an agent task, evaluated with fixed references, baselines and measurement rules.
