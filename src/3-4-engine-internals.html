Engine internals

Chapters 3.1 to 3.3 introduced the parts of an inference engine one at a time. This chapter puts them together and opens the code. You will follow one engine step from scheduling to streamed token, read the real scheduler of a 1,200-line engine, see how inputs for a mixed batch are prepared, and learn the debugging method engine teams use when output is silently wrong.

Before you start: skip check

  2. What is a "slot mapping", and why does the model runner need it?
  3. Why does monkey-patching vLLM's scheduler from your own script often not work?
Answers
  1. Schedule (choose requests and token counts), prepare inputs, run the forward pass, sample next tokens, post-process (append tokens, check stop rules, free finished requests, stream output).
  2. For each new token in the batch, the physical KV slot (block ID × block size + offset) where its key and value must be written. The attention kernel writes the new K and V there before reading the cache.
  3. The scheduler runs inside the engine-core process, not in the process where your script patched it, so the engine keeps using the original code. Plugins are the supported way.

1. The engine loop

Every LLM engine is, at heart, one loop that never stops while there is work:

  1. Schedule. Look at waiting and running requests, the token budget and free KV blocks (chapters 3.2 and 3.3). Decide which requests run this step, how many tokens each processes, and allocate blocks.
  2. Prepare inputs. Flatten all scheduled tokens into one array, with their positions, the KV slot each new token writes, and each sequence's block table and context length.
  3. Forward pass. Run the model once over the whole flattened batch.
  4. Sample. Take the logits at the last position of each sequence and pick the next token with that request's sampling settings (chapter 1.2).
  5. Post-process. Append tokens, check stop conditions, free finished requests' blocks, and send new text to the API server for streaming.

Production engines split these across operating-system processes, so that slow Python work in one does not stall the GPU. vLLM's current architecture has:

  • API server process(es): HTTP, tokenization and multimodal input loading, streaming. They talk to the engine core over ZMQ sockets.
  • One engine-core process per data-parallel rank: runs the scheduler and KV cache manager in a busy loop and coordinates the workers.
  • One worker process per GPU: loads weights, runs forward passes, manages GPU memory. With tensor parallelism of 4, one engine core has 4 workers.

This matters for deployment: an engine needs several CPU cores per GPU, and a starved CPU shows up as low GPU utilization.

3. Reading a real scheduler: nano-vLLM

nano-vLLM re-implements vLLM's core ideas in about 1,200 lines of Python (paged KV cache with prefix caching, CUDA graphs, tensor parallelism), and its authors report throughput comparable to vLLM on its benchmark. It is the best code to read first. Its whole engine step is:

def step(self):
    seqs, is_prefill = self.scheduler.schedule()
    token_ids = self.model_runner.call("run", seqs, is_prefill)
    self.scheduler.postprocess(seqs, token_ids, is_prefill)
    return [(s.seq_id, s.completion_token_ids) for s in seqs if s.is_finished]

And the core of its scheduler, slightly shortened:

def schedule(self):
    scheduled, num_batched_tokens = [], 0
    # 1. prefill first: admit waiting sequences while the token budget and blocks allow
    while self.waiting and len(scheduled) < self.max_num_seqs:
        seq = self.waiting[0]
        remaining = self.max_num_batched_tokens - num_batched_tokens
        num_cached_blocks = self.block_manager.can_allocate(seq)   # -1 if not enough free blocks
        if remaining == 0 or num_cached_blocks == -1: break
        num_tokens = seq.num_tokens - num_cached_blocks * self.block_size   # prefix-cache hits are skipped
        if remaining < num_tokens and scheduled: break                       # only the first seq may be chunked
        self.block_manager.allocate(seq, num_cached_blocks)
        seq.num_scheduled_tokens = min(num_tokens, remaining)
        ...
        scheduled.append(seq)
    if scheduled:
        return scheduled, True                     # this step is a prefill step
    # 2. otherwise decode: one token per running sequence, preempting from the back if blocks run out
    while self.running and len(scheduled) < self.max_num_seqs:
        seq = self.running.popleft()
        while not self.block_manager.can_append(seq):
            if self.running: self.preempt(self.running.pop())   # newest running sequence loses its blocks
            else: self.preempt(seq); break
        else:
            seq.num_scheduled_tokens = 1
            self.block_manager.may_append(seq)
            scheduled.append(seq)
    return scheduled, False                        # this step is a decode step

Read it against chapter 3.2. Four design choices stand out:

  1. Prefill priority, separate steps. A step is either all prefill or all decode. If anything is waiting and fits, the step prefills. This gives fast TTFT but pauses decoding during prefills.
  2. Limited chunking. Only the first waiting sequence may be split to fit the budget.
  3. Prefix caching in admission. can_allocate hashes the prompt block by block and counts blocks already in the cache; only uncached tokens are scheduled.
  4. Recompute preemption from the back. When a decode needs a block and none are free, the most recently scheduled running sequence is sent back to the waiting queue with its blocks freed.

Its defaults are also instructive: a token budget of 16,384, up to 512 sequences, 90% memory use, and a KV block size of 256 tokens (much larger than vLLM's usual 16). The KV cache is one tensor of shape [2, layers, blocks, block size, KV heads, head size], sized at startup from free memory after a warm-up pass. CUDA graphs are captured for decode batch sizes 1, 2, 4, 8, then every 16 up to the maximum; prefill, and batches above 512, run eagerly.

mini-SGLang (about 5,000 lines) shows overlap scheduling clearly. Its main loop launches the forward pass for batch n on the GPU, and while it runs, processes the results of batch n − 1 on the CPU:

def overlap_loop(self, last_data):
    for msg in self.receive_msg(blocking=...):      # new requests, aborts
        self._process_one_msg(msg)
    forward_input = self._schedule_next_batch()     # prefill batch, else decode batch
    ongoing = None
    if forward_input is not None:
        with self.engine_stream_ctx:                # launch on the GPU stream, do not wait
            ongoing = (forward_input, self._forward(forward_input))
    self._process_last_data(last_data)              # CPU work for the PREVIOUS step overlaps the GPU
    return ongoing

The CPU cost of scheduling and output processing is hidden behind GPU work. The catch is subtle: when step n is scheduled, the tokens of step n − 1 are not known yet on the CPU, so the code must handle requests that finished one step "late" (the source has a comment about avoiding a double free for exactly this case).

5. Preparing inputs for a mixed batch

The model runner turns the scheduler's decision into tensors. For a step with one sequence prefilling 5 tokens (positions 0 to 4) and two sequences decoding one token each (at positions 9 and 6), it builds:

TensorContentsPurpose
input_ids[a0, a1, a2, a3, a4, b9, c6] (7 tokens, flattened)All tokens of the step in one array; no padding
positions[0, 1, 2, 3, 4, 9, 6]For RoPE (chapter 2.3); each token's own position in its sequence
slot_mappingphysical slot for each new token, for example block 7 × 4 + offsetWhere to write each token's new K and V
query start offsets[0, 5, 6, 7]Where each sequence's tokens begin in the flat array
context lengths[5, 10, 7]How many cached tokens each sequence's queries attend to
block tablesone row of physical block IDs per sequenceWhere to read each sequence's cached K and V (chapter 3.3)
sample indices[4, 5, 6]Which rows of the output to sample from: the last token of each sequence

The linear layers do not care about sequence boundaries: they process all 7 rows as one matrix (chapter 1.1). Only attention needs the metadata, so engines bundle it into an "attention metadata" object that each attention backend (FlashAttention, FlashInfer and others) reads in its own format.

6. CUDA graphs inside the runner

Decode steps are short and launch-bound for small and medium models (chapter 2.5). Engines capture a CUDA graph for each of a set of batch sizes at startup and, at each decode step, pad the batch up to the nearest captured size and replay the graph. Inputs are copied into fixed buffers before replay, because a graph always reads the same memory addresses. That is why max-num-seqs also sets buffer and graph sizes, and why startup takes longer with graphs enabled (in vLLM, --enforce-eager turns them off for debugging).

7. Changing an engine: plugins, not forks

Teams often need a custom scheduler rule, a new model, a different KV policy or extra metrics. Three options:

  • Fork the engine. Full control, but every upstream release must be merged by hand.
  • Monkey-patch from your script. Fragile, and often silently ineffective: in vLLM the scheduler runs inside the engine-core process, which does not see patches applied in the API process.
  • Plugins. vLLM loads registered Python entry points in every process at startup. Plugins can register out-of-tree models, platforms and general modifications, and are the supported path. Community lists of vLLM plugins and vendor plugins (for example Snowflake's ArcticInference, which adds speculative decoding and other optimizations) show the pattern at scale.

8. Debugging silent errors

The hardest engine bugs do not crash. A published example from AI21: their hybrid Mamba-attention model produced pure gibberish about once per thousand prompts in vLLM, but never in Hugging Face transformers. The cause: under heavy memory pressure, state slots were recycled quickly, and in rare scheduling cases a new request was treated as if it were already decoding. It then read the previous occupant's Mamba state instead of starting from zero. Attention layers are protected from this by sequence-length masking (stale KV beyond a sequence's length is never read), but a recurrent state carries its whole history in one tensor, so stale state corrupts everything that follows.

The method they used is the standard one, and you should learn it:

  1. Find a reference. A slow but trusted implementation, usually transformers.
  2. Compare logprobs on the same tokens. Take the tokens the engine generated and ask the reference for the logprob it would give each one. Normal runs differ only by small floating-point noise.
  3. Watch for confident nonsense. Corruption shows as tokens the engine was sure of but the reference finds extremely unlikely.
  4. Make it repeatable. Use temperature 0 and the same load pattern until one request fails every time, then shrink the case.

Lab Part D does steps 1 to 3 on a healthy model, so you know what "normal" looks like.

9. Expert layer

Model runner rewrites

The model runner is where most engine performance work lands: input preparation on the GPU instead of the CPU, persistent buffers, fewer host-device syncs, and better attention metadata building. vLLM has gone through more than one generation of its GPU model runner for these reasons. Read the pull requests of such rewrites to see which overheads matter at scale.

Data parallelism and MoE coordination

With data parallelism, each rank has its own engine core and scheduler. For MoE models with expert parallelism, all ranks must run their forward passes in lockstep, even if one has no work, because experts communicate across ranks every layer. vLLM adds a coordinator process for this (chapter 4.5).

Returning routing and internal state

Reinforcement-learning pipelines sometimes need more than tokens: for example, which experts each token was routed to, so the trainer can replay the same routing. Engines have added options to return such internal data alongside outputs. Supporting this touches the model code, the runner and the output path.

10. Common mistakes

  • Reading engine code from the HTTP layer down. Start from the step function and the scheduler.
  • Patching engine internals from a client script and assuming the engine-core process sees the change.
  • Giving an engine too few CPU cores for its processes.
  • Debugging output quality by eye. Compare logprobs against a reference implementation.
  • Disabling CUDA graphs (--enforce-eager) for debugging and forgetting to turn them back on.

Answer these from the code (an AI assistant may explain lines, but find the answers yourself):

  1. In engine/scheduler.py, under what condition is a step a prefill step?
  2. In engine/block_manager.py, how does compute_hash make a block's hash depend on every earlier block? Why is that needed?
  3. In engine/model_runner.py, find where the number of KV blocks is computed. Which memory numbers does it subtract?
  4. Find the list of CUDA graph batch sizes. Which batches run without graphs?
  5. In scheduler.postprocess, what two conditions finish a sequence?
Answers
  1. When at least one waiting sequence fits the token budget and the free blocks. Then the step contains only prefills.
  2. Each block's hash is computed from its tokens plus the previous block's hash, so equal hashes mean equal full prefixes, not just equal blocks. Two prompts that share block 5's tokens but differ earlier must not share block 5's KV, because the K and V depend on everything before them.
  3. Blocks = (total memory × gpu_memory_utilization − used − peak + current) ÷ bytes per block, measured after a warm-up pass: memory for weights and the peak activation use are excluded.
  4. [1, 2, 4, 8] then every 16 up to the maximum batch. Prefill steps, eager mode, and batches above 512 tokens run without graphs.
  5. The token is the end-of-sequence token (unless ignore_eos), or the completion reached max_tokens.

Part D: compare an engine against a reference (T4)

import torch, math
from vllm import LLM, SamplingParams
name = "Qwen/Qwen2.5-0.5B-Instruct"
llm = LLM(model=name, dtype="half", gpu_memory_utilization=0.5, max_model_len=2048)
prompts = ["Explain what a scheduler does in one paragraph.", "List three prime numbers and why."]
outs = llm.generate(prompts, SamplingParams(temperature=0, max_tokens=64, logprobs=1))

from transformers import AutoModelForCausalLM, AutoTokenizer
tok = AutoTokenizer.from_pretrained(name)
ref = AutoModelForCausalLM.from_pretrained(name, torch_dtype=torch.float16).cuda().eval()
for o in outs:
    p_ids, g_ids = o.prompt_token_ids, list(o.outputs[0].token_ids)
    eng_lp = [o.outputs[0].logprobs[i][t].logprob for i, t in enumerate(g_ids)]
    ids = torch.tensor([p_ids + g_ids], device="cuda")
    with torch.inference_mode():
        lp = torch.log_softmax(ref(ids).logits[0].float(), -1)
    ref_lp = [lp[len(p_ids) - 1 + i, t].item() for i, t in enumerate(g_ids)]
    diff = [abs(a - b) for a, b in zip(eng_lp, ref_lp)]
    print(f"max |engine - reference| logprob diff: {max(diff):.3f}   mean: {sum(diff)/len(diff):.4f}")

Predict first: how large will the differences be for a healthy engine in FP16? Then deliberately corrupt the comparison (for example, shift ref_lp by one position) and see what a real bug looks like in these numbers.

What to expect

Mean differences around 0.01 or below, with occasional larger values (up to a few tenths) where two tokens were nearly tied. These come from different kernels and summation order (chapter 1.2, determinism). A bug shows as large differences on many tokens, often with the engine very confident (logprob near 0) while the reference gives a very low logprob.

12. In the real world

Engines in practice
  • Engine teams run logprob and output comparisons against reference implementations in continuous integration for every supported model.
  • Platform teams customize engines through plugins (custom schedulers, metrics, model variants) and keep close to upstream releases.
  • Small educational engines such as nano-vLLM and mini-SGLang are used as starting points for research prototypes, because their core loops fit in one reading session.
  • Capacity planning includes CPU cores per GPU, because API servers, engine cores and workers are separate processes.

14. Summary

  • An engine step is: schedule, prepare inputs, forward, sample, post-process.
  • Engines split work across processes: API server, engine core (scheduler, KV manager) and one worker per GPU.
  • nano-vLLM's scheduler: prefill-first separate steps, limited chunking, prefix hashing at admission, recompute preemption from the back. vLLM mixes decodes and prefill chunks in one step.
  • The runner flattens a mixed batch into token, position and slot arrays plus attention metadata; linear layers ignore sequence boundaries.
  • CUDA graphs are captured per batch size and replayed with padding.
  • Extend engines with plugins; debug silent errors by comparing logprobs with a reference.
