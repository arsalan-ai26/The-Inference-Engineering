Routing, load balancing and queueing

With more than one replica, every request needs a destination. For web services, spreading requests evenly is nearly optimal. For LLMs it is not: one request may carry 50 tokens and the next 50,000, replicas hold different cached prefixes and LoRA adapters, and responses stream for seconds or minutes. This chapter covers the difference between routers and load balancers, the routing policies used for LLMs and when each wins, queues and priorities, the queueing math that tells you how much headroom to keep, and how modern LLM-aware gateways put it together.

Answers
  1. Requests differ hugely in cost. Round-robin counts requests, not work, so a replica that received a 50,000-token prompt keeps getting its share of new requests, which queue behind it.
  2. Pick two replicas at random and send the request to the less loaded one. Much better than random, with very little state.
  3. Several times longer. For 4 servers in the standard M/M/c model, mean wait goes from about 0.75 to about 4.5 service times. Waits explode as utilization nears 100%.

1. Routers, load balancers and queues

  • Load balancer: a system-level component that spreads traffic over healthy replicas ("where could this request go?"). It handles health checks and removes failing replicas.
  • Router: a request-level decision ("where should this request go?") using information about the request and the replicas: prompt length, prefix, requested model or LoRA adapter, priority, replica load and cache contents.
  • Queue: where requests wait when every replica is at its concurrency target, while the autoscaler adds capacity (chapter 6.3).

Real stacks chain them: a global load balancer picks a region (chapter 6.5), a gateway routes to a model deployment, and an LLM-aware router picks a replica.

2. Why LLM routing is different

  • Request cost varies by orders of magnitude. Prefill cost scales with prompt length, decode time with output length; a request count says almost nothing about load.
  • Replicas have state. A replica that holds a prefix in its KV cache serves that request much faster (chapter 4.4); one that has a LoRA adapter loaded avoids loading it.
  • Long-lived streams. A request occupies a slot for its whole generation; connection-level balancing at the start of a stream decides its fate for minutes.
  • Engines already batch internally. Sending more requests to a replica is fine until its concurrency target, then latency rises steeply.

4. Queues, priorities and fairness

When every replica is at its target, requests wait. Queue design decides who waits:

  • FIFO is fair in arrival order and simple.
  • Priority queues serve higher tiers first (paid over free, interactive over batch). Combine with aging so low priority still progresses.
  • Per-tenant fairness (fair-share scheduling) stops one customer's burst from filling the queue for everyone.
  • Deadlines: each request carries a time after which its answer is useless; drop or reject it then instead of spending GPU time on it.
  • Admission control: when the queue predicts a wait beyond the SLO, reject early (HTTP 429 with a retry hint) or route to a lower tier, rather than accepting requests that will fail anyway.

When new replicas come up, the queue must hand them work immediately up to their concurrency target; otherwise requests keep waiting for the old replicas while the new ones idle.

5. The queueing math behind headroom

A standard model for c identical servers with random (Poisson) arrivals and random service times is M/M/c. Its key result is that waiting time is not proportional to load: it grows slowly at first and explodes near full utilization. The Erlang C formula gives the probability that a request must wait and the mean wait.

Two practical conclusions. First, plan to run at 70% to 80% of capacity, not 95%: the last 20% of utilization costs most of your latency budget, and bursts push you there anyway. Second, larger pools tolerate higher utilization for the same wait (pooling): 16 replicas behind one queue wait far less than 4 groups of 4 at the same load, which is another reason to route across the whole pool rather than pin traffic.

6. LLM-aware gateways in practice

  • llm-d (Kubernetes): a gateway proxy following the Gateway API Inference Extension, with an Endpoint Picker that scores pods on KV-cache affinity, queue depth and live metrics, multi-priority flow control with fair sharing, and an optional latency predictor for SLO-aware routing.
  • NVIDIA Dynamo: KV-aware routing across workers, integrated with disaggregation (chapter 4.6).
  • SGLang router and vLLM's production stack: cache-aware routing in front of engine replicas.
  • Ray Serve: pluggable request routers, including the prefix-aware router above.

Whatever the stack, the router needs live data from replicas (in-flight requests, waiting queue, KV usage, cache events). Stale data leads to herding: every router sends to the replica that looked emptiest a second ago.

7. Expert layer

Routing inside a replica: DP ranks

With data-parallel attention for large MoE models (chapter 4.5), one "replica" contains several DP ranks, each with its own KV cache. Requests must be routed to the rank holding their prefix, so prefix-aware routing extends inside the replica.

Herding and randomization

Many independent routers reading the same slightly stale load data all choose the same "least loaded" replica. Power of two choices and adding randomness to scores avoid this; so does centralizing the decision in one Endpoint Picker per pool.

Semantic and model routing

Some gateways route by content: easy questions to a small model, hard ones to a large model, or each domain to a fine-tuned variant. This saves cost but changes quality; evaluate it like any model change.

8. Common mistakes

  • Round-robin or least-connections in front of LLM replicas with heavy-tailed prompts.
  • Cache affinity without a load cap (chapter 4.4).
  • Unbounded queues that accept requests guaranteed to miss their SLO.
  • Planning capacity at 95% utilization.
  • Long-lived streams cut by load balancer idle timeouts.
  • Routers acting on stale metrics and herding.

Part C: headroom from Erlang C

import math
def erlang_c(c, rho):                                # probability a request must wait
    a = c * rho
    s = sum(a**k / math.factorial(k) for k in range(c))
    top = a**c / math.factorial(c) / (1 - rho)
    return top / (s + top)
for rho in [0.5, 0.7, 0.8, 0.9, 0.95, 0.98]:
    pw = erlang_c(4, rho)
    print(f"utilization {rho:.2f}: P(wait) {pw:.2f}, mean wait {pw / (4 * (1 - rho)):5.2f} x service time")
What we measured

For 4 servers: mean wait 0.09, 0.36, 0.75, 1.97, 4.46 and 11.95 service times at 50%, 70%, 80%, 90%, 95% and 98% utilization. Repeat with c = 16 at 90%: the wait is far smaller. Use this to argue for a utilization target in your capacity plan (chapter 6.5).

10. In the real world

Routing in production
  • Kubernetes inference stacks adopt LLM-aware gateways (llm-d, Gateway API Inference Extension) instead of plain service load balancing.
  • Agent and chat platforms route sessions to replicas holding their history, with load caps.
  • Multi-tenant APIs use per-tenant quotas, priority tiers and early rejection (429s) to keep SLOs under overload.
  • LoRA platforms route by adapter residency to avoid loading adapters on every request.

12. Summary

  • Load balancers keep healthy options; routers pick per request; queues hold overflow while capacity is added.
  • LLM requests differ hugely in cost and replicas hold state (KV prefixes, adapters), so request-count routing fails.
  • Use work-aware or power-of-two routing, add cache and adapter affinity with load caps, and consider SLO-aware scoring.
  • Design queues with priorities, per-tenant fairness, deadlines and early rejection.
  • Queueing math says waits explode near full utilization: keep 20% to 30% headroom and pool capacity.
