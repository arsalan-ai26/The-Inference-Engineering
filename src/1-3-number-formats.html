Number formats

Every weight and every activation in a model is stored in some number format. The format sets how much memory the model needs, how fast the GPU can do the math, and how much accuracy you lose. Choosing it well is one of the biggest levers in inference. This chapter shows what the bits mean and how to calculate model memory in any format.

1. Why the format matters so much

An 8B-parameter model stores 8 billion numbers. In FP32, each takes 4 bytes: 32 GB. In BF16, 2 bytes: 16 GB. In a 4-bit format, half a byte: about 4 GB. The same model can need an 80 GB GPU or fit on a laptop.

The format also sets speed, in two ways:

  • Memory traffic. Generating a token reads all the weights from memory (chapter 1.1, section 5). Half the bytes means about half the read time.
  • Math throughput. GPU math units do more operations per second on smaller formats. On an H100, dense FP8 math runs about twice as fast as BF16.

The cost is accuracy. Fewer bits means fewer distinct values, so each stored number is a rougher approximation. Quantization (chapter 4.1) is the craft of using fewer bits with little loss. This chapter gives you the foundation for it.

2. Integers: evenly spaced values

An integer format with n bits can store 2ⁿ distinct values. Signed formats use about half for negative numbers.

FormatBitsDistinct valuesRange
INT88256−128 to 127
INT4416−8 to 7

Integers are evenly spaced. The gap between neighbours is always 1. To store a weight such as 0.0137 as an integer, you divide it by a scale factor first, round, and multiply back later:

stored = round(w ÷ scale) restored = stored × scale

The scale is chosen so the largest weight maps to the largest integer. The problem: one large outlier forces a large scale, and then all the small weights round to 0 or 1. Model weights and activations do have outliers, so pure integer formats need careful handling.

3. Floating point: a number in scientific notation

A floating-point number is stored like scientific notation in base 2:

value = (−1)^sign × (1.mantissa) × 2^(exponent − bias)
Definitions

Sign bit: 0 for positive, 1 for negative.

Exponent bits: set the power of 2, so they set the range: how big and how small a number can be.

Mantissa bits (also called fraction or significand): set the digits after the binary point, so they set the precision: how finely you can tell two nearby numbers apart.

Bias: a fixed number subtracted from the stored exponent so that negative powers are possible. For an exponent with E bits, the bias is 2^(E−1) − 1.

The key idea: exponent bits buy range, mantissa bits buy precision. With a fixed bit budget you must trade one for the other.

A good picture: a ruler whose tick marks are close together near zero and spread out for large numbers. Between 1 and 2, the ticks are evenly spaced. Between 2 and 4, there are the same number of ticks, so they are twice as far apart. Each power of 2 is a new "window" with the same number of ticks. Floats keep a constant relative error, not a constant absolute error.

Worked example: what precision means

FP16 has 10 mantissa bits, so each window has 2¹⁰ = 1,024 ticks. Between 1 and 2 the gap is 1/1,024 ≈ 0.001. So FP16 can store 1.001 only as 1.0009766.

BF16 has 7 mantissa bits: 128 ticks per window, a gap of 1/128 ≈ 0.0078. So 1.001 becomes exactly 1.0 in BF16. The small change is lost.

Between 65,536 and 131,072 the BF16 gap is 65,536/128 = 512. So 70,000 is stored as 70,144.

FP4 E2M1 can store only 16 values: 0, 0.5, 1, 1.5, 2, 3, 4, 6 and their negatives (two of the 16 are +0 and −0). That is barely a number system. It works only because each small block of weights gets its own scale factor (section 6).

5. Why BF16 replaced FP16

FP16 and BF16 both use 16 bits. FP16 spends more on precision (10 mantissa bits). BF16 spends more on range (8 exponent bits, the same as FP32).

Training produces some very large and some very small numbers. In FP16, large activations overflow to infinity above 65,504, and tiny gradients underflow to zero below about 6 × 10⁻⁸. Engineers worked around this with "loss scaling": multiplying the loss by a big number so gradients stay in range. BF16 has FP32's range, so it rarely needs loss scaling. Its lower precision turned out to matter less than its range. Since the A100 (2020), BF16 is the standard format for training and for serving model weights.

For inference, this has two practical effects:

  • Most open models ship in BF16. Running a BF16 model in FP16 usually works, but some models produce infinities or NaNs (Not a Number) because a few activations exceed 65,504.
  • The free Colab T4 GPU has no fast BF16 math. On a T4, use FP16, and if you see NaNs, suspect overflow.

6. Scale factors and granularity

Low-bit formats store a few values well. To cover real weights, every format below 16 bits is used with scale factors. The question is how many numbers share one scale. This is called granularity.

GranularityOne scale perTrade-off
Per tensorWhole weight matrixAlmost no overhead; one outlier hurts the whole tensor
Per channelEach row or columnSmall overhead; outliers stay in their row
Per group or blockEach run of 16 to 128 numbersBest accuracy; scales take memory and work to apply

The newest formats build block scaling into the hardware:

  • MXFP8 and MXFP4 ("microscaling", an Open Compute Project standard): blocks of 32 values share one 8-bit power-of-two scale.
  • NVFP4 (NVIDIA): blocks of 16 FP4 values share one FP8 E4M3 scale, plus one FP32 scale for the whole tensor.

NVIDIA Blackwell GPUs (B200, B300) apply these scales inside the tensor cores, so the overhead is small. Older GPUs must apply them in software.

Watch out: what "MX" means

"MX" in MXFP8 and MXFP4 stands for microscaling, not "mixed precision". Some texts expand it wrongly.

Effective bits per weight

Scales add memory. To get the real size, add the scale bits spread over the block:

effective bits = value bits + (scale bits ÷ block size)
  • MXFP4: 4 + 8/32 = 4.25 bits per weight.
  • NVFP4: 4 + 8/16 = 4.5 bits per weight (the one tensor-wide FP32 scale is negligible).
  • INT4 with a 16-bit scale per group of 128: 4 + 16/128 = 4.125 bits. Many INT4 methods also store a zero point per group, which adds a few more bits.

7. Model memory in any format

weight memory ≈ parameters × bytes per parameter

Use bits ÷ 8 for bytes. Weights are only part of what a GPU must hold. Chapter 2.4 adds the KV cache, and the engine needs some working memory too.

Worked example: Llama 3.1 70B
  • BF16: 70.6 × 10⁹ × 2 bytes = 141 GB. Needs at least two 80 GB GPUs for weights alone.
  • FP8: 70.6 GB. Fits on one 80 GB GPU, with about 9 GB left for everything else. In practice that is too tight to serve many users.
  • 4-bit at 4.5 effective bits: 70.6 × 10⁹ × 4.5 ÷ 8 ≈ 39.7 GB. Fits on one 48 GB card.

8. Accumulation: why sums use more bits

A dot product adds many small products. If the running sum is stored in a low-precision format, small additions get lost once the sum is large (the gap between ticks becomes bigger than the number you add). So hardware multiplies in low precision but accumulates the sum in a wider format, usually FP32. A "BF16 matmul" on a GPU reads BF16, multiplies, and adds in FP32.

The same rule applies to sensitive steps such as softmax and normalization. Frameworks often run them in FP32 even when the model is in BF16. You will see this in the lab: adding 0.0001 ten thousand times in FP16 does not reach 1.

9. Expert layer

Subnormal numbers

When the exponent field is all zeros, IEEE formats switch to "subnormal" numbers with no hidden leading 1. These fill the gap between 0 and the smallest normal number. In FP16 the smallest normal is about 6.1 × 10⁻⁵ and the smallest subnormal about 6 × 10⁻⁸. Some hardware paths flush subnormals to zero for speed.

FP8 variants are not all the same

The common E4M3 used in AI has no infinity and only one NaN pattern. That frees bit patterns and raises its maximum to 448. In PyTorch this type is float8_e4m3fn ("fn" means finite, with NaN). AMD's MI300 used a different variant (e4m3fnuz) with another exponent bias. A model quantized for one variant needs conversion for another.

Format support by GPU generation

Tensor-core support arrived generation by generation: FP16 with Volta and Turing (Turing also has INT8 and INT4), BF16 and TF32 with Ampere (A100), FP8 with Hopper (H100) and Ada (L4, L40S), and FP4 with the MX and NVFP4 formats on Blackwell. On a GPU without native support, a low-bit model can still save memory, but the math runs after converting back to a higher format, so you do not get the math speed-up.

Outliers in activations

Large language models develop a few activation channels with values far larger than the rest. These outliers are the main obstacle to 8-bit and 4-bit activations. Methods such as SmoothQuant move the difficulty from activations into weights, and rotation methods spread outliers across channels. Chapter 4.1 covers them.

10. Common mistakes

  • Calling 1 GB "2³⁰ bytes" in one place and "10⁹ bytes" in another. State which you use. This book uses 10⁹.
  • Forgetting scale factors when computing 4-bit model size.
  • Running a BF16 model in FP16 and not checking for infinities or NaNs.
  • Expecting a speed-up from FP8 on a GPU without FP8 tensor cores (for example the T4 or A100).
  • Thinking precision and range are the same. Exponent bits give range; mantissa bits give precision.

Part B: overflow and lost precision

Predict first: what does each line print?

x = torch.tensor([70000.0, 1.001, 1e-8])
print(x.to(torch.float16))     # ?
print(x.to(torch.bfloat16))    # ?
print(torch.tensor([300., 500.]).to(torch.float8_e4m3fn).float())
Expected output

FP16: [inf, 1.0010, 0.0]. 70,000 overflows; 1e-8 underflows below the smallest subnormal.

BF16: [70144, 1.0, about 1e-8]. No overflow, but 1.001 loses its small part, and 70,000 rounds to 70,144.

FP8 E4M3: 300 becomes 288 (the gap between 256 and 512 is 32). 500 is above the maximum 448. In current PyTorch this cast clamps it to 448; other tools may return NaN. Real FP8 pipelines scale values into range first, so they never rely on this behaviour.

Part C: accumulation error

for d in [torch.float32, torch.float16, torch.bfloat16]:
    s = torch.tensor(0.0, dtype=d)
    step = torch.tensor(1e-4, dtype=d)
    for _ in range(10_000):
        s = s + step
    print(d, s.item())          # the exact answer is 1.0
What you should see

FP32 is close to 1.0. FP16 stops at 0.25: once the sum reaches 0.25, the gap between FP16 values (about 0.00024) is more than twice the step, so each addition rounds away. BF16 stops at 0.03125, much earlier. This is why GPUs accumulate dot products in FP32.

Part D: matmul error by format

torch.manual_seed(0)
A = torch.randn(256, 1024); B = torch.randn(1024, 256)
ref = A.double() @ B.double()
for d in [torch.float32, torch.bfloat16, torch.float16]:
    out = (A.to(d) @ B.to(d)).double()
    rel = ((out - ref).norm() / ref.norm()).item()
    print(f"{str(d):16s} relative error {rel:.2e}")
# FP8: store in FP8, compute in FP32 (a common pattern on GPUs without FP8 math)
A8 = A.to(torch.float8_e4m3fn).float(); B8 = B.to(torch.float8_e4m3fn).float()
print("fp8 storage     relative error", f"{((A8 @ B8).double() - ref).norm() / ref.norm():.2e}")

Part F: build a tiny block quantizer

This shows why block scales help. Write it with AI help if you like; focus on reading the result.

def quant_int4(w, block):
    w = w.reshape(-1, block)
    scale = w.abs().amax(dim=1, keepdim=True) / 7          # map the block max to 7
    q = torch.clamp(torch.round(w / scale), -8, 7)
    return (q * scale).reshape(-1)

w = torch.randn(4096 * 64)
w[123] = 40.0                                             # one outlier
for block in [w.numel(), 4096, 128, 32]:
    err = ((quant_int4(w, block) - w).norm() / w.norm()).item()
    print(f"block={block:>8}  relative error {err:.3f}")

Predict: how does the error change as the block gets smaller? Why does the outlier matter less for small blocks?

12. In the real world

Formats in production today
  • Model releases come in BF16 by default. Many vendors also ship official FP8 versions. Some recent open models ship natively in low precision; for example, gpt-oss uses MXFP4 for its MoE weights.
  • Serving engines (vLLM, SGLang, TensorRT-LLM) can load FP8 weights and run FP8 math on Hopper and newer GPUs, and can store the KV cache in FP8 (chapter 2.4).
  • Local inference (llama.cpp, Ollama) uses the GGUF file format with block-quantized 2- to 8-bit weights so large models run on laptops (chapter 3.6).
  • Hardware marketing quotes FLOP/s for the smallest format. Compare GPUs at the same format and note whether a number assumes sparsity.

14. Summary

  • Memory ≈ parameters × bytes per parameter. 8B in BF16 ≈ 16 GB; in FP8 ≈ 8 GB; in 4-bit ≈ 4 to 4.5 GB.
  • Floats are sign × 1.mantissa × 2^exponent. Exponent bits give range; mantissa bits give precision.
  • BF16 has FP32's range with less precision, which is why it replaced FP16 for training and serving.
  • FP8 E4M3 (max 448) and FP4 E2M1 (max 6) need scale factors. Smaller blocks give better accuracy at a small memory cost.
  • Low-precision math still accumulates in FP32.
  • Speed-ups need hardware support for the format: FP8 on Hopper and Ada, FP4 on Blackwell.
