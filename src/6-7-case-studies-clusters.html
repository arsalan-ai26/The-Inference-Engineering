Expert depth: production case studies, cluster infrastructure and confidential inference

This chapter looks at how real systems put the earlier chapters together. Two published deployments come first: DeepSeek's own service for V3 and R1, with its full cost and token statistics, and Cursor's real-time coding models served by Together AI on Blackwell. Then the cluster layer underneath: Kubernetes and its GPU extensions, Slurm, and multi-cloud orchestrators such as dstack and SkyPilot, plus how fleets keep GPUs busy. Last, confidential inference: how trusted execution environments protect prompts even from the machine's owner, what they cost, and what they do not protect against.

1. Case study: DeepSeek's V3/R1 service

In February 2025 DeepSeek published how it serves DeepSeek-V3 and R1 (671B-parameter mixture-of-experts models, chapter 4.5) and a day of production statistics. It uses nearly every technique from Part 4.

  • Disaggregation (chapter 4.6): separate prefill and decode deployments.
  • Large-scale expert parallelism. Prefill units span 4 nodes (32 GPUs, expert parallelism 32, with 9 routed experts and 1 shared expert per GPU). Decode units span 18 nodes (144 GPUs, 2 routed experts and 1 shared expert per GPU). Attention and shared experts use data parallelism across the same GPUs. Both include 32 redundant copies of busy experts.
  • Overlapping communication with computation. Each batch is split into two micro-batches so one computes while the other communicates; decode uses a 5-stage pipeline because its stages have uneven lengths.
  • Three load balancers: prefill (balance attention work and input tokens across GPUs), decode (balance KV cache use and request counts), and experts (balance expert work so no GPU becomes the bottleneck).
  • Precision as in training: FP8 for matmuls and dispatch, BF16 for attention and combine.
  • A KV cache on disk for prefix reuse (chapter 4.4).

One prefill unit (4 nodes) and one decode unit (18 nodes), each with 8 H800 GPUs per node. Many such units run side by side.

Three lessons. First, expert parallelism trades latency for throughput deliberately: 20 to 22 tokens per second per user is modest, but each decode node produces about 14,800 tokens per second. Second, prefix caching changes the economics: over half of all input tokens were cache hits, billed at a quarter of the price. Third, fleets follow the day: DeepSeek runs inference on all nodes at peak and moves nodes to research and training at night, which is how the average stays 18% below the peak. Actual revenue is much lower than the theoretical figure (free web and app use, cheaper V3 pricing, night discounts), so read the margin as an upper bound.

2. Case study: Cursor on Together AI

Cursor's in-editor agents must answer while the developer is still looking at the same code; a late suggestion no longer matches the file. That makes worst-case latency under concurrency the main requirement. Together AI's published account of the work:

  • New hardware early: GB200 NVL72 and HGX B200 for memory bandwidth and tensor throughput, with the reliability work early hardware needs.
  • ARM hosts: GB200 pairs GPUs with Grace CPUs (ARM). Much of the inference stack assumed x86, so the host side had to be ported and tuned (recall chapter 5.1: CPU overhead matters at small batch).
  • Custom kernels for Blackwell's low-precision tensor core instructions, and parallelism layouts designed for the 72-GPU NVLink domain.
  • A weights-to-production pipeline: each new model from Cursor's research team is quantized to NVFP4 with TensorRT-LLM, validated, and deployed to a test endpoint within days; Cursor runs its evaluations, then A/B tests on production traffic, and cuts over only after validation and live checks (chapters 4.1, 6.5 and 6.6).

The lesson: for a fast-moving product, the speed and safety of shipping new weights matters as much as the kernels. Quantization is part of the release pipeline, with quality gates, not a one-off optimization.

3. The cluster layer

Definitions

Orchestrator (scheduler): software that decides which job or service runs on which machines, starts it, and restarts it on failure.

Pod: Kubernetes' unit of deployment, one or more containers scheduled together on one node.

Gang scheduling: start all parts of a multi-node job together or none of them, so half a model never sits waiting for the other half.

SystemModelStrengths for inference
KubernetesContainers on a cluster with a control plane and worker nodesThe standard for services: autoscaling, rolling updates, health checks, service discovery. Most inference platforms (llm-d, Dynamo, KServe) build on it.
SlurmBatch jobs as native processes on static HPC nodes, with partitions and queuesCommon in research and training clusters; good for batch inference and evaluations; less natural for long-running autoscaled services.
dstackContainer-first, provisions cloud instances on demand, or uses Kubernetes or SSH-reachable machinesOne YAML file for development, training and inference services across clouds and on-premises; fleets as explicit pools of capacity.
SkyPilotMulti-cloud orchestrator over clouds and Kubernetes clustersRuns the same job or service on whichever cloud has GPUs, including AMD Instinct GPUs; treats several clusters as one pool.

GPUs in Kubernetes

  • The NVIDIA device plugin makes GPUs a schedulable resource (nvidia.com/gpu: 1); the GPU Operator installs drivers, the device plugin and monitoring (DCGM, chapter 6.6) on each node. AMD has an equivalent ROCm GPU operator.
  • Sharing one GPU: MIG gives hardware-isolated slices (chapter 5.5). The device plugin also offers time-slicing (workloads interleave with no memory isolation, and if one crashes they all do) and MPS (memory and compute limits per workload). Use sharing for small models and development, not for latency-critical services.
  • Multi-node replicas: a model sharded across nodes (chapter 4.5) needs its pods created, placed close together, updated and restarted as one unit. The LeaderWorkerSet API does this: each replica is a leader pod plus worker pods, with gang scheduling, topology-aware placement and all-or-nothing restart. Its DisaggregatedSet extension manages prefill and decode roles together, with rollouts that keep their capacity ratio. Both are co-designed with llm-d.
  • Networking: multi-node inference needs RDMA networks (InfiniBand or RoCE) exposed to pods, and placement that keeps a replica's nodes on the same network fabric (chapters 4.5 and 4.6).

Keeping a fleet busy

Past a few hundred GPUs, the problem becomes capacity spread over regions and clouds, with some clusters starved while others idle. The answer is to treat all capacity as one pool: a global control plane (chapter 6.5) that places replicas wherever GPUs are free, plus work that can fill gaps. DeepSeek's day and night reallocation is one example; low-priority batch inference, evaluations and training jobs that can be preempted are others. Each requires fast, reliable start-up (chapter 6.2) so capacity can move back when traffic returns.

4. Confidential inference

Normally you must trust whoever runs the hardware: the cloud provider, the GPU marketplace host, their staff and anyone who compromises their machines. A trusted execution environment (TEE) removes them from that trust.

Definitions

Confidential VM: a virtual machine whose memory is encrypted with keys held inside the CPU, so the host operating system and hypervisor cannot read it (Intel TDX, AMD SEV-SNP).

GPU confidential computing: a GPU mode (from NVIDIA Hopper onwards) that protects the GPU's memory and encrypts traffic between the confidential VM and the GPU over PCIe.

Remote attestation: a signed report, produced by the hardware, of exactly what was booted and loaded. A client checks it against known-good values before sending data.

Interactive: who can see a prompt?
Pick a deployment. Red parties can read prompts while they are processed, amber ones are reduced risks, green ones are blocked.

Chutes, a decentralized GPU network whose machines are run by anonymous operators, describes a full stack for this case. Its confidential mode runs workloads in Intel TDX confidential VMs with NVIDIA's protected PCIe between CPU and GPU. Attestation ties into disk access: the encrypted root filesystem's key is released only after the measured boot checks out. Only images built and signed by its own build system can run. Outbound network traffic is blocked by default. Random challenges hash slices of the model weights to catch a host that swaps in a cheaper model. The important caveat, which Chutes states: a TEE protects you from the host, not from malicious code inside the TEE. A server that logs prompts inside the protected VM still leaks them, which is why signed images and egress control are part of the design.

Cost: a 2024 benchmark of LLM inference on Hopper GPUs in confidential mode found little overhead inside the GPU; the cost came from encrypted CPU to GPU transfers over PCIe. For most typical queries the overhead stayed below 7%, and it approached zero for larger models and longer sequences, where GPU computation dominates.

5. Expert layer

Why expert-parallel decode needs a load balancer for experts

Some experts are popular. With 2 experts per GPU across 144 GPUs, the GPU that holds the hottest experts receives the most tokens, and every step waits for the slowest GPU. Redundant copies of hot experts, placed by observed load, spread that work. It is the same straggler problem as in chapter 6.4, inside a single model step.

Verifying the model, not just the machine

Attestation shows which software booted. It does not prove which weights produced a given answer. Weight-slice hashing challenges and per-token verification hashes bound to a specific model revision (as Chutes describes) address the "bait and switch" where a provider serves a smaller or more quantized model than advertised. Chapter 6.6's provider comparison is the statistical version of the same check.

6. Common mistakes

  • Reading published margins or throughput as typical without the assumptions (GPU price, billing mix, free traffic).
  • Deploying multi-node models as independent pods that can be scheduled, updated or restarted separately.
  • Using GPU time-slicing for latency-sensitive services.
  • Assuming a TEE protects data from the code that runs inside it.
  • Accepting a TEE claim without checking attestation against known-good values.

Part B: design a multi-node deployment

You must serve a model that needs 16 GPUs (two 8-GPU nodes, tensor parallelism inside each node and pipeline parallelism across them) on Kubernetes, with autoscaling from 2 to 6 replicas. Write down: the LeaderWorkerSet layout (leader and workers, size), what happens on a rolling update and when one worker pod crashes, the network and placement requirements, and the readiness check that decides when a replica can take traffic. Then compare with running the same model as a dstack or SkyPilot service across two clouds: what changes in failover and capacity?

Part C: a confidential inference threat model

For a hospital that wants to use an open-weight model on a GPU marketplace: list who could see prompts in a standard deployment, which of them a TEE removes, what remains (the serving code, the client side, logs and traces, the model output), and which controls address each. Decide which attestation evidence the hospital's client must check before sending a request.

8. In the real world

Where these patterns appear
  • Large MoE providers use disaggregation with wide expert parallelism and expert load balancing, as DeepSeek describes.
  • Inference platforms run multi-cloud control planes on Kubernetes, with LeaderWorkerSet-style groups for multi-node models.
  • Research labs run Slurm or Kubernetes for training and lend capacity between training and inference over the day.
  • Privacy-sensitive users (health, finance, decentralized networks) use confidential VMs with GPU confidential computing and client-side attestation checks.

10. Summary

  • DeepSeek combines disaggregation, wide expert parallelism, overlapped communication, three load balancers and a disk KV cache; its fleet shrinks at night for training.
  • Cursor's real-time serving depends on new hardware, custom kernels and a fast, gated pipeline from new weights to NVFP4 production endpoints.
  • Kubernetes is the base for services; LeaderWorkerSet groups multi-node replicas; Slurm, dstack and SkyPilot cover batch, multi-cloud and on-premises work.
  • TEEs protect prompts from the host at modest cost, but not from the code inside; pair them with signed images, egress control and checked attestation.
