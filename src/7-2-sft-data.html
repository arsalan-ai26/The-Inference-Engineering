Supervised fine-tuning and data

Supervised fine-tuning is next-token training on example conversations, with one twist: the loss counts only the tokens the model should learn to write. Most SFT failures are not algorithm problems but data and formatting problems: the wrong chat template, the loss computed on the user's text, too few good examples or too many bad ones, a learning rate that wipes out what the model knew. This chapter covers the data format, chat templates, loss masking, packing, the few hyperparameters that matter, and how to avoid overfitting and forgetting.

Answers
  1. So the model learns to write assistant replies, not to imitate users. Gradient spent on predicting the user's text is wasted at best, and teaches the wrong behaviour at worst.
  2. The model sees token patterns it was never trained on: it may not stop, may leak role markers into answers, or may lose the behaviour you trained. Train and serve with the same template, from the same tokenizer files (chapter 6.6).
  3. Overfitting and catastrophic forgetting of general skills. Fixes: fewer epochs or a lower learning rate; mix general chat data into the training set; or use LoRA (chapter 7.3), which tends to forget less.

1. The data format

Definitions

Conversational dataset: each example is a list of messages with roles (system, user, assistant, sometimes tool).

Prompt-completion dataset: each example is one prompt and one target completion.

Chat template: the rule (a Jinja template stored with the tokenizer) that turns a list of messages into the exact token sequence the model was trained on, with its special tokens.

Loss mask: a per-token flag that says whether a token's prediction counts in the loss. Masked tokens get the label -100 in PyTorch and Hugging Face code.

Packing: concatenating several short examples into one training sequence up to a maximum length, so batches contain no padding.

The model never sees roles; it sees tokens. Qwen-family models use ChatML-style markers: <|im_start|>assistant, the reply, then <|im_end|>. The end-of-turn token matters most: if the model never learns to produce it, generation does not stop. Reasoning models add <think>...</think> blocks, and tool-using models add tool-call and tool-result formats (chapter 3.5). The Smol playbook recommends ChatML or Qwen's templates as a starting point when designing your own; when fine-tuning an existing instruct model, keep its template.

2. Loss masking

SFT minimizes the average negative log probability of the target tokens. With assistant-only loss, the targets are the assistant tokens plus their end-of-turn token; system and user tokens are context only.

In TRL, set assistant_only_loss=True for conversational data; the chat template must mark assistant spans with {% generation %} tags, which TRL adds automatically for known families such as Qwen3. For prompt-completion data, TRL trains on the completion only by default. How much it matters: Hugging Face found masking user turns gave a few points on most evaluations, with the biggest effect on instruction following (IFEval). "Last turn only" is useful when earlier assistant turns in your data came from a weaker model you do not want to imitate.

3. Data: quality, quantity and mixture

  • Quality first. LIMA showed strong alignment from 1,000 carefully chosen examples (chapter 7.1). A few hundred to a few thousand clean, consistent examples of your task usually beat a large noisy set.
  • Match the deployment distribution: real input lengths, real edge cases, the same system prompt and tools you will serve with.
  • Consistent targets. If two annotators format answers differently, the model learns an average of both.
  • Mix in general data when training on a narrow task, to limit forgetting of general skills. Thinking Machines found that mixing chat data into domain training preserved instruction following only partly, and that on-policy distillation afterwards restored it (chapter 7.5).
  • Synthetic data from a stronger model is common (it is distillation, chapter 7.5). Check its licence terms and filter it like any other data.
  • Hold out an evaluation set before training, from the same distribution, and never train on it (chapter 7.6).

4. The hyperparameters that matter

SettingGuidance from the sources
Learning rateThe most important setting after the data. For full fine-tuning, typically an order of magnitude or more below the pretraining rate; Hugging Face used 1e-5 for SmolLM3 and suggests scanning 1e-6, 3e-6, 1e-5, 3e-5, 1e-4. LoRA's best rate is about 10 times the full fine-tuning rate (chapter 7.3).
EpochsStart with one. More epochs can add a few points on the task but often hurt other skills; Raschka found multiple epochs on a static dataset often made results worse.
Batch size and packingPacking raised SFT throughput 3 to 5 times in Hugging Face's runs, and lets each step contain many more tokens; for small datasets, fewer optimizer steps can hurt, so compare evaluations with and without it.
Maximum sequence lengthCover your real inputs; truncated examples teach truncated answers.
OptimizerAdamW is the default; Raschka saw little difference between AdamW and SGD with a schedule for LoRA.
Worked example: how much padding does packing remove?

10,000 examples with a median length of about 400 tokens and a long tail (the lab's distribution), in random batches of 8: 61% of all token positions are padding, so most compute is wasted. Sorting by length before batching cuts the waste to under 1%. Packing into 4,096-token rows fills the rows completely. Packing needs attention that does not cross example boundaries (position IDs reset and a block-diagonal mask, or a padding-free kernel), otherwise one example attends to another.

5. Overfitting and forgetting

Overfitting: training loss keeps falling while held-out loss and quality stop improving. Catastrophic forgetting: skills not in the fine-tuning data degrade, such as general instruction following, safety behaviour or other languages. Watch for both with a held-out task set and a small general evaluation (chapter 7.6). Remedies, cheapest first: lower learning rate, fewer epochs, LoRA instead of full fine-tuning, mixing general data, and on-policy distillation from the original model to restore lost behaviour.

7. Expert layer

Tokenization traps at the template boundary

Tokenizing the prompt and the answer separately and concatenating them can give different tokens from tokenizing the full text (a space or newline merges differently at the boundary). Build training examples by tokenizing the rendered conversation once and computing the mask from token positions, as the lab does, or use the template's assistant mask. A mismatch here means the model trains on token sequences it never sees at inference.

Per-token loss averaging

With packing or variable lengths, averaging the loss per sequence weights short answers more than long ones; averaging per token weights every token equally. Frameworks differ in their default, which changes what the model favours (short or long answers). Check which one your trainer uses when results differ between frameworks.

8. Common mistakes

  • Training on user and system tokens by accident.
  • Dropping the end-of-turn token from the targets, so the model never stops.
  • Training with one chat template and serving with another.
  • Several epochs at a high learning rate on a few hundred examples.
  • No held-out task evaluation and no general evaluation.
  • Packing without resetting attention between examples.

9. Lab

Part A: render a conversation and build the mask

from transformers import AutoTokenizer
tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")
conv = [{"role": "system", "content": "You are a support agent for Acme Bank."},
        {"role": "user", "content": "I lost my card. What should I do?"},
        {"role": "assistant", "content": "Block it now in the app under Cards > Block. Then order a new one."},
        {"role": "user", "content": "How long does a new card take?"},
        {"role": "assistant", "content": "Usually 5 to 7 working days."}]
text = tok.apply_chat_template(conv, tokenize=False)
print(text)
ids = tok(text, add_special_tokens=False)["input_ids"]
start, end = tok.convert_tokens_to_ids("<|im_start|>"), tok.convert_tokens_to_ids("<|im_end|>")
labels = [-100] * len(ids); i = 0
while i < len(ids):
    if ids[i] == start and tok.decode(ids[i+1:i+3]).startswith("assistant"):
        j = i + 1
        while tok.decode([ids[j]]) != "\n": j += 1          # skip the "assistant\n" header
        k = j + 1
        while ids[k] != end: k += 1
        for p in range(j + 1, k + 1): labels[p] = ids[p]    # reply tokens + <|im_end|>
        i = k
    i += 1
trained = [t for t, l in zip(ids, labels) if l != -100]
print(f"tokens {len(ids)}, trained on {len(trained)} ({len(trained)/len(ids):.0%})")
print(repr(tok.decode(trained)))
What we measured
tokens 79, trained on 28 (35%)
trained text: 'Block it now in the app under Cards > Block. Then order a new one.<|im_end|>Usually 5 to 7 working days.<|im_end|>'

Only 35% of the tokens are targets. Check by eye that both replies and both end-of-turn tokens are included, and nothing from the system prompt or the user. Then compare with TRL: build an SFTTrainer with assistant_only_loss=True on the same conversation and confirm its mask selects the same 28 tokens.

Part B: padding and packing

import numpy as np
rng = np.random.default_rng(0)
lens = rng.lognormal(np.log(400), 0.8, 10_000).astype(int).clip(20, 4096)
waste = lambda order: 1 - lens.sum() / sum(order[i:i+8].max() * len(order[i:i+8]) for i in range(0, len(order), 8))
print("median", int(np.median(lens)), "random batches", f"{waste(lens):.0%}", "sorted batches", f"{waste(np.sort(lens)):.1%}")
rows = []                                    # first-fit decreasing packing into 4,096-token rows
for l in sorted(lens, reverse=True):
    for i, r in enumerate(rows):
        if r + l <= 4096: rows[i] += l; break
    else: rows.append(l)
print(len(rows), "packed rows, fill", f"{lens.sum() / (len(rows) * 4096):.1%}")

median 396 random batches 61% sorted batches 0.3%
1342 packed rows, fill 100.0%

Part C: audit a dataset

Take 50 examples from a dataset you plan to use. For each, check: template correct, target answer consistent in format, no truncation at your maximum length, no evaluation items leaked in, no personal data that should not be there. Count the problems per category; a problem rate above a few percent is worth fixing before any training.

10. In the real world

SFT in practice
  • Model releases use large, curated SFT mixtures (instruction following, code, maths, multilingual, tool use, reasoning traces) with assistant-only loss.
  • Product teams fine-tune on hundreds to tens of thousands of in-house examples, usually with LoRA, and mix in general data to protect broad skills.
  • Data work dominates: most of the time goes into collecting, cleaning and evaluating examples, not training.

12. Summary

  • Render conversations with the model's own chat template; train and serve with the same one.
  • Compute loss on assistant tokens and their end-of-turn token only.
  • A few thousand clean, consistent, representative examples beat a large noisy set; hold out an evaluation.
  • Tune the learning rate first; start with one epoch; pack sequences with attention reset between examples.
  • Watch for overfitting and forgetting with task and general evaluations.
