Packaging, API layer, startup and shutdown

A tuned engine on a laptop is not a service. To serve traffic it must be packaged so it runs the same everywhere, expose a stable API, start quickly when capacity is added, report when it is ready, and stop without dropping requests. This chapter covers containers for GPU inference, how model weights get onto the GPU, every stage of a cold start and how to shorten it, the API layer in front of the engine, health checks, and graceful shutdown.

1. Containers for GPU inference

A container packages an application with everything it depends on, so it runs the same on every node. For inference that matters more than usual, because the dependency chain is long and fragile: GPU driver (on the host) → CUDA runtime and libraries → PyTorch → kernel libraries (FlashAttention, FlashInfer, Triton) → the engine → your code. A version mismatch anywhere can mean a crash, a silent slow path, or different outputs.

Definitions

Image: an immutable package built from a Dockerfile, made of layers. Container: a running instance of an image with a thin writable layer that disappears when it stops. Registry: where images are stored and pulled from.

NVIDIA Container Toolkit: lets containers use the host's GPUs and driver. The host driver must be new enough for the CUDA version inside the image (chapter 1.6).

Practices

  • Start from the engine's official image (for example vllm/vllm-openai or SGLang's image) rather than building CUDA and PyTorch yourself.
  • Pin everything: image tags by digest, Python packages by exact version (a lock file from uv, pip-tools or poetry). A rebuild next month must produce the same image.
  • Keep images lean. An inference image is already large (the CUDA libraries and PyTorch alone are several GB). Every extra GB slows every pull on every new node.
  • Order layers by change frequency: base and dependencies first, your code last, so code changes rebuild and ship only a small top layer.
  • New model releases often need pre-release engine builds; plan to rebuild on the stable release when it arrives.
FROM vllm/vllm-openai:v0.X.Y           # pin an exact version (use the digest in production)
COPY requirements.lock /tmp/
RUN pip install --no-cache-dir -r /tmp/requirements.lock
COPY app/ /app/                          # small, changes often: last
ENV HF_HOME=/models                      # weights mounted here, not baked in
ENTRYPOINT ["vllm", "serve"]

Prebuilt model containers such as NVIDIA NIM bundle a model, an optimized engine for specific GPUs, an OpenAI-compatible API, metrics and health endpoints. They are quick to adopt and a good reference; custom images give more control over engine versions, kernels and configuration.

2. Getting weights onto the GPU

Loading weights is usually the longest part of a cold start for large models: a 70B model in BF16 is 141 GB.

SourceTypical bandwidthNotes
Hugging Face Hub (internet)Limited by egress and your networkFine for development; slow and rate-limited at scale. Use a token.
Object storage (S3, GCS) in the same regionHundreds of MB/s to several GB/s with parallel streamsNeeds parallel, chunked downloads to be fast.
Shared network file system or node-local cacheSeveral GB/sPre-populated caches near the GPUs are the usual answer at scale.
Local NVMe on the nodeSeveral GB/s per driveFastest; requires the weights to already be there.

Three tricks shorten loading:

  • Smaller weights: quantized checkpoints (chapter 4.1) halve or quarter the bytes to move.
  • Streaming straight to the GPU: loaders that read file chunks in parallel and copy them to GPU memory as they arrive, instead of reading the whole file first (vLLM supports alternative load formats, for example a Run:ai model streamer, for this).
  • Memory-mapped safetensors: the file is mapped into memory and read only when tensors are used. Note what this means for measurement: "loading" a mapped file looks instant; the real cost appears when bytes are copied to the GPU (Part A of the lab shows this).

With tensor parallelism each GPU loads only its shard, so loading parallelizes across GPUs if storage can keep up.

3. Anatomy of a cold start

A cold start is the time from deciding to add a replica to that replica serving traffic. Each stage has its own fix:

StageWhat happensHow to shorten it
GPU node procurementA node is provisioned or freed and assignedWarm node pools; reserved capacity; contract terms on node start time
Image pullContainer layers are downloaded and unpackedLean images; layer caching on nodes; registries near the cluster; lazy-loading image formats
Weight loadingWeights move from storage to GPU memoryLocal caches, parallel streaming loaders, quantized checkpoints
Engine startMemory profiling, KV cache allocation, torch.compile, CUDA graph captureCompile caches (chapter 5.7), fewer graph sizes, prebuilt engines
Warm-upFirst requests trigger lazy initialization and cachingSend synthetic warm-up requests before reporting ready
Interactive: a cold-start budget
Estimate each stage and see which dominates. Defaults: Llama 3.1 70B on 4 GPUs from a regional object store. Change the source and precision to see what moves. Assumptions: image pulls at about 0.5 GB/s; engine start 90 s with compilation and graph capture, 20 s with caches; 10 s warm-up; node provisioning about 3 minutes.

The autoscaler's behaviour depends on this number (chapter 6.3): if adding a replica takes ten minutes, you must scale up ten minutes before you need it, and you cannot afford to scale down eagerly.

Avoiding the cold start entirely

  • Warm pools: idle replicas already loaded, at the cost of paying for them.
  • Sleep and wake: some engines can offload weights to CPU memory and free GPU memory while idle, then restore them much faster than a full start (vLLM has a sleep mode for this, used for example in reinforcement learning loops).
  • Snapshots: checkpointing a started process (CPU and GPU state) and restoring it, which some platforms offer to skip engine start-up.

4. The API layer

Clients talk to an HTTP API, almost always OpenAI-compatible (/v1/chat/completions, /v1/completions, /v1/embeddings, /v1/models), so the same client SDKs and frameworks work with any backend (chapter 3.1). Around the engine's own server, production stacks add:

  • A gateway for authentication (API keys, tokens), rate limits and quotas per customer, request size limits, and routing to models and versions.
  • Validation of prompts against the model's context window and of parameters (max tokens, temperature ranges, structured output schemas) before they reach the GPU.
  • Streaming: server-sent events over HTTP for token streams; WebSockets or gRPC for bidirectional real-time use such as voice. Long-lived streams need load balancers and timeouts configured for them.
  • Timeouts and cancellation: when a client disconnects, the engine must stop generating and free its KV cache (chapter 3.3).
  • Asynchronous (batch) endpoints for work that is not latency-sensitive: the request is accepted at once and the result delivered later by polling or a webhook, which lets the platform schedule it into idle capacity.

Client-side overhead counts too: establishing a TLS connection costs tens of milliseconds, a real share of a 300 ms latency budget. Reuse connections (the standard SDKs do), and keep clients close to the servers.

5. Health checks, readiness and graceful shutdown

  • Startup and readiness: report ready only after weights are loaded, graphs captured and a warm-up request succeeded. Until then the load balancer must not send traffic. vLLM exposes /health; NIMs expose separate live and ready endpoints.
  • Liveness: restart a replica whose engine has crashed or hung. Make liveness checks cheap and tolerant: a replica busy with a long prefill is not dead.
  • Graceful shutdown: when a replica is removed (scale-down, rollout, node maintenance), first take it out of the load balancer, then let in-flight requests finish, then stop. In Kubernetes: a preStop hook that marks the pod not ready and waits, and a terminationGracePeriodSeconds longer than your p99 request duration. Too short cuts long answers mid-stream; too long slows every rollout.
Watch out: long requests and shutdown

Reasoning models and long generations can run for minutes. Size drain timeouts from the measured p99 request duration, and decide what happens to requests that exceed it (retry elsewhere, or return a partial result with an error).

6. Expert layer

Compound and multi-model services

Many products chain models (speech recognition, an LLM, speech synthesis; or an embedding model, a reranker and an LLM). Package and scale each model as its own service, sized for its own hardware, but keep them in the same cluster: a few tens of milliseconds per hop between regions adds up across a pipeline. Chapter 6.3 covers scaling each component independently.

Reproducible builds for regulated environments

Air-gapped and regulated deployments need images and weights built, scanned and signed in advance, with no downloads at start-up. That means mirroring model weights, pinning every artifact by hash, and testing the exact image that ships.

7. Common mistakes

  • Unpinned dependencies, so a rebuild silently changes the engine or a kernel.
  • Downloading weights from the internet on every cold start.
  • Reporting ready before warm-up, so the first users pay compilation time.
  • Liveness probes that kill replicas during long prefills.
  • No drain on shutdown, so every deploy cuts off streaming answers.
  • Measuring "load time" of memory-mapped files without touching the data.

8. Lab

Goal: measure weight loading honestly, write a deployable image definition, and time a real engine's start-up stages.

Part A: load two model sizes (CPU, a minute)

import time, os, glob, torch
from huggingface_hub import snapshot_download
from safetensors.torch import load_file
dev = "cuda" if torch.cuda.is_available() else "cpu"
for mid in ["Qwen/Qwen2.5-0.5B-Instruct", "Qwen/Qwen2.5-1.5B-Instruct"]:
    path = snapshot_download(mid)                                   # downloads once, then cached
    files = glob.glob(os.path.join(path, "*.safetensors"))
    size = sum(os.path.getsize(f) for f in files)
    t = time.perf_counter()
    tensors = {}
    for f in files: tensors.update(load_file(f))                    # memory-mapped: lazy
    t_map = time.perf_counter() - t
    t = time.perf_counter()
    on_dev = {k: v.to(dev, copy=True) for k, v in tensors.items()}  # forces every byte to be read
    if dev == "cuda": torch.cuda.synchronize()
    t_read = time.perf_counter() - t
    print(f"{mid}: {size/1e9:.2f} GB  map {t_map:.2f} s  read+copy {t_read:.2f} s  "
          f"({size/t_read/1e9:.2f} GB/s)")
What we measured, and why
Qwen2.5-0.5B-Instruct: 0.99 GB  map 0.04 s  read+copy 0.47 s  (2.09 GB/s)
Qwen2.5-1.5B-Instruct: 3.09 GB  map 0.06 s  read+copy 2.20 s  (1.40 GB/s)

Mapping is instant for both: no bytes were read. The real cost appears when data is copied, and it scales with size (3.1 times the bytes took about 4.7 times as long here). The first run of snapshot_download (not timed) is the internet download, usually far slower than both. Extrapolate: at 1.4 GB/s, how long would a 141 GB model take, and what would you change?

9. In the real world

Packaging and start-up in production
  • Platforms keep weights in caches close to GPU nodes and stream them in parallel, because weight loading dominates cold starts for large models.
  • Teams ship compile caches with their images or volumes so new replicas skip torch.compile and engine builds.
  • Gateways (cloud API gateways, Envoy-based AI gateways, LiteLLM-style proxies) handle authentication, quotas and routing in front of engines.
  • Rollouts rely on readiness probes and graceful draining to deploy without dropping streams (chapter 6.5).

11. Summary

  • Containers freeze a fragile dependency chain; start from official engine images, pin everything, keep images lean, and keep weights separate.
  • Weight loading dominates cold starts for large models; use nearby caches, parallel streaming and quantized checkpoints.
  • Cold start = node + image + weights + engine start + warm-up; shorten each with its own fix, or avoid it with warm pools and sleep modes.
  • An OpenAI-compatible API behind a gateway handles authentication, quotas, validation, streaming, cancellation and async jobs.
  • Readiness after warm-up, tolerant liveness, and graceful draining make deploys and scale-downs invisible to users.
