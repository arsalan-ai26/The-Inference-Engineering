Compilation and CUDA graphs

Eager PyTorch runs one operation at a time, deciding and launching each kernel as Python reaches it. That is flexible and easy to debug, but it pays Python and launch overhead on every operation and cannot fuse across operations. Compilers capture the whole computation and generate fused kernels; CUDA graphs record a whole sequence of kernel launches and replay it with one call. Together they remove most of the overhead regime of chapter 5.1. This chapter explains how torch.compile works, what CUDA graphs are and their rules, and how vLLM combines both.

1. What eager execution costs

In eager mode, for every operation PyTorch's Python code runs, the dispatcher picks an implementation, memory is allocated for the output, and a kernel is launched. That costs microseconds of CPU time per operation (chapter 5.3), and each operation reads and writes its tensors through HBM (chapter 5.4). For a large batch the GPU work hides this. For decode at small batch, the CPU work becomes the bottleneck, and the many small memory-bound kernels waste bandwidth.

Two complementary fixes:

  • Compile: see a whole region of the program at once, fuse operations, and generate fewer, better kernels. This cuts memory traffic and the number of launches.
  • CUDA graphs: record the kernel launches of a whole step once, then replay them with a single launch. This removes per-kernel CPU cost entirely.

2. torch.compile, step by step

model = torch.compile(model) changes nothing until the first call. Then:

  1. Capture (TorchDynamo). Dynamo watches the Python bytecode run and records the tensor operations into a graph (an FX graph). Code it cannot trace (data-dependent Python control flow, unsupported calls) causes a graph break: it compiles what it has, runs the unsupported part in eager mode, and starts a new graph after it.
  2. Guards. Dynamo records assumptions the graph depends on: tensor shapes, dtypes, devices, some Python values. On later calls it checks these guards; if one fails (for example a new batch size), it recompiles or switches to a version with dynamic (symbolic) shapes.
  3. Lowering and code generation (TorchInductor). The graph is lowered to a loop-level representation, operations are fused (element-wise chains, reductions with element-wise work, epilogues around matmuls), and code is generated: Triton kernels on GPUs, C++ with OpenMP on CPUs. Large matmuls usually still call cuBLAS or a template kernel.
  4. Run. Later calls that pass the guards run the compiled code directly.

Watch out

Compilation happens on the first call with each new set of guards. In a server, that first call is a user request. Warm up with every shape you will see before taking traffic, limit the shapes (pad batches to a few sizes), and use a compile cache so restarts do not recompile.

3. CUDA graphs

A CUDA graph is a recorded sequence of GPU operations (kernels, copies) with their arguments. You capture it once by running the code in capture mode; afterwards one replay call launches the entire sequence, and the driver submits it to the GPU with much less CPU work than launching each kernel.

g = torch.cuda.CUDAGraph()
static_in = torch.zeros(batch, hidden, device="cuda", dtype=torch.float16)   # fixed buffer
s = torch.cuda.Stream(); s.wait_stream(torch.cuda.current_stream())
with torch.cuda.stream(s):                       # warm up on a side stream before capture
    for _ in range(3): step(static_in)
torch.cuda.current_stream().wait_stream(s)
with torch.cuda.graph(g):                        # capture: kernels are recorded, not just run
    static_out = step(static_in)

static_in.copy_(new_input)                       # put new data at the captured address
g.replay()                                       # one launch for the whole step
result = static_out                              # results appear at the captured output address

The rules a graph imposes

  • Fixed shapes. Each graph is for one set of shapes. Engines capture one graph per batch size in a list (for example 1, 2, 4, 8, 16, ... up to the maximum) and pad each real batch up to the nearest captured size (chapter 3.4).
  • Fixed memory addresses. Inputs and outputs live in static buffers; data is copied in before replay.
  • No CPU work inside. No Python decisions, no synchronizations, no allocation that changes between replays. Anything data-dependent must be expressed on the GPU.
  • Memory. Each captured graph reserves memory for its intermediates (shared pools reduce this). More capture sizes means more memory taken from the KV cache and longer startup.
Interactive: what CUDA graphs save in a decode step
A decode step with a fixed number of kernels per layer. Without graphs, each kernel costs a CPU launch; if the launch is slower than the kernel, the GPU waits. With a graph, the whole step costs one launch. Estimate for a model you choose.

With 24 layers × 14 kernels = 336 launches at 8 µs each, the CPU needs 2.7 ms per step; if the GPU work is 1.5 ms, eager decode runs at the CPU's pace. A graph brings the step to about the GPU time. This is why small models gain the most, and why the gain fades as batch size (and so GPU time per step) grows.

4. How vLLM uses both

vLLM enables torch.compile by default and combines it with CUDA graphs:

  • Compile before serving. All compilation and graph capture happen at startup; no request triggers a compile. Compiled artifacts are cached on disk (in ~/.cache/vllm/torch_compile_cache), keyed by model, configuration and code, so restarts and identical deployments can reuse them, which shortens cold starts (chapter 6.2).
  • Piecewise graphs. The model's graph is split at attention operations. The pieces between attention calls (projections, norms, activations, residuals) are compiled and captured as CUDA graphs; attention runs outside them, because its metadata (sequence lengths, block tables) varies per step. vLLM can also capture full graphs including attention for uniform decode batches when the attention backend supports it.
  • Capture sizes. Graphs are captured for a list of batch sizes, configurable through --compilation-config (newer versions separate token sizes for batches with prefill from request sizes for uniform decode batches). Larger caps capture more graphs and take more memory and startup time.
  • Escape hatch. --enforce-eager disables graphs (and compilation) for debugging; do not leave it on in production.
vllm serve Qwen/Qwen2.5-1.5B-Instruct \
  --compilation-config '{"cudagraph_capture_sizes": [1, 2, 4, 8, 16, 32, 64]}'

Option names change between vLLM versions; check vllm serve --help and the torch.compile design document for your version.

SGLang captures CUDA graphs for decode batch sizes up to a configurable maximum (--cuda-graph-max-bs) and can use torch.compile for small models. TensorRT-LLM builds an optimized engine per model and GPU, with its own graph capture.

5. Ahead-of-time compilation

JIT compilation (on first call) and AOT compilation (before deployment) trade flexibility against startup cost:

  • JIT (torch.compile): works on any PyTorch model, adapts to shapes at run time, but pays compile time at startup or first use.
  • AOT (TensorRT and TensorRT-LLM engines, torch.export with AOTInductor): compile once per model, GPU and shape range, ship the result. Fast startup and stable performance; changing the GPU type or shape range means recompiling.
  • Caches blur the line: vLLM's compile cache and Triton's kernel cache let a JIT system behave like AOT after the first run.

6. Expert layer

Custom compiler passes

vLLM adds its own passes on top of Inductor: fusing RMSNorm with quantization to FP8, fusing activation with quantization, fusing all-reduce with the following RMSNorm (with tensor parallelism), and others. Each is a pattern match on the captured graph that replaces several operations with one custom kernel, the "fusion the compiler cannot find on its own" of chapter 5.4, automated.

Dynamic shapes

Compilers can treat a dimension (such as the number of tokens) as symbolic, so one compiled graph serves many sizes. PyTorch distinguishes "backed" symbols, which may still pick up guards and specializations (for example for sizes 0 and 1), from "unbacked" ones, which never guard but can miss optimizations. vLLM exposes this choice because a stray guard can trigger an unexpected recompile; most users keep the default.

CUDA graphs and speculative decoding

Speculative decoding verifies several tokens per sequence per step (chapter 4.3), which changes decode shapes. Engines capture graphs keyed on the number of tokens per request, or by total tokens for mixed batches; adaptive draft lengths make capture more complex. This is one reason new speculative methods often launch with graphs disabled and gain them later.

7. Common mistakes

  • Benchmarking the first call of a compiled model and concluding compilation is slow.
  • Letting compilation or graph capture happen on user requests.
  • Leaving --enforce-eager on after debugging.
  • Capturing graphs for dozens of batch sizes and wondering why the KV cache shrank.
  • Putting .item(), Python branches on GPU values, or new allocations inside code meant for graph capture.
  • Changing the GPU type or engine version without expecting caches to be invalidated.

Part A: torch.compile on a transformer block tail (CPU, then T4)

import torch, time
dev = "cuda" if torch.cuda.is_available() else "cpu"
def sync():
    if dev == "cuda": torch.cuda.synchronize()
def bench(f, *a, reps=50):
    for _ in range(3): f(*a)
    sync(); t = time.perf_counter()
    for _ in range(reps): f(*a)
    sync(); return (time.perf_counter() - t) / reps * 1e6

def block_tail(x, res, w, gate, up):        # residual add, RMSNorm, SiLU(gate) * up
    h = x + res
    h = h * torch.rsqrt(h.pow(2).mean(-1, keepdim=True) + 1e-6) * w
    return h, torch.nn.functional.silu(gate) * up

D, F = 4096, 14336
x, res = torch.randn(8, D, device=dev), torch.randn(8, D, device=dev)
w = torch.ones(D, device=dev)
gate, up = torch.randn(8, F, device=dev), torch.randn(8, F, device=dev)
eager_us = bench(block_tail, x, res, w, gate, up)
t0 = time.perf_counter(); compiled = torch.compile(block_tail); compiled(x, res, w, gate, up); sync()
print(f"first compiled call: {time.perf_counter() - t0:.1f} s")
comp_us = bench(compiled, x, res, w, gate, up)
print(f"eager {eager_us:.0f} us, compiled {comp_us:.0f} us")
x2, res2 = torch.randn(13, D, device=dev), torch.randn(13, D, device=dev)
g2, u2 = torch.randn(13, F, device=dev), torch.randn(13, F, device=dev)
t0 = time.perf_counter(); compiled(x2, res2, w, g2, u2); sync()
print(f"first call with batch 13: {time.perf_counter() - t0:.2f} s")
What we measured on CPU, and what to look for on a T4

On a 2-core CPU: first compiled call 24.6 s (compilation), then eager 159 µs vs compiled 69 µs (2.3 times faster), identical results, and 1.14 s for the first call with a new batch size. On a T4, also set TORCH_LOGS="output_code" before running to print the generated Triton kernels; count them, and find the fused kernel that computes the add, the norm and the multiply in one pass. Then try torch.compile(block_tail, mode="reduce-overhead") and compare.

Part B: a CUDA graph for a small decode step (T4)

import torch, time
torch.manual_seed(0)
L, D = 24, 1024
layers = [torch.nn.Linear(D, D, bias=False).cuda().half() for _ in range(2 * L)]
norm_w = torch.ones(D, device="cuda", dtype=torch.float16)
def step(x):                                   # a toy decode step: 24 x (norm, linear, silu, linear, add)
    for i in range(L):
        h = x * torch.rsqrt(x.float().pow(2).mean(-1, keepdim=True) + 1e-6).half() * norm_w
        x = x + layers[2*i+1](torch.nn.functional.silu(layers[2*i](h)))
    return x

static_in = torch.randn(1, D, device="cuda", dtype=torch.float16)
def timeit(f, reps=200):
    for _ in range(10): f()
    torch.cuda.synchronize(); t = time.perf_counter()
    for _ in range(reps): f()
    torch.cuda.synchronize(); return (time.perf_counter() - t) / reps * 1e6

print(f"eager: {timeit(lambda: step(static_in)):.0f} us per step")

#       (warm up on a side stream, then torch.cuda.graph(g)), then time g.replay()
Solution 
g = torch.cuda.CUDAGraph()
s = torch.cuda.Stream(); s.wait_stream(torch.cuda.current_stream())
with torch.cuda.stream(s):
    for _ in range(3): step(static_in)
torch.cuda.current_stream().wait_stream(s)
with torch.cuda.graph(g):
    static_out = step(static_in)
print(f"graph: {timeit(g.replay):.0f} us per step")
static_in.copy_(torch.randn_like(static_in)); g.replay()
print("matches eager:", torch.allclose(static_out, step(static_in), atol=1e-2))

What to expect: the eager step launches roughly 24 × 9 ≈ 200 kernels and is limited by launch and Python overhead; the replay removes most of it, typically several times faster for this tiny step. Increase the batch from 1 to 256 and repeat: the GPU time grows, the CPU launch time does not, and the graph's advantage shrinks. Check your result against the widget in section 3.

9. In the real world

Compilation and graphs in production
  • All major engines replay CUDA graphs for decode; it is one of the largest single wins for small and medium models.
  • vLLM compiles by default, splits graphs at attention, and caches compiled artifacts; teams ship the cache with their images to cut cold starts.
  • TensorRT-LLM users build engines ahead of time per GPU type and shape range as part of their release pipeline.
  • Engine contributors add fusion passes as new model architectures and quantization formats appear.

11. Summary

  • Eager execution pays Python, dispatch and launch costs per operation and cannot fuse.
  • torch.compile captures graphs with guards, fuses operations and generates Triton or C++; graph breaks and failed guards cost performance and recompiles.
  • CUDA graphs replay a recorded step with one launch; they require fixed shapes, fixed addresses and no CPU work inside, and they use memory.
  • vLLM compiles before serving, captures piecewise graphs around attention for a list of batch sizes, and caches artifacts.
  • Warm up every shape before traffic, limit shapes, and keep caches to protect startup and tail latency.
