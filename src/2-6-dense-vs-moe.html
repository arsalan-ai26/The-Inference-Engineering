Dense vs mixture-of-experts models

Most of the largest open models today are mixture-of-experts (MoE) models. They hold hundreds of billions of parameters but use only a small share of them for each token. That split, total parameters for memory and active parameters for compute, changes every estimate from chapter 2.5. This chapter shows how MoE layers work and what they cost to serve.

  2. Why does an MoE model read almost all of its weights each decode step on a busy server, even though each token uses only a few experts?
  3. Does MoE make the KV cache smaller?
Answers
  1. About 671 GB of weights (1 byte each) and about 2 × 37 × 10⁹ = 74 GFLOPs per token.
  2. Different tokens in the batch pick different experts. With enough tokens, nearly every expert is picked by at least one token, so every expert's weights must be read.
  3. No. Experts replace the MLP. The KV cache depends only on attention: layers, KV heads, head size and type.

1. The problem: more knowledge costs more compute

Bigger models know more and reason better. But in a dense model (every model so far in this book), every parameter takes part in every token, so FLOPs per token = 2 × parameters (chapter 1.1). Doubling the parameters doubles the cost of every token.

The MLP blocks hold most of the parameters (about two thirds in Llama 3.1 8B). They work on each token separately (chapter 2.2). So here is the idea: replace one big MLP with many smaller MLPs, called experts, and send each token to only a few of them. The model keeps the knowledge of all experts, but each token pays for only the ones it uses.

2. How an MoE layer works

An MoE layer replaces the MLP inside a transformer block. Attention is unchanged.

  1. Route. A small linear layer, the router (or gate), maps each token's vector (size D) to one score per expert (E scores).
  2. Select. Keep the top k scores. Common values: E = 8 to 256 experts, k = 1 to 8.
  3. Weight. Turn the selected scores into weights with a softmax (or a similar normalization).
  4. Compute. Run the token through only its k chosen experts. Each expert is a normal gated MLP, usually much narrower than a dense model's MLP.
  5. Combine. The layer output is the weighted sum of the k expert outputs.
MoE(x) = Σ over chosen experts i of w_i(x) × Expert_i(x)

Many recent designs add one or more shared experts that every token always uses, plus the routed ones. Some keep the first few layers dense. DeepSeek-V3, for example, has 1 shared and 256 routed experts per MoE layer, picks 8 routed experts per token, and keeps its first 3 layers dense.

3. Total parameters and active parameters

Definitions

Total parameters: every weight in the model, including all experts. Sets memory.

Active parameters: the weights one token actually uses: attention, embeddings and output head, shared experts, and k routed experts per layer. Sets FLOPs per token.

Model names often show both: Qwen3-30B-A3B has about 30.5 B total and 3.3 B active. You can recompute both from the config:

Worked example: Qwen3-30B-A3B

Config: 48 layers, hidden size 2,048, 128 experts per layer, 8 active, expert MLP size 768, 32 query heads and 4 KV heads of size 128, vocabulary 151,936, untied embeddings.

  • One expert (gate, up and down): 3 × 2,048 × 768 = 4.72 M. All experts: 128 × 4.72 M × 48 layers = 29.0 B.
  • Attention per layer: Q 2,048 × 4,096 + K and V 2 × 2,048 × 512 + O 4,096 × 2,048 = 18.9 M. × 48 = 0.91 B.
  • Embeddings and output head: 2 × 151,936 × 2,048 = 0.62 B. Routers: about 0.01 B.
  • Total ≈ 29.0 + 0.91 + 0.62 + 0.01 ≈ 30.5 B.
  • Active ≈ 8 experts × 4.72 M × 48 (1.81 B) + attention (0.91 B) + embeddings and head (0.62 B) ≈ 3.3 B.

So the weights need about 61 GB in BF16, like a dense 30B model, but each token costs about 6.7 GFLOPs, like a dense 3B model.

4. Memory follows total parameters

Every expert must be in GPU memory (or reachable quickly), because any token may pick any expert. So the memory estimate of chapter 1.3 uses total parameters. A 235B MoE needs as much memory for weights as a 235B dense model.

The KV cache is unchanged by experts: it depends on attention only (chapter 2.4). MoE models often have small attention blocks for their size, so their cache per token can be modest. Qwen3-30B-A3B stores 98,304 bytes per token in BF16, less than Llama 3.1 8B's 131,072.

5. Compute follows active parameters

FLOPs per token = 2 × active parameters. In prefill, which is compute-bound (chapter 2.5), an MoE runs at roughly the speed of a dense model of its active size, if the experts are evenly loaded and the kernels are efficient. Qwen3-30B-A3B prefill needs about 2 × 3.3 B × T FLOPs: about 9 times fewer than a dense 30B.

6. Decode: the subtle part

Decode is memory-bound, so its time follows bytes read, not FLOPs. Which expert weights must be read in one step depends on the batch:

  • Batch 1: one token picks k experts per layer. Only those are read, plus attention and the head. Bytes ≈ active parameters × b. Fast, like a dense model of the active size.
  • Large batch: each token picks its own k experts. The union quickly covers almost every expert. Bytes ≈ total parameters × b. Each step now reads as much as a dense model of the total size, but does far fewer FLOPs.

If each of B tokens picks k of E experts at random, the expected number of distinct experts read per layer is:

experts read ≈ E × ( 1 − (1 − k/E)^B )

For Qwen3-30B-A3B (E = 128, k = 8): about 8 at batch 1, 82 at batch 16, and 126 (almost all) at batch 64. Real routers are not uniform, which changes the curve somewhat, but the shape holds.

There is a second effect. Each expert sees only about B × k / E of the batch's tokens. Its matmul therefore has a small "batch", so its arithmetic intensity is low. To make expert matmuls compute-bound, the whole batch must be about E / k times larger than for a dense model: 16 times for Qwen3-30B-A3B. MoE models need large batches to use a GPU efficiently.

7. A rule of thumb

Putting it together:

  • An MoE is cheaper to serve than a dense model with the same total parameters: far fewer FLOPs, often a smaller attention block, and fewer layers for its size.
  • An MoE is more expensive to serve than a dense model with the same active parameters: much more memory, and at real batch sizes much more weight traffic.

One published analysis puts it this way: for short-context decoding, an 8-way sparse model (8 times more total than active parameters) has roughly the economics of a dense model of about half its total size. Treat this as an order-of-magnitude guide, not a law.

Where MoE shines:

  • Prefill-heavy and high-throughput work at large batch, where compute matters and the GPUs are kept full.
  • Single-user local inference with enough memory: batch 1 reads only the active weights, so a 30B-A3B model can generate quickly on a laptop with enough RAM.
  • Large multi-GPU deployments with expert parallelism (next section).

8. Serving MoE models

  • Fused MoE kernels. Engines group tokens by expert and run all experts in one "grouped GEMM" kernel instead of a loop over experts.
  • Expert parallelism (EP). Instead of splitting every expert across GPUs, place whole experts on different GPUs. Each token's vector is sent to the GPUs holding its chosen experts and back again: an all-to-all exchange in every MoE layer. Chapter 4.5 covers this.
  • Load imbalance. If many tokens pick the same expert, that GPU becomes the bottleneck. Training adds balancing losses; serving systems can replicate popular experts on extra GPUs.
  • Memory first. Choose the deployment by total memory: 8 × 80 GB for many 200B to 700B models, or fewer GPUs with FP8 or 4-bit weights.

9. Expert layer

Fine-grained and shared experts

Early MoEs used a few large experts (Mixtral: 8 experts, 2 active). Newer ones use many small experts (128 to 256, 8 active) plus shared experts. Many small experts give the router more combinations to choose from, and the shared expert captures knowledge every token needs, so routed experts can specialize.

Load balancing without an auxiliary loss

DeepSeek-V3 balances expert load by adding a per-expert bias to the routing scores, adjusted during training, instead of the usual extra balancing loss. At serving time, DeepSeek also published an expert-parallel load balancer (EPLB) that replicates heavily used experts and places them across GPUs.

Expert offloading for local inference

Because a single user touches only k experts per layer per token, local runtimes can keep attention and shared weights on a small GPU and stream or compute expert weights from CPU memory. This makes large MoEs usable on consumer hardware at modest speed, and is a common use of llama.cpp (chapter 3.6).

Routing and determinism

Routing is a discrete choice. Tiny numeric differences (chapter 1.2, determinism) can flip which expert a token goes to, which changes later tokens more than a small numeric error in a dense layer would. Reinforcement-learning pipelines that need the training and serving engines to agree sometimes record the routing decisions made during generation and replay them.

10. Common mistakes

  • Sizing GPU memory from active parameters. Memory follows total parameters.
  • Expecting batch-1 decode speed at large batch. The union of experts grows with batch.
  • Saying "22B parameters are active per request". They are active per token; a single request touches many different experts across its tokens.
  • Assuming MoE shrinks the KV cache. Experts live in the MLP; the cache depends on attention.
  • Comparing an MoE with a dense model by active parameters alone when judging serving cost.

from transformers import AutoConfig
def moe_counts(name):
    c = AutoConfig.from_pretrained(name)
    D, L, V = c.hidden_size, c.num_hidden_layers, c.vocab_size
    hd = getattr(c, "head_dim", None) or D // c.num_attention_heads
    attn = D * c.num_attention_heads * hd * 2 + 2 * D * c.num_key_value_heads * hd       # q, o, k, v
    E = getattr(c, "num_experts", None) or getattr(c, "num_local_experts", None)
    k, F = c.num_experts_per_tok, getattr(c, "moe_intermediate_size", None) or c.intermediate_size
    expert = 3 * D * F
    emb = V * D * (1 if c.tie_word_embeddings else 2)
    total = L * (attn + E * expert + D * E) + emb
    active = L * (attn + k * expert) + emb
    print(f"{name}: E={E} k={k}  total={total/1e9:.2f} B  active={active/1e9:.2f} B  ratio={total/active:.1f}x")

import torch, torch.nn as nn, torch.nn.functional as F
torch.manual_seed(0)
class Expert(nn.Module):
    def __init__(s, D, Fd):
        super().__init__(); s.g, s.u, s.d = nn.Linear(D, Fd, bias=False), nn.Linear(D, Fd, bias=False), nn.Linear(Fd, D, bias=False)
    def forward(s, x): return s.d(F.silu(s.g(x)) * s.u(x))

class MoE(nn.Module):
    def __init__(s, D=64, Fd=128, E=8, k=2):

Part C: watch a real router

from transformers import AutoModelForCausalLM, AutoTokenizer
name = "ibm-granite/granite-3.0-1b-a400m-instruct"      # 1.3 B total: runs on a CPU
tok = AutoTokenizer.from_pretrained(name)
m = AutoModelForCausalLM.from_pretrained(name).eval()
texts = {"english": "The history of the Roman Empire spans many centuries.",
         "code": "def fibonacci(n):\n    return n if n < 2 else fibonacci(n-1) + fibonacci(n-2)",
         "math": "Solve 3x + 7 = 22 for x. Subtract 7, then divide by 3."}
k = m.config.num_experts_per_tok
for label, t in texts.items():
    ids = tok(t, return_tensors="pt")
    with torch.inference_mode():
        rl = m(**ids, output_router_logits=True).router_logits    # one [tokens, experts] per layer
    layer = 12
    chosen = rl[layer].topk(k, dim=-1).indices.flatten()
    counts = torch.bincount(chosen, minlength=m.config.num_local_experts)
    print(f"{label:8s} layer {layer}: experts used {int((counts > 0).sum())}/{len(counts)}  busiest {counts.topk(3).indices.tolist()}")

12. In the real world

MoE in production
  • Frontier open models released in 2025 and 2026 are mostly MoE (DeepSeek, Qwen3 MoE, gpt-oss, Kimi, GLM and others).
  • Serving engines (vLLM, SGLang, TensorRT-LLM) ship fused MoE kernels and expert-parallel modes. Large deployments combine expert parallelism with data parallelism for attention.
  • Pricing: API prices for MoE models usually track active parameters for compute and total parameters for the hardware footprint, so large sparse models can be priced close to much smaller dense ones.
  • Local use: small-active MoEs are popular on laptops and workstations, because batch-1 decode reads only active weights.

14. Summary

  • An MoE layer replaces the MLP with E experts; a router sends each token to its top k, and their outputs are combined by weight.
  • Total parameters set memory; active parameters set FLOPs per token.
  • Decode at batch 1 reads only active weights; at real batch sizes nearly all experts are read: distinct experts ≈ E(1 − (1 − k/E)^B).
  • Expert matmuls need about E/k times larger batches to become compute-bound.
  • The KV cache is unaffected by experts.
  • MoE is cheaper than dense of the same total size, and dearer than dense of the same active size.
