PagedAttention and KV memory management

The KV cache is the largest and most changeable thing in GPU memory during serving. Chapter 2.4 showed that storing it in one contiguous block per request wastes most of the memory. PagedAttention borrows the operating system's answer to the same problem, virtual memory: cut the cache into small fixed-size blocks, hand them out on demand, and keep a table per request. This chapter builds that allocator step by step, with sharing, copy-on-write, preemption, and the newer caches for hybrid models.

1. The problem: contiguous caches fragment

A request's KV cache grows by one token per decode step, and the engine does not know in advance how long the output will be. The simple design gives each request one contiguous region sized for the maximum length. Three kinds of waste follow:

  • Reservation waste. Space reserved for tokens that are not generated yet, and may never be. A request that ends after 200 tokens of an 8,192-token reservation wastes 97.6% of it (chapter 2.4).
  • Internal fragmentation. Space inside a reservation that is never used, because the request ends early.
  • External fragmentation. Free gaps between reservations that are too small for a new request, even though their total is large.

The vLLM paper measured earlier serving systems and found that only 20.4% to 38.2% of their KV cache memory held real token states. The rest was waste. Since the KV cache decides how many requests fit at once (chapter 2.4), waste directly limits batch size and so throughput (chapter 3.2).

2. The idea: virtual memory for the KV cache

Operating systems solved this problem decades ago. A program sees a continuous range of virtual addresses. Physical memory is cut into small fixed-size pages. A page table maps each virtual page to any free physical page. Pages are given out only when touched, and any free page can serve any program.

3. Blocks and block tables

Definitions

Block: storage for the keys and values of B consecutive tokens (B is the block size, commonly 16 in vLLM), for the layers that share a block layout.

Block table: one list per request. Entry i is the physical block that holds the request's tokens i × B to (i + 1) × B − 1.

Free pool: the list of physical blocks not used by any request.

The life of a request in a paged allocator:

  1. Admit. The prompt has P tokens, so it needs ⌈P ÷ B⌉ blocks. Take them from the free pool and write their IDs into the request's block table.
  2. Grow. Each decode step adds one token. If the last block still has room, write into it. If it is full, take one more block from the pool.
  3. Finish or abort. Return every block in the table to the free pool.

The blocks of one request can be anywhere in memory. Waste is at most B − 1 token slots per request, in its last block. Any free block can serve any request, so external fragmentation disappears.

4. PagedAttention: attention through a block table

Standard attention kernels expect each sequence's keys and values in one contiguous array. With paging, they are scattered. PagedAttention is an attention kernel that takes the block table as an extra input. For each query, it walks the sequence's blocks in order, loads each block's keys and values from wherever it lives, and computes exactly the same result as ordinary attention.

The extra cost is small: one table lookup per block and slightly less regular memory access. Blocks of 16 tokens are large enough that each load is efficient. All major engines and attention libraries (FlashAttention, FlashInfer, TensorRT-LLM kernels) now support paged KV layouts.

5. Sizing the block pool

At startup an engine computes how many blocks fit (chapter 2.4 for the memory pool):

bytes per block = block size × KV bytes per token (all layers) blocks = KV pool bytes ÷ bytes per block
Worked example: Llama 3.1 8B on one H100

KV bytes per token: 131,072. Block size 16, so each block holds 2 MiB (2,097,152 bytes) across all 32 layers.

KV pool at 0.92 memory fraction with a 2 GB runtime reserve: about 55.5 GB. Blocks ≈ 55.5 × 10⁹ ÷ 2,097,152 ≈ 26,500. Tokens ≈ 26,500 × 16 ≈ 424,000.

vLLM prints both numbers when it starts: the KV cache size in tokens, and the maximum concurrency for requests of max-model-len tokens. Those log lines are this calculation for your exact setup.

6. Sharing blocks: reference counts and copy-on-write

Because a block table is only a list of IDs, two requests can point at the same physical block. Each block keeps a reference count: how many block tables include it. A block returns to the free pool only when its count reaches 0.

Sharing appears in three places:

  • Parallel sampling (n > 1): several completions of one prompt share all the prompt's blocks.
  • Beam search: beams share the blocks of their common history and split when they diverge.
  • Prefix caching: different requests with the same beginning (a system prompt, a document) reuse blocks that are already computed. Engines find them by hashing each full block's tokens together with everything before it. Chapter 3.5 covers this in depth.

When a sequence must write into a block whose count is above 1, the allocator gives it a fresh block, copies the shared contents into it, and decrements the old block's count. This is copy-on-write. With paging it only ever copies one block, never a whole cache. In practice it is needed only when the shared block is the partly filled last block: full blocks never change again.

7. When the pool runs out

Requests grow, so a batch that fits now may not fit in 100 steps. When a running request needs a new block and the pool is empty, the scheduler must act:

  1. Stop admitting new requests until blocks free up. Some engines keep a small watermark of free blocks in reserve, so that running requests can keep growing.
  2. Preempt one or more running requests, usually the lowest priority or the most recently arrived, and free their blocks. Two ways to bring them back:
    • Recompute: drop the blocks. When the request resumes, prefill its prompt plus the tokens generated so far again. Costs compute, needs no extra memory.
    • Swap: copy the blocks to CPU memory and back later. Costs PCIe bandwidth and CPU memory.

Current vLLM uses recompute by default; prefill is fast on modern GPUs, and prefix caching often brings back much of the prompt for free. Frequent preemption (watch vllm:num_preemptions, chapter 3.1) wastes compute and means the batch limits are set higher than memory can support.

Cancellation is the same path in reverse: when a client disconnects, the engine releases the request's blocks, their reference counts fall, and unshared blocks return to the pool at once (chapter 3.2).

8. KV caches for sliding windows, hybrids and state-space layers

Not every layer keeps a cache that grows forever (chapters 2.4 and 2.7):

  • Sliding-window layers need only the last W tokens. Blocks that fall wholly outside the window can be freed while the request continues.
  • Hybrid models mix full-attention layers with window layers (for example Gemma 3 has 52 sliding-window layers and 10 full layers in its 27B model) or with linear-attention and Mamba layers.
  • State-space and linear layers keep one fixed-size state per request instead of a per-token cache.

vLLM handles all of these with a hybrid KV cache manager. It keeps one memory pool with a single page size, groups layers of the same type so that each group needs the same number of blocks per request, and gives each group its own block table. Mamba-style states, which are much larger per request than one token's KV, are fitted into the same page size. The design has some padding overhead for awkward layer ratios, which its documentation discusses openly.

9. Expert layer

Choosing the block size

Smaller blocks waste less (at most B − 1 slots per request) and share prefixes more finely. Larger blocks mean fewer table entries, fewer lookups and more efficient memory loads in the attention kernel. Some kernels and hardware prefer larger blocks (for example 64 or 128), and prefix caching can only share whole blocks. Engines pick a default per backend; changing it is rarely the first thing to tune.

Virtual memory without a block table

An alternative keeps the attention kernel unchanged: reserve a large contiguous virtual address range per request and let the GPU driver's virtual memory API map physical pages into it on demand (the vAttention approach). The kernel sees contiguous memory; the driver does the paging. It trades kernel simplicity for driver-level page management.

KV beyond one GPU

Once the cache is cut into blocks, blocks can live in other tiers: CPU memory, local SSD or a remote store, and be moved back on demand. Block-level hashing makes those moves address the same "content" everywhere. Chapter 4.7 builds on this for very long contexts, and chapter 4.6 moves blocks between prefill and decode GPUs.

Correctness traps

A paged allocator must never hand one block to two writers, never free a block that is still referenced, and never leave a request pointing at a freed block. These bugs do not crash; they silently corrupt another request's output. Engine teams test allocators with randomized property tests, which is exactly Part C of the lab.

10. Common mistakes

  • Estimating concurrency with the maximum length instead of the real average length on a paged engine.
  • Forgetting that sharing only works on whole blocks: a 1,000-token shared prefix with 16-token blocks shares 62 blocks, and the last 8 tokens are recomputed.
  • Tuning max-num-seqs up until preemptions appear, and reading the higher batch as a win.
  • Assuming every layer of a hybrid model uses the same cache layout.
  • Freeing blocks on finish but not on client abort.

Part C: a paged allocator and its property tests

The AI may write the allocator. Here is a complete one. The data lists stand in for the real K and V values, so tests can check what each sequence would read. Read it until you can explain every line.

from collections import deque

class OutOfBlocks(Exception):
    pass

class BlockAllocator:
    """A tiny paged KV allocator: fixed-size blocks, a free list, reference counts and copy-on-write."""
    def __init__(self, num_blocks, block_size):
        self.block_size = block_size
        self.free = deque(range(num_blocks))           # free list of physical block ids
        self.ref = [0] * num_blocks                    # how many block tables point at each block
        self.tables = {}                               # seq_id -> list of physical block ids
        self.ntok = {}                                 # seq_id -> tokens stored
        self.data = [[None] * block_size for _ in range(num_blocks)]   # stands in for the K/V values
        self.copies = 0                                # copy-on-write events

    def _take(self):
        if not self.free:
            raise OutOfBlocks
        b = self.free.popleft(); self.ref[b] = 1
        return b

    def _drop(self, b):
        self.ref[b] -= 1
        if self.ref[b] == 0:
            self.free.append(b)

    def add(self, seq, tokens):                        # new sequence: allocate blocks and write its prompt
        need = -(-len(tokens) // self.block_size)
        if need > len(self.free):
            raise OutOfBlocks
        self.tables[seq] = [self._take() for _ in range(need)]
        for i, tok in enumerate(tokens):
            self.data[self.tables[seq][i // self.block_size]][i % self.block_size] = tok
        self.ntok[seq] = len(tokens)

    def append(self, seq, tok):                        # write one new token for a running sequence
        t, n = self.tables[seq], self.ntok[seq]
        if n % self.block_size == 0:                   # last block is full: take a new block
            t.append(self._take())
        elif self.ref[t[-1]] > 1:                      # last block is shared: copy on write
            new = self._take(); self.copies += 1
            self.data[new] = list(self.data[t[-1]])    # on a GPU: copy one block of K/V
            self._drop(t[-1]); t[-1] = new
        self.data[t[-1]][n % self.block_size] = tok
        self.ntok[seq] = n + 1

    def read(self, seq):                               # what attention would see for this sequence
        bs = self.block_size
        return [self.data[self.tables[seq][i // bs]][i % bs] for i in range(self.ntok[seq])]

    def fork(self, parent, child):                     # parallel sampling or beam search: share all blocks
        self.tables[child] = list(self.tables[parent])
        self.ntok[child] = self.ntok[parent]
        for b in self.tables[child]:
            self.ref[b] += 1

    def release(self, seq):                            # finished, aborted or preempted
        for b in self.tables.pop(seq):
            self._drop(b)
        del self.ntok[seq]

Now write the tests yourself. A property test runs thousands of random operations and checks rules that must always hold. Write a check(a, num_blocks, expected) function that asserts these invariants after every operation:

  1. Every sequence reads back exactly the tokens it wrote, and no others (no shared block was overwritten).
  2. No block appears twice in the free list (no double free).
  3. No block in the free list has a reference count above 0 (no double allocation).
  4. Each block's reference count equals the number of block tables that contain it (no stale references).
  5. Free blocks plus referenced blocks equal all blocks (no leaks), and every sequence has exactly enough blocks for its tokens.
import random
def run(seed, steps=3000, num_blocks=64, bs=4):
    rnd = random.Random(seed); a = BlockAllocator(num_blocks, bs); next_id = 0; expected = {}
    for _ in range(steps):
        op = rnd.random(); live = list(a.tables)
        try:
            if op < 0.25 or not live:
                toks = [rnd.randint(0, 999) for _ in range(rnd.randint(1, 20))]
                a.add(next_id, toks); expected[next_id] = toks; next_id += 1
            elif op < 0.75:
                s = rnd.choice(live); tok = rnd.randint(0, 999)
                a.append(s, tok); expected[s] = expected[s] + [tok]
            elif op < 0.85:
                p = rnd.choice(live); a.fork(p, next_id); expected[next_id] = list(expected[p]); next_id += 1
            else:
                a.release(rnd.choice(live))
        except OutOfBlocks:
            if live: a.release(rnd.choice(live))       # preempt someone, like a scheduler would
        check(a, num_blocks, expected)              # TODO: write check()
    for s in list(a.tables): a.release(s)
    check(a, num_blocks, expected); assert len(a.free) == num_blocks
    return a.copies

print([run(s) for s in range(20)])
Solution: check() 
def check(a, num_blocks, expected):
    for seq in a.tables:
        assert a.read(seq) == expected[seq], "a sequence reads tokens it never wrote (shared block overwritten)"
    counted = [0] * num_blocks
    for seq, t in a.tables.items():
        for b in t: counted[b] += 1
        assert len(t) * a.block_size >= a.ntok[seq], "sequence has fewer slots than tokens"
        assert len(t) == -(-a.ntok[seq] // a.block_size), "sequence holds extra blocks"
    assert counted == a.ref, "reference counts disagree with block tables (stale reference)"
    assert len(set(a.free)) == len(a.free), "a block is in the free list twice (double free)"
    for b in a.free: assert a.ref[b] == 0, "a free block is still referenced (double allocation risk)"
    assert len(a.free) + sum(1 for r in a.ref if r > 0) == num_blocks, "a block was lost (leak)"

All 20 seeds should pass, and each run should report about 115 to 155 copy-on-write events.

Then prove the tests work: break the allocator on purpose and make sure a test fails. Try each bug, one at a time:

  • In append, disable the copy-on-write branch (change it to elif False:). Invariant 1 catches it: two sequences now write into one shared block.
  • In fork, forget to increase the reference counts. Invariant 4 catches it.
  • In _drop, append to the free list without checking the count. Invariant 3 catches it.

Notice that the structural invariants alone (2 to 5) do not catch the missing copy-on-write. Only the data check does. Real engine bugs of this kind show up as one user's output containing another user's text.

12. In the real world

Paging in production
  • Every major engine uses a paged KV cache: vLLM (where PagedAttention was introduced), SGLang (with its radix-tree cache on top, chapter 3.5) and TensorRT-LLM (paged KV cache with block reuse).
  • Capacity planning uses average real lengths and the engine's reported KV capacity, then leaves headroom so preemption stays rare.
  • Parallel sampling and agents benefit most from sharing: many branches over one long context cost little extra memory.
  • New architectures (sliding windows, hybrids, MLA) each needed allocator work in engines before they could be served efficiently.

14. Summary

  • Contiguous KV allocation wastes memory through reservations and fragmentation; earlier systems used only 20% to 38% of KV memory for real tokens.
  • Paging cuts the cache into fixed-size blocks, allocates them on demand, and records them in a per-request block table. Waste is at most B − 1 slots per request.
  • PagedAttention kernels read K and V through the block table with the same results as normal attention.
  • Reference counts let requests share blocks (parallel sampling, beam search, prefix caching); copy-on-write handles writes to shared partial blocks.
  • When blocks run out: stop admitting, then preempt by recompute or swap. Aborts free blocks at once.
  • Hybrid models need a cache manager that handles windows, multiple layer groups and fixed-size states.
